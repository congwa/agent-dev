# 25 · 调试手册与常见坑

> 基于 `deepseek-ai/deepseek-harness` v0.1.0-rc.5（commit `47f9438`），2026-08-14 核对。

前面二十四章是顺着读的，这一章不是。你多半是带着一个具体症状翻过来的：进程一起来就退了、某个工具凭空消失了、patch 改了保存了却像没保存过、审批弹窗死活不出来。

动手之前，先拆一个几乎所有症状共用的误解：**"终端上没有报错，说明系统没报错。"**

不是的。dsh 出厂时没有挂 console 日志导出器，所有 `logger.error` / `logger.warn` 都写进一个内存环形缓冲，你在终端上一个字都看不到。很多"完全没有线索"的故障，其实线索早就打出来了，只是没人把它接到 stdout。**先把日志接出来，再开始排查**——这件事在第 3 节，卡住的时候优先去看那一节。

本章其余部分按"症状落在启动 / 配置 / 运行哪一段"组织，每条给报错原文、发生位置、以及怎么自己确认一遍。

---

## 1. 先分诊：症状落在哪一段

dsh 一次启动的形状是这样的：

```
argv 解析 ──► 组 profile 补丁栈 ──► boot() ──► 挂 patch 文件监听 ──► 跑会话
  args.ts        composeProfile        app-boot        watchUserPatches
                 (bundle→profile→        │
                  home→--patch)          ├─ mountRootInclude  挂 cordis:include
                                         ├─ loader.await()    等整棵树落定
                                         └─ assertEntriesActivated  ← 断言在这
```

出处：`apps/cli/src/bin.ts:27-49`、`apps/cli/src/profile-boot.ts:207-299`。

| 症状 | 落在哪段 | 看第几节 |
|---|---|---|
| 进程直接退出，stderr 一行 `dsh: …` | 启动 | 2 |
| 起来了但某个功能整块不在（工具没了 / 命令不存在） | 配置 | 4 |
| 改了 `cordis.patch.yml` 没反应，进程也没报错 | 配置（热重载失败） | 4.5 |
| 什么日志都看不到 | 全局（默认无 exporter） | 3 |
| 模型说工具被拒 / 审批弹不出来 | 运行 | 5 |
| 浏览器白屏 | 运行（Web 前端） | 5.4 |

## 2. 启动就挂：两道断言在查两件不同的事

启动失败的 stderr 有两种形状：一种说 `plugin(s) failed to load`，另一种说 `N entries did not activate`。它们来自同一次调用——`boot()` 在 Loader 树落定后调 `assertEntriesActivated`，而它进门第一件事就是调 `assertEntriesLoaded`——但两条报错查的是两件完全不同的事。

分清它们，要先分清两个词。你写在 `cordis.yml` / `cordis.patch.yml` 里的一行配置，有个名字叫 **entry**；Loader 按这一行真正挂起来的插件实例，带自己的状态机与服务表，叫 **fiber**。fiber 的构造见 [05 章](./05-Cordis是什么.md)，pending 的完整故事在 [07 章](./07-Service能力从哪来.md)。

**"一行 entry 没长出 fiber"和"fiber 长出来了但没转到 ACTIVE"，是两类完全不同的故障。** 两道断言串成一条判定线：先问"这一行有没有长出 fiber"，有了才继续问"fiber 转到哪个状态"，四个状态分四种报错形状。

```
assertEntriesActivated():
    assertEntriesLoaded()                   // 进门第一件事，先把这条跑完
    坏账 = []
    for entry in 所有 entry:
        switch entry.fiber.state:
            ACTIVE:   跳过
            FAILED:   await fiber.await() 捞出私有 rejection → 记 stack
            PENDING:  记 "waiting for services: " + 当前取不到的服务名
            其它:     记 "fiber state <数字>"        // 兜底档
    坏账非空 → 汇总抛出

assertEntriesLoaded():
    没长出来的 = [e for e in 所有 entry if e.fiber 是 undefined and not e.disabled]
    非空 → 抛 "plugin(s) failed to load: ..."
```

对应 `packages/boot/app-boot/src/index.ts:784`（boot 调用点）与 `index.ts:693`（进门就调 loaded）。

### 2.1 有 entry，却没长出 fiber

判据只有一行：把所有 entry 过一遍，挑出 `entry.fiber === undefined && !entry.disabled` 的那些。**这一行是启用的，却没有 fiber**——合法的"无 fiber"只有 `disabled: true` 一种。

报错原文：

```
dsh: plugin(s) failed to load: @deepseek-ai/dsh-tool-bash, ./my-plugin.ts; Cordis startup failed because these plugin(s) could not be resolved (see the error(s) logged above)
```

它列的是 `entry.options.name`，也就是你写在 patch 里的那个 `name` 字段。**这一条等价于模块解析/import 失败**：包名拼错、包没装进 profile、相对路径写错、TS 源没编译。

末尾那句 "see the error(s) logged above" 是一句善意的谎言——第 3 节会讲为什么"上面"很可能一片空白。

出处：判据在 `index.ts:658-664`，报错模板在 `index.ts:662`。

### 2.2 fiber 长出来了，但没转到 ACTIVE

它先复用上一条，然后逐个 entry 看 fiber 状态。Cordis 的 fiber 有六态：`PENDING(0) / LOADING(1) / ACTIVE(2) / FAILED(3) / DISPOSED(4) / UNLOADING(5)`。断言对它们的处理是分档的：

| fiber 状态 | 断言怎么处理 | 你看到什么 |
|---|---|---|
| `ACTIVE`(2) | 跳过 | — |
| `FAILED`(3) | `await fiber.await()` 把私有 rejection 捞出来 | `<name>: <原始 Error.stack>` |
| `PENDING`(0) | 列出 `fiber.inject` 里当前取不到的服务名 | `<name>: pending (waiting for services: a, b)` |
| 其它 | 兜底，打印数字 | `<name>: fiber state 5` |

汇总后抛：

```
dsh: 2 entries did not activate
@deepseek-ai/dsh-tool-fs: pending (waiting for service: fs)
./my-plugin.ts: Error: config.token is required
    at apply (/Users/x/plugins/my-plugin.ts:12:11)
```

只有一条时文案会变成单数形式：`1 entry`、`waiting for service:`。

出处：状态分档在 `index.ts:692-725`，抛出点在 `index.ts:723`，单数分支的代码在 `:712`、`:722`；六态枚举在 `vendor/cordis/src/fiber.ts:147-154`。

### 2.3 pending 那串服务名怎么读

算法就一行：

```
缺什么 = [ s for s in fiber.inject 的键
           if fiber.ctx.get(s) === undefined ]    // 剩下的就是没人 provide 的
```

所以 `pending (waiting for services: sandbox, approval)` 的意思很朴素：这个插件声明了 `inject: ['sandbox', 'approval']`，但整棵树里没有任何一行提供它们。

修法只有两种，把提供者那一行补进 patch，或者把这个消费者行 `disabled: true`。算法实现在 `index.ts:711`。

最容易在这里绕进去的是级联：提供者其实在树里，但**它自己也 pending**，于是一串插件全 pending，报错一次列出好几行。别从上往下看，从依赖最少的那条往上查，那才是根。

级联的形状是一条单向的等待链，报错把链上每一环都列了一遍，但真正缺东西的只有链尾那一环：

### 2.4 import 失败的两个经典成因

**第一个：`export default` 会把 `inject` 吃掉。**

Loader 用 `unwrapExports` 归一化模块，机制是这样的：

```
mod = import(插件模块)
if mod 里存在 default 导出:
    实际拿到的插件 = mod.default        // name / inject / Config 这些兄弟具名导出全没了
```

插件于是在一个空 `inject` 的 fiber 里跑，第一次读 `ctx.agents` 就抛 `cannot get property "agents" without inject`。这是事故 0001 的根因一。

规则记死：**namespace 插件与 `export default` 互斥，二选一。**

出处：抛错点在 `vendor/cordis/src/reflect.ts:144`，复盘在 `docs/postmortem/0001-acp-default-export-drops-inject.md:39-54`。

**第二个：可选服务不能用属性读。**

`ctx.<name>` 走的是只向祖先走的 fiber walk，跨 shadow 边界会一路走到 root 然后抛错；`ctx.get(name)` 才是与拓扑无关的查找。

所以：**没写进 `inject` 的服务，一律用 `ctx.get()`。**

出处：fiber walk 在 `vendor/cordis/src/reflect.ts:156-166`，复盘在 `docs/postmortem/0001-acp-default-export-drops-inject.md:56-87`、`:111`。

### 2.5 挂载之后才炸的，有 fail-loud 兜着

前两条断言只能看到"挂载这一刻"的状态。插件挂载完成之后才 reject 的游离异步工作归 `installFailLoud` 管，它挂 `unhandledRejection`，把这类失败变成一行 stderr 加 `exit(1)`：

```
dsh: fatal load failure: <stack>
```

退出前它会先 await 一个 `release` 钩子——CLI 传的是"dispose 整棵树"——上限 `FAIL_LOUD_RELEASE_TIMEOUT_MS = 2000`。目的是让占着终端的 surface 把 raw mode 还回来再死。

这里的设计口径写得很明确：**卡住的 disposer 只会推迟退出，不会取消退出**。已经被上面那条断言报告过的 rejection 会被跳过，不重复报。

出处：`installFailLoud` 在 `index.ts:609-649`，超时常量在 `index.ts:578`，退出口径写在 `index.ts:574-577`，去重在 `index.ts:616`；CLI 传的 release 钩子在 `apps/cli/src/profile-boot.ts:223-225`。

## 3. 你看不见的日志：默认没有 console exporter

这是整章最容易把人卡住的一条，也是开头那个误解的机制根源。直觉里 `logger.error` 天生就该出现在终端——但"日志被打出来"和"日志被送到你眼前"是两个独立的环节，dsh 只做了前一个。

Cordis 的 `LoggerService` 构造时只注册**一个**默认 exporter，而它不是 stdout，是个内存环形缓冲：

```ts
self.exporter({
  colors: 3,
  export: (message) => {
    self.buffer.push(message)
    …
  },
})
```

这段在 `vendor/cordis/src/logger.ts:213-221`，容量 `bufferSize = 1000` 在 `:195`。

打个比方：这是一台行车记录仪，一直在录，但只录进卡里，没人给它接屏幕。从"唯一的出口通向一块内存"能直接推出两个结论：终端零输出不代表零日志；只要补上第二个出口，全部日志立刻可见。

全仓（不含测试）只有两处注册 exporter：上面这个内存缓冲，和 `@deepseek-ai/cordis-plugin-logger-console`（注册在 `vendor/logger-console/src/shared.ts:57`，真正 `console.log` 在 `:68-71`）。

而三个发行 bundle（`base` / `headless` / `web-app`）**都没有挂它**——我在全仓 `*.yml`/`*.yaml`（除 `pnpm-lock.yaml`）里 grep `logger-console`，只命中一处测试 fixture：`examples/headless-agent/tests/fixtures/session-telemetry-otel.cordis.yml:5-6`。

后果是一串"我明明该看到警告"的场景全部静默：

| 你以为会看到的 | 实际走的通道 | 出处 |
|---|---|---|
| `assertEntriesLoaded` 让你看的 "error(s) logged above" | 插件加载/卸载失败路径一律走 `ctx.logger.error`，全进内存缓冲 | `vendor/cordis/src/fiber.ts:126`、`:661`、`:684` |
| patch 命中不到 id 的警告 | `ctx.root.logger?.('loader').warn` | `vendor/include/src/index.ts:269` |
| 热重载失败的 `config reload at %C failed` | 同上，走 logger | `vendor/hmr/src/index.ts:309-310` |

这条因果链上没有任何一步是坏的：日志确实打了，只是唯一的出口通向一块内存，而终端不在那条路上。

把它接出来的办法是往 `$DSH_HOME/cordis.patch.yml` 里插一行：

```yaml
- insert:
    - id: logger-console
      name: '@deepseek-ai/cordis-plugin-logger-console'
      config:
        colors: false
        levels:
          default: 3
```

这段的 `- insert:` 加行内 `id`/`name`/`config` 写法来自 `packages/bundle/base/cordis.patch.yml:15-22`，logger-console 的字段与取值抄自上面那个真实 fixture（`session-telemetry-otel.cordis.yml:5-11`）。

级别是数字，越大越啰嗦，但这个枚举的顺序违反直觉：`ERROR=0 / INFO=1 / WARN=2 / DEBUG=3`，WARN 比 INFO 大（`vendor/cordis/src/logger.ts:22-27`）。

可用字段共六个：`colors` / `maxLength` / `levels` / `showDiff` / `showTime` / `label`（`vendor/logger-console/README.md:27-32`，类型定义在 `vendor/logger-console/src/shared.ts:17-24`）。另有一份把它挂进 `cordis.yml` 顶层的官方示例：`docs/cordis-tutorial/06-composition-and-hmr.md:29-40`。

> ⚠️ 有两类形态千万别插这一行：`examples/jsonrpc-agent/cordis.yml:2` 和 `examples/acp-agent/cordis.yml:4` 明确写了 **stdout 被 JSON-RPC 占用，不要加 console logger**。

## 4. 配了没生效：patch 到底命中没有

[09 章](./09-插件配置与Schema.md)末尾那份"我配了但没生效，按这个顺序查"是四种静默失败的清单，先按那个排一遍。本节补的是它背后的工具和机制：怎么把合成结果打出来看，以及 patch 自己会在哪些地方悄悄失手。

### 4.1 用 dump 看合成结果，别猜

```sh
dsh --profile web --dump-default-config
dsh --profile web --dump-config
dsh --profile web --patch ./extra.yml --dump-config
```

| 命令 | 吃进哪些层 |
|---|---|
| `--dump-default-config` | 只合成 bundle 层 |
| `--dump-config` | 再叠上 profile 与 home 两个用户层 |
| `--patch X --dump-config` | 把 `--patch` overlay 也算进去 |

三条命令的语义见 `apps/cli/reference/README.md:32-39`。两条参数限制：`--dump-default-config` 不接受 `--patch`，写了直接报参数错（`apps/cli/src/args.ts:99-101`）；任何 dump 都不接受传给 app 的参数（`args.ts:95-97`）。

两者真正的差别在 `--dump-default-config` 传 `userLayer: false`，**根本不去解析** `cordis.patch.yml`。这让它成为"用户层写坏了"时的救命诊断——用户层已经炸到 boot 不起来，它照样能打出 bundle 层长什么样。

出处：`apps/cli/src/dump-config.ts:31-49`，`packages/boot/app-boot/src/profile.ts:366-368`、`:399-401`。

`renderConfigDump` 用的是 include 本体的解析器与补丁算法（`entryListSchema` / `applyEntryPatches`），所以 dump 出来的东西**等于 boot 会挂的东西**。每段连续同源的行前面会打一条注释：

```yaml
# == @deepseek-ai/dsh-base, patched by /Users/x/.dsh/profiles/web/cordis.patch.yml
- id: tool-bash
  name: '@deepseek-ai/dsh-tool-bash'
  disabled: !!js process.platform === 'win32'
```

这三行是 `packages/bundle/base/cordis.patch.yml:210-212` 的真实内容。`!!js` 表达式在 dump 里**原样打印、不求值**——实现是直接用同一套 `entryListSchema` 做 `yaml.dump`。

出处：解析器与补丁算法在 `packages/boot/app-boot/src/index.ts:379-441`，来源注释在 `index.ts:452-464`，`!!js` 不求值在 `index.ts:355-356`、`:455`。

两条 dump 吃进去的层不一样，正是这个差别让它们可以互为对照：一条只吃 bundle 层，另一条吃满用户层，中间的差就是你的 patch 干的事。

```mermaid

    O["<b>--patch overlay</b><br/>命令行点名的文件"]
```

于是有了本章最实用的一个动作：


你的 patch 该改的行会出现在 diff 里，还带上 `patched by <你的文件>` 标注。diff 是空的，就是没命中。

### 4.2 命中不到 id 只是一条警告

补丁匹配失败**不是错误，是跳过加警告**（`vendor/include/src/index.ts:52`）。`applyEntryPatches` 里一共五条警告文本：

| 警告 | 触发条件 | 出处 |
|---|---|---|
| `patch: entry %C not found` | 目标 id 不在合成树里 | `vendor/include/src/index.ts:112` |
| `patch: id is required for non-insert patches` | 非 insert 补丁没写 `id` | `:106` |
| `patch: name mismatch for %C (expected %C, got %C), skipping` | 写了 `name` 但与目标行的 `name` 不一致 | `:117` |
| `patch insert: entry %C not found` | `insert` 指定的父 id 不存在 | `:84` |
| `patch insert: entry %C is not a group` | 父行不是 group | `:88` |

同一条消息在两条路径下长得不一样，这点值得留意。

dump 路径下它带层标签打到 stderr，`%C` 被 `JSON.stringify` 替换成带引号的值（`packages/boot/app-boot/src/index.ts:413-431`）：

```
dsh: [/Users/x/.dsh/profiles/web/cordis.patch.yml] patch: entry "tool-bash" not found
```

真实 boot 路径下，同样的消息走 `ctx.root.logger?.('loader').warn(...)`，也就是第 3 节那个内存缓冲，而且 `%C` 在真实 logger 里只做着色、不加引号。

结论：**想看命中情况就用 `--dump-config`，别指望启动输出。**

出处：boot 路径在 `vendor/include/src/index.ts:268-269`，`%C` 的渲染在 `vendor/cordis/src/logger.ts:58-60`。

### 4.3 patch 是整块替换，不是深合并

写 patch 时最自然的心智模型是"往原配置里合并几个字段"。不是的——`applyEntryPatches` 的写入是一层浅赋值（`vendor/include/src/index.ts:121-124`）：

```ts
for (const [key, value] of Object.entries(overrides)) {
  if (key === 'id') continue
  target[key] = value
}
```

`config` 就是普通的一个 key，所以**你写的 `config` 整块顶掉原来的 `config`**。这不是往抽屉里放东西，是把整个抽屉换掉：没写的字段不是"保留"，是"没了"——连原来抽屉里那些看不见的东西也一起没了。

app-boot README 把这条列成已知限制（`packages/boot/app-boot/README.md:60`，正文在 `:43`），CLI 参考也重申了一遍（`apps/cli/reference/README.md:9`）。

"看不见的东西一起没了"落到实处，就是本项目最贵的坑：这条单独看不算致命，跟 `!!js` 组合起来才要命。CLI 参数的优先级依赖行内保留的表达式，比如 `port: !!js ctx.webStartup.port ?? 3080`；用户 patch 把整个 `config` 换成字面量，就把这个运行时读取删掉了，**`--port` 从此失效**（`apps/cli/reference/README.md:19`）。改端口的时候请把你要保留的字段一并重述。

顺带记住 `!!js` 的合法位置只有两个：**插件 `config` 和 entry 的 `disabled`**，其它 entry 元数据一律字面量（`AGENTS.md:96`、`docs/cordis-primer.md:38`）。`disabled` 的表达式求值在 `vendor/loader/src/config/entry.ts:101-107`，仓库还有一道守门脚本会把写错位置的表达式报成 `!!js is not interpolated here`（`scripts/verify-cordis-config.ts:437`）。

事故 0002 就是把 `disabled: !!js …` 当成"条件启用"用，而**当时** `disabled` 还没被插值（今天已经插值了，见上面 `entry.ts`），整个文件系统工具栈被一个恒真的表达式对象永久禁用（`docs/postmortem/0002-js-expression-disabled-filesystem-tools.md:13-15`、`:32`）。

### 4.4 空的 patch 文件会抛错，不会被忽略

`loadOptionalPatches` 的语义精确到只有一条豁免：**文件不存在等于没有这一层**，其它一切失败都 fail loud。空文件或只有注释的文件 `yaml.load` 出来不是数组，于是撞上：

```
dsh: patches /Users/x/.dsh/cordis.patch.yml must be a top-level YAML array of loader patch entries
```

想临时停用这一层，写 `[]`，别清空文件（`packages/boot/app-boot/README.md:43`）。

同一个函数还会因为条目不是 mapping 抛 `dsh: patches entry 3 in <file> must be a mapping (a loader patch entry)`，序号从 1 起。

`--patch` 指定的 overlay 走的是另一个函数 `loadOverlayPatches`：**文件不存在也抛**，因为那是你亲口点的名。

出处：豁免语义在 `packages/boot/app-boot/src/index.ts:278-287`，数组断言在 `index.ts:329-331`，mapping 断言在 `index.ts:332-335`，overlay 在 `index.ts:298-306`。

### 4.5 改了文件却毫无反应

每次 profile 启动都会给 `profiles/<name>/cordis.patch.yml` 和 `$DSH_HOME/cordis.patch.yml` 两个文件挂监听（`apps/cli/src/profile-boot.ts:285-294`；树里没有 HMR 服务时先自己补一个只监听配置的实例，`:279-284`）。

## 5. 跑起来之后：被拒、没弹窗、找日志、白屏

### 5.1 被拒和抛错，模型那头长得一模一样

拒绝有三个来源：`tools/pre-execute` 返回 `{kind:'deny', reason}`、`ctx.tools.guard()` 返回一个字符串、以及 `{kind:'ask'}` 但审批没放行。三者分别在 `packages/core/tools/README.md:49`、`:51`、`:57`、`:49`。

模型那头看到的是 `Error: <message>`——抛错和被拒是同一个形状，模型分不出来（`packages/core/tools/README.md:180`；拒绝结果的构造在 `packages/core/tools/src/index.ts:1489-1498`）。

你该看的是会话日志里的 `tool/result` 事件，配对的调用事件是 `tool/call`（`packages/core/session/src/types.ts:279`）。但这里有个细节会让人扑空——`error` 是**可选**字段，写不写 `code` 取决于结果里有没有 `info`：

```
// 写 tool/result 时
if 结果带 HarnessError 的 info:
    error = { name, code }      // 例如 UNKNOWN_TOOL
else:
    error = { message }         // 三种"拒绝"都落这一档，没有 info，也就没有 code
```

**所以被拒的调用在日志里没有 code，只有消息内容里那句 `Error: <reason>`。** 带 code 的是抛错类失败，例如 `ToolNotFoundError` → `UNKNOWN_TOOL`。方向跟直觉相反：被系统主动拦下的那类反而"裸奔"，自己炸的那类才有编号。

出处：`error?: { name, code }` 的可选声明在 `types.ts:291-297`，写入条件在 `packages/core/agent-loop/src/tool-calls.ts:284`，三种拒绝只产生 `error: { message }` 见 `packages/core/tools/src/index.ts:1493-1497`，`UNKNOWN_TOOL` 的映射在 `src/index.ts:1436-1443`、`:1870-1878`。

两条路在模型那头长得一模一样，在会话日志里却差一个字段——有没有 `code`，就是判断这次失败是被拦下的还是自己炸的唯一线索：

```mermaid

    C["<b>模型发起 tool-call</b><br/>日志先落 tool/call"]
```

### 5.2 审批没弹窗，多半不是 UI 的错

弹窗没出来，第一反应是去查 UI。先别——`ApprovalOutcome` 是封闭且 fail-closed 的四态：`allowed-once / rejected / cancelled / unavailable`。**缺失、非属主、抛错、不合规的 answerer 一律归为 `unavailable`，而不是放行**（`docs/subsystems/approval.md:21`、`:28`）。

tools 侧对 approval 是机会式注入（`ctx.get('approval')`，没有静态 inject），所以没挂审批的部署会保持 "ask → deny" 的降级，注册表照常活着（`packages/core/tools/README.md:31`）。

一次 `ask` 要走到 UI 前得先过两道岔口，两条岔路都通向"不弹窗且拒绝"，而且都不会在界面上留任何痕迹：


所以"没弹窗"通常压根不是 UI 问题，而是两种情况之一：树里根本没有 answerer（走 `unavailable`，直接拒），或者本会话策略是 `never`（直接 `rejected`，不派发任何 answerer，`docs/subsystems/approval.md:33`）。

要查就查 `approval/asked` / `approval/decided` 这对审计事件（`docs/subsystems/approval.md:11`），详见 [18 章](./18-沙箱审批与权限.md)。

### 5.3 会话日志在哪

发行的 base bundle 把 JSONL 后端的根目录配成 `~/.dsh/sessions`（`packages/bundle/base/cordis.patch.yml:98-101`，值是 `!!js dshHomePath('sessions')`）。落盘布局是三层：

```
~/.dsh/sessions/
  --<归一化的-cwd>--/
    <encoded-id>/
      session.jsonl.zstd
      session.jsonl
```

中间那层是可读的项目目录，没有 cwd 时是 `_no-cwd/`；最里面默认写压缩的 `session.jsonl.zstd`，只有 `compression: 'none'` 才会出现裸的 `session.jsonl`。布局出处：`packages/session/session-persistence-jsonl/README.md:9-14`。

`~/.dsh` 本身的解析规则是"显式配置 > `$DSH_HOME` > `~/.dsh`"（`packages/util/home-paths/README.md:9`）。

找具体某个会话的日志有两条路：

| 路子 | 怎么用 | 注意 | 出处 |
|---|---|---|---|
| 环境变量 | 模型的 shell 调用里直接有 `DSH_SESSION_JSONL=<绝对路径>` | 只是位置提示，首次 flush 前文件可能还不存在 | `packages/shell/shell-env/README.md:20` |
| Web 导出 | `/export` 斜杠命令，或 Session Header 上的 `Session log` 按钮，下载整个 ZIP | — | `packages/session-query/session-log-export/README.md:5`、`:11` |

日志本身怎么读、怎么 fork 在 [16 章](./16-会话日志与分叉.md)。

### 5.4 Web 白屏 / 改了没生效

浏览器抛 `client-modules: window.__DSH_BOOT__ is missing or not an object`（`packages/client/modules/src/client/manifest.ts:110`）意味着一件事：你打开的**不是完整的 host**。

裸跑 `apps/web` 的 Vite 会返 HTTP 200 但没有这份 manifest，事故 0003 整场就栽在"HTTP 200 ≠ 应用就绪"上（`docs/postmortem/0003-web-agent-gui-feedback-loop.md:28`、`:36`）。现在 `apps/web` 的独立 Vite serve 模式会在配置期直接拒绝（`:44`）。

启动页本身是个被低估的诊断面：它按真实 fiber 状态逐行投影 `pending / loading / active / failed / disposed / unloading`（`packages/client/web/src/loader-status.ts:31-41`），刻意手写、不 value-import 任何插件包，就是为了插件挂掉时它还能显示（`:6-11`）。插件树炸了的时候，浏览器里那一页往往比终端更有信息量。

生产形态需要先 `pnpm run build`（`apps/cli/reference/README.md:64`）。启动器不检查新鲜度，**旧的 bundle 会安静地继续跑老前端代码**（`:84`）——"我明明改了"的第二个来源就在这里。

## 6. 护栏是选装件：`dsh-invariants` 出厂一个都不挂

`packages/runtime-diagnostics` 这个包组下目前只有一个包：`invariants`。

它是个**注册表服务**（`ctx.invariants`），本体不含任何产品检查、不 import 任何产品包；每个 workspace 包各自发布一个 `./invariant` 伴生插件，用自己的完整 npm 包名注册（`packages/runtime-diagnostics/invariants/README.md:5`）。

它检查的是"事件流与可变数据的关系"，**不是**"某个方法在不在"——后者属于类型、加载和单测的事（`README.md:31`）。当前有可执行检查的伴生包见 `README.md:37-46`，覆盖 session 闭包与 call/result 轨迹、agent 状态迁移、inbox FIFO、流语法、工具管线阶段与结果冻结、压缩与 hook 配对、沙箱模式词表、审批 asked/decided 配对等。

违规抛 `InvariantError`：`extends Error`，稳定 `code: 'INVARIANT'`，带 `packageName`（`packages/runtime-diagnostics/invariants/src/index.ts:50-65`），消息前缀固定（`:62`）：

```
invariant violated by "@deepseek-ai/dsh-session": <具体消息>
```

但**发行的 dsh 配置树一个都不挂**——服务和任何 `./invariant` 伴生包都不挂。这是明写的决定，并且有构建后的 config-dump 测试守着（`.agents/notes/implemented/simplification/2026-08-03-omit-invariants-from-shipped-config.md:13`、`:17`；我对全仓 `*.yml`/`*.yaml` grep `invariant` 也确实没有配置行命中）。

要用就自己组合：服务加上你想检查的伴生插件。配置支持 `enabled` / `package_allowlist` / `package_blocklist`，条目是**大小写敏感的正则源**，不加 `^$` 就是非锚定匹配，空白、无效或重复的条目会让服务启动直接失败（`README.md:10-19`）。组合示例见 `README.md:54-67`。

三条限制照抄它自己的 Known Limitations（`README.md:83-85`）：请求重建只覆盖 loop 显式标记过的请求；**live-only 的伴生包无法重建自己 reload 之前就开始的操作**；正则过滤器在服务生命周期内固定，改了得重载插件。

另有一条不需要配置的自省路子：`cordis_inspect` 工具能对当前进程出只读报告，包括服务、所有活着的插件 fiber、已注册工具、本会话的动态包、`api`/`events` 引用（`packages/extensions/tool-cordis/README.md:11`）。它需要 `ctx.dynamic`（`@deepseek-ai/dsh-cordis-host-runner`）才会激活（`README.md:5`），且信任等级等同 bash 访问（`README.md:23`）。

## 7. 报错速查表

前缀 `dsh:` 来自 binName。

| 错误信息 | 原因 | 怎么修 |
|---|---|---|
| `plugin(s) failed to load: <names>; Cordis startup failed…` | 模块解析失败：包没装、名字拼错、相对路径不对 | `--dump-config` 确认 `name` 字段；profile 里 `dsh plugin --profile <n> add <pkg>` |
| `N entries did not activate` + `pending (waiting for services: …)` | 声明的 `inject` 服务无人提供 | 补 provider 行，或把消费者 `disabled: true` |
| `N entries did not activate` + 一段原始 stack | 插件 `apply` 自己抛了 | 按 stack 定位；常见是 config 校验 |
| `cannot get property "X" without inject` | 没写进 `inject` 却用 `ctx.X` 属性读；或 `export default` 吃掉了 namespace | 改 `ctx.get('X')`；删掉 `export default` |
| `cannot get required service "X" in inactive context` | `X` 在这一层 fiber 的 `inject` 里，但它的 store 是空的：fiber 尚未激活或已在拆卸（`vendor/cordis/src/reflect.ts:159-161`，store 的装配/清空在 `vendor/cordis/src/fiber.ts:647`、`:687`） | 检查生命周期/effect 顺序，别在 dispose 途中再读服务 |
| `host preparation failed: …` | `boot()` 的 `prepare` 钩子在任何配置行挂载**之前**就炸了 | 宿主准备逻辑的问题，不是插件树（`index.ts:767-772`） |
| `plugin tree failed to load: …` | 配置树挂载失败；末尾会追加最深层 cause 的 stack | 看追加的那段 stack（`index.ts:797-800`） |
| `fatal load failure: <stack>` | 挂载完成后才 reject 的游离异步工作 | 在插件里给异步工作接错误处理 |
| `patches <file> must be a top-level YAML array of loader patch entries` | patch 文件空 / 只有注释 / 顶层不是数组 | 写 `[]` 来停用该层 |
| `patches entry N in <file> must be a mapping (a loader patch entry)` | 数组里某项不是 mapping | 修那一项 |
| `failed to read overlay <file>: …` | `--patch` 点名的文件读不到 | 路径写对；overlay 缺失不降级 |
| `patch: entry "<id>" not found` | 补丁目标 id 不在合成树里 | `--dump-config` 查真实 id |
| `patch: name mismatch for "<id>" (expected …, got …), skipping` | 补丁里写的 `name` 与目标行不符 | 删掉 `name`，或抄成一致 |
| `patch insert: entry "<id>" is not a group` | 往非 group 行里 insert | 换目标，或去掉 `id` 直接 append 到顶层（`vendor/include/src/index.ts:93-95`） |
| `profile "<name>" does not exist; create it with 'dsh plugin --profile <name> add <package>'` | 非模板 profile 未初始化（`web`/`headless` 会自动建） | 照提示跑（`packages/boot/app-boot/src/profile.ts:379-381`） |
| `cannot resolve profile bundle "<pkg>" …` | bundle 在安装目录和 profile 目录都找不到 | `dsh plugin --profile <n> install`（`profile.ts:351-354`） |
| `profile bundle "<pkg>" declares no dsh.bundle in its package.json` | 把普通包写进了 `dsh.profile.bundles` | 该包要声明 `"dsh":{"bundle":{"patch":"./cordis.patch.yml"}}`（`profile.ts:391-393`） |
| `<file> sets "<NAME>", which only the launching environment may set` | `.env` 里写了 bootstrap-only 变量（`PATH`/`DSH_*`/`HTTP_PROXY` 等） | 改成 export（`index.ts:157-161`，名单在 `:93-117`） |
| `client-modules: window.__DSH_BOOT__ is missing or not an object` | 打开的是裸 Vite，不是完整 host | 用 `dsh web`；生产形态先 `pnpm run build` |
| `MISSING_CREDENTIAL` / `UNKNOWN_MODEL` | 密钥未存 / 模型未配 | `docs/user/guide/providers.md:88-94` 有完整清单 |
| `SANDBOX_UNAVAILABLE`（子进程明明跑了） | 见事故 0004：把内核的良性提示行当成 launcher 失败 | 已修；老版本上先看子进程真实退出码 |
| `invariant violated by "<pkg>": …` | 运行时不变量被破坏 | 按包名找对应 `./invariant` 伴生包的检查项 |
| `INACTIVE_EFFECT` | 在已 dispose 的 fiber 上注册 effect | 看 `vendor/cordis/src/fiber.ts:351-354` 的 `assertActive` |
| 编辑 patch 无反应、无报错 | 热重载解析失败，旧树继续跑 | 跑 `--dump-config`；或挂 console logger 看 `config reload at … failed` |

压缩失败的六个失败码是另一套，在 [17 章](./17-压缩与长会话.md)。

## 8. 四篇事故复盘，各能学到什么

`docs/postmortem/` 下四篇都有中文版（`*.zh.md`）。值得单独读的原因是它们写的不是"某处写错了"，而是"为什么所有防线都没拦住"。

**0001，ACP 的 `export default` 吃掉了 inject**（`docs/postmortem/0001-acp-default-export-drops-inject.zh.md`）。178 个单测全绿、100% 行覆盖，真实编辑器一连就崩（`0001-…md:13`）。

带走两条硬规则——namespace 插件不许 `export default`，可选服务用 `ctx.get()`——外加一条更值钱的方法论：**手工构造插件的测试无法验证插件怎么被加载**（`:93-98`）。

**0002，`!!js` 让文件系统工具永久禁用**（`docs/postmortem/0002-js-expression-disabled-filesystem-tools.zh.md`）。表达式对象恒真，工具栈在所有模式下都是关的；更糟的是快照刷新把 `UNKNOWN_TOOL` 收成了"期望输出"（`:19`、`:34`）。

两句话：**语法能通过不等于那个位置会求值**；快照刷新是产物生成，不是正确性评审（`:45-46`）。

**0003，Web agent 验证了一台替身服务器**（`docs/postmortem/0003-web-agent-gui-feedback-loop.zh.md`）。改了 GUI 源码，却在另一个端口上验收，HTTP 200 一路掩盖了白屏（`:28-29`）。

HTTP 就绪、构建成功、boot manifest 是**三件不同的事**；验收必须点名 origin 并从外部观察（`:51`）。

**0004，Landlock 的良性提示被当成致命失败**（`docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.zh.md`）。共享前缀加上任意非零退出码等于误判沙箱不可用，连 ripgrep 无匹配的 exit 1 也中招（`:15`）。

**共享前缀不是协议**，进程归因要多条独立证据合取；适配器不能把下层的结构化错误替换成自己的泛化分类（`:52-54`）。

配套的 `docs/defensive-patterns.md` 把这些教训压成了可执行规则，写生命周期、并发、子进程、拆卸代码之前先读它（`:5`）：

| 规则 | 出处 |
|---|---|
| 正交结果各报各的 | `:9` |
| 双向遵守公开契约 | `:13` |
| 异步状态不是同步状态 | `:17` |
| dispose 必须到达静止，而不只是发出请求 | `:21` |
| 派发器里兜住回调异常 | `:25` |

## 一句话带走

把全章倒着串一遍，每条都能从前面的画面重新推出来：

- 排障第一步不是读源码，是挂上 console logger、跑一遍 `--dump-config`——因为唯一的默认 exporter 是那台没接屏幕的行车记录仪，日志全录进了内存（第 3 节）；
- 启动失败先问两个问题：这一行长出 fiber 了吗，长出来的转到什么状态了——因为两道断言就是按这个顺序串的（第 2 节）；
- "配了没生效"不要猜，diff 两份 dump——因为 patch 不命中只是一条 warn，而这条 warn 也进了内存（4.1、4.2）；
- 改 patch 时把要保留的字段一并重述——因为写入是换整个抽屉，原来抽屉里的 `!!js` 表达式会被你的字面量一起顶掉（4.3）；
- 热重载失败后旧树继续安静地跑——所以"保存了没反应"要先怀疑解析失败，而不是怀疑监听没挂（4.5）;
- 模型说工具被拒时，去 `tool/result` 里看有没有 `code`——被拒的没有 code，自己炸的才有（5.1）；
- 审批没弹窗先查 `approval/asked` / `approval/decided`——fail-closed 的四态里，"不弹窗"多半是 `unavailable` 或 `never`，两条路都不经过 UI（5.2）；
- HTTP 200 不等于应用就绪——白屏验收要看 `window.__DSH_BOOT__`，不是看端口通不通（5.4）。

一句话压缩：**dsh 的报错基本都是准确的，问题在于你未必看得见它们**——把系统本来就想告诉你的话接出来，排查就成功了一半。
