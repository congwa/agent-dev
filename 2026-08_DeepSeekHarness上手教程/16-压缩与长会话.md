# 16 · 压缩与长会话

> 基于 `deepseek-ai/deepseek-harness` v0.1.0-rc.5（commit `47f9438`），2026-08-14 核对。本章讲上下文快满时 dsh 做了什么、这件事在会话日志上留下什么痕迹、你能拧哪些旋钮。

**读完这章你会**：

- 说清压缩为什么是"日志上的一次区间 replace"，而不是"把历史重写一遍"
- 找到阈值 / 保留量 / 摘要模型这三组配置的确切位置并改掉它们
- 认出压缩失败时日志里那行 warn 撞的是哪一道机械防线
- 用 `/compact` 手动压一次，并读懂它的六种失败码
- 关掉自动压缩、或者用自己的插件整体顶替压缩后端

## 1. 一个跑了两小时的会话，是怎么被压下去的

会话越长，每一步请求带的历史越多。dsh 有三档减压手段，**发生时机不同、代价不同、改动落点也不同**：

| 档位 | 什么时候跑 | 花模型调用吗 | 单位 | 改动落在哪 | 插件 |
|---|---|---|---|---|---|
| spill 溢写 | 单个工具**刚返回**时 | 不花 | UTF-8 字节 | 完整文本写磁盘，模型只看到预览 + 路径 | `dsh-spill-policy` + `dsh-spill-local` |
| tool-result 修剪 | 压力**已经超阈值之后**、选摘要区间之前 | 不花 | Unicode 码点 | 日志里追加一条替换版 `tool/result` | `dsh-compaction-tool-result-pruner` |
| 摘要压缩 | 同上，修剪后仍超阈值 | **花一次额外请求** | token（估算） | 一段旧历史被一条摘要节点整段遮蔽 | `dsh-compaction-basic` |

时间轴上它们是这样接力的：

```
工具返回超大文本 ──spill──► 日志里存的就是"预览+磁盘路径"（整段 ≤ maxInlineBytes）
                                  │
     每步开始前测一次压力 ◄───────┘   agent/pre-step，请求组装之前
                                  │  totalTokens ≥ thresholdTokens ?
                                  ├─ 否 ──► 什么都不做
                                  └─ 是 ──► 修剪超长 tool/result ──► 重新测量
                                                                     ├─ 已降到阈值下 ──► 收工，不调模型
                                                                     └─ 仍超 ──► 选区间 → 调模型出摘要 → replace
```

> 想知道这一点上 Pi / Codex / LangChain 怎么做，见 [五个 agent 系统源码解剖](../2026-08_五个agent系统源码解剖/00-总览与阅读指南.md)。

## 2. 压缩不是重写历史，是日志上的一次区间 replace

会话日志是 append-only 的（第 15 章）。"surface"（模型可见面）是这条日志投影出来的、当前真正会进模型请求的那串节点。压缩**一个字节都不删**，它只是往后追加事件，让老事件不再出现在 surface 上。一次成功的压缩恰好追加**四条**事件（`packages/compaction/compaction/README.md:41-49`；四次 append 分别在 `packages/compaction/compaction-basic/src/region.ts:189`、`:447`、`:462`、`:215`）：

```
compaction/start    log-only，拿锁
   （调模型出摘要，这一步不落事件）
compaction/summary  log-only，记摘要、被遮区间、shadowedSeqs、token 数、provider/model
user/message        ★ 唯一一次改动 surface：surfaceOp = { op:'replace', start, end }
compaction/end      log-only，放锁
```

`compaction/*` 事件**一条都进不了 surface**——`SurfaceEventType` 是封闭联合，只有 `user/message` / `assistant/message` / `tool/result` 能带 `surfaceOp`（`packages/core/session/src/types.ts:343-346`）。所以摘要必须"搭车"在一条合成的 `user/message` 上（`docs/subsystems/compaction.md:11`）。顺带一提，`dsh-compaction` 这个包实际声明了**四种** `compaction/*` 事件：`start` / `summary` / `end` / `prune`（`packages/compaction/compaction/src/types.ts:16-89`），子系统文档还写着"三种"，是 `compaction/prune` 加进来之后没同步。

surface 的变化就是一次数组 splice，被替换的区间整段换成新节点一个（`packages/core/session/src/surface.ts:369-370`）：

```
replace 前： [12] [13] [14] [15] [16] [17]
              └──── 被遮蔽 ────┘
replace 后： [ 41 ] [16] [17]        41 = 摘要节点的 seq
```

**这里最容易踩的两件事**：

1. **新节点必须列全被它遮蔽的每一个源节点 seq**。`sourceEventSeqs` 少写一个就直接抛：`surface replace: sourceEventSeqs must include every shadowed surface node; missing …`（`packages/core/session/src/surface.ts:239-242`）。compaction-basic 写的是 `[startEvent.seq, summaryEvent.seq, ...shadowedSeqs]`，把两条簿记事件也一并引用（`packages/compaction/compaction-basic/src/region.ts:462-465`）。
2. **`start`/`end` 是"surface 上的位置区间"，不是数字大小区间**。校验比的是 `indexOf` 出来的下标而不是 seq 值（`surface.ts:250-260`）；上一次压缩留下的摘要节点 seq 很大却坐在很靠前的位置，所以 `start` 完全可能大于 `end`（`docs/subsystems/compaction.md:44-52`）。真正权威的是 `shadowedSeqs` 那个有序列表（`docs/subsystems/compaction.md:53-54`）。

锁也在日志里：`compaction/start` 先落盘、`compaction/end` 最后落盘，中途崩溃会留下一个"没配对的 start"，下次进来直接报 busy——而不是留下一个假装压缩成功的 end（`docs/subsystems/compaction.md:19`、`packages/compaction/compaction/README.md:49`、`:57`）。被遮蔽的原始事件仍在日志里，重放依然确定（`packages/compaction/compaction/README.md:53`）。

## 3. 触发条件与阈值在哪配

两个自动入口，都由 `compaction-basic` 在构造时注册（前提是 `auto: true`，默认开，`packages/compaction/compaction-basic/src/index.ts:129`）：

| 触发器 | 挂在哪个事件上 | 语义 |
|---|---|---|
| `pressure` | `agent/pre-step`（waterfall 事件，第 10 章），请求组装之前 | 估算 token 超过阈值 |
| `context-overflow` | `agent/request-error`（同为 waterfall），且 `failure.code === CONTEXT_WINDOW_EXCEEDED` | 厂商已经明确说超窗了 |

两个事件的 `@mode waterfall` 声明在 `packages/core/agent/src/runtime-types.ts:229-231` 与 `:258-260`；那个错误码常量是 `CONTEXT_WINDOW_EXCEEDED_CODE`，值就是字符串 `'CONTEXT_WINDOW_EXCEEDED'`（`packages/llm/llm/src/error.ts:25`）。监听代码在 `compaction-basic/src/index.ts:147-165`（pre-step）与 `:179-223`（overflow 恢复），另有两个只做记账的监听器在 agent 变 idle、或收到新的 `assistant/message` 时清零超窗重试计数（`:167-177`）。

overflow 这条路**不看阈值也不留保留尾**（`selectCompactableRange(..., 0)`，`:283-291`），只要 `surface.replaceGeneration`（surface 被 replace 过几次的计数器）涨了就返回 `{ kind: 'retry' }` 让这一步重来（`:191`、`:218-222`）。还有一个前置条件容易忽略：会话还没落过一次请求头（没有路由过任何 provider/model）时，`compactIfNeeded` 直接返回 `null`，什么都不做（`:263-264`）。

阈值不是绝对 token，是按**最近一次落盘请求所用模型的 contextWindow 的比例**现算的（`compaction-basic/src/config.ts:144-147`）：

```
thresholdTokens = floor(contextWindow × thresholdRatio)
retainTokens    = floor(contextWindow × retainRatio)     若没给绝对值
```

默认值（`config.ts:20`、`:23`、`:89-95`）：

| 键 | 默认 | 含义 |
|---|---|---|
| `thresholdRatio` | `0.8` | 到窗口的 80% 就压 |
| `retainRatio` | `0.16` | 最近 16% 的历史原样保留（与 `retainTokens` 二选一） |
| `summarizationProvider` / `summarizationModel` | `''` / `''` | 空对 = 跟着会话当前路由走 |
| `maxTokens` | `8192` | 摘要生成上限（可能被推理 token 吃掉） |
| `compactionRetries` | `1` | 第一次压完还超阈值，最多再补几次 |
| `maxOverflowRetries` | `1` | 超窗恢复的重试上限，`0` = 只关恢复 |
| `auto` | `true` | 置 `false` 则上面那四个监听器一个都不注册，只留手动 |
| `modelPolicies` | `[]` | 按 `{provider, model}` 精确覆盖上表中除 `auto` / `modelPolicies` 外的任意一项（`config.ts:26-35`） |

`contextWindow` 不归压缩管，归**该路由的 LLM 适配器**：`compactIfNeeded` 拿的是 `(await ctx.llm.resolveModelInfo(provider, model, signal)).context`，拿不到就抛 `compaction-basic: no context capacity for <provider>/<model>; configure contextWindow on that adapter model`，自动路径对同一个 target 只 warn 一次然后带着完整历史继续跑（`index.ts:293-302`、`:155-162`）。**"我明明配了阈值却从来不压缩"先查这里**——不过内置的两个适配器都自带兜底容量（如 `llm-deepseek` 的 `defaultContextWindow` 默认 1,000,000，`packages/llm/llm-deepseek/src/index.ts:97` → `src/adapter.ts:91`），所以这条主要坑的是自定义适配器。

base bundle 里这一串默认就挂着：`token-meter`（`packages/bundle/base/cordis.patch.yml:281-282`）、`compaction-basic`（`:284-285`，不带任何 config）、`command-compact`（`:289-290`）、`tool-result-pruner`（`:360-365`）、spill 两件套（`:346-352`）。

## 4. 摘要请求长什么样

不是"另起一个干净的 summarizer 会话"，而是**把原对话的前缀原样重放一遍**：同一份 system prompt、同一份 tools schema、被遮区间自己的那些消息，最后追加一条 user 消息作为压缩指令（`compaction-basic/src/region.ts:498-514`、`summarizer.ts:145-163`）。这样做的理由是 **KV cache**（厂商对完全相同的请求前缀有缓存，命中就便宜）：这次调用是上一次请求的真前缀，热前缀缓存能复用到最后那条指令为止（`summarizer.ts:24-29`、`compaction-basic/README.md:156`）。

指令要求模型**严格输出八段固定 Markdown 结构，缺一段就写 `(none)`，不许少**（`summarizer.ts:31-66`）：`Primary Request and Intent` / `Key Technical Concepts` / `Files and Code` / `Errors and Fixes` / `Pending Jobs` / `Current Work` / `Next Step` / `Critical Context`。里面还有两条重点规则：逐字保留路径、命令、报错原文、标识符、数值、函数签名（`:61`）；如果历史里已经有一个 `<compacted-summary>` 块，那是上一次的 checkpoint，**要合并成一份而不是照抄下去**（`:65`）。

落到日志上的那条 `user/message` 长这样（`summarizer.ts:69-70`、`:189-195`）：

```
This is an automatically generated checkpoint condensing an earlier span …

<compacted-summary>
（模型吐出来的八段结构）
</compacted-summary>
```

摘要用哪个模型，按 `configured ?? latest ?? agentTarget` 三级回退：显式配的 pair → 最近一次落盘请求的路由 → agent 自己的 provider/model；三个都没有就抛错（`summarizer.ts:128-143`）。请求带 `purpose: 'compaction'`（`summarizer.ts:161`），DeepSeek 适配器据此加一个 `x-deepseek-harness-compact: 1` 请求头，不动 body（`packages/llm/llm-deepseek/src/adapter.ts:293`、`compaction-basic/README.md:18`）。

## 5. 六道机械防线

这些不是"建议"，是会当场抛错的检查。摘要模型再不靠谱也捅不穿它们：

| # | 防线 | 位置 | 撞上时 |
|---|---|---|---|
| 1 | **摘要必须比被遮内容小**（按加框后的 token 算） | `region.ts:373-378` | `summary is not smaller than the shadowed content (N estimated framed tokens >= M)`，本次压缩作废 |
| 2 | **摘要不能含图片输出** | `summarizer.ts:217-222` | 抛 `LlmError('compaction summary cannot contain image output', 'UNSUPPORTED_CONTENT')`，而不是悄悄丢掉图 |
| 3 | **只有 text 块进 checkpoint** | `summarizer.ts:223` | reasoning 与 tool call 被剔除，避免泄露推理或造出无主调用 |
| 4 | **`max-tokens` 结束视为失败** | `summarizer.ts:206-210` | `summarization truncated at the token cap (incomplete checkpoint)`，宁可不压也不留半截 checkpoint |
| 5 | **空摘要视为失败** | `summarizer.ts:170-172` | `summarization produced no text summary content` |
| 6 | **区间两端必须 tool 调用/结果配对平衡** | `region.ts:327-333` | `compactRegion: start seq N is not a balanced boundary (would split a step's tool-call/result pair)` |

还有两道跟并发有关的：

- **摘要期间 surface 变了就作废**。自动压缩要求整个 surface 逐节点相等（`region.ts:387-396`）；手动 `/compact` 只要求**选中的那一段**没变，因为摘要跑着的时候允许有别的东西被注入进来（`region.ts:403-424`、`packages/compaction/compaction/README.md:51`）。
- **锁**：任何入口进来先查有没有未配对的 `compaction/start`，有就 `busy`；但如果那个 start 比最新的 `session/end-seed` 还早，它属于上一个进程生命周期的残留，不拦（`region.ts:286-298`）。另有一层 invariant companion——包内自带的日志校验器——逐条校验事件配对，比如 `compaction/summary repeated within one compaction`、`successful compaction/end requires one compaction/summary`（`packages/compaction/compaction/src/invariant.ts:184`、`:215`）。

失败之后不会把会话搞坏：`changed` 和 `summary` 两类失败**不改动 surface**，但失败记录仍留在日志里（`docs/subsystems/compaction.md:84`）。自动路径只 warn 一句 `step compaction failed: …; continuing the turn` 然后带着超预算的完整历史继续（`index.ts:161`）。重试若干次仍压不下去，才抛 `compaction still above threshold after N compaction attempts`（`index.ts:328-331`）。

## 6. tool-result-pruner：不花钱的那一档

它是**可选**的补充策略，compaction-basic 用 `ctx.get('toolResultPruner')` 软引用（`index.ts:281`），没装照样能跑。

- 只在**压力已经超阈值之后**才动手，动完重新测量；如果这一下就降到阈值以下，**这一步完全不调模型**（`index.ts:308-312`）。
- 算的是 **Unicode 码点，不是 token**——所以它只是粗筛，判断"降下来没有"仍以 `ctx.tokenMeter` 为准（`packages/compaction/compaction-tool-result-pruner/README.md:60`）。
- 超预算的 `tool/result` 被替换成「头 + 固定标记 + 尾」，标记是 `\n\n[... tool result middle pruned ...]\n\n`（`.../src/config.ts:7`）。默认 `thresholdChars: 8192` / `headChars: 4096` / `tailChars: 1024`（`config.ts:10-14`）。
- 每次替换前会**同步紧邻**追加一条 `compaction/prune` 影子定价事件，记下被遮节点的估算 token，好让纯函数消费者不必自己记账（`.../src/index.ts:162-173`、`docs/persistence-catalog.md:299-321`）。
- 替换只改 `content`，`turn` / `step` / `callId` / 错误字段全部原样保留（`.../README.md:11`）。

它救不了什么：非工具类的大节点、以及修剪完剩下的部分仍然超窗的工具对（`compaction-basic/README.md:162`）。修剪是**纯语法**的，不判断中间哪几行更重要（pruner `README.md:61`）。

## 7. spill 与压缩的分工

spill 是**另一条线**，比压缩早得多：它是一个 `tools/post-execute` 变换器，工具刚返回就动手（`packages/spill/spill-policy/README.md:5`）。

| | spill | 压缩 |
|---|---|---|
| 触发 | 单个工具结果 > `maxInlineBytes`（base 里配 50000，`packages/bundle/base/cordis.patch.yml:349-352`） | 整个请求的估算 token 超阈值 |
| 看的范围 | 一次工具调用 | 整条会话历史 |
| 全文去哪 | 写磁盘：`<root>/session-<sha256前缀>/<随机>-<安全名>`（`packages/spill/spill-local/README.md:9`、`:12-13`） | 不搬家，留在日志里 |
| 模型看到 | 头尾预览 + `(Omitted N bytes. Full formatted result stored at: <路径>. <取回提示>)` | 一段 `<compacted-summary>` |
| 模型还能拿回来吗 | 能，用 `read` / `grep` 去读那个路径 | 不能，只剩摘要 |
| 失败了怎么办 | best-effort：存不下就保留原始内联结果，绝不把成功的调用变成 `isError`（spill-policy `README.md:31`） | 见第 5 节 |

几个边界值得记住：`read` 工具的结果**不 spill**（否则 `read → spill → 再 read` 死循环）；被 block 的结果不 spill；非纯文本结果不 spill（spill-policy `README.md:18-19`）。spill 文件**没有生命周期清理**，因为 resume / fork 出来的会话可能还引用着那个路径（spill-local `README.md:33`）。spill 后的结果留在历史里，直到被压缩吃掉（spill-policy `README.md:49`）。

## 8. 实操 A：调阈值

用户 patch 层的位置与顺序：各 bundle 的 patch → `$DSH_HOME/profiles/<name>/cordis.patch.yml` → `$DSH_HOME/cordis.patch.yml` → `--patch` 覆盖层（`apps/cli/README.md:34-37`）。把下面这段写进 `~/.dsh/profiles/web/cordis.patch.yml`：

```yaml
- id: compaction-basic
  config:
    thresholdRatio: 0.6
    retainRatio: 0.2
    maxTokens: 4096
    modelPolicies:
      - provider: deepseek-official
        model: deepseek-v4-flash
        thresholdRatio: 0.75
```

`provider` / `model` 必须写成路由上真实存在的那一对，`modelPolicies` 是精确匹配、不做前缀或通配（`config.ts:109-111`）；base 默认路由就是这一对（`packages/bundle/base/cordis.patch.yml:63-67`，模型清单见 `packages/llm/llm-deepseek/src/index.ts:49-51`）。改完用 `dsh --profile web --dump-config` 看合成结果（`docs/architecture.md:32`），确认 `compaction-basic` 那一行的 config 就是你想要的。

**三个必踩的坑**：

1. **按 id 打 patch 是整体替换 `config`，不深合并**（`packages/boot/app-boot/README.md:60`）。base 里 `compaction-basic` 本来没 config，所以上面这例安全；但 `tool-result-pruner` 在 base 里带着三个字段，你只写 `thresholdChars: 4096` 会让另外两个退回插件默认值 4096/1024，于是 `4096 + 39(标记) + 1024 = 5159 > 4096`，**插件加载直接失败**：`ToolResultPruneConfig: headChars + marker + tailChars (5159) must be at most thresholdChars (4096)`（`.../compaction-tool-result-pruner/src/config.ts:55-63`；39 是标记的码点数）。要改就把三个一起写全。
2. **配错是加载期失败，不是运行期降级**。未知键 → `BasicCompactionConfig: unknown key "<键>"`（`compaction-basic/src/config.ts:278-282`）；`retainRatio` 与 `retainTokens` 同时给 → `retainRatio and retainTokens are mutually exclusive`（`:240-242`）；`retainRatio >= thresholdRatio` → 直接抛（`:185-190`）；`summarizationProvider` / `summarizationModel` 必须**同为空或同为非空**地成对出现（`:267-274`）。
3. **`retainTokens` 这种绝对值要等模型容量出来才能校验**，所以它会在第一次能解析到该 target 时才失败：`retainTokens (N) must be less than threshold tokens M`（`:148-153`）。

压缩成功时日志里会有一行 info（`compaction-basic/src/index.ts:139-144`）：

```
compaction (step pressure): shadowed 24 surface nodes (seqs 12-35, ~48210 tokens)
```

## 9. 实操 B：手动触发一次压缩

`/compact` 由 `dsh-command-compact` 注册成一条全局命令，**不触发模型 turn**；base 默认挂着它，Web 客户端提供命令适配器（`packages/compaction/command-compact/README.md:5`、`:44`）。

| 输入 | 结果 |
|---|---|
| `/compact` | `Compacted N history items (~T tokens).`（`command-compact/src/index.ts:70`） |
| 没有可压的历史 | `No compactable history yet.`，一条事件都不写（`README.md:12`） |
| `/compact 随便什么参数` | `Usage: /compact (no arguments)`，压根不调后端（`README.md:13`、`src/index.ts:62-64`） |

它走的是 `compactNow()`：**低于阈值也压一次**，标记对写成 `turn: null` 的独立 bracket，并在返回前等一次持久化 flush（`compaction-basic/src/index.ts:368-420`）。失败码一共**六个**（`packages/compaction/compaction/src/index.ts:28-34`），命令层把它们映射成六句固定文案（`command-compact/src/index.ts:24-54`）：`busy`（有 turn 在跑或已有压缩在进行）、`cancelled`（→ `Compaction cancelled.`）、`changed`、`summary`、`commit`、`persistence`；包 README 的表只列了其中五个，漏掉 `cancelled`（`command-compact/README.md:19-25`）。`changed` / `summary` 两类**不改动会话**，但失败记录会留在日志里。

两条限制：**只能在 idle 时用**，命令本身不排队（`README.md:64`）；**不接受区间参数**，指定区间只有编程入口 `compactRegion()`（`README.md:65`），而且它要求会话有一个打开着的 turn，全闭合会话上调会抛 `compactRegion: no open turn — automatic compaction events must be enclosed in a turn`（`compaction-basic/src/region.ts:177-179`、`compaction-basic/README.md:163`）。没有命令适配器的形态只有自动压缩（`command-compact/README.md:66`）；headless bundle 的 patch 里确实没插任何命令适配器（`packages/bundle/headless/cordis.patch.yml:22-35`）。

## 10. 实操 C：换掉整个压缩策略

三种力度，从轻到重：

**只关自动**：`- id: compaction-basic` + `config: { auto: false }`，`/compact` 仍可用（`compaction-basic/README.md:41`）。

**只换摘要生成方式**：`summarize()` 是唯一的子类钩子，压力判断、保留策略、区间选择、收缩校验全部照旧（`compaction-basic/README.md:24`、`src/index.ts:236-246`）。骨架长这样：

```ts
import { BasicCompactionEngine } from '@deepseek-ai/dsh-compaction-basic'
import type { SummarizationInput, SummaryResult } from '@deepseek-ai/dsh-compaction-basic/src/summarizer.ts'
import type { Agent } from '@deepseek-ai/dsh-agent'

export class TemplateCompactionEngine extends BasicCompactionEngine {
  protected override async summarize(
    input: SummarizationInput,
    agent: Agent,
  ): Promise<SummaryResult> {
    const text = `## Current Work\n- elided ${input.messages.length} messages`
    return { summary: [{ type: 'text', text }], provider: 'local', model: 'template' }
  }
}

export default TemplateCompactionEngine
```

返回值不带 `llmStreamCall` 就属于"未标记"分支，`rawOutput` 可选（`summarizer.ts:88-108`）。上面这个模板摘要不发请求，所以省掉了第三个 `signal` 参数；**只要你的实现真去调模型，就必须把 `signal` 收下并透传进去**（`packages/compaction/compaction/README.md:29`）。注意第 5 节那六道防线**照样生效**——模板摘要如果不比被遮内容小，一样会被拒。

**整体顶替后端**：`CompactionEngine` 是 cordis Service，构造时 `super(ctx, 'compaction')` 注册（`packages/compaction/compaction/src/index.ts:96-99`）；同一个 isolate 里重复注册同名 service，cordis 会抛 `service "compaction" has been registered at <…>`（`vendor/cordis/src/service.ts:57` → `vendor/cordis/src/reflect.ts:289-291`）。所以要先禁掉原来那行再插自己的。patch 写法（`disabled` 与 `insert` 的形态照抄 `packages/bundle/headless/cordis.patch.yml:14-15` 与 `:22-25`）：

```yaml
- id: compaction-basic
  disabled: true
- insert:
    - id: my-compaction
      name: '/absolute/path/to/my-compaction/index.ts'
```

本地插件路径必须是绝对路径（`docs/user/develop/basic/index.md:56`）。想临时试，不用改 profile：`dsh web --patch ./my-compaction/cordis.yml`（`apps/cli/reference/README.md:59`；启动器的 flag 必须写在应用参数之前，`packages/boot/cmdline/README.md:71`）。

从零实现的话要实现三个抽象方法 `compactIfNeeded` / `compactNow` / `compactRegion`，并且**替换用的那条 user 消息必须用 `compactCheckpointSource(compactionId)` 当 source**，否则包内 invariant 会拒（`packages/compaction/compaction/README.md:65-67`、`src/invariant.ts:63-71`）。

**完全不要压缩**：把 `compaction-basic` 和 `command-compact` 两行都 `disabled: true`。代价是上下文满了只会撞厂商的超窗错误，没有任何恢复动作。
