# 15 · 系统提示词与上下文装配

> 基于 `deepseek-ai/deepseek-harness` v0.1.0-rc.5（commit `47f9438`），2026-08-14 核对。本章讲清一轮请求里的 `system` 字符串和 `tools` 字段是怎么被拼出来的，以及你能在哪一步、用什么代价插手。压缩与长会话归第 17 章。

**读完这章你会**：

- 复述一次 prompt 装配的六步流水，并指出哪一步是 waterfall、它能改哪四样东西
- 写一个本地插件往系统提示词里加一段，并预测它会落在哪个位置
- 用四种手法改掉或整段接管内置的段落，并说清各自代价
- 按条件动态注入：让一段 prompt 只在某个 agent / 某个会话下出现
- 说清 `AGENTS.md` 是被哪个插件、按什么顺序读进来的，以及它为什么**不是**一个 prompt section

## 1. 先看模型这一轮实际收到了什么

`find . -name system-prompt.expected.md` 命中 15 个文件：13 份是录制下来的真实系统提示词（`examples/acp-agent/tests/snapshots/` 12 份 + `apps/web/tests/snapshots/fresh-round-trip/` 1 份），另外 2 份在 `packages/test-support/acp-snapshot/tests/fixtures/` 下是占位假数据（正文就一行 `SYS PROMPT`）。挑一份真的看开头：

```text
You are an AI agent powered by DeepSeek Harness.

You are a coding assistant powered by the deepseek-v4-flash model. Your working directory is {{cwd}}.

Verify your work by running the code or tests. Keep answers brief and factual.


Use the read tool — not shell commands like cat — to inspect text files. Results include line numbers. ...
```

出处 `examples/acp-agent/tests/snapshots/agent-instructions/system-prompt.expected.md:1`–`:8`。四处要点：

1. 第 1 行是 harness 固定身份，来自 `packages/core/system-prompt/src/index.ts:358`–`:362`。
2. 第 3–5 行是这份 composition 配的 persona，原文在 `examples/acp-agent/agent-instructions.cordis.snapshot.yml:24`–`:27`——快照跑的是 keyless 回放，配置被换成同名的 `*.cordis.snapshot.yml`（`packages/test-support/acp-snapshot/src/suite.ts:150`），所以模型名渲染成 `deepseek-v4-flash`；日常那份 `agent-instructions.cordis.yml:21`–`:24` 文本一模一样，只是 `model` 配的是 `deepseek-v4-pro`。
3. `{{cwd}}` 在这里**不是**没渲染的变量，而是快照归一化把真实路径替换成的占位符（`packages/test-support/acp-snapshot/src/normalize.ts:10`）。真跑时它已被插值成绝对路径。第 6–7 行的两个连续空行则来自 persona 文本自己的结尾换行（YAML `|` 块标量保留末尾换行）叠加段落间固定的 `\n\n`；它**不是**某个空段落留下的坑，空段落在渲染时被整条 filter 掉、不占位（`packages/core/system-prompt/src/index.ts:213`–`:216`）。

一次模型请求最终长这样（`packages/core/agent-loop/src/agent.ts:486`–`:493`）：

```text
request = { ...header.config, messages, system, tools, sessionId, signal }
  · ...header.config → provider / model 等路由参数（第 04 章）  · messages → deriveMessages() 日志投影（第 16 章）
  · system → renderPrompt(assembly)，本章主角                  · tools → assembly.tools，本章主角
```

`system` 与 `tools` 只在非空时才进请求（`agent.ts:489`–`:490`），两者都来自同一次装配（`:230` 装配、`:337` 渲染 system、`:341` 传 tools）。想看**这台机器上真实发出去的那份**不用猜：第一次请求必定往会话日志追加一条 `request/header` 事件（`reason` = `initial` 或 `resume`），此后只在 header 变了才再追一条（`reason: 'change'`），事件里带完整的 `system` 与 `tools`（`agent.ts:458`–`:470`）。会话日志怎么读见第 16 章。

## 2. 四种贡献物，进四个不同的地方

`ctx.systemPrompt` 是一个注册表服务（`packages/core/system-prompt/src/index.ts:338`）。插件往里塞四类东西：

| API | 贡献物 | 最终去哪 | 何时求值 |
|---|---|---|---|
| `section({name, order, text, complete?})` | 有名字、有序号的一段文本 | 拼进 `system` 字符串 | 每步装配一次 |
| `context({name, order, text})` | 动态运行时上下文 | 变成一条 **user 角色**消息进会话历史 | 每步装配一次 |
| `tools(provider)` | 工具 schema，provider 返回 `{ schemas, knownNames? }` | 请求的 `tools` 字段 | 每步装配一次 |
| `variable(name, provider)` | `{{name}}` 的值 | 供 section/context 插值 | 每步装配一次 |

签名逐条见 `packages/core/system-prompt/src/index.ts:381`（section）、`:398`（context）、`:430`（tools，返回值类型在 `:104`–`:109`）、`:446`（variable）。四个方法都返回 Cordis effect 的 disposer（卸载时要调的清理函数）——插件卸下来，贡献自动消失（effect 见第 08 章）。其中 **`tools()` 你多半用不上**：全仓非测试代码只有一个 provider 注册点，就是工具注册表自己（`packages/core/tools/src/index.ts:832`），你的工具通过 `ctx.tools` 注册（第 12 章）schema 就自动进来了。

**section 与 context 的区别是本章最容易搞混的一点**，它不是风格问题，是 KV cache（模型对请求前缀的缓存，只有前缀逐 token 一致才能复用）问题：

- section 拼进 `system`，位于请求最前缀。改它 = 从第一个变化的 token 起，后面全部缓存作废（`packages/core/system-prompt/README.md:69` 的规格描述；缓存行为发生在模型服务端，本仓库里无从验证）。
- context 走另一条路：agent loop 把渲染结果投影成一条 user 消息，追加到这一步的消息尾部（`packages/core/agent-loop/src/agent.ts:232`–`:239`），并且**只在内容相对上一份快照发生变化时才追加**（`packages/core/agent-loop/src/runtime-context.ts:64`–`:75`）。前缀不动，缓存保住。

快照文本自带一句头："`Current runtime context. This snapshot supersedes earlier runtime-context snapshots.`"（`system-prompt/src/index.ts:239`）；曾经有过快照、现在全部渲染成空时，改投一句 `Current runtime context: none. Earlier runtime-context snapshots no longer apply.`（`runtime-context.ts:13`、`:65`–`:67`）。**判据**：会随会话状态反复变的事实（沙箱模式、审批策略）用 `context`；一次装好基本不动的规矩用 `section`。仓库里全部三个 context 注册都属于前者：`sandbox:policy`（`packages/sandbox/sandbox-policy/src/index.ts:113`，order 110）、`approval:policy`（`packages/interaction/user-approval/src/index.ts:205`，order 115）、`subagent:delegation`（`packages/subagent/subagent/src/child-agent.ts:170`，order 120）。

## 3. 装配的六步流水：哪一步是 waterfall

`assemble()` 的全部逻辑在 `packages/core/system-prompt/src/index.ts:467`–`:542`，六步，顺序不可调。这里的 scope 是 agent 维度的一条层级链：global 层铺底，agent 自己那层盖在上面（`packages/core/scope/src/store.ts:208`–`:217`）。

```text
① 解析变量      global 层 → scope 链（远祖先→近），同名后写覆盖   :473-:482
② 合并 section  global + scope 链，同名 scoped 遮蔽 global        :484
   合并 context  同上                                              :485
③ 收集 tools    global provider + scope 链 provider，逐个调用      :487-:503
                parameters 做 structuredClone，与注册表脱钩        :495-:499
④ 归一顺序      section 按 order 升序；tools 按 toolOrder 或字典序 :504、:529
⑤ waterfall     system-prompt/assemble ← 你唯一的整体改写点       :532-:535
⑥ 收尾约束      complete 段恢复为唯一段落；suppress 清空 contexts  :536-:541
```

第 ⑤ 步是全章重点。它是 waterfall（洋葱中间件：每个 listener 拿到 `next()`，自己决定何时调用、要不要改返回值，语义见第 11 章），签名声明在 `:31`：

```ts
'system-prompt/assemble'(this: Scoped<SystemPrompt>, assembly: PromptAssembly, context: AssembleContext, next: () => Promise<PromptAssembly>): Promise<PromptAssembly>
```

`PromptAssembly` 是 `{ sections, contexts, tools, variables }`（`:115`–`:120`），**四样都可以增删改**。返回值即权威（事件文档 `:20`–`:26` 明写 "The returned value is authoritative"），唯一的例外是第 ⑥ 步的 complete 与 suppress 两条约束。包里另有一个 companion 会在 waterfall 之后校验结果形状（重名 section、非字符串文本、非法变量名），但它只报错、不改写（`packages/core/system-prompt/src/invariant.ts:16`–`:52`）。

注意 ④ 在 ⑤ 之前：`order` 排序和 `toolOrder` 归一是**把注册顺序这个随机性从输出里挤掉**用的（注册顺序本就是插件加载顺序的产物），waterfall 拿到的是已确定的列表；你在 ⑤ 里重排之后的确定性由你自己负责（`.agents/notes/implemented/feature/2026-07-06-explicit-tool-order.md:22`、`:24`）。另外，装配每一步都跑一次（`packages/core/agent-loop/src/agent.ts:230`），而 `text` 写成函数时签名是同步的（`index.ts:67`），做不了 `await`——别在里面读文件或算重活。

## 5. 变量与严格插值

`renderPrompt()` 在拼接前做 `{{name}}` 插值（`packages/core/system-prompt/src/index.ts:212`–`:217`）。shipped loop 只注册三个变量，全部从 `context.agent` 上取，没有 agent 时一律 `undefined`（`packages/core/agent-loop/src/index.ts:351`–`:353`）：`{{provider}}` = `agent?.options.provider`、`{{model}}` = `agent?.options.model`、`{{cwd}}` = `agent?.session.header.cwd`（`cwd` 本身也是可选字段，`packages/core/session/src/types.ts:73`）。

插值是**严格**的，四种情况直接 throw，而且四条错误信息各不相同：`{{` 后面还有 `}}` 但不构成完整组（`{{{model}}}` 会炸）报 `malformed prompt variable reference at ...`（`:270`–`:271`）；名字不匹配 `/^[a-z][a-z0-9_]*$/` 报 `malformed prompt variable reference "{{...}}"`（`:279`–`:281`）；名字没注册过报 `unknown prompt variable ...`（`:283`–`:286`）；注册了但这次装配求值为 `undefined` 报 `prompt variable "{{...}}" has no value`（`:288`–`:290`）。只有"`{{` 之后全文再无 `}}`"才当普通文本放行（`:269`–`:275`）。**没有转义语法**，想写字面量花括号目前做不到（`README.md:88`）。自己加变量：`ctx.systemPrompt.variable('team', () => 'infra')`，随后任何 section 里写 `{{team}}`。注册时名字非法当场 throw（`:447`–`:449`）；scoped 注册遮蔽同名的 global 值（契约在 `:439`–`:440`，实现在 `:477`–`:482`）。

## 6. workspace context：`AGENTS.md` 是怎么进来的

**它不是 prompt section**。读项目指令文件的是独立插件 `@deepseek-ai/dsh-agent-instructions`（`packages/context/agent-instructions/`），它把内容作为**durable user 消息**注入会话历史，外面套 `<system-reminder>` 框（该包 `README.md:17`–`:31`）。所以它不动系统提示词前缀、不废掉已有 KV cache（`README.md:160`），也能被压缩掉（`README.md:55`）。

读取顺序（`src/files.ts:280`–`:307`）：

```text
$DSH_HOME/AGENTS.md              ← 用户全局，固定文件名，无 local 覆盖层
project-root/ …逐层向下… cwd/    ← 每层先 base 候选（AGENTS.md CLAUDE.md），再 local 覆盖层（*.local.md）
```

默认值都在 `src/config.ts:11`–`:13`：候选 `['AGENTS.md','CLAUDE.md']`、local 候选 `['AGENTS.local.md','CLAUDE.local.md']`、项目根标记 `['.git']`（向上找到第一个带标记的目录，找不到就退回 cwd，见 `files.ts:176`–`:190`）。`maxBytes` **必填**，逼每个部署显式做预算决定（`config.ts:24`、`:42`）。候选名必须是同目录文件名：空串、`.`、`..` 以及含 `/` 或 `\` 的条目直接被丢弃（`config.ts:119`–`:123`）。用户全局那份固定叫 `AGENTS.md`，两个候选列表都管不到它（`README.md:72`、`src/render.ts:98`）。下面这张表里除预算提示（已在 `render.ts` 核对到实现）外，其余各条都只核到该包 README 的规格描述，未逐条追进实现代码：

| 行为要点 | 出处 |
|---|---|
| 同目录内 trim 后内容相同的候选只渲染一次（`CLAUDE.md` 复制 `AGENTS.md` 时只出 `AGENTS.md` 那份） | `README.md:70` |
| 超预算时**先整份丢掉更宽泛的文件**，最后才截断最具体的那份，并输出 `Workspace instruction budget ...` 提示 | `README.md:76`、`src/render.ts:215`–`:224` |
| **没有文件监听器**：磁盘上改了要等下一次成功的 `read`/`write`/`edit` 工具调用才被发现 | `README.md:165` |
| `bash` 里 `cd` 进子目录**不会**触发嵌套指令发现（只认结构化 fs 工具） | `README.md:164` |
| 小写文件名、`.claude/rules/`、`@path` import **都不支持** | `README.md:166` |
| 指令内容里的字面 `</system-reminder>` 会被转义，仓库文本关不掉插件的框 | `README.md:45` |

挂在哪：`dsh-base` bundle 把它放在宿主层（`packages/bundle/base/cordis.patch.yml:232`–`:235`，`maxBytes: 65536`）；Web bundle 把宿主那行关掉（`packages/bundle/web-app/cordis.patch.yml:401`–`:402`），改由 agent preset 各自挂载（`apps/cli/config/agent-presets/standard/agent.cordis.yml:30`–`:33`，`code`、`cordis` 两个 preset 同样挂）。想改候选名或预算，就在对应那一层写 patch（四层叠加见第 03 章）。

## 7. 实操 A：加一段自己的 prompt section

插件文件（形状照抄 `packages/client/ui-deliverables/src/index.ts`，一个只做 prompt 贡献的最小插件，全文 28 行）：

```ts
// scratch-plugin/src/house-rules.ts
import type { Context } from '@deepseek-ai/cordis'
import type {} from '@deepseek-ai/dsh-system-prompt'

export const name = 'house-rules'

export const inject = ['systemPrompt']

export function apply(ctx: Context): void {
  ctx.systemPrompt.section({
    name: 'house:rules',
    order: 60,
    text: 'Never push to a protected branch. Run the test suite before reporting a task as done.',
  })
}
```

挂载（本地插件用相对路径引用，形式见 `docs/user/develop/basic/config.md:37`–`:39`）：

```yaml
- insert:
    - id: house-rules
      name: './src/house-rules.ts'
```

三处解释：`import type {}` 那行是把 `systemPrompt` 字段合并进 `Context` 类型（同款写法见 `ui-deliverables/src/index.ts:9`）；`inject = ['systemPrompt']` 不能省，没有它插件可能在注册表服务就绪前 apply、拿不到 `ctx.systemPrompt`（Service 依赖见第 07 章）；`order: 60` 让它落在 persona（0）之后、工具指引（99+）之前。`section()` 返回的 disposer 本身就是 effect，不必再包一层 `ctx.effect()`，包了也没错（`packages/preset/persona/src/index.ts:61`–`:66` 就是包着写的）。**怎么确认生效**：发一轮消息，然后在会话日志里找 `request/header` 事件（`packages/core/agent-loop/src/agent.ts:465`–`:470`），`header.system` 就是渲染后的完整字符串。

## 8. 实操 B：改掉内置的一段

四种手法，代价各不相同：

| 手法 | 怎么做 | 代价 |
|---|---|---|
| **同名遮蔽**（推荐） | 在 agent scope 里注册同名 section，遮蔽 global 同名段 | 只对该 scope 生效；同一层里重复注册同名直接 throw |
| **关掉拥有它的插件行** | 配置里给那行加 `disabled: true`（真实例子 `packages/bundle/web-app/cordis.patch.yml:401`–`:402`） | 连带该插件的工具/服务一起没了 |
| **配置项** | `includeHarnessIdentity: false` 去掉 -100 身份行；`includeRuntimeContext: false` 关掉所有动态 context | 注册表 config 一共四个字段（`:186`–`:202`），开关只有这两个，粒度粗 |
| **waterfall 过滤** | 在 `system-prompt/assemble` 里改 `assembly.sections` | 你要为最终组合负责，包括别人塞进来的协议片段 |

同名遮蔽是官方给出的正解，`@deepseek-ai/dsh-persona` 这个包存在的唯一理由就是它：注册表自己无条件注册 `deployment:persona`，所以这个包**只能挂在 agent scope 里**，挂到 global 会跟注册表撞名而 fail loud（`packages/preset/persona/src/index.ts:1`–`:13`、`:60`–`:66`）。遮蔽规则本身在 `packages/core/scope/src/store.ts:208`–`:217`：global 先铺底，再按 scope 链从远祖先到近后代逐层 `set`，最近的 scope 赢。

waterfall 写法，形状抄 `packages/core/system-prompt/src/invariant.ts:47`–`:51`：

```ts
ctx.on('system-prompt/assemble', async (_assembly, _context, next) => {
  const assembled = await next()
  return {
    ...assembled,
    sections: assembled.sections.filter(section => section.name !== 'tool:ralph'),
  }
}, { global: true, prepend: true })
```

`{ global: true, prepend: true }` 的含义在 `vendor/cordis/src/events.ts:111`–`:117`：`prepend` 排到最前，`global` 绕过 context filter 检查（`:173`）。不加 `global` 要过两道筛：先是服务自己的 filter（listener 必须解析到同一个 `systemPrompt` 实例，`vendor/cordis/src/service.ts:61`–`:63`），再是 scope tag——无 tag 的监听器收全部装配，带 tag 的只收该 scope 及其后代的装配（`packages/core/scope/src/index.ts:154`、`:170`–`:185`）。要改结果就**先 `await next()` 再改**：全仓两个会改写的 listener 都这么写（`invariant.ts:47`–`:51`；`packages/core/agent/src/model-selection.ts:40`–`:53` 在所有下游 listener 之后覆写 `variables.provider`/`variables.model`，保证提示词里写的模型和真正路由到的模型是同一个）。只做前置校验的那个则直接 `return next()`（`packages/preset/agent-presets/src/invariant.ts:60`–`:71`）。

**整段接管**用 `complete: true`：这一段会在 waterfall 跑完后被恢复为唯一的 prompt section（`packages/core/system-prompt/src/index.ts:509`–`:518`、`:536`–`:541`），身份行、Web 定位、工具指引、别的 listener 加的东西全部作废；出现两个 complete 段则装配直接拒绝（`:505`–`:508`）。shipped 的 `minimal` preset 就是这么干的（`apps/cli/config/agent-presets/minimal/agent.cordis.yml:8`–`:13`）：

```yaml
- id: persona
  name: '@deepseek-ai/dsh-persona'
  config:
    text: You are a helpful software engineer assistant.
    complete: true
    includeRuntimeContext: false
```

代价写在它自己的文件头注释里（同文件 `:3`–`:6`）：这个 agent 从此看不到任何工具指引段，Code Mode / 结构化输出这类协议片段也一并消失——**要用 complete，就得自己把模型需要的协议说明写进这段文本**。末尾那行 `includeRuntimeContext: false` 是 persona 包自己的开关，走 scope 级的 `suppressRuntimeContext()`（`packages/preset/persona/src/index.ts:67`、`system-prompt/src/index.ts:415`–`:421`）。

## 9. 实操 C：按条件动态注入

`text` 可以是 `(context: AssembleContext) => string`，返回空串就等于这次不出现（空 section 渲染时被丢掉，`packages/core/system-prompt/src/index.ts:215`）。`AssembleContext` 自带 `scope` 与 `signal`（`:42`–`:50`），`dsh-agent` 用 TypeScript 声明合并（往同一个 interface 上补字段）加了 `agent`（`packages/core/agent/src/runtime-types.ts:16`–`:21`，说明见 `docs/subsystems/system-prompt.md:11`）。仓库里三个真例：

- 按模式：`tools:code-only` 只在有效模式是 `code` 时出文本，`both`/`native` 返回 `''`（`packages/core/tools/src/index.ts:855`–`:862`）。
- 按 agent 有无：`plan:policy` 遇到 `context.agent === undefined` 直接返回 `''`（`packages/plan/plan-mode/src/index.ts:228`–`:229`）——bare `assemble()`（测试、诊断）没有 agent，provider **必须**容忍字段缺失。
- 按会话：`sandbox:policy` 从 `context.agent?.session` 解析当前策略再渲染，无 session 返回 `''`（`packages/sandbox/sandbox-policy/src/index.ts:116`–`:121`）。

写自己的条件段落就照第三种来：

```ts
ctx.systemPrompt.section({
  name: 'house:release-window',
  order: 61,
  text: context => context.agent?.session.header.cwd?.endsWith('/deploy') === true
    ? 'Release freeze is active. Do not modify deployment manifests.'
    : '',
})
```

同一个函数每步都会被调用，所以它反映的是**当前这一步**的事实，不是会话开始时的。
