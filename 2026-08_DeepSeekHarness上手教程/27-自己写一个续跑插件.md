# 27 · 自己写一个续跑插件

> 基于 `deepseek-ai/deepseek-harness` v0.1.0-rc.5（commit `47f9438`），2026-08-14 核对。本章不用内置的 goal（25 章）也不用内置的 ralph（26 章），从零写一个插件，让 agent 在"自以为干完了"的那一刻被拦下来接着干。

> ⚠️ **本篇未通过对抗式引用核验**：起草已完成，但逐条打开源码比对行号/字段名/英文引文的那一遍因会话额度耗尽未执行。文中 `path:line` 与配置字段请以源码为准，核验后本行会被移除。

**读完这章你会**：

- 说清 `agent/turn-stopping` 为什么不是拦截器：serial 派发，没有 `next()`，返回值不算数
- 用 `agent.steer()` 让一个已经准备关闭的轮次再跑一步，并知道它和 `followup()` / `inject()` 的分工
- 用 `ctx.fs` 真实存在的方法读工作区的 progress 文件，并正确处理"文件不存在"
- 给续跑装三条防线（次数上限 / 取消信号 / 完成标记），说清每条各防哪种翻车
- 判断计数该放进程内存还是落进会话日志，并在 25 / 26 / 27 三种长程方案之间选型

## 1. 结论先行：续跑不是"拦返回值"，是往 inbox 里塞东西

第 10 章讲的 waterfall 是"监听器拿到 `next()`，不调用就短路"。**`agent/turn-stopping` 不是这种事件。** 循环里那一行是：

```ts
// packages/core/agent-loop/src/agent.ts:296
await this.dispatch.serial('agent/turn-stopping', { turn, signal })
```

`serial` 只按注册顺序 await 每个监听器（`vendor/cordis/src/events.ts:204-210`），没有 `next()` 可传，返回值也被循环整个丢掉。那"要不要再跑一步"谁说了算？事件声明上方那段注释就是官方契约，逐字抄在这里（`packages/core/agent/src/runtime-types.ts:261-271`）：

> The turn is about to close: the model owes no response (no live tool calls, no fresh steering). Awaited before the boundary commits — a listener that objects steers (`agent.steer(...)`) and the machine re-reads its inbox: fresh steering runs another step, none closes the turn. Data decides, so listener order cannot change the outcome.

"Data decides" 落到代码上，就是 dispatch 前后各查一次 inbox（`packages/core/agent-loop/src/agent.ts:295-299`）：

```
  步骤跑完 → nextStep 空？ ──否──→ 直接再跑一步（事件根本不烧）
                  │是
     dispatch.serial('agent/turn-stopping')  ← 你的监听器在这里 steer()
                  │ 然后 signal.throwIfAborted()
        nextStep 还是空？ ──是──→ break，关闭轮次
                  │否 → 再跑一步
```

一句话：**你不是在"否决关闭"，你是在这个窗口期往 inbox 塞一条 steering；循环再看一眼 inbox，有货就继续。**

这里最容易踩的是 serial 的 bail 语义：监听器返回"非 null / 非 false / 非 undefined"时 `serial` 会提前 return（`isBailed`，`vendor/cordis/src/events.ts:13`），后面的监听器一个都不跑。事件声明的返回类型是 `Promise<void> | void`，但 TypeScript 允许把"返回 boolean 的函数"赋给"返回 void 的函数类型"——你顺手写个 `return true`，编译器不拦、循环不理，**唯一后果是把别人注册的监听器静默吃掉**。只写 `return`，别写 `return 值`。

## 2. 事件什么时候烧、烧几次

payload 就三个字段（`packages/core/agent/src/runtime-types.ts:278`）：`agent` / `turn` / `signal`。触发条件比想象中窄，看 `step()` 的返回值：模型只出文本时返回 `{ kind: 'completed' }`（`agent.ts:394`）→ 烧；有 tool call 且没 `concludeTurn` 时返回 `null`（`agent.ts:399`）→ 不烧，直接进下一步；tool 结果带 `concludesTurn` 或撞到 max tokens 也返回非 null（`agent.ts:391`、`:399`）→ 烧；步骤里抛异常 → 走 catch，轮次以 error 收尾，不烧。

**它是"每个停止边界烧一次"，不是"每轮烧一次"。** 你 steer 一次 → 多跑一步 → 那一步又没 tool call → 又烧一次。没有上限的插件 = 无限循环，每一圈都是一次真实模型请求。

## 3. steer / followup / inject：塞哪个口子

三个方法的实现只差一行（`packages/core/agent-loop/src/agent.ts:122-132`）：

| 方法 | 落到哪个 inbox | 唤醒 driver | 声明处语义（`runtime-types.ts`） |
|---|---|---|---|
| `steer(msg)` | `next-step` | 是 | 「Submit steering for the nearest step」：空闲则开一轮，运行中则在下一个步骤边界被消费（:126-133） |
| `followup(msg)` | `next-turn` | 是 | 「Queue an ordinary follow-up turn」：独占一个新轮次（:119-124） |
| `inject(msg)` | `next-step` | **否** | 只排队上下文、不唤醒；可能错过已领完批次的那次请求（:135-143） |

turn-stopping 里必须用 `steer`：`followup` 会另开一个轮次（UI 上就是"又一条新对话"）；`inject` 虽然也落 `next-step`，但契约明写"idle driver 会把它挂着不动"，语义对不上。

两个代价都写在 `steer` 的注释里（`runtime-types.ts:129-131`）：**被 `agent/pre-step` 拒绝的步骤会把 steering 原样停在 inbox 里等下一次唤醒**；**取消或 dispose 可能直接丢弃 pending steering**。`steer()` 返回不等于"模型一定看到了"。

## 4. 这是个 Scoped 事件：你的监听器默认收所有 agent

签名里的 `this: Scoped<Agent>` 不是装饰。派发时循环用 agent 自己当 scope key 建 carrier（`packages/core/agent-loop/src/agent.ts:94`），准入规则在 `scopeTarget`（`packages/core/scope/src/index.ts:170-183`）：

- 注册在**没有 scope 标签**的 context 上 → 全收（`index.ts:176`）。你在插件顶层 `ctx.on(...)`，就会收到**每一个 agent** 的 turn-stopping，包括子 agent（18 章）派生出来的。
- 注册在**某个 agent 的 scope**（或其祖先 scope）上 → 只收该 agent 及其后代；比 dispatch key 更"低"的标签收不到——事件只沿 scope 链往上走，不往下走。

生成的路由表把这件事写死：`'agent/turn-stopping': args => args[0]['agent']`（`packages/core/scope/src/scoped-events.generated.ts:22`）。

实践含义：本章插件用顶层 `ctx.on`，所以计数必须**按 agent 分桶**（WeakMap 就干这个），否则父 agent 和它派生的子 agent 共用一个配额。只想管某一个 agent，就在 `agent/created` 里用 `agent.ctx.on(...)` 注册——`Agent.ctx` 的注释写明"agent-scoped，随 disposal 回滚"（`runtime-types.ts:75-76`）。

## 5. 完整插件（单文件，可照抄）

放在 dsh 仓库 checkout 的 `scratch-plugin/src/keep-going.ts`（官方第一个插件教程就是这么起步的，`docs/user/develop/basic/index.md:9-13`）：

```ts
import type { Context } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'
import type { Agent } from '@deepseek-ai/dsh-agent'
import { createUserMessage, errorChain } from '@deepseek-ai/dsh-llm'

export const name = 'keep-going'

export const inject = ['agents', 'fs']

export interface Config {
  maxContinuations: number
  progressFile: string
  doneMarker: string
}

export const Config: z<Config> = z.object({
  maxContinuations: z.number().step(1).min(1).default(3),
  progressFile: z.string().default('PROGRESS.md'),
  doneMarker: z.string().default('ALL DONE'),
})

export function apply(ctx: Context, config: Config): void {
  const spentByAgent = new WeakMap<Agent, { turn: number; count: number }>()

  async function progressText(agent: Agent, signal: AbortSignal): Promise<string | undefined> {
    const cwd = agent.session.header.cwd
    if (cwd === undefined) throw new Error(`agent "${agent.id}" has no workspace cwd`)
    const target = await ctx.fs.resolve(config.progressFile, { cwd, signal })
    const info = await ctx.fs.stat(target, signal)
    if (info === undefined || info.type !== 'file') return undefined
    return await ctx.fs.readText(target, signal)
  }

  ctx.on('agent/turn-stopping', async ({ agent, turn, signal }) => {
    const previous = spentByAgent.get(agent)
    const spent = previous !== undefined && previous.turn === turn ? previous.count : 0
    if (spent >= config.maxContinuations) return
    if (signal.aborted) return

    let progress: string | undefined
    try {
      progress = await progressText(agent, signal)
    } catch (error: unknown) {
      ctx.logger.warn(`${name}: cannot read ${config.progressFile}: ${errorChain(error)}`)
      return
    }
    if (signal.aborted) return
    if (progress !== undefined && progress.includes(config.doneMarker)) return

    const round = spent + 1
    spentByAgent.set(agent, { turn, count: round })
    agent.steer(createUserMessage({
      content: [{
        type: 'text',
        text: [
          `Automatic continuation ${round} of ${config.maxContinuations} for turn ${turn}.`,
          `You are not finished. Re-read ${config.progressFile} in the workspace, pick the next unfinished item, complete it now, and record what you finished back into that file.`,
          `When everything is done, write the exact line "${config.doneMarker}" into ${config.progressFile}; that line is the only thing that stops this continuation.`,
        ].join('\n'),
      }],
      source: { kind: 'plugin', plugin: name },
    }))
  })
}
```

逐个 API 的出处：`name` / `inject` / `Config` / `apply` 四件套照 `packages/context/time-context/src/index.ts:20-38`；`z.number().step(1).min(1).default(...)` 照 `packages/attachment/attachment-local/src/index.ts:41`；`createUserMessage({ content, source })` 的真实调用现场是 `packages/schedule/schedule/src/runtime.ts:271-274`；`source: { kind: 'plugin', plugin: string }` 的类型在 `packages/llm/llm/src/message.ts:102`；`ctx.logger.warn` 照 `packages/goal/goal-round-driver/src/index.ts:122`；`errorChain` 由 `@deepseek-ai/dsh-llm` 导出（`packages/llm/llm/src/index.ts:36` 转出 `packages/llm/llm/src/error.ts:114`）。

## 6. 三条防线，各自防什么

| 防线 | 代码 | 不写会怎样 |
|---|---|---|
| 次数上限 | `if (spent >= config.maxContinuations) return` | 模型每答完一次就被叫醒一次，**无限循环烧 token** |
| 取消信号 | `if (signal.aborted) return`（两处） | 用户已点停止、你还在塞消息。循环在 dispatch 之后立刻 `signal.throwIfAborted()`（`agent.ts:297`），白塞 |
| 完成标记 | 读 progress 文件命中 `doneMarker` 就 return | 任务其实做完了，插件还在逼它"接着干"，模型只能原地打转、编造工作量 |

三条是"或"关系：任一命中就放行（收工）。`signal.aborted` 要查**两次**——做 I/O 之前一次、`await` 回来之后一次，因为读文件期间用户完全可能按下取消。

还有一条隐性防线：`try/catch`。读文件失败（权限、二进制、沙箱拒绝、超大文件，错误码表见 `packages/fs/fs/src/types.ts:175-188`）时我们**放行**而不是续跑——看不清完成标记时宁可早收工。而且监听器抛异常有真实代价，见第 8 节。

## 7. 用 `ctx.fs` 真实存在的方法读文件

`FileSystem` 是抽象服务类，签名都在 `packages/fs/fs/src/index.ts`：

| 方法 | 签名 | 行号 |
|---|---|---|
| `resolve` | `(path: string, opts?: { cwd?: string; signal?: AbortSignal }) => Promise<FsTarget>` | :116 |
| `stat` | `(target: FsTarget, signal?: AbortSignal) => Promise<FsInfo \| undefined>` | :152 |
| `readText` | `(target: FsTarget, signal?: AbortSignal) => Promise<string>` | :176 |

**没有 `readOrEmpty`、没有 `exists`、没有 `readFile(path)`。** 想要"读不到就当空"，自己拼 `resolve → stat → readText`，就像第 5 节的 `progressText`。三个细节：

1. **文件不存在时 `resolve` 不报错。** 本地后端会 realpath 最近的存在祖先目录再把缺失后缀接回去（`packages/fs/fs-local/src/fsio.ts:161-168`），所以"文件还没被创建"只能靠 `stat` 返回 `undefined` 判断（契约见 `packages/fs/fs/src/index.ts:147-152`）。别拿 `try { readText } catch` 当存在性检查。
2. **`cwd` 得自己给。** 相对路径按 `opts.cwd` 解析，正确的 cwd 是这个会话自己的工作区 `agent.session.header.cwd`（`packages/core/session/src/types.ts:72-73`）——内置文件工具就是这么取的（`packages/fs/tool-fs/src/session-cwd.ts:23-27`）。不给的话后端退回自己的默认 cwd（web profile 里 `ctx.fs` 由 `dsh-fs-sandbox` 提供，`packages/bundle/base/cordis.patch.yml:441-444`，默认 `process.cwd()`），多工作区场景直接读错文件。
3. **为什么用工作区文件而不是插件内存里的 flag？** 因为完成标记必须由**模型自己**写得进去：它手里有 write / edit 工具，写的是工作区；插件内存对模型既不可见也不可写。这也是 ralph 的同一条思路——"workspace 是长期记忆"（`packages/workflow/tool-ralph/README.md:11`）。

## 8. 监听器抛异常 = 这一轮以错误收尾，但循环还活着

有专门的回归测试，名字就很直白：`it('a throwing agent/turn-stopping listener ends the turn with an error, loop survives')`（`packages/core/agent-loop/tests/contract-regressions.spec.ts:345`）。它断言两件事：最后一条 `turn/end` 的 reason 是 `{ kind: 'error', error: { message: 'broken continuation plugin', code: 'UNKNOWN' } }`（:360-362）；紧接着再 send 一次仍然正常跑完、`agent.status` 回到 `idle`（:365-368）。对应实现是 `turn()` 的 catch 把任意异常压成 `{ kind: 'error', error: { message: errorChain(error), code: 'UNKNOWN' } }`（`packages/core/agent-loop/src/agent.ts:309-314`）。

翻译成人话：**你的 bug 不会搞挂 harness，但会把用户这一轮的正常结束染成一个红色错误。** 第 5 节那个 `try/catch` 是必需品。

反过来，本章插件的"官方样例"是 `packages/core/agent-loop/tests/loop.spec.ts:766` 的 `agent/turn-stopping can steer another step (/loop pattern)`：监听器里 steer 两次、断言总共跑了 3 步（:777-786），用的 source 正是 `{ kind: 'plugin', plugin: 'loop-test' }`。

## 9. 续跑提示怎么写才有用

模型在续跑那一步看到的只有你这条消息。四样东西缺一样它就会瞎猜：**当前第几次 / 上限几次**（让它判断还剩多少预算，别开一个做不完的坑）、**progress 文件路径**（否则它猜文件名或凭记忆答）、**完成标记的精确字面量**（判定是 `includes(doneMarker)` 的字符串匹配，不是语义理解）、**"把做完的记回文件"**（否则下一次续跑没有可读状态，等于每次从头开始）。

这条消息在会话日志里的形态是**一条 `user/message`，`source.kind === 'plugin'`**（步骤领取它时由循环 append，`packages/core/agent-loop/src/agent.ts:283`）。三层含义：模型在下一次请求里看得见；UI 转录会标成插件来源（`time-context` 也靠同一特征找自己写过的消息，`packages/context/time-context/src/index.ts:86-95`）；它**必须能被无损 JSON 序列化**——`steer()` 走的 `Inbox.splice` 第一件事就是 `session.append('agent/inbox/spliced', ...)`（`packages/core/agent/src/inbox.ts:186`），塞个 `bigint` 会当场抛（测试见 `packages/core/agent-loop/tests/loop.spec.ts:753-755`）。老实用纯字符串。

## 10. 计数放哪：WeakMap 的代价，与落日志的改法

`WeakMap<Agent, { turn, count }>` 完全活在进程里。好处是零成本、agent 回收时自动清理；代价很明确：**进程重启或 resume 会话后计数归零**（一个已经烧掉 3 次续跑的会话被 resume 回来，配额又满血），而且计数对模型和 UI 都不可见。

内置的 goal 驱动器是另一个极端：`roundsStarted` 不是内存变量，而是**从会话日志重算**的。`foldGoal()` 顺序重放事件（`packages/goal/goal/src/fold.ts:339-349`），每遇到一条带 goal 来源的 `user/message` 就把 `roundsStarted` 推进到那个 round，且严格要求它正好是 `state.roundsStarted + 1`（`packages/goal/goal/src/fold.ts:321-331`）；驱动器发新一轮前先比 `goal.roundsStarted >= goal.maxGoalRounds`（`packages/goal/goal-round-driver/src/index.ts:166`）。日志即事实源，resume 之后配额分毫不差——代价是你要设计一套自己的持久事件和折叠规则。

中间路线：不发明新事件，直接数**自己写过的消息**（第 9 节说过它们本来就在日志里）。`time-context` 用的就是同一个识别特征——扫会话日志找 `source.kind === 'plugin' && source.plugin === name` 的消息：

```ts
function continuationsInTurn(agent: Agent, turn: number): number {
  let count = 0
  for (const event of agent.session.events) {
    if (event.type === 'turn/start' && event.data.turn === turn) count = 0
    if (event.type === 'user/message'
      && event.data.source.kind === 'plugin'
      && event.data.source.plugin === name) count += 1
  }
  return count
}
```

把第 5 节的 `spentByAgent` 换成它即可（`turn/start` 的 payload 形状见 `packages/core/agent-loop/src/agent.ts:255`；扫日志找自己插件来源的写法见 `packages/context/time-context/src/index.ts:73-95`）。一个必须知道的时序：`steer()` 当场落的是 `agent/inbox/spliced`，`user/message` 要等**步骤真的领取**了才落（`agent.ts:283`）。所以这个函数数到的是"已经生效的续跑次数"——被拒绝或被取消丢弃的那些不占配额，也确实数不到，正是想要的语义。

## 11. 挂上去跑

`scratch-plugin/cordis.yml`（路径**必须绝对**，`docs/user/develop/basic/index.md:48-56`）：

```yaml
- insert:
    - id: keep-going
      name: '/absolute/path/to/deepseek-harness/scratch-plugin/src/keep-going.ts'
      config:
        maxContinuations: 3
        progressFile: 'PROGRESS.md'
        doneMarker: 'ALL DONE'
```

```sh
pnpm dsh web --patch ./scratch-plugin/cordis.yml --dump-config   # 先干跑，在输出里搜 keep-going
pnpm dsh web --patch ./scratch-plugin/cordis.yml
```

`--patch <path>` 可重复、overlay 合成在 profile 层之后（`apps/cli/src/args.ts:163`，实现 `apps/cli/src/profile-boot.ts:148-151`）；`--dump-config` 打印合成后的 web profile 树后退出（`apps/cli/src/args.ts:164`）。`- insert:` 这个 patch 形态的解析有测试兜底（`packages/boot/app-boot/tests/user-patches.spec.ts:54-65`）。

验证脚本：工作区放一个写了三条待办的 `PROGRESS.md`，让 agent"做第一条"。它答完第一条本该收工，你应该看到它被自动推着做第二条、第三条；把 `ALL DONE` 写进文件后，下一次停止边界就不再续跑。

## 12. 这个插件危险在哪

- **烧钱**：每次续跑 = 一次完整模型请求。`maxContinuations: 3` 意味着一次用户提问最多变成 4 次请求。上限调到两位数之前先算账。
- **原地打转**：被强行唤醒的模型如果找不到"下一件事"，最常见的行为是把做过的事换个说法再说一遍，并在 progress 文件里追加一条假进展——于是完成标记永远等不到，直到撞上限。**上限是唯一能保证终止的东西**，完成标记只是优化。
- **对所有 agent 生效**：顶层 `ctx.on` 会收到子 agent 的 turn-stopping（第 4 节）。一个 ralph 子 agent 被你又续三次，账单是乘法。要上生产就换 `agent.ctx.on`，或按 `agent.session.header.origin === 'subagent'`（`packages/core/session/src/types.ts:85`）过滤。
- **它绕过了 goal 的所有闸门**：goal 有 phase / blocked / disarm 一整套状态机，本章这 60 行没有。

## 13. 三种长程推进方案对照

| | 25 章 goal | 26 章 ralph | 本章 keep-going |
|---|---|---|---|
| 状态存在哪 | 会话日志（`goal/change` + 带 goal 来源的 `user/message`，`fold.ts:313-331` 重算） | 工作区文件 + 每轮结构化 handoff（`tool-ralph/README.md:11`） | 进程内 `WeakMap`（可改成扫日志，第 10 节） |
| 上下文累不累积 | 累积（同一个会话一路长下去） | 不累积（每轮全新子 agent，不继承父会话） | 累积（同一个会话） |
| 谁决定停 | goal 状态机：`roundsStarted >= maxGoalRounds`，或模型把 goal 标成 complete / blocked | 子 agent 报 `status: complete \| blocked`，或撞 `maxRounds` | 三条防线：次数上限 / `signal.aborted` / progress 文件里的完成标记 |
| 崩溃或 resume 后 | 能恢复：日志重放即得 `roundsStarted` | 这次 run 作废（前台工具调用，取消即错误），但工作区产物还在，可以重新发起 | WeakMap 版归零；落日志版能恢复 |
| 适合什么 | 需要完整上下文连续性的长任务 | 上下文必然爆掉的重复性长任务 | 给现成会话补一层轻量"别急着收工"策略 |

三者不互斥但**别叠加**：goal 驱动器和本章插件都在往同一个 inbox 里塞东西，叠起来的行为没人验证过。两条内置路线的完整用法见 [25 章](25-Goal模式.md) 与 [26 章](26-RalphLoop.md)；派发模式本身回头看 [09 章](09-事件系统.md) 与 [10 章](10-waterfall专章.md)。
