# 24 · 遥测与数据边界

> 基于 `deepseek-ai/deepseek-harness` v0.1.0-rc.5（commit `47f9438`），2026-08-14 核对。

合规评审只关心一个问题：跑一次 dsh，哪些字节可能离开这台机器，哪些字节落到了磁盘上。

这一章逐条回答它，顺便说清默认状态下能关什么、关不掉什么、以及要在哪个位置挂脱敏。读完你应该能对着评审表逐行打勾，而不是回去猜。

先交代方法论：本仓库未安装依赖、未运行过任何命令，**下面每条结论都来自静态阅读源码与配置文件，没有抓包验证**。凡是「文档这么说、代码里没确认」的地方我都单独标出来了。

## 默认状态下只有两条路出网

「默认组合」指 `web` 档的两层 bundle：`@deepseek-ai/dsh-base` + `@deepseek-ai/dsh-web-app`（`packages/boot/app-boot/src/profile.ts:115`）。base 那层挂了 **78 个插件条目**（`grep -c "  - id:" packages/bundle/base/cordis.patch.yml` → 78）。`headless` 档是 base + `@deepseek-ai/dsh-headless`（`:116`），后者整份只有 35 行，没有任何出网行。

| 通道 | 默认状态 | 目标地址 | 传的内容 | 出处 |
|---|---|---|---|---|
| 模型请求（DeepSeek 直连） | **开** | `https://api.deepseek.com/chat/completions` | 完整对话请求体 + `authorization` + 最多 4 个归因/身份头 | `packages/llm/llm-deepseek/src/index.ts:104`、`adapter.ts:301` |
| `web_search` 工具 | **开** | `https://api.deepseek.com/anthropic/v1/messages` | 见下方拆解 | `packages/web/web-search-deepseek/src/provider.ts:35`、`:204` |
| `web_fetch` 工具 | **关**（`fetch: false`，且未挂任何 fetch provider） | — | — | `packages/bundle/base/cordis.patch.yml:414-418`、`:399-401` |
| 会话遥测（OTLP，即 OpenTelemetry 的传输协议） | **关**（`DISABLED`） | 默认端点明文写在配置里：`https://harness-telemetry.deepseeksvc.com/v1/logs` | 见后文 | `packages/bundle/base/cordis.patch.yml:148-161` |
| Web UI 监听 | 本机回环 | 缺省 `127.0.0.1:3080` | — | `packages/bundle/web-app/cordis.patch.yml:119-120` |
| 崩溃上报 | **不存在** | — | — | 见「没有的东西」一节 |
| 版本更新检查 | **不存在** | — | — | 同上 |
| MCP / hook 桥 / 外部 subagent 代理 | **未挂载** | — | — | base 的 78 个 id 里没有它们；web-app 那层也没有 |

Web UI 那行还有一条硬编码的安全闸。`--host` / `--port` 可以改绑定，但 `--host 0.0.0.0` 会被直接判为用法错误并拒绝启动，理由就写在报错文案里：「it would expose remote code execution to the network」（`packages/bundle/web-app/src/startup.ts:48-49`、`:69-71`）。

`web_search` 那条容易被误读成「联网搜索 = 把会话发出去」，其实不是。请求体的类型被写成定长元组、`messages` 恰好一条 user 消息（`packages/web/web-search-deepseek/src/provider.ts:62-77`），构造处在 `:205-213`，整份文件只有一处 `fetch()`（`:222`）。四个字段里只有一个装你的数据：`model`（默认 `deepseek-v4-flash`，`:38`）、`max_tokens`（默认 `4096`，`:44`）、`tools`（固定一项 `{ type: 'web_search_20250305', name: 'web_search', max_uses }`，`:212`），以及唯一带内容的 `messages` —— 一条 user 文本 `Perform a web search for the query: <query>`（`:210`）。出去的就是那句 query。

凭据用的是同一个 `DEEPSEEK_API_KEY`（`packages/bundle/base/cordis.patch.yml:409-412`），但端点不共用，源码注释明写「only the API key is shared」（`provider.ts:29-33`）。

## 最大的一条出网通道，是模型请求本身

做合规评估最容易只盯着遥测那一行，然后漏掉最大的那条：每一次模型请求。DeepSeek 直连适配器每次都会发这些头（`packages/llm/llm-deepseek/src/adapter.ts:283-295`）：

| 头 | 值 | 何时带 |
|---|---|---|
| `authorization` | `Bearer <你的 key>` | 总是 |
| `user-agent` | `deepseek-harness/<version> (+https://github.com/deepseek-ai/deepseek-harness)` | 总是，且**无法关闭** |
| `x-deepseek-harness-user-id` | 匿名 UUID | 凭据解析成功后总是（`adapter.ts:221-222` 先 key 后 id） |
| `x-deepseek-harness-session-id` | 当前 `Session.id` | 调用方给了 `sessionId` 时 |
| `x-deepseek-harness-compact` | `1` | 这次请求是压缩用途时 |

`user-agent` 由 `attributionHeaders()` 生成，它的 JSDoc 把话说死了：「omission cannot suppress attribution」（`packages/llm/llm/src/attribution.ts:61`）。好在 `APP_IDENTITY` 里只有产品名、版本、仓库 URL 三个字段（`:40-44`），没夹带别的。

真正要留意的是 `x-deepseek-harness-user-id`：它是一个**跨会话稳定的匿名标识，而且不受遥测开关控制**。设计说明写得很直白——「the first authorized provider request can create it even when `DSH_TELEMETRY_DISABLED` is set」（`.agents/notes/implemented/feature/2026-08-11-deepseek-request-user-id-header.md:17`），以及「SessionTelemetryBackend sharing controls only telemetry export and does not disable provider request identity」（同文件 `:19`）。你把遥测关到底，这个 id 照发。

它的物理形态倒是很好处理。文件是 `$DSH_HOME/.anonymous-user-id`，缺省即 `~/.dsh/.anonymous-user-id`（`packages/identity/anonymous-user-id/src/index.ts:29`、`:69`），内容是一行 UUID v4，由 `crypto.randomUUID()` 生成，**不从主机名、网络地址、git remote 或任何其它可识别来源派生**（`:4-7`、`:75`）。它的作用域是 harness home 而不是机器，共用同一个 `$DSH_HOME` 的进程报同一个 id（`:7-8`）。想重置就删掉文件，下次启动会重新生成；不过进程内有 memo，运行中删掉不影响本次（`:11-14`）。

顺带一句：如果你把 `baseURL` 指到自建网关，这两个头一样会发给网关——同一份 note 的 `:19` 写着「A configured gateway receives them.」

### 陌生仓库的 `.env` 改不动你的端点

`DEEPSEEK_BASE_URL`（`packages/llm/llm-deepseek/src/index.ts:107`）和 `DEEPSEEK_SEARCH_BASE_URL`（`packages/web/web-search-deepseek/src/index.ts:82`）能把上面两条通道指到别处，这是最直接的「把会话送到第三方」的改法。dsh 显然想到了这一层，所以启动器把它们连同 `HTTP_PROXY` / `HTTPS_PROXY` / `NODE_TLS_REJECT_UNAUTHORIZED` / `SSL_CERT_FILE` 这一整排「网络可达性与信任」变量（`packages/boot/app-boot/src/index.ts:108-113`），再加上前缀 `DSH_`、`XDG_`、`DYLD_`、`BASH_FUNC_`（`:117`），一起列进了 **bootstrap-only 名单**：这些名字只能来自继承的进程环境，任何被发现的 `.env` 声明了它们就直接抛错（`:93-114`、`:125-128`、`:130-138`）。

于是 clone 一个陌生仓库、里面塞一个 `.env`，既改不了你的模型端点，也打不开你的遥测——`DSH_TELEMETRY_MODE` 命中 `DSH_` 前缀。

## 遥测默认是关的，而且有三种关法

### 端点明文写死在 bundle 配置里

不用抓包也能看见它要往哪发：

```yaml
# packages/bundle/base/cordis.patch.yml:148-161（原文缩进四格，在 base 的 insert 列表内）
- id: session-telemetry-otel
  name: '@deepseek-ai/dsh-session-telemetry-otel'
  config:
    mode: !!js process.env.DSH_TELEMETRY_MODE || 'DISABLED'
    shutdownTimeoutMillis: 3000
    exporter:
      url: !!js process.env.DSH_TELEMETRY_OTLP_URL ?? 'https://harness-telemetry.deepseeksvc.com/v1/logs'
      compression: gzip
      timeoutMillis: 1000
    processor:
      scheduledDelayMillis: 10000
      maxQueueSize: 2048
      maxExportBatchSize: 2048
      exportTimeoutMillis: 1500
```

看到这一行挂在那儿别紧张，它是**挂载但禁用**。`DISABLED` 分支在构造函数里直接早退，`provider` 置为 `undefined`，OTel 的 provider / processor / exporter 一个都不建（`packages/session/session-telemetry-otel/src/index.ts:160-168`）。README 的说法是「No coordinator, provider, processor, or exporter is constructed. No telemetry record leaves the process.」（`README.md:26`）。

那为什么不干脆删掉这一行？为了让 `/feedback` 还能告诉你「什么都没有共享」：「The shared dsh base keeps the backend row mounted so disabled feedback can still explain that nothing was shared.」（`.agents/notes/implemented/feature/2026-08-10-telemetry-default-off.md:13`）

### 三种模式

| `mode` | 行为 | 出处 |
|---|---|---|
| `DISABLED` | **默认**。不构造 SDK 管线，一条记录都不出进程 | `packages/session/session-telemetry-otel/src/index.ts:51`、`:160-168` |
| `FEEDBACK_ONLY` | 平时什么都不交出去；`/feedback` 落下 `feedback/record` 事件时，回放**截至该事件（含）**、且尚未交接过的那一段会话日志 | `:243-252`、`packages/session/session-telemetry/src/coordinator.ts:138-149` |
| `FULL` | 每条投影后的记录（会话事件的镜像）实时交给 OTel SDK | `:237-241` |

「投影」在这里是个具体动作：协调器把会话事件转成一条 `SessionTelemetryRecord` 再交出去，转的过程中会丢掉重复的流式 chunk（下一节详述）。

默认值来自两处，任缺一处都还是 `DISABLED`——Schema 上 `mode` 的 `.default(DEFAULT_TELEMETRY_MODE)`（`:120-121`），以及常量 `DEFAULT_TELEMETRY_MODE = SessionTelemetryMode.DISABLED`（`:51`）。写错值也不会被悄悄当成默认吞掉：走配置层由 Schema 的枚举校验挡下（`:121`），绕开 Schema 直接构造则由 `resolveMode()` → `assertNever()` 抛错（`:57-73`）。

### 两个环境变量，语义完全不同

| 开关 | 语义 | 出处 |
|---|---|---|
| `DSH_TELEMETRY_MODE` | **正向同意**。不设 / 设空串都落回 `DISABLED`（`\|\|` 的短路） | `packages/bundle/base/cordis.patch.yml:151` |
| `DSH_TELEMETRY_DISABLED` | **硬关**。任何非空值都算关，**包括 `'0'` 和 `'false'`** | `apps/cli/src/profile-boot.ts:80-83` |

`'0'` 和 `'false'` 也算关，这个反直觉，但源码注释给了理由：「a privacy switch prefers off-by-mistake over on-by-mistake」（`:70-72`）。隐私开关宁可误关，不可误开。

硬关的实现是启动前给这一行打一个 `disabled: true` 的 patch，比插件加载和端点校验都早：

```ts
// apps/cli/src/profile-boot.ts:80-83
export function resolveTelemetryPatch(disabledEnv: string | undefined, hasRow: boolean): PatchOptions | undefined {
  if ((disabledEnv ?? '') === '' || !hasRow) return undefined
  return { id: TELEMETRY_ROW_ID, disabled: true }
}
```

### 不想依赖环境变量，就自己 patch 掉这一行

`disabled` 是 patch 层的合法字段（`vendor/include/src/index.ts:145-156`，`disabled?: boolean | null`），加载器在初始化前就检查它并直接返回（`vendor/loader/src/config/entry.ts:104-107`、`:126`）。所以在 `$DSH_HOME/cordis.patch.yml` 里写三行就够了：

```yaml
# $DSH_HOME/cordis.patch.yml
- id: session-telemetry-otel
  disabled: true
```

这与 launcher 自己生成的那个 patch 是同一形状、同一个 patch 栈（家目录层排在 profile 层之后、`--patch` 之前，`apps/cli/src/profile-boot.ts:122-128`、`:147`）。profile 自带的模板文件也把它列为合法用法之一：「id-targeted config overrides, disables, and insert lists」（`packages/boot/app-boot/src/profile.ts:127-130`）。

还想更彻底，就自己做 profile，压根不装这一行——`resolveTelemetryPatch` 的 `hasRow` 分支旁边就写着「A composition without the telemetry row exports nothing」（`apps/cli/src/profile-boot.ts:72-73`）。做 profile 的手艺见 [22 章](./22-做一个bundle和profile.md)。

### `--dump-config` 在这件事上会骗你

查配置的标准手段是 `--dump-config`（`apps/cli/src/args.ts:133`），但对遥测这一行，它给你的答案不可信，两个原因叠加：

它不求值 `!!js`，模块头就写着 "without booting or evaluating `!!js`"（`apps/cli/src/dump-config.ts:2-6`），所以你看到的是字面量 `!!js process.env.DSH_TELEMETRY_MODE || 'DISABLED'`，不是解析结果。而 `DSH_TELEMETRY_DISABLED` 生成的 overlay 只在启动路径 `composeProfile()` 里追加（`apps/cli/src/profile-boot.ts:168-169`），`runDumpConfig()` 的图层列表里根本没有这一步（`apps/cli/src/dump-config.ts:32-49`）。

运行期唯一的确认途径是 `/feedback` 的回执。它读挂载后端的 `sharing` 属性（`packages/feedback/command-feedback/src/index.ts:49-53`、`:92-96`），输出三句之一（`:27-38`）：

```
Session sharing is disabled.
Session sharing is feedback-gated; recording feedback releases the session prefix for sharing.
Session sharing is enabled.
```

没挂遥测服务时是第四句：`Session sharing is not configured.`（`:50-52`）。

但这个查法本身带副作用，用之前想清楚。`/feedback` 必须带文本（`Usage: /feedback <text>`，空输入直接返回用法错误、不落事件，`:18`、`:88-90`），带了文本就会往会话日志里追加一条 `feedback/record`（`:72-76`）——而在 `FEEDBACK_ONLY` 模式下，这一条恰恰就是触发上传的那个动作。回执里还会连带打印当前的匿名 user id（`:95`）。

## 一旦打开，传出去的是会话事件全文

一条记录的结构是这样的（`packages/session/session-telemetry/src/index.ts:64-87`）：

| 字段 | 内容 |
|---|---|
| `channel` | `ledger`（会话日志镜像）或 `ops`（运维信号） |
| `time` | epoch 毫秒 |
| `severity` | `info` / `warn` / `error` |
| `attributes` | 仅身份：`session.id`、`event.type`、`event.seq`，加上 header 里有的 `session.cwd`、`session.parent_id`、`session.seed_length` |
| `body` | **会话事件 `data` 的完整深拷贝** |

关键在 `body`。它是 `structuredClone(event.data)`，没有任何字段裁剪（`packages/session/session-telemetry/src/coordinator.ts:199`，上下文 `:191-202`）。也就是说下面这些会原样离开进程：

- `user/message` 的 `content` 全文（`docs/persistence-catalog.md:928`，语义说明在 `:924-927`）
- `tool/call` 的 `arguments` —— 「the raw `arguments` JSON string exactly as the model produced it (unparsed)」（`docs/persistence-catalog.md:732-733`，字段在 `:736`）
- `request/header` 里的 `system`（**渲染后的完整系统提示词**）与 `tools`（**完整工具 schema**）（`packages/core/session/src/types.ts:206-209`、`docs/persistence-catalog.md:557`）
- 工具结果（命令输出、文件内容）、todo 文本、压缩摘要、hook 的 `stderrSummary`、feedback 文本，以及 `session.cwd` 这个本地路径

这份清单不是我推的，包 README 直接列在那儿（`packages/session/session-telemetry-otel/README.md:38`）。Resource 上还会额外挂一次 `user.id`，就是前面那个匿名 UUID（`packages/session/session-telemetry-otel/src/index.ts:197-205`，具体在 `:204`）。

**被裁掉的只有两类。** 一是流式 chunk，每个 `(turn, step)` 只发第一条 `assistant/chunk`，其余丢弃——所以 `seq` 出现空洞是正常现象，不是丢包信号（`packages/session/session-telemetry/README.md:31`）。二是 resume / fork 继承来的历史前缀，它在上一个进程或父会话的流里已经出过，不重发（同一份 README，`:27`）。

**结构性不会出现的**是 provider API key：适配器的 key 是构造参数、不是会话事件，因此结构上不进日志，也就不进遥测（`packages/session/session-telemetry-otel/README.md:38`）。

### 一条脱敏规则都不带，这是明写的缺省

脱敏点是一个 waterfall（洋葱式中间件事件，机制见 [11 章](./11-waterfall专章.md)）。seam（本仓库术语，指「只声明契约、由某个后端实现」的那一层）自己一条规则都不带，最内层 `next()` 原样返回：

```ts
// packages/session/session-telemetry/src/coordinator.ts:213-215
private redact(record: SessionTelemetryRecord): SessionTelemetryRecord {
  return this.ctx.waterfall('session-telemetry/record', record, () => record)
}
```

README 的「Known Limitations」把后果写死了：「with no `sessionTelemetry/record` listener mounted, records leave the process exactly as captured, **including any credentials embedded in file contents or command output**」（`packages/session/session-telemetry/README.md:48`）。CLI 参考手册是同一口径：「The shipped base has no telemetry redaction rule, so explicitly enabled exports can contain message text, tool arguments and results, and workspace paths」（`apps/cli/reference/README.md:78`）。

所以要脱敏就得自己挂。仓库里有个真实可读的形状——e2e fixture `examples/headless-agent/tests/fixtures/telemetry-redact-rule.ts`，全文 29 行，[10 章](./10-事件系统.md)讲 capability 域事件时已经拆过它的 `apply()`。这里给一份改了正则与占位符的完整版，方便你直接照着改：

```ts
// 改编自 examples/headless-agent/tests/fixtures/telemetry-redact-rule.ts
import type { Context } from '@deepseek-ai/cordis'

const SECRET = /sk-[A-Za-z0-9]{16,}/g

function scrub(value: unknown): unknown {
  if (typeof value === 'string') return value.replace(SECRET, '[REDACTED]')
  if (Array.isArray(value)) return value.map(scrub)
  if (value !== null && typeof value === 'object') {
    return Object.fromEntries(Object.entries(value).map(([key, entry]) => [key, scrub(entry)]))
  }
  return value
}

export const name = 'telemetry-redact-rule'

export function apply(ctx: Context): void {
  ctx.on('session-telemetry/record', (_record, next) => {
    const record = next()
    return { ...record, body: scrub(record.body) }
  })
}
```

挂载方式和其它本地插件没有区别，见 [06 章](./06-你的第一个插件.md)；fixture 自己的挂法就在同目录的 `session-telemetry-otel.cordis.yml:16-17`（`name: './telemetry-redact-rule.ts'`）。

有三点语义得记住，都写在 `packages/session/session-telemetry/src/index.ts:25-43` 的 JSDoc 里。监听器**抛异常等于那条记录被扣下**（fail-closed），而且不会打断 agent loop。脱敏只作用于**外发副本**，canonical 会话日志**从不被改写**（`:37-38`）。`FEEDBACK_ONLY` 是在 feedback 触发回放时才跑规则，用的是**当时挂着的**那套规则（`:36-37`、`coordinator.ts:130-132`）。

### 事件名有个坑，照 README 抄会监听不到

源码里的声明是 `session-telemetry/record`（`packages/session/session-telemetry/src/index.ts:43`，`coordinator.ts:214` 的 `waterfall()` 调用也是它），而两个 README 正文里写的是 `sessionTelemetry/record`（`packages/session/session-telemetry/README.md:23`、`:35`、`:48`；`packages/session/session-telemetry-otel/README.md:38`）。

这两份 README 明显被批量改名污染过。同样的痕迹还有 `README.md:5` 里的 instrumentation scope 名 `@deepseek-ai/dsh-session-sessionTelemetry-otel`，以及 `:26` 把日志文案写成 `session sessionTelemetry is DISABLED`（真值见 `src/index.ts:53`）。**这两份 README 里凡是标识符，一律以源码为准。**

## 会话日志：路径公开、内容全量、没有脱敏

默认落盘路径是 `~/.dsh/sessions`（`packages/bundle/base/cordis.patch.yml:98-101`，`root: !!js dshHomePath('sessions')`；`dshHomePath` 解析 `$DSH_HOME` → `~/.dsh`，`packages/util/home-paths/src/index.ts:12`、`:87-100`）。目录结构见 `packages/session/session-persistence-jsonl/README.md:9-15`：

```
~/.dsh/sessions/
  --<归一化后的 cwd>--/        # 或 _no-cwd/
    <编码后的 session id>/
      session.jsonl.zstd        # 默认：zstd 压缩
      session.jsonl             # 仅当 compression: 'none'
```

## 子进程只挡四个词，剩下的照传

所有 harness 子进程（bash / pwsh / 后台任务 / node-pty）共用一份清洗定义：

```ts
// packages/subprocess/subprocess/src/index.ts:44
export const SENSITIVE_ENV_PATTERN = /KEY|PASSWORD|SECRET|TOKEN/i

// packages/subprocess/subprocess/src/index.ts:60-66
export function scrubbedParentEnv(): Record<string, string> {
  const env: Record<string, string> = {}
  for (const [key, value] of Object.entries(process.env)) {
    if (value !== undefined && !SENSITIVE_ENV_PATTERN.test(key) && !key.toUpperCase().startsWith(DSH_ENV_PREFIX)) env[key] = value
  }
  return env
}
```

`DSH_ENV_PREFIX` 就是字符串 `'DSH_'`（`packages/subprocess/subprocess/src/types.ts:13`）。归纳成四条：

| 规则 | 说明 |
|---|---|
| 名字命中 `/KEY\|PASSWORD\|SECRET\|TOKEN/i` → 剔除 | `DEEPSEEK_API_KEY`、`AWS_SECRET_ACCESS_KEY`、`GITHUB_TOKEN`、`NPM_CONFIG_.../:_authToken`（含 `Token`）都命中 |
| 名字以 `DSH_` 开头（大小写不敏感）→ 剔除 | 防止 harness 身份隐式泄漏；Windows 环境名大小写不敏感所以统一 upper 比较 |
| 其余全部保留 | `PATH`、`HOME`、locale、**代理变量**都留着，子进程 CLI 才能正常跑 |
| 显式 `env` 在清洗**之后**合并 | 想放行某个 key 就显式传；传 `undefined` 是墓碑，删掉一个普通变量 |

合并逻辑在 `packages/subprocess/subprocess-local/src/spawn.ts:37-47`（Windows 分支额外做大小写归一去重）。

清洗完之后还有一次反向注入：模型发起的 shell 调用会被塞进一组**受信 `DSH_*` 事实**——`DSH_HOME`、`DSH_SHELL=1`，agent 调用另加 `DSH_SESSION_ID`，以及当持久化 seam 能定位到 JSONL 时的 `DSH_SESSION_JSONL=<绝对路径>`（`packages/shell/shell-env/README.md:20`）。换句话说，**模型跑的每条命令都知道你的会话日志在哪**。README 明说这是位置提示、不是授权凭证，但做威胁建模时它是一条真实的信息通路（权限那一层怎么兜，见 [18 章](./18-沙箱审批与权限.md)）。

最容易踩的是把这个正则当白名单用。它是启发式，源码注释自己就这么称呼：「One heuristic for every in-repo spawner」（`packages/subprocess/subprocess/src/index.ts:37-43`）。只要名字不含那四个词就原样传给子进程——拿正则逐个试过去，`DATABASE_URL`（连接串里带口令）、`GH_PAT`、`SSH_AUTH_SOCK`（等于把 ssh-agent 转发给了子进程）全都漏过去。要挡住某个变量，只能在启动 dsh 前就不让它进 `process.env`。
