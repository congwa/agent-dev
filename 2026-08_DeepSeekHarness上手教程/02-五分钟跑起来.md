# 02 · 五分钟跑起来

> 基于 `deepseek-ai/deepseek-harness` v0.1.0-rc.5（commit `47f9438`），2026-08-14 核对。

这一章是动手环节：把 dsh 装上、Web UI 起起来、配好 key、发出第一条消息，最后用 `dsh --profile headless "..."` 跑一个一次性任务。

顺带把一件容易被跳过的事讲清楚：**它在你磁盘上留下了什么。**`~/.dsh` 底下十来个文件和目录，谁写的、什么时候写的、改了会怎样，如果一开始不弄明白，后面调配置、换 key、清状态的时候会反复困惑。所以本章后半段是一次逐项的家底盘点。

命令和路径请逐字照敲，别改。

## dsh 不是 agent，是个启动器

先纠正一个可能的预期：`dsh` 本身不干活。它是个 **launcher**——找到一个 profile 目录，把里面列的一串 plugin bundle 按顺序叠成一棵插件树，挂载它，然后把剩下的命令行参数原样丢给树里的 app 插件（`apps/cli/README.md:5`、`apps/cli/README.md:20`）。

所以 dsh 没有"主程序"这个东西。Web UI 只是众多 profile 中的一个。

两个名词后面一直会用到，都出自 `packages/boot/app-boot/README.md:38`：

**bundle** 是一个普通 npm 包，它的 `package.json` 里声明了 `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`，那个 yml 就是它往插件树上叠的一层。

**profile** 是 `$DSH_HOME/profiles/<name>` 下的一个目录，装着一个 `package.json`（里面 `dsh.profile.bundles` 是有序的 bundle 清单）和你自己的 `cordis.patch.yml`。

它认识四种入口（`apps/cli/README.md:11`–`apps/cli/README.md:14`）：

| 命令 | 干什么 |
|---|---|
| `dsh --profile <name>` | 启动 `$DSH_HOME/profiles/<name>` 下的 profile |
| `dsh --profile headless "job"` | 跑一个全新的持久化会话，打印最终答案，退出 |
| `dsh web` | `--profile web` 的硬编码别名（`apps/cli/src/args.ts:156`、`apps/cli/src/args.ts:168`） |
| `dsh plugin --profile <name> <pnpm args>` | 在 profile 目录里转发给 pnpm 管插件（第 22 章） |

不管哪种入口，**调用命令时所在的目录就是默认 workspace 根**（`apps/cli/README.md:16`、`apps/cli/reference/README.md:68`）。所以先 `cd` 到你想让 agent 干活的项目里，再敲命令。

环境上只有两个要求。Node.js 要 22.19+ 或 24+，这个范围写在仓库根的 `package.json:8`–`package.json:9`（`"node": "^22.19.0 || >=24.0.0"`），`docs/development.md:11` 也写了。pnpm 只有**从源码跑**和 `dsh plugin` 才需要，仓库锁的是 `pnpm@11.7.0`（`docs/development.md:12`、`apps/cli/reference/README.md:43`）。

这里有个陷阱值得单独拎出来：**发布出去的那个包自己没有声明 Node 版本。**`apps/cli/package.json` 里只有 `name`/`bin`/`files` 这些字段，没有 `engines`（`apps/cli/package.json:2`、`apps/cli/package.json:14`–`apps/cli/package.json:16`）。上面那个 22.19+/24+ 的范围只在仓库根，不随包发布。也就是说 npm 不会在你 Node 版本过低的时候拦住你，报错会以别的形态出现，而且大概率看不出跟 Node 版本有关。动手之前先 `node -v` 自己确认一遍。

## 路线 A：`npx` 一行起 Web UI

```sh
cd /path/to/your/project
npx @deepseek-ai/dsh web
```

命令来自 `README.zh.md:20`。

**先说清 `dsh` 这三个字母怎么敲。** 本章后文为了短，一律写 `dsh`；走 npx 的读者请把它整个换成 `npx @deepseek-ai/dsh`，从源码跑的换成 `pnpm dsh`。可执行名 `dsh` 来自 `apps/cli/package.json:14`–`apps/cli/package.json:16` 的 `bin` 字段，只有全局装过（`npm i -g @deepseek-ai/dsh`）它才在 PATH 上。仓库文档本身只给了 `npx` 和 `pnpm dsh` 两条路。

启动成功后终端会打印一行 URL，格式是 `dsh web: <url>`，检测到局域网地址时后面追加 `(LAN: http://<addr>:<port>)`（`packages/bundle/web-app/src/index.ts:168`）。这行由 web-app bundle 自己打印，默认开着（`packages/bundle/web-app/cordis.patch.yml:134` 的 `printUrl: true`）。默认地址是 `http://127.0.0.1:3080`——host 和 port 写在 web-app 的 bundle patch 里，`ctx.webStartup` 没给值时回落到这两个默认（`packages/bundle/web-app/cordis.patch.yml:119`–`packages/bundle/web-app/cordis.patch.yml:120`）。

这行 URL 不是随手打的日志，它是**就绪信号**：代码专门等 Loader 整棵树 settle 之后才打印，因为监管进程看到它就会发 RPC（`packages/bundle/web-app/src/index.ts:159`–`packages/bundle/web-app/src/index.ts:173`）。URL 出来之前别急着刷浏览器。

### 第一次启动，它在磁盘上做了什么

四步：

1. launcher 先解析自己的 flag（`--profile` / `--patch` / `--dump-config` / `--dump-default-config`，`apps/cli/src/args.ts:131`–`apps/cli/src/args.ts:134`），遇到第一个不认识的 token 就停手，后面全归 app（`apps/cli/src/args.ts:123`–`apps/cli/src/args.ts:128`）。
2. **先**自愈 `$DSH_HOME/profiles/node_modules`。这是一个扁平的符号链接目录，dsh 安装里 app 依赖闭包（从 app manifest 的 `dependencies` 做 BFS）中每个包一条链接，**每次启动都修一遍**，好让任何 profile 里写裸插件名都能被 Node 的逐级向上查找解析到（`packages/boot/app-boot/src/profile.ts:204`–`packages/boot/app-boot/src/profile.ts:219`、`apps/cli/src/profile-boot.ts:99`）。
3. **再**定位 `$DSH_HOME/profiles/web`（`apps/cli/src/profile-boot.ts:100`）。`web` 和 `headless` 这两个名字有内置模板，**首次使用自动初始化**；其它名字不存在就直接抛错，并提示你去跑 `dsh plugin --profile <name> add <package>`（`packages/boot/app-boot/src/profile.ts:376`–`packages/boot/app-boot/src/profile.ts:384`）。
4. 按顺序叠 patch 层，挂树，起 HTTP server，打印 URL。

初始化只写三个文件，且**已存在的文件绝不覆盖**，重跑是幂等的（`packages/boot/app-boot/src/profile.ts:152`–`packages/boot/app-boot/src/profile.ts:168`）。但你打开目录会看到四个文件——多出来的那个 `cordis.yml` 由每次启动**无条件重写**，内容是一个空 entry 列表，文件里的注释就写着"改 cordis.patch.yml，不要改这个文件"（`apps/cli/src/profile-boot.ts:60`–`apps/cli/src/profile-boot.ts:67`、`apps/cli/src/profile-boot.ts:101`）：

```
~/.dsh/profiles/web/
├── package.json          initProfile 写：name / private / dependencies / dsh.profile.bundles
├── cordis.patch.yml      initProfile 写：三行说明 + 一行 []
├── pnpm-workspace.yaml   initProfile 写：packages 只含 .、nodeLinker: hoisted、autoInstallPeers: false
└── cordis.yml            每次启动重写：空 entry 列表，改了也白改
```

`package.json` 由 `initProfile` 现场构造，字段固定为这四个（`packages/boot/app-boot/src/profile.ts:156`–`packages/boot/app-boot/src/profile.ts:162`，bundle 列表来自 `packages/boot/app-boot/src/profile.ts:115`）：

```json
{
  "name": "dsh-profile-web",
  "private": true,
  "dependencies": {},
  "dsh": {
    "profile": {
      "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app"]
    }
  }
}
```

`cordis.patch.yml` 的初始模板是三行说明加一行 `[]`（`packages/boot/app-boot/src/profile.ts:127`–`packages/boot/app-boot/src/profile.ts:131`）。有个反直觉的地方：**把内容删干净反而会抛错。** 空文件或只有注释的文件，解析出来是"什么都没有"，而不是"空列表"。想停用这一层，留着那个 `[]`（`packages/boot/app-boot/README.md:43`）。

### 端口被占了怎么办

```sh
dsh web --port 8080
dsh web --host 127.0.0.1 --port 8080
dsh web --port 0
```

`web` app 只认三个 flag：`--host`、`--port`、可重复的 `--trusted-host`（`packages/bundle/web-app/src/startup.ts:48`–`packages/bundle/web-app/src/startup.ts:50`）。`--port 0` 是让操作系统挑一个空闲端口，实际端口以打印出来的那行 URL 为准（`packages/bundle/web-app/src/startup.ts:49`）。

**`--host 0.0.0.0` 被明确拒绝**，以 usage error 退出，理由直接写在报错文本里：那等于把远程代码执行能力暴露到网络上（`packages/bundle/web-app/src/startup.ts:69`–`packages/bundle/web-app/src/startup.ts:70`、`apps/cli/reference/README.md:64`）。想让局域网访问，别指望这条路。非数字的 `--port` 同样是 usage error（`packages/bundle/web-app/src/startup.ts:72`–`packages/bundle/web-app/src/startup.ts:73`）。

这一段最容易踩的两个坑，都跟"flag 归谁管"有关。

**launcher 的 flag 必须排在 app 参数前面。** `dsh --profile web --help` 打的是 web app 的帮助，而且不启动任何东西；`dsh --help` 打的才是 launcher 自己的（`apps/cli/reference/README.md:17`）。

**flag 能盖住配置，是因为配置行里那个表达式还在。** `port` 那行写的是 `!!js ctx.webStartup.port ?? 3080`。如果你在自己的 patch 层里把整个 `config` 换成字面量，就把这个运行时读取删掉了，`--port` 从此失效（`apps/cli/reference/README.md:19`）。至于为什么 patch 是整体替换而不是深合并，第 03 章讲。

## 路线 B：从源码跑

```sh
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
pnpm install
pnpm run build
pnpm dsh web
```

命令来自 `README.zh.md:30`–`README.zh.md:34`。`pnpm dsh` 这个脚本是 `node --import tsx/esm apps/cli/src/bin.ts`（`package.json:136`），也就是**直接跑 TypeScript 源码入口，不做任何构建**，参数原样转发（`apps/cli/reference/README.md:84`）。

正因为它不构建，源码路线有三个现象值得先记住，出问题时能少查半小时（都出自 `apps/cli/reference/README.md:84`）：

| 现象 | 原因 |
|---|---|
| profile 启动时报一堆模块解析错误，且没提示你去 build | Typert host 产物缺失，`pnpm run build` 没跑（Typert 是构建期生成 Host 反射产物的那一步，`docs/development.md:76`） |
| host 产物有了，但启动时提示你运行 `pnpm run build` | 前端 / client 插件 bundle 缺失 |
| 改了前端代码但浏览器里没变化 | **launcher 不检查产物新鲜度**，旧 bundle 会照跑不误 |

第三条尤其阴——它不报错，只是安静地给你旧代码。

`pnpm install` 之后先跑一次 `pnpm run typecheck`。官方把"它成功退出"当作环境搭好了的判据（`docs/development.md:34`–`docs/development.md:40`）。

## Web UI 起来之后的三步

官方指南的顺序是配模型 → 选 workspace → 发消息（`docs/user/guide/index.zh.md:7`–`docs/user/guide/index.zh.md:23`）。

### 第一步，配 key

打开 **设置 → 模型**，在 DeepSeek 卡片里填 API key 保存。模型路由立即可用，**不用重启服务器**（`docs/user/guide/index.zh.md:9`）。

key 是只写的：页面保存后只拿得回一个脱敏描述符，明文存进 `$DSH_HOME/.credentials.yaml`，settings 里只留一个凭据引用（`docs/user/guide/providers.md:13`）。文件以 `0600` 写在 `0700` 的目录下（`packages/credentials/credentials-local/README.md:40`）。

但 UI 只是四层来源里的一层。完整的优先级从高到低是这样（`packages/credentials/credentials-local/README.md:7`–`packages/credentials/credentials-local/README.md:12`，与 `apps/cli/reference/README.md:76` 一致）：

| 优先级 | 来源 | 能不能从 UI 写 |
|---|---|---|
| 1 | 继承的进程环境变量 | 不能，且 `set`/`unset` 会直接拒绝 |
| 2 | `$DSH_HOME/.credentials.yaml`（受管文档） | 能，Models 页面写的就是这个 |
| 3 | 调用目录的 `.env` | 不在这里写 |
| 4 | `$DSH_HOME/.env` | 不在这里写 |

环境变量排第一的理由写得很直白：`DEEPSEEK_API_KEY=… dsh` 这种单次覆盖是操作者对**这一次运行**的意图；而且它从程序内部改不了，所以必须**可见地**只读（`packages/credentials/credentials-local/README.md:14`）。受管文档则从不物化进 `process.env`（`apps/cli/reference/README.md:76`）。

配套有个坑：环境层读的是 launcher 在启动瞬间冻结的环境快照，不是活的 `process.env`。所以**进程起来之后再 export 一个变量，它永远看不见——改环境变量必须重启**（`packages/credentials/credentials-local/README.md:18`、`packages/credentials/credentials-local/README.md:70`）。

`.credentials.yaml` 的格式就是一个纯映射，没有 `version`，没有外层包裹（`packages/credentials/credentials-local/README.md:31`、`packages/credentials/credentials-local/README.md:38`）：

```yaml
DEEPSEEK_API_KEY: sk-…
OPENAI_API_KEY: sk-…
```

任何偏离都是**报错**而不是跳过：根不是映射、key 不是 POSIX 标识符、值不是字符串、空字符串、重复 key、YAML 坏了，启动时直接 fail loud。进程跑起来之后再把它改坏，则是告警并继续用上一份好快照（`packages/credentials/credentials-local/README.md:38`）。其它厂商与自定义 OpenAI 兼容端点见第 04 章。

### 第二步，选 workspace

点**选择工作区**，把启动 `dsh` 时所在的项目目录加进去并选中。**选中之前会话输入框是不可用的**（`docs/user/guide/index.zh.md:15`），第一次用很容易以为是页面坏了。

workspace 是一条持久记录：一个生成的 uuid（`packages/workspace/workspace/src/types.ts:24`）、一个规范化路径、一个标题，外加属于它的会话列表。它对模型完全不可见——没有工具、没有 prompt 文本、没有会话事件（`docs/subsystems/workspace.md:5`）。

### 第三步，发第一条消息

官方示例就是这句（`docs/user/guide/index.zh.md:21`）：

> Summarize this repository and identify its main packages.

新会话默认用 `workspace-write` 权限预设，这个默认值就写在 base bundle 的 patch 里：`mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'`（`packages/bundle/base/cordis.patch.yml:175`），配套的审批策略默认是 `ask`（`packages/bundle/base/cordis.patch.yml:191`）。

它的含义值得逐字读一遍：**bash 与文件写被限制在会话 workspace 和平台临时目录内；读、网络访问、进程可见性不受限制**（`apps/cli/reference/README.md:70`）。需要审批的操作会先弹窗问你（`docs/user/guide/index.zh.md:23`）。沙箱到底管什么、不管什么，第 18 章有完整边界。

## `~/.dsh` 里到底有什么

harness home 的解析顺序是：显式配置的路径 > `$DSH_HOME` 环境变量 > `~/.dsh`。空白值视为未设置，所以一个空的 `DSH_HOME` 不会把 home 解析成当前目录（`packages/util/home-paths/README.md:9`、`packages/util/home-paths/src/index.ts:87`–`packages/util/home-paths/src/index.ts:91`）。所有用户数据只有这**一个根**。

```
~/.dsh/
├── profiles/
│   ├── node_modules/            自愈的扁平符号链接兜底
│   ├── web/                     package.json + cordis.patch.yml + pnpm-workspace.yaml + cordis.yml
│   └── headless/
├── cordis.patch.yml             home 级 patch 层
├── settings.yaml                用户设置文档（Models 页面写这里）
├── .credentials.yaml            受管密钥
├── .env                         用户级环境层
├── AGENTS.md                    用户全局指令
├── .anonymous-user-id           匿名 UUID
├── sessions/                    会话日志
├── storages/                    JSON 存储单元（workspace 记录等）
├── attachments/v1/              图片附件
├── skills/                      用户级 skills
└── .agent-presets/              用户级 agent preset
```

逐项说清楚是谁写的。按"谁动它"分成三组会好记一些。

**dsh 自己写、你别管的：**

`profiles/<name>/` 由 `initProfile` 在首次使用时自动建，内容是一个可启动组合（manifest 加你自己的 patch 层），细讲在第 21 章。`profiles/node_modules/` 每次启动自愈一遍（`apps/cli/src/profile-boot.ts:99`），作用是让任何 profile 里的裸插件名可解析（`packages/boot/app-boot/src/profile.ts:204`–`packages/boot/app-boot/src/profile.ts:219`），同样属于第 21 章。`.anonymous-user-id` 更懒一些，`getOrCreateAnonymousUserId()` **首次真正用到时才建**，也就是 DeepSeek 请求发出的那一刻（`packages/llm/llm-deepseek/src/adapter.ts:222`）；内容是一行裸 UUID v4，删掉它下次启动就换一个身份（`packages/identity/anonymous-user-id/README.md:5`、`packages/identity/anonymous-user-id/README.md:7`），第 23 章细讲。

**你手写的：**

home 级的 `cordis.patch.yml` 放各 profile 共享的机器本地偏好，注意它**优先级高于 profile 级那份**（`packages/boot/app-boot/README.md:43`）。`.env` 是普通启动环境层，被调用目录的 `.env` 压过，值会被物化进 `process.env`（`packages/boot/app-boot/README.md:42`），配置怎么叠是第 03 章。`AGENTS.md` 是用户全局指令，在发现顺序里排在最前（`packages/context/agent-instructions/src/files.ts:280`，文件名常量见 `packages/context/agent-instructions/src/render.ts:98`），第 14 章讲。`skills/` 是用户级 skill 根，rank 400（`packages/skill/skill-filesystem/README.md:38`），第 19 章讲。`.agent-presets/` 是用户级 agent preset 根（常量见 `packages/preset/agent-presets/src/discovery.ts:41`，挂载见 `packages/preset/agent-presets/src/index.ts:134`），第 18 章讲。

**两边都可能写的，以及纯运行时数据：**

`settings.yaml` 是运行时用户设置，Models 页面写它，你也可以手写，支持热重载（`packages/bundle/base/cordis.patch.yml:75`–`packages/bundle/base/cordis.patch.yml:79`）；文档不存在时以仅属主权限独占创建（`packages/settings/settings-file/README.md:30`）。`.credentials.yaml` 同理，是受管密钥文档（`packages/bundle/base/cordis.patch.yml:81`–`packages/bundle/base/cordis.patch.yml:86`）。这两个都在第 03 章细讲。

`sessions/` 由 JSONL 持久化后端写，根路径 `dshHomePath('sessions')`（`packages/bundle/base/cordis.patch.yml:98`–`packages/bundle/base/cordis.patch.yml:101`），每会话一份 append-only 日志，第 15 章讲。`storages/` 由 JSON 存储后端按需以 `0o700` 创建（`packages/storage/storage-json/README.md:17`），每个存储单元一个 `<unit>.json`，workspace 记录走这里；有个细节容易忽略——它的根路径是 **web-app bundle** 给的（`packages/bundle/web-app/cordis.patch.yml:57`），headless 根本不挂它。`attachments/v1/` 归 attachment-local 管，根路径见 `packages/attachment/attachment-local/src/index.ts:53`，目录**首次写附件时**才以 `0o700` 建（`packages/attachment/attachment-local/src/store.ts:145`–`packages/attachment/attachment-local/src/store.ts:147`）；它存的是图片字节，会话日志里只留内容寻址引用（`docs/subsystems/attachment.md:7`）。

`sessions/` 内部是三层结构（`packages/session/session-persistence-jsonl/README.md:9`–`packages/session/session-persistence-jsonl/README.md:15`）：

```
~/.dsh/sessions/
  --<规范化后的cwd>--/        可读的项目目录，无 cwd 时是 _no-cwd/
    <编码后的会话id>/
      session.jsonl.zstd      默认：带校验的头帧 + 追加帧
      session.jsonl           仅当把压缩关成 'none'
```

最后三个容易搞混的点，都是我自己第一遍看时想当然过的。

**`settings.yaml` 和 `cordis.patch.yml` 是两回事。** 前者是运行时的用户设置文档，Models 页面写它，热重载；后者是**插件树的配置补丁层**，决定挂哪些插件、每个插件拿什么配置。第 03、04 章分别细讲。

**`~/.dsh` 与项目里的 `.dsh/` 不是一个东西。** `<projectRoot>/.dsh/skills` 是项目级 skill 根，rank 100，优先级高于 `<dshHome>/skills` 的 rank 400，因为 rank 数字小的赢（`packages/skill/skill-filesystem/README.md:35`、`packages/skill/skill-filesystem/README.md:38`、`packages/skill/skill/src/index.ts:75`）。

**想试新配置，换 home 比改文件安全。** `DSH_HOME=/tmp/dsh-test npx @deepseek-ai/dsh web` 会得到一整套干净的 profile、会话和凭据。注意匿名身份是按 home 隔离的，换 home 就换身份（`packages/identity/anonymous-user-id/README.md:7`）。

## headless：一次性跑一个任务

```sh
cd /path/to/your/project
DEEPSEEK_API_KEY=sk-… dsh --profile headless "run the tests"
```

`headless` 也是自动初始化的模板 profile，bundle 列表是 base + headless（`packages/boot/app-boot/src/profile.ts:116`）。

它的行为契约写在 `apps/cli/reference/README.md:30`，逐条都对得上 `packages/bundle/headless/src/index.ts` 的实现。任务文本作为位置参数传入，多个词按空格拼接；任务为空或全是空白是 usage error（`packages/bundle/headless/src/startup.ts:36`、`:53`）。拿到任务后，它通过 core registry 建**一个全新的持久化 Agent**，提交任务，等静默，然后 flush Session（`packages/bundle/headless/src/index.ts:111`–`:127`）。打印的是从本次区间里取到的最后一条非空 assistant 文本，走 stdout（`packages/bundle/headless/src/index.ts:61`–`:81`、`:129`）。退出码看 `turn/end` 的原因：是 `completed` 就 0，否则 1（`packages/bundle/headless/src/index.ts:133`）。

它不挂什么也同样重要：没有 Host、HTTP server、Web runtime、浏览器插件（`packages/bundle/headless/cordis.patch.yml:2`；ApiProxy 那一项只见于 `apps/cli/reference/README.md:30`）。一次干净的运行表现为 stderr 一个字都不写（只有出错才写），不开任何监听端口（`packages/bundle/headless/src/index.ts:130`–`:132`）。这两条合起来意味着它可以直接进管道和 CI。

没有 UI 就**没法用 Models 页面配 key**，所以 key 只能来自四层里的其它三层：环境变量、`$DSH_HOME/.credentials.yaml`、两个 `.env`。上面示例里那个行内环境变量就是最省事的写法。headless bundle 还把 system prompt 的 persona 换成了一句带 `{{model}}` / `{{cwd}}` 占位的固定模板，并关掉了 HMR 行（`packages/bundle/headless/cordis.patch.yml:7`–`packages/bundle/headless/cordis.patch.yml:15`）。

`Ctrl+C` 的语义最好提前知道，尤其是在脚本里判断退出码的时候：第一个 `SIGINT`/`SIGTERM` 启动优雅关闭，插件树最多有五秒 dispose（`apps/cli/src/process-shutdown.ts:4`）；`SIGTERM` 各平台都退 0，`SIGINT` 退 130（`apps/cli/src/profile-boot.ts:221`–`apps/cli/src/profile-boot.ts:222`）；第二个信号强制立即退出（`apps/cli/src/process-shutdown.ts:11`、`apps/cli/reference/README.md:66`）。

JSON-RPC 接口、Python SDK、ACP、把 dsh 当库嵌进自己程序，全在第 23 章。

顺手记一下 launcher 自己帮助文本里给的例子（`apps/cli/src/args.ts:66`–`apps/cli/src/args.ts:71`），它本身就是一张入口速查表：

```
dsh --profile web                          boot the web profile (same as: dsh web)
dsh --profile headless "run the tests"     answer one task, print the result, and exit
dsh --profile tui --patch ./extra.yml      boot a custom profile with one extra overlay
dsh --profile tui --resume <session>       arguments after the launcher flags reach the app
dsh --profile web --help                   the web app's own flags and help
dsh plugin --profile tui add <package>     install a plugin into the tui profile
```

想在启动前先看看这棵树长什么样，用 `dsh web --dump-config` / `--dump-default-config`（`apps/cli/src/args.ts:164`–`apps/cli/src/args.ts:165`、`apps/cli/reference/README.md:39`）。怎么读它是第 03 章的内容。

## 一句话带走

**`dsh` 只负责把一个 profile 里的 bundle 叠成插件树然后交棒，你装的、跑的、配的所有东西，最终都落在 `$DSH_HOME` 这一个根下面。**

搞清楚"哪个文件是 dsh 写的、哪个是你写的、哪个每次启动都会被重写"，后面几章的配置叠加就不会再让你意外。
