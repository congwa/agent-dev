登录全流程，一页看清

先看数据住在哪里，再沿七个环节看它怎样被取出、校验和使用。

图中用户为 42；A1 是访问 JWT，R1 是刷新原值，H1 是 R1 的哈希，F1 是会话家族，T1 是临时 2FA Token。所有值均为示意。

01

启动：把签名密钥从数据库读到内存

这把密钥供所有登录会话签名与验签；它不随 Token 续期而变化。

  1. PostgreSQL01

    查已有密钥

    按 key 找到系统密钥这一行。

    key = "jwt_secret"
  2. 后端02

    没有时生成

    未配置且数据库无记录时，生成 32 字节随机值，再编码为 64 位 hex。

    JWT_KEY = hex(rand(32B))
  3. PostgreSQL03

    保存为一行

    插入 key / value；唯一约束冲突时保留已有值。

    ON CONFLICT DO NOTHING
  4. 后端04

    再读最终值

    读取数据库实际保存的 value，加载到运行配置。

    cfg.JWT.Secret = value
存、取、用security_secrets.value 是 TEXT；启动时读出，后续在内存中用于 HS256。已有持久化值优先；配置中的密钥只参与首次保存，密钥原值没有固定业务前缀。
02

登录：查用户、验证密码、签发两种 Token

邮箱密码主线；入口还会做请求校验、限流和按配置启用的人机验证。

  1. 浏览器01

    提交邮箱和密码

    密码原文作为本次请求的临时值。

    POST /api/v1/auth/login
  2. PostgreSQL02

    读出用户行

    按邮箱读出 bcrypt 哈希、角色和状态。

    users.password_hash
  3. 后端03

    验证身份

    bcrypt 比对密码；检查 active、登录模式和是否需要 2FA。

    bcrypt.CompareHashAndPassword
  4. 后端04

    生成 F1、A1、R1

    新会话 F1 → JWT A1 → 随机刷新 Token R1 → 哈希 H1。

    F1 = hex(rand(16B)) A1 = JWT_HS256(载荷, JWT_KEY) R1 = "rt_" + hex(rand(32B)) H1 = hex(SHA256(R1))
  5. 后端 / Redis05

    分开保存

    H1 对应的会话写 Redis；A1 / R1 原值随响应交给浏览器。

    SET refresh_token:H1 SADD user_refresh_tokens:42 H1 SADD token_family:F1 H1 返回 A1 / R1 原值
浏览器保存原值

auth_token = A1，refresh_token = R1；另存资料 JSON 和预计到期时间。

Redis 保存会话与索引

refresh_token:H1 是 String JSON；user_refresh_tokens:42 和 token_family:F1 是 Set。

取出来怎么用A1 用于接口鉴权，R1 用于换发新 Token。PostgreSQL 尝试记录登录时间；用户行不保存这两张 Token。需要 2FA 时，先走下一环节，完成后再正式签发。
03

双重验证：临时 Token 把两次请求连起来

只有系统和用户均启用 TOTP 时，密码通过后才走这条分支。

  1. Redis01

    保存临时会话

    生成 T1 原值，保存等待验证的用户编号与邮箱，TTL 5 分钟。

    SET totp:login:T1 JSON
  2. 浏览器02

    接收 T1，输入动态码

    响应 requires_2fa；第二次提交临时 Token 和六位动态码。

    temp_token + totp_code
  3. 后端03

    用 T1 查回用户编号

    GET 临时 JSON，反序列化后取出 UserID。

    GET totp:login:T1 → 42
  4. PostgreSQL04

    取出 TOTP 密文

    读取用户的加密 TOTP 密钥；后端解密并验证动态码。

    users.totp_secret_encrypted
  5. 后端05

    再查状态，完成登录

    重新检查当前用户与模式；删除 T1，记录登录，再签发 A1 / R1。

    DEL totp:login:T1 然后签发正式凭据对
前缀区别T1 本身是 hex(rand(32B))，64 位 hex，没有固定前缀。totp:login: 是 Redis key 前缀，后面直接拼 T1 原值，这里不先做 SHA-256。
04

访问接口：取出 JWT，验签后再检查当前用户

A1 已经保存在 localStorage。每次请求都重新确认服务器是否还接受它。

  1. 浏览器01

    取出 A1

    从本地读完整 JWT 字符串。

    getItem("auth_token")
  2. 浏览器02

    拼成请求头

    Bearer 后有一个空格，再跟 JWT 原值。

    Authorization: Bearer A1
  3. 后端03

    验证签名和时间

    用内存密钥验签，再检查 exp / nbf，得到可信载荷。

    HS256 · exp · nbf
  4. PostgreSQL04

    读取当前用户

    按 user_id 查状态与角色；用邮箱和密码哈希计算当前版本。

    当前 V1 == JWT 的 V1
  5. 后端05

    使用身份执行业务

    可选绑定检查通过后，将当前用户与会话放入请求上下文。

    user_id / role / email / sid
取出来怎么用JWT 载荷中的 user_id 用来查用户，token_version 用来比较版本。业务使用当前角色；普通 JWT 鉴权不读取 Redis 刷新主记录。
05

续期：用刷新原值定位会话，再换两张新 Token

前端预计到期前 120 秒尝试续期；普通接口的 401 也可能触发。

  1. 浏览器01

    取出 R1

    读刷新 Token 原值，放进请求体。

    POST /api/v1/auth/refresh
  2. 后端02

    计算 H1，读会话

    验证 rt_ 前缀，哈希完整 R1；用带前缀的 Redis key GET JSON。

    H1 = hex(SHA256(R1)) GET refresh_token:H1
  3. PostgreSQL03

    确认当前用户

    从会话取 user_id / V1 / F1 / 到期时间；查询用户并检查版本与可选绑定。

    会话 V1 == 当前 V1
  4. 后端 / Redis04

    删旧主记录，生成新对

    DEL H1；生成 A2 / R2 / H2，家族 F1 不变。

    DEL refresh_token:H1
  5. 后端 / Redis05

    写新记录，返回原值

    SET H2，两个 Set 加入 H2；返回 A2 / R2，前端替换本地凭据。

    SET refresh_token:H2 SADD user_refresh_tokens:42 H2 SADD token_family:F1 H2
轮换后的数据

refresh_token:H1 主记录已删除；refresh_token:H2 成为新的 String JSON。两个 Set 是 {H1, H2}，旧 H1 可残留。浏览器先存 A2 与预计到期时间，最后存 R2；由 401 触发时，用 A2 重试原请求一次。

取出来怎么用会话的 user_id 指向用户，token_version 与当前版本比较，family_id 保持登录链。读、删、签发是分开的操作；并发或删除失败时，不能把这条成功流程理解成原子消费。
06

退出：撤销刷新资格，清理浏览器登录状态

这里展示普通退出的正常删除路径。

  1. 浏览器01

    取出当前 R2

    将刷新原值交给退出接口。

    POST /api/v1/auth/logout
  2. 后端02

    算出 H2

    对完整 R2 做同一套 SHA-256 + hex。

    H2 = hex(SHA256(R2))
  3. Redis03

    删除当前主记录

    删除 String，用户集合与家族集合仍可能保留旧成员。

    DEL refresh_token:H2
  4. 浏览器04

    清理本地状态

    删除两张 Token、资料与到期时间；停止续期定时器。

    removeItem × 4
退出后的用途R2 无法再从主记录取得会话。前端即使退出请求失败也会清本地；若 A2 曾另行保留，它仍可能在到期前通过普通鉴权，删除刷新记录不会直接改写 JWT。
07

改密：更新持久化哈希，让旧版本校验失败

正常改密服务从已完成 JWT 鉴权的当前用户开始；旧 Token 自身的内容不会被改写。

  1. PostgreSQL01

    取旧哈希，验证旧密码

    读取当前用户，用 bcrypt 比对当前密码。

    读取 password_hash
  2. 后端02

    生成新 bcrypt 哈希

    新密码产生新的哈希材料。

    bcrypt(新密码)
  3. PostgreSQL03

    只更新密码哈希列

    保存新 password_hash；没有独立 token_version 数据库列。

    UPDATE users.password_hash
  4. 后端04

    下次加载得到 V2

    新邮箱 / 哈希材料产生当前 V2，旧 A2 与 H2 会话还保存 V1。

    V1 ≠ V2 → 拒绝
旧 access token

验签后读当前用户，比较 V1 与 V2，返回 401 TOKEN_REVOKED。

旧 refresh token

GET H2 会话并查用户，版本不匹配；尝试 SMEMBERS token_family:F1，逐个 DEL 主记录并删除家族 Set。

取出来怎么用版本值用于把签发时凭据与当前用户材料对齐；改密后无需等待 JWT 自然到期。刷新被明确拒绝时，前端清本地状态；用户 Set 的旧哈希仍可能残留。

Token 怎么生成，前缀加在哪里

原值、哈希、Redis key 是三层不同的东西。这里展开图中的 A1、R1、H1、F1 和 T1。

A1 · access token：HS256 签名的 JWT

原值没有固定业务前缀。它是三个 Base64URL 段，以两个点分隔；Base64URL 编码不带尾部 =。常见开头 eyJ… 是 JSON 编码结果，不是人为加上的 jwt_ 前缀。

header = {"alg":"HS256","typ":"JWT"}
payload = {user_id, email, role, token_version, sid, bnd?, iat, nbf, exp}
X = Base64URL(UTF8(JSON(header)))
Y = Base64URL(UTF8(JSON(payload)))
S = Base64URL(HMAC-SHA256(UTF8(jwt_secret), ASCII(X + "." + Y)))
A1 = X + "." + Y + "." + S
保存：localStorage["auth_token"] = A1使用：Authorization: Bearer A1

Bearer 后的空格属于请求头方案，不属于 JWT 原值。载荷可解码阅读；只有验签通过才能信任。默认访问有效期为 24 小时，可配置覆盖。三段格式依据 RFC 7515。

R1 与 H1 · 刷新原值和存储哈希

R1 = "rt_" + hex(crypto/rand 的 32 字节)
// 前缀 rt_ + 64 位小写 hex = 67 个字符
H1 = hex(SHA256(UTF8(完整 R1)))
// 输入包含 rt_；输出 64 位 hex，无额外前缀
Redis key = "refresh_token:" + H1

R1 是随机字符串，没有 JWT 载荷。原值保存在浏览器，后端 Redis 保存关联会话；续期时重新生成 R2，按同一公式算 H2。

F1 与 T1 · 会话家族和临时 2FA

F1 = hex(crypto/rand 的 16 字节)
// 32 位 hex，无固定前缀
家族 Redis key = "token_family:" + F1

T1 = hex(crypto/rand 的 32 字节)
// 64 位 hex，无固定前缀
临时 Redis key = "totp:login:" + T1

正式凭据对的 F1 写入 JWT 的 sid 与会话 JSON 的 family_id；只签发 access token 的兼容路径会另用 8 字节随机值编码成 sid。T1 直接拼 Redis key，完成 2FA 后删除；不拿它访问普通接口。

V1 · 当前凭据版本怎样算

材料 = lower(trim(email)) + "\n" + password_hash
sum = SHA256(UTF8(材料))
fingerprint = BigEndianUint64(sum[0:8])
              & 0x7fffffffffffffff
V1 = 未解析的内存 TokenVersion XOR fingerprint
// 已解析过时，直接使用现有版本，不重复计算

数据库没有独立版本列；持久化的邮箱与密码哈希是计算材料。改密让新请求读到新的材料，得到 V2。

B1 · 可选 IP / UA 绑定指纹

材料 = trim(IP) + "\n" + trim(User-Agent)
B1 = hex(SHA256(UTF8(材料))[0:16])
// 32 位 hex，无固定前缀
// 缺少绑定，或 IP / UA 都为空：空字符串

放入 JWT 的 bnd 与会话 JSON 的 binding_hash。校验由 session_binding_enabled 控制，默认关闭；有请求指纹时仍可写入字段。

落到存储里的具体结构

流程里的写入和读取，对应下列 key、类型与字段。

Redis：四种 key 的拼法与用途

名称 / key 前缀前缀后拼什么Redis 类型 / value取出后怎么用
刷新主记录refresh_token:H1 = hex(SHA256(完整 R1))String / JSONGET 后反序列化，检查用户、版本、家族、到期时间；默认 TTL 30 天。
用户索引user_refresh_tokens:用户编号，如 42Set / H1、H2SMEMBERS 找哈希，再定位主记录；TTL 在添加成员时重设。
家族索引token_family:F1（32 位 hex）Set / H1、H2SMEMBERS 找同一登录链的哈希，批量 DEL；成员没有单独 TTL。
临时 2FAtotp:login:T1 原值（64 位 hex）String / JSONGET 后取 UserID，查用户 TOTP 密钥；TTL 5 分钟。

刷新主记录的 String JSON

key: refresh_token:H1
value:
{
  "user_id": 42,
  "token_version": 123456789,
  "family_id": "F1",
  "binding_hash": "B1",
  "created_at": "2026-10-09T02:00:00Z",
  "expires_at": "2026-11-08T02:00:00Z"
}

F1 / B1 / H1 用简写，版本数字为示意。binding_hash 为空时可省略。JSON 是 String 的内容，不是 Redis Hash；TTL 是 key 的属性，JSON 的 expires_at 另供程序判断。

Set 索引与临时会话

key: user_refresh_tokens:42
类型: Set     成员: H1、H2

key: token_family:F1
类型: Set     成员: H1、H2

key: totp:login:T1
类型: String  value:
{
  "UserID": 42,
  "Email": "user@example.com",
  "TokenExpiry": "2026-10-09T02:05:00Z"
}

Set 成员是哈希，不是 JSON，也不含刷新原值。清理时先 SMEMBERS，再拼主记录 key。成员存在不代表主记录仍有效。

PostgreSQL：按关系表的行和列保存

表列SQL 类型用途
usersidBIGINT按用户编号关联 JWT 与刷新会话
usersemail / password_hashVARCHAR(255)邮箱；bcrypt 密码哈希，也是版本计算材料
usersrole / statusVARCHAR(20)当前权限角色、账号状态
