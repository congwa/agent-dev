# Sub2API 登录凭据完整流程：存储、续期与退出立即失效

退出登录，要让服务器不再接受这次登录产生的 `access_token`，不能只删除浏览器中的字符串。服务器必须保存“这次登录是否仍然有效”，并在每次请求时检查它。

本文沿着 **系统启动 → 登录 → 请求接口 → 续期 → 退出 → 退出所有设备 → 改密码 → 自然过期** 讲解。每个环节都用从上往下读的流程图，写清数据从哪里来、放在哪里、什么时候过期，以及删除哪些东西。

需要区分两部分：

- **Sub2API 原有行为**：保存刷新主记录和两个 Set 索引；普通接口鉴权不检查刷新记录是否存在。正常退出删除提交的刷新主记录，已经签发的 `access_token` 可能继续有效。
- **本文的改造方案**：新增 `login_session:{family_id}` 和 `user_login_sessions:{user_id}`；访问接口、续期都检查登录记录；退出撤销整条登录链；续期清理旧 Set 成员，并协调并发操作。

原有行为以文末固定源码为依据。新增方案是设计说明，不代表原 Sub2API 或已有 Python 学习示例已经实现。本文只讲邮箱、密码登录后的正式凭据主线。

## 1. 先看数据存放地图

| 位置 | 保存什么 | 目的 |
|---|---|---|
| PostgreSQL `users` | 用户编号、邮箱、密码哈希、角色、状态、登录和活跃时间 | 核对身份，检查当前账号 |
| PostgreSQL `security_secrets` | 系统 `jwt_secret` | 系统重启后仍能使用同一签名密钥 |
| 后端内存 | 加载的密钥、当前请求读出的资料、临时计算结果 | 校验、计算、签名 |
| Redis | 刷新主记录、登录有效记录、三个索引 Set | 判断能否续期、是否退出、找到待撤销记录 |
| 浏览器 localStorage | 两个凭据原值、用户资料、前端预计到期时间 | 请求接口、续期、恢复界面 |

**JWT 不是另一台数据库。** 它是 `access_token` 的一种字符串格式，里面包含字段和签名；整个字符串保存在浏览器 `localStorage.auth_token`。

同一个值可能有多个副本。例如 `token_version` 同时在 JWT 和 Redis JSON 中，这些副本不会自动互相修改。

## 2. 每个值的来源、期限、位置、目的和用途

### 2.1 登录之前就存在的资料

| 值 | 来源 | 保存位置 | 期限 | 后续用途 |
|---|---|---|---|---|
| `user_id` | 注册时数据库分配的 `users.id` | PostgreSQL；签发时复制到 JWT、Redis 和返回资料 | 账号编号没有 token TTL；副本随所在记录保存 | 按编号查询账号、核对归属 |
| `email` | 用户注册时填写，登录时再次输入 | `users.email`；JWT 和用户资料可能有副本 | 数据库没有 token TTL | 查找登录账号，也是版本计算材料 |
| `password` | 用户本次输入 | 表单、请求的临时内存 | 不设持久化 TTL，不作为登录凭据保存 | 核对密码 |
| `password_hash` | 注册或改密时用 bcrypt 处理密码 | `users.password_hash`，请求中读到后端内存 | 没有 token TTL，改密时替换 | 核对密码，也是版本计算材料 |
| `role` | 账号创建和管理流程设置 | `users.role`；JWT 可有签发时副本 | 没有独立 token TTL | 采用当前角色决定权限 |
| `status` | 账号创建和管理流程设置 | `users.status` | 没有 token TTL，管理操作可修改 | 检查账号能否登录、访问和续期 |
| `jwt_secret` | 启动时读取；首次使用配置值或随机生成 | `security_secrets` 中 `key = jwt_secret` 的 `value`，并加载到后端内存 | 没有登录 token TTL | 生成 JWT 时签名，使用 JWT 时验签 |

数据库不保存明文密码。bcrypt 核对不需要把 `password_hash` 解密成密码。

### 2.2 token_version

- **来源**：根据当前 `email` 和 `password_hash` 计算。普通数据库加载路径中，它来自这两项的指纹。
- **期限**：没有独立 TTL，副本跟随 JWT 或 Redis 主记录。
- **位置**：计算时的后端内存、JWT 的 `token_version` 字段、Redis JSON 的 `token_version` 字段。
- **目的**：发现旧凭据与当前账号资料不匹配。
- **用途**：访问接口时比较 JWT 中的值；续期时比较 Redis 中的值。

`users` 没有独立的 `token_version` 列。它不是续期次数，不是续期一次就加一。

改密码后，新 `password_hash` 让当前结果改变。旧 JWT 和旧 Redis JSON 中的值不会自动改变，所以比较不一致时拒绝旧凭据。

### 2.3 family_id

- **来源**：登录时安全随机生成 16 字节，转为 32 个十六进制字符。
- **期限**：本身没有独立 TTL，跟随所在 JWT 或 Redis key。
- **位置**：JWT 中叫 `sid`；Redis 主记录中叫 `family_id`；相关 key 的后半段，以及用户登录索引的成员。
- **目的**：关联同一次登录及其后续续期。
- **用途**：续期沿用；退出时撤销这条登录链。

电脑和手机分别登录，通常得到不同 `family_id`。同一设备重新登录，也生成新的值。它不是设备硬件编号。

### 2.4 access_token

- **来源**：把用户资料、版本、登录链编号和时间写进 JWT，再用 `jwt_secret` 签名。
- **期限**：默认 24 小时，由 JWT 的 `exp` 决定；改密、账号停用或本文方案的登录撤销，可提前使它被拒绝。
- **位置**：响应字段叫 `access_token`；浏览器保存键叫 `auth_token`。
- **目的**：为业务接口请求证明身份。
- **用途**：放在 `Authorization: Bearer` 后面，服务端验证通过后才处理业务。

这两个名字是源码不同位置的实际名称。服务端不逐个保存 JWT 原值。JWT 签名检查篡改，载荷可解码阅读，不是加密后的保密资料。

### 2.5 refresh_token

- **来源**：安全随机生成 32 字节，转为 64 个十六进制字符，前面加 `rt_`。
- **期限**：对应 Redis 主记录默认 30 天；主记录删除、账号不匹配或登录撤销时，提前不能续期。
- **位置**：浏览器 `localStorage.refresh_token` 保存原值，续期或退出时提交。
- **目的**：通常不用重新输入密码，就能取得新凭据。
- **用途**：后端根据原值查刷新记录，通过检查后轮换。

它不是 JWT，里面没有用户编号、版本或截止时间。Redis 不保存原值。

### 2.6 token_hash

- **来源**：对完整 `refresh_token`，包括 `rt_`，做 SHA-256，再转为 64 个十六进制字符。
- **期限**：没有独立 TTL，跟随所在 key；主记录删除不会自动清除其他 Set 的成员。
- **位置**：刷新主记录 key 的后半段，两个刷新索引 Set 的成员。源码局部变量叫 `tokenHash`。
- **目的**：不用保存可直接续期的原值，也能找到记录。
- **用途**：重新计算、拼出 key，执行 `GET` 或 `DEL`。

它不是 Redis JSON 的字段。它与 `token_version` 也不同：一个定位刷新记录，一个检查账号凭据是否变化。

### 2.7 前端保存的其他数据

| 值 | 来源 | 位置 | 期限及用途 |
|---|---|---|---|
| `expires_in` | 访问有效期配置换算成秒，默认 86400 | 登录、续期响应 | 是时长，没有独立 TTL；用于计算提醒时间 |
| `token_expires_at` | `Date.now() + expires_in * 1000` | 同名 localStorage key，毫秒数字的字符串 | 没有自动删除 TTL；安排续期定时器 |
| `auth_user` | 返回资料经过 `JSON.stringify` | 同名 localStorage key | 没有 TTL；显示资料、恢复界面，不替代服务端授权 |

## 3. Redis 的五类 key：数据结构与内容

| key 格式 | 数据结构 | value / 成员 | 默认 TTL 及设置 | 用途 |
|---|---|---|---|---|
| `refresh_token:{token_hash}` | String | 刷新记录 JSON 字符串 | `SET` 时设 30 天 | 判断这一份凭据能否续期 |
| `login_session:{family_id}`，新增 | String | 用户编号字符串，如 `"42"` | 登录 `SET` 设 30 天；续期延长期限 | 判断登录链是否仍有效 |
| `user_refresh_tokens:{user_id}` | Set | 该用户的 `token_hash` | 加成员后对整个 key `EXPIRE`，默认 30 天 | 找到用户的刷新主记录 |
| `token_family:{family_id}` | Set | 该登录链的 `token_hash` | 加成员后对整个 key `EXPIRE`，默认 30 天 | 找到登录链的刷新主记录 |
| `user_login_sessions:{user_id}`，新增 | Set | 该用户的 `family_id` | 登录、续期维护成员和整个 key 的期限，默认 30 天 | 退出所有设备时找到登录链 |

大括号表示需要替换的部分，不是本文实际 key 名中的字符。例如用户编号是 42，用户刷新索引就是 `user_refresh_tokens:42`。

三个 Set 是索引。**不能仅凭成员存在，就认定登录或刷新凭据有效。**

### 3.1 刷新主记录的 JSON

下面是教学数据，不是真实账号的凭据：

~~~json
{
  "user_id": 42,
  "token_version": 8211179643193139419,
  "family_id": "efefefefefefefefefefefefefefefef",
  "created_at": "2026-10-10T02:00:00Z",
  "expires_at": "2026-11-09T02:00:00Z"
}
~~~

| 字段 | 来源 | 目的 |
|---|---|---|
| `user_id` | `users.id` | 查询当前账号，核对归属 |
| `token_version` | 邮箱和密码哈希的计算结果 | 续期时检查账号凭据变化 |
| `family_id` | 登录时生成，续期沿用 | 关联新凭据、按登录链撤销 |
| `created_at` | 后端生成这份凭据时的时间 | 记录创建时刻 |
| `expires_at` | 创建时刻加刷新有效时长 | 程序检查截止时间 |

源码另有可选 `binding_hash`，本文不展开环境绑定，示例省略。时间中的 `Z` 表示 UTC，示例对应 UTC+8 的 10:00。版本在 JSON 中是整数；前端如要处理这种大整数，应避免 JavaScript Number 精度丢失。

后端把整个对象序列化成 JSON 文字，再用 `SET` 存为 **String**。没有使用 `HSET`，不是 Redis Hash，JSON 字段也没有分别设置 TTL。

### 3.2 登录记录的内容

~~~text
key   = login_session:{family_id}
type  = String
value = "42"
TTL   = 默认 2592000 秒
~~~

key 中的 `family_id` 定位登录链，value 中的用户编号核对归属。它不保存两个凭据原值，也没有在 value 中保存截止时间；期限由 Redis key 的过期元数据维护。

### 3.3 Set 的成员没有单独 TTL

~~~text
SADD：添加成员
    ↓
EXPIRE：设置整个 Set key 的剩余存活时长
    ↓
key 到期
    ↓
整个 Set 不再可读

不是给每个成员分别设置 TTL
~~~

读取 key 不会延长 TTL，`SADD` 也不会自动延长已有 TTL。必须明确执行 `EXPIRE`。

本文方案在续期时主动 `SREM` 旧哈希，减少失效索引。自然过期后仍可能留下失效成员，清理时必须允许对应主记录已不存在。

## 4. 过期时间怎么存、怎么设置

### 4.1 access_token：时间写在 JWT.exp 里

~~~text
读取访问有效期配置
    ↓
jwt.access_token_expire_minutes > 0？
    ├─ 是 → 使用配置分钟数
    └─ 否 → 使用 jwt.expire_hour，默认 24 小时
    ↓
expiresAt = 后端当前时间 + 有效时长
    ↓
转成 Unix 秒时间戳，写入 JWT.exp
    ↓
签名后生成 access_token
    ↓
浏览器保存完整字符串到 auth_token
    ↓
服务器使用时检查 exp
~~~

`iat` 是签发时刻，`nbf` 是开始可用时刻，`exp` 是截止时刻。它们不是 Redis TTL，不负责删除浏览器字符串。

### 4.2 refresh_token：程序截止时间与 Redis TTL 同时设置

~~~text
读取 jwt.refresh_token_expire_days
默认 30 天
    ↓
ttl = 30 × 24 × 60 × 60 = 2592000 秒
    ↓
created_at = 后端当前时间
expires_at = created_at + ttl
    ↓
把两个时间写进 JSON
Go time.Time 序列化为带时区的时间文本
    ↓
SET 主记录时，同时给 key 设置 ttl
    ↓
Redis TTL：到期后 key 不再可读
JSON.expires_at：程序读到记录后检查截止时间
~~~

只把 `expires_at` 写进 JSON，不会让 Redis 自动删除。原源码使用 `rdb.Set(ctx, key, val, ttl)`，写值时一起设置期限。后端时钟与 Redis 写入延迟可能使两个截止时刻有细微差异。

### 4.3 新增登录记录和索引的期限

~~~text
login_session 的存活期
必须覆盖这条链中仍有效凭据的期限
    ↓
默认访问有效期 24 小时、刷新有效期 30 天
设置 30 天即可
    ↓
成功续期
按新凭据需要的期限延长
    ↓
如果配置缩短
不能提前截短仍需覆盖的旧凭据期限
    ↓
用户级索引也必须覆盖其他仍有效的登录
不能被某一次写入缩短期限
~~~

实现时可取“现有剩余 TTL”与“本次需要 TTL”的较大值。默认情况下，每次续期重新设置为 30 天。本文后续图按默认配置说明。

`TTL key` 查询剩余秒数：`-1` 表示没有过期设置，`-2` 表示 key 不存在。TTL 是 Redis 的元数据，不是 JSON 字段。

### 4.4 浏览器保存时间，不设置自动删除期限

~~~text
收到 expires_in
    ↓
expiresAtMs = Date.now() + expires_in × 1000
    ↓
localStorage.setItem(
  "token_expires_at",
  String(expiresAtMs)
)
    ↓
安排提前约 2 分钟尝试续期
    ↓
到了该时间
localStorage 不自动删除任何 key
~~~

这是前端的提醒时间。服务端最终以 JWT.exp、账号和登录状态为准。浏览器时钟、响应延迟可能使前端时间与 exp 略有差异。

PostgreSQL 的登录、活跃、创建和更新时间是事件记录，不是 token 自动删除期限。

## 5. 系统启动与注册

### 5.1 系统启动：准备 jwt_secret

~~~text
后端启动
    ↓
查询 security_secrets 中 key = jwt_secret 的行
    ↓
已有值？
    ├─ 有 → 使用已有 value
    └─ 无 → 使用配置值或安全随机生成，再持久化
    ↓
加载到后端运行配置 / 内存
    ↓
生成 access_token 时签名
验证 access_token 时验签
~~~

密钥不会每次登录重建，没有登录 token TTL，也不会发给浏览器。

### 5.2 注册：登录核对的资料从这里来

~~~text
用户填写 email、password 注册
    ↓
后端校验资料
    ↓
用 bcrypt 得到 password_hash
    ↓
写入 users：

id            = 数据库分配
email         = 注册邮箱
password_hash = bcrypt 结果
role          = 默认角色
status        = 账号状态
    ↓
以后登录读取这行资料
~~~

注册入口如果直接签发凭据，再接下面的凭据生成和保存步骤。

## 6. 登录：创建新的登录链

~~~text
浏览器提交 email、password
    ↓
按 email 查询 users
读取 id、email、password_hash、role、status
    ↓
用 bcrypt 核对密码
检查账号是否可用
    ↓
根据当前 email、password_hash 计算 token_version
    ↓
安全随机生成 family_id
    ↓
生成 access_token：

user_id、email、role = 读取的账号资料
token_version       = 当前计算结果
sid                 = family_id
iat、nbf            = 签发时刻
exp                 = 签发时刻 + 24 小时
    ↓
安全随机生成 refresh_token
    ↓
计算 token_hash
    ↓
准备主记录 JSON：

user_id、token_version、family_id
created_at = 生成时刻
expires_at = 生成时刻 + 30 天
    ↓
校验准备写入的 key 类型、参数和期限
进入协调后的 Redis 写入操作
    ↓
① SET login_session:{family_id}
   value = 用户编号字符串，TTL = 30 天

② SET refresh_token:{token_hash}
   value = 主记录 JSON 字符串，TTL = 30 天

③ SADD user_refresh_tokens:{user_id} token_hash
   设置整个 key 的 TTL，默认 30 天

④ SADD token_family:{family_id} token_hash
   设置整个 key 的 TTL，默认 30 天

⑤ SADD user_login_sessions:{user_id} family_id
   设置整个 key 的 TTL，默认 30 天
    ↓
必要记录全部写入成功
    ↓
返回 access_token、refresh_token、expires_in、用户资料
    ↓
浏览器保存：

auth_token       = access_token 原值
refresh_token    = refresh_token 原值
auth_user        = 用户资料 JSON 字符串
token_expires_at = 计算的预计到期毫秒时间
~~~

密码或状态不通过，不签发凭据。必要 Redis 操作失败，不返回登录成功。登录时间可另行记录到 `users.last_login_at`、`last_active_at`，这些列不保存凭据原值。

## 7. 请求接口：每次检查登录是否仍有效

~~~text
读取 localStorage.auth_token
    ↓
发送请求头：
Authorization: Bearer access_token原值
    ↓
后端验证签名和允许的算法
    ↓
检查 JWT.exp、JWT.nbf
    ↓
按 JWT.user_id 读取当前账号
    ↓
检查 status
比较 JWT.token_version 与当前计算结果
    ↓
从经过验证的 JWT.sid 取得 family_id
    ↓
GET login_session:{family_id}
    ↓
存在，且 value 对应相同 user_id？
    ├─ 是 → 按当前账号权限处理业务
    └─ 否 → 返回 401
~~~

普通业务请求不生成新凭据，不修改凭据，不延长 TTL。不能在验签前相信 JWT.sid、JWT.user_id。

Redis 查询故障应返回服务不可用，例如 503，不能跳过检查放行，也不能把查询故障当作“确定不存在”。要求退出立即失效时，检查应读取权威主节点；缓存“登录仍有效”的结果或读取有延迟的副本，可能推迟撤销生效。

## 8. 续期：完整的删除、写入与覆盖

### 8.1 逐节点流程

~~~text
浏览器提交 localStorage.refresh_token 的原值
    ↓
后端检查格式，计算旧 token_hash
    ↓
GET refresh_token:{旧 token_hash}
    ↓
检查主记录存在、JSON.expires_at 未过期
    ↓
从主记录取得 user_id、family_id、token_version
    ↓
查询当前账号，检查 status、token_version
    ↓
GET login_session:{family_id}
检查存在且属于相同 user_id
    ↓
准备新数据，暂不写 Redis、暂不返回：

新 access_token
新 refresh_token
新 token_hash
新主记录 JSON、新截止时间

family_id 沿用
token_version 采用当前计算结果
    ↓
进入 Redis 原子操作
    ↓
再次确认：

旧主记录仍存在且未改变、未过期
login_session 仍存在且属于相同用户
相关 key 类型、参数和期限正确
    ↓
删除旧数据：

① DEL refresh_token:{旧 token_hash}
② SREM user_refresh_tokens:{user_id} 旧 token_hash
③ SREM token_family:{family_id} 旧 token_hash
    ↓
保存新数据：

④ SET refresh_token:{新 token_hash}
   value = 新主记录 JSON
   TTL = 新生成时刻起 30 天
   expires_at = 新生成时刻 + 30 天

⑤ SADD user_refresh_tokens:{user_id} 新 token_hash
   设置整个 Set 的 TTL，默认重设 30 天

⑥ SADD token_family:{family_id} 新 token_hash
   设置整个 Set 的 TTL，默认重设 30 天

⑦ 延长 login_session:{family_id} 的 TTL
   默认重设 30 天
   只延长仍存在的记录，不能重新创建

⑧ SADD user_login_sessions:{user_id} family_id
   维护用户登录索引，设置整个 Set 的 TTL
    ↓
原子操作成功
    ↓
返回新 access_token、新 refresh_token、新 expires_in
    ↓
浏览器覆盖：

auth_token       = 新 access_token
refresh_token    = 新 refresh_token
token_expires_at = 新计算的预计到期时间

用户资料未变化时，auth_user 可以保留
~~~

如果提前准备新记录，最终写入时要让剩余 TTL 与准备好的截止时间一致。图中的“30 天”忽略很短的处理耗时；程序不能因此无意中多延长记录期限。

### 8.2 到底删除哪些、保留哪些

| 数据 | 续期处理 | 原因 |
|---|---|---|
| 旧刷新 String | DEL | 旧凭据不能重复消费 |
| 两个 Set 的旧 token_hash | SREM | 清理旧索引 |
| 两个 Set 本身 | 保留，加新成员、更新 TTL | 用户和登录链仍有效 |
| login_session | 保留、延长期限 | 这次登录继续有效 |
| 用户登录索引中的 family_id | 保留或补齐、维护期限 | 全设备退出仍要找到它 |
| 浏览器旧原值 | 被新原值覆盖 | 后续使用新凭据 |
| PostgreSQL 账号和签名密钥 | 保留 | 续期不是重新注册或创建系统密钥 |

续期**不会自动撤销旧 access_token**。服务端不逐个保存其原值，不能对它执行 Redis DEL。旧 JWT 未过期、账号和登录仍有效时，可能继续使用。

退出则删除 login_session，让这条链中所有新旧 JWT 都被拒绝。这是两个不同动作。

### 8.3 两个请求同时续期怎么办

~~~text
两个请求都先读到了同一份旧主记录
    ↓
在最终原子操作中再次检查
    ↓
第一个请求消费旧主记录、写入新记录
    ↓
第二个请求发现旧记录不存在
    ↓
拒绝重复消费，不返回第二套有效凭据
~~~

可用 Redis Lua 协调这些检查和修改。提前生成字符串只是准备材料，最终消费成功前不能返回。

原 Sub2API 的读取、删除、生成写入是分开的；删除失败会记日志并继续，不等同于本文的严格消费方案。

## 9. 退出这一次登录：先撤销，再清理

~~~text
浏览器请求退出
    ↓
验证凭据，取得可信 user_id、family_id
    ↓
进入与续期协调的撤销操作
    ↓
① DEL login_session:{family_id}
    ↓
新进入登录状态检查的请求从此被拒绝
    ↓
② SMEMBERS token_family:{family_id}
   取得这条链的 token_hash
    ↓
③ 对每个 token_hash：

   DEL refresh_token:{token_hash}
   SREM user_refresh_tokens:{user_id} token_hash
    ↓
④ DEL token_family:{family_id}
    ↓
⑤ SREM user_login_sessions:{user_id} family_id
    ↓
空 Set 会被 Redis 自动移除
其他设备的索引成员保留
    ↓
确认必要撤销成功，返回退出成功
    ↓
浏览器停止续期定时器，清空前端内存状态
删除四个 localStorage key：

auth_token
refresh_token
auth_user
token_expires_at
    ↓
回到登录页
~~~

可以用有效 JWT.sid 确定登录链；访问凭据已过期时，也可通过经过校验的刷新主记录确定。不能直接相信浏览器随便提交的 family_id。

退出接口要支持幂等重试：已撤销的登录不能重新通过普通业务鉴权，但可通过合法的退出验证流程确认“已退出”，不能恢复登录记录。删除不存在的 Redis key 可以重复执行。

### 9.1 复制出去的 access_token 为什么也不能用

~~~text
有人拿着退出前复制的 access_token
    ↓
签名可能正确，exp 也可能没到
    ↓
按 JWT.sid 查 login_session
    ↓
记录不存在
    ↓
返回 401
~~~

不需要修改 JWT 原值，也不需要更换全系统 jwt_secret。其他设备使用不同 family_id，不受这次退出影响。

“立即失效”指服务端退出成功后，后续进入检查的请求被拒绝。已通过检查、正在执行的请求不会自动中止；已建立的长连接也需要另行关闭或重新校验。

### 9.2 退出请求失败或超时

~~~text
Redis / 网络故障
    ↓
不能确认服务端撤销是否成功
    ↓
不能承诺旧 access_token 已在服务端失效
    ↓
可重试幂等退出操作
~~~

前端可以清理本机状态，但“本机没有凭据”和“服务器已撤销凭据”是两件事。

## 10. 退出所有设备：找到并撤销全部登录链

只有 user_refresh_tokens 可以找到刷新主记录，却不能直接、可靠地列出所有 login_session，所以新增用户登录索引：

~~~text
user_login_sessions:{user_id}
    ↓
Set 成员是 family_id
    ↓
登录添加、续期维护、退出移除
整个 key 有期限，成员没有独立 TTL
~~~

完整流程：

~~~text
验证用户身份，取得 user_id
    ↓
进入与该用户登录、续期协调的撤销操作
    ↓
SMEMBERS user_login_sessions:{user_id}
取得当前全部 family_id
    ↓
对每个 family_id：

① DEL login_session:{family_id}

② SMEMBERS token_family:{family_id}
   对每个 token_hash：
   DEL refresh_token:{token_hash}

③ DEL token_family:{family_id}
    ↓
再读 user_refresh_tokens:{user_id}
删除其中 token_hash 对应的残留主记录
    ↓
DEL user_refresh_tokens:{user_id}
DEL user_login_sessions:{user_id}
    ↓
确认服务端撤销成功
    ↓
当前浏览器清理四个 key、定时器和内存状态
    ↓
其他设备下次请求或续期：
login_session 不存在 → 被拒绝
~~~

其他浏览器的 localStorage 不会被 Redis 远程自动清空；它们收到认证拒绝后再清理。

撤销针对生效时已存在的登录；之后重新输入密码登录，得到新 family_id，属于新的登录。

不能把“读取、逐个删除、最后删索引”任意拆开与登录写入交错，否则可能漏撤销或误删新索引。实现时必须按同一用户协调登录、续期和全设备撤销。

## 11. 改密码：旧版本为什么不匹配

~~~text
验证用户身份和改密条件
    ↓
对新密码生成新的 bcrypt password_hash
    ↓
更新 PostgreSQL users.password_hash
    ↓
数据库修改成功
如有用户资料缓存，及时更新或失效
    ↓
当前 token_version 的计算结果改变
    ↓
旧 JWT、旧刷新 JSON 仍保存旧 token_version
    ↓
下次校验，与当前值不匹配
    ↓
拒绝旧凭据
    ↓
产品要求改密后全部退出时
执行“退出所有设备”的撤销清理
    ↓
浏览器清理状态，重新登录
~~~

这里没有在数据库中把 token_version 加一，真正持久化的是新 password_hash。

改密成功但 Redis 清理失败时，旧版本也应在读取当前账号后被拒绝；物理清理可以重试。不能长期使用缓存中的旧账号资料。

## 12. 自然过期：分别由谁处理

### 12.1 access_token 到期

~~~text
到达 JWT.exp
    ↓
服务器时间校验不通过，返回 401
    ↓
刷新凭据和登录仍有效？
    ├─ 是 → 尝试续期
    └─ 否 → 清理登录状态，重新登录
~~~

浏览器字符串不会自动消失，但服务器已不接受它。

### 12.2 刷新主记录到期

~~~text
refresh_token:{token_hash} 的 TTL 到期
    ↓
key 不再可读
    ↓
后端收到旧 refresh_token，重新计算哈希
    ↓
GET 找不到主记录
    ↓
拒绝续期
~~~

如果程序读到记录，仍检查 JSON.expires_at。Set 成员不能让失效主记录复活。

### 12.3 登录有效记录到期

~~~text
login_session:{family_id} 的 TTL 到期
    ↓
访问检查失败、续期检查失败
    ↓
这条登录链不能继续使用
~~~

成功续期会延长期限，因此默认 30 天不是从第一次登录起绝对最多 30 天。若要求定期强制重新登录，要另外设置绝对会话期限。

### 12.4 索引 Set 到期

~~~text
某个索引 key 的 TTL 到期
    ↓
整个 Set 不再可读
    ↓
不是单个成员分别过期
~~~

主记录到期不会自动移除其他 Set 的成员。索引用于找到记录，不是有效性的最终依据。完整批量撤销依赖完整索引，因此新增方案不能忽略索引写入错误。

### 12.5 浏览器到达预计到期时间

~~~text
接近 token_expires_at
    ↓
定时器尝试续期
    ↓
成功 → 覆盖新凭据和时间
确定已失效 → 清理登录状态
临时网络 / 服务故障 → 按策略重试或显示错误
~~~

localStorage 没有 TTL。数据库用户行和系统密钥也不会因 token 到期自动删除。

## 13. 关闭网页再打开：恢复之后仍要验证

~~~text
关闭网页
    ↓
定时器不再运行
localStorage 通常仍保留
Redis TTL 继续计时
    ↓
重新打开
    ↓
读取四个 localStorage key
恢复界面，重新安排续期
请求服务端确认当前身份
    ↓
仍有效 → 继续使用或续期
已撤销 / 到期 → 清理状态，重新登录
~~~

本机还有字符串，不等于服务器仍认可登录。如果在另一台设备退出所有登录，旧网页重新打开仍会被拒绝。

## 14. 用一次实际时间串起来

以下按 UTC+8、默认配置展示，忽略请求耗时：

~~~text
10 月 10 日 10:00 登录
    ↓
access_token.exp：10 月 11 日 10:00
刷新主记录截止：11 月 9 日 10:00
登录记录和索引默认 TTL：30 天
    ↓
10 月 11 日 09:58 续期成功
    ↓
删除旧主记录、移除旧哈希
写入新主记录、加入新哈希
    ↓
新 access_token.exp：10 月 12 日 09:58
新刷新主记录截止：11 月 10 日 09:58
登录记录和索引默认重设 30 天
    ↓
10 月 11 日 09:59 退出
    ↓
删除登录记录、这条链的刷新记录
清理索引和本机状态
    ↓
虽然新 access_token 明天才到 exp
现在再请求也因登录记录不存在而被拒绝
~~~

续期不修改旧 JWT 内部的 exp；它产生新凭据和新时间。

## 15. 退出和续期同时发生：不能恢复已退出的登录

~~~text
续期先读取旧主记录
    ↓
退出删除 login_session
    ↓
续期准备好新字符串
    ↓
最终原子操作再次检查 login_session
    ↓
不存在 → 拒绝提交，不返回新凭据
~~~

反过来的顺序：

~~~text
续期先完成原子操作
    ↓
新主记录已经加入登录链索引
    ↓
退出撤销相同 family_id
    ↓
删除 login_session 和新主记录
    ↓
即使新凭据响应之后才到浏览器
新 access_token 也无法通过登录检查
~~~

实现时守住这些边界：

- 登录创建 login_session；续期只延长仍存在的记录。
- 单次退出和续期不能任意交错；全设备撤销还要协调该用户的登录创建。
- 浏览器协调并发续期，后端最终原子检查仍不能省略。
- 返回成功前确认必要存储修改成功；临时故障不能直接放行。
- 全部接受这类登录 JWT 的入口都要检查登录记录，不能只改一个接口。

Redis Lua 的原子性表示执行期间不被其他命令插入，**不表示报错后自动回滚之前的写入**。应先校验参数、key 类型和前置条件，再修改，并设计错误恢复。本文是逻辑流程，不是完整可执行脚本。

实际 Lua 脚本访问的 key 必须通过 KEYS 显式传入。批量撤销若先在后端读取索引、收集 key，提交操作时还要核对索引是否变化，必要时重新读取，不能漏掉期间新增的登录；也不能在脚本中任意根据 Set 内容拼接未声明的 key。

本文的跨 key 操作按单个 Redis 实例说明。Redis Cluster 还要求脚本相关 key 满足同槽约束，需要另行规划 hash tag 和 key 布局，不能直接照抄后宣称跨槽原子执行。

## 16. 原 Sub2API 与本文方案的区别

| 项目 | 原 Sub2API 固定版本 | 本文方案 |
|---|---|---|
| 刷新主记录和两个 Set | 已有 | 保留并严格维护 |
| login_session | 没有本文新增 key | 新增 String |
| user_login_sessions | 没有本文新增 key | 新增 Set |
| 普通接口查登录记录 | 不查 | 每次查并核对归属 |
| 续期读取、删除、写入 | 分开执行 | 最终检查与轮换协调为原子操作 |
| 清理旧 Set 成员 | 没有这里的 SREM | 主动移除旧 token_hash |
| 单次退出 | 删除提交的刷新主记录 | 撤销登录链，清理主记录和索引 |
| 退出后复制的 JWT | 未过期、状态和版本匹配时可能仍可用 | 登录记录不存在，后续请求被拒绝 |
| token_version | 根据账号资料推导，没有独立数据库列 | 保持含义，不作为续期次数 |
