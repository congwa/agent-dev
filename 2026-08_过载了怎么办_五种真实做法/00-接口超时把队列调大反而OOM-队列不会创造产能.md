# 00 · 接口超时，把队列调大，反而 OOM：队列不会创造产能

> 这是系列的第一篇，也是唯一一篇没有 GitHub 源码剖析的。
> 后面 5 篇讲的都是「怎么做」，这一篇讲「为什么必须这么做」。
> 跳过它你也能抄代码，但遇到没见过的场景就不会推了。

---

## 一个几乎每个后端都干过的蠢事

你的接口平时挺好，突然某天流量涨了，超时告警炸了。

你打开代码，看到线程池 `corePoolSize=20, queueCapacity=200`。

你想：队列太小了，请求都被拒了。于是改成 `queueCapacity=10000`，重启，发布。

十分钟后，超时告警没停，反而多了一条 OOM 告警。

这个操作我见过太多次了。它的问题不在于「10000 太大」，而在于**改队列长度这件事本身，从来就不会增加任何产能**。

---

## 用奶茶店把这事说清楚

一家奶茶店，**1 个店员**，做一杯**平均 1 秒**。

所以这家店的产能是死的：**1 杯/秒**。不管门口排多少人，它一秒就出一杯。

现在让客人以不同速度进店：

| 客流（人/秒） | 队伍平均多长 L_q | 客人平均总耗时 W |
|---|---|---|
| 0.5 | 0.5 人 | 2 秒 |
| 0.8 | 3 人 | 5 秒 |
| 0.9 | 7.6 人 | 9.5 秒 |
| 0.95 | 19 人 | 21 秒 |
| 0.99 | 78 人 | 80 秒 |

盯着最后两行看：**客流从 0.9 涨到 0.99，只多了 10%，等待时间涨了 8 倍。**

这不是巧合。排队论里有个最基本的公式（M/M/1 模型）：

```
平均总耗时 W = 单次服务时间 × 1/(1-ρ)      其中 ρ = 客流 ÷ 产能
```

（严格说 W 是「排队 + 被服务」的总时间；纯排队那部分是 `W_q = 单次服务时间 × ρ/(1-ρ)`。
上表第二列的「队伍平均多长」统计的是不含正在被服务那位的排队人数 `L_q = ρ²/(1-ρ)`。
这些区别在推导时要留意，但不影响下面的结论。）

`1/(1-ρ)` 这个东西在 ρ=1 的地方是一个**极点** —— 它不是"变大"，是"飞到无穷"。

- ρ = 0.9 → 放大 10 倍
- ρ = 0.99 → 放大 100 倍
- ρ = 0.999 → 放大 1000 倍
- ρ ≥ 1 → **这个方程没有有限解**

最后一行才是关键：**当客流超过产能，不存在任何"等多久"的答案**。队伍每秒净增 (λ−μ) 个人，永远增长，直到内存耗尽。

你可以自己跑一下：

```bash
python3 demos/demo00_queue.py
```

```
店员产能 μ = 1 杯/秒

    客流 λ      利用率 ρ     队伍人数 L_q        总耗时 W     理论 1/(μ-λ)
--------------------------------------------------------------
    0.50       0.50          0.5         2.0s           2.0s
    0.80       0.80          3.2         5.0s           5.0s
    0.90       0.90          7.6         9.5s          10.0s
    0.95       0.95         19.4        21.4s          20.0s
    0.99       0.99         77.9        79.8s         100.0s
```

（模拟值和理论值有点差距，是因为 ρ 越接近 1，需要模拟越久才收敛。趋势是对的。）

## 所以「加大队列」到底改变了什么

把护栏从能站 20 人换成能站 500 人。店员还是 1 个。

结果是：第 500 位客人要等 500 秒。

你没有多服务任何一个人。你只是把「第 21 个人在门口被告知满了」，变成了「第 500 个人在队伍里站 8 分钟，然后还是没买到，而且极其愤怒」。

Fred Hébert 在 [Queues Don't Fix Overload](https://ferd.ca/queues-don-t-fix-overload.html) 里的原话是：

> 当人们不动脑子地拿队列当缓冲区用时，他们做的只是造了一个更大的桶，来装那些迟早要倒掉的水。

他的结论只有两条路，逃不掉：

1. **背压（back-pressure）**：堵住输入
2. **丢弃（load-shedding）**：主动扔掉一部分

不选，就等着系统自己崩。

---

## 那背压呢？背压不是很时髦吗

背压 = 在门口挂个「满员，请稍后」的牌子。

门里确实不挤了。但**队伍并没有消失，它移到了门外的人行道上**。

- 如果门外是你自己家的另一个服务 —— 那就是你另一个服务炸了。
- 如果门外是公网上的手机 App —— 你根本管不了它。

Reactive Streams 规范自己说得很明白（[原文](https://github.com/reactive-streams/reactive-streams-jvm)）：

> 背压是这个模型不可分割的一部分，**目的是让线程之间的队列保持有界**。

注意它承诺的是「有界」，**不是「不丢数据」，也不是「上游不会崩」**。

更要命的是 Marc Brooker 指出的一点（[Open and Closed, Omission and Collapse](https://brooker.co.za/blog/2023/05/10/open-closed/)）：**背压只在闭环系统里成立**。

- **闭环**：客人看到「满员」牌子，回家了。你慢一点，客流自然就少了。
- **开环**：客人看到牌子，**再敲一次门**。你慢一点，敲门声反而更多了。

现实中的客户端几乎全是后者 —— SDK 自带重试，用户自己会刷新。所以你的背压往往不是"减少了流量"，而是"把一次请求变成了三次"。

Brooker 的原话：

> 一旦某个请求的响应时间超过 15ms，我们就加一个新请求，这稍微提高了到达率……这又稍微提高了延迟……一路烧到系统毁灭。

**背压是把拥堵推给上游，不是消除拥堵。** 这是这套教程的第一个核心判断。

---

## 那到底该怎么办

摊开来只有三件事可做，而且它们互相不能替代：

| 想改变什么 | 手段 | 代价 |
|---|---|---|
| 降低 λ（进来的量） | 限流、丢弃、降级、采样 | 一部分请求失败 |
| 提高 μ（处理的量） | 扩容、加机器、优化代码 | 花钱，而且慢 |
| 切断正反馈 | 重试预算、熔断、有界队列 | 需要提前埋好 |

你在标题那张表里看到的五种做法，全都落在这三件事上：

| 场景 | 本质是在做什么 |
|---|---|
| 秒杀、抢票、热点查询 → 快速失败 + 丢弃 | 降低 λ |
| 第三方 webhook 回调 → 立即 ACK + 有界队列 | 切断正反馈 + 把压力还给上游 |
| IoT 上报、行情推送 → 丢弃 + 采样 | 降低 λ |
| 监控指标、埋点、弹幕 → 丢旧留新 | 降低 λ，且优先保新鲜度 |
| 稳定超载 → 扩容 | 提高 μ |

**最后一行是唯一真正解决问题的那个，也是唯一要花钱的那个。** 前四行都是在「花不起钱之前，怎么优雅地少干点活」。

## 一个立刻能用的公式

利特尔法则（Little's Law）长这样：

```
L = λ × W
系统里的东西数量 = 到达率 × 每个东西待的时间
```

这条法则的厉害之处在于它**对分布和调度方式一无所求** —— 不要求泊松到达、不要求指数服务时间、不要求 FIFO、不要求单服务器。唯一的必要条件是系统处于稳态（长期平均存在且有限，也就是 λ < 产能）。John Little 在[五十周年回顾](https://pubsonline.informs.org/doi/10.1287/opre.1110.0940)里对这些做过逐条说明。

注意最后那个条件：**λ ≥ 产能时，L 和 W 都发散** —— 这正是「稳定超载只能扩容」的数学表述。

把它反过来用，就是一个直接能填进配置文件的公式：

```
单实例产能  = 并发数 ÷ 单请求耗时
队列长度上限 = (SLO 延迟预算 − 单请求耗时) × 产能
需要的实例数 = 峰值 QPS ÷ 单实例产能
```

举个具体的：

- 你的接口 P99 SLO 是 **500ms**
- 一个请求真正干活要 **50ms**
- 单实例线程池 **32**

那么：

```
产能     = 32 ÷ 0.05s = 640 QPS
队列上限 = (500-50)ms × 640 = 288 个
```

**288**，不是 10000。你把它设成 10000，排满时一个请求要等 15.6 秒 —— 早就没人在等了。

验算一下 Google SRE 书里的例子（[Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/)）：

> 如果队列长度是线程数的 10 倍，单个请求处理要 100 毫秒，那么队列排满时，一个请求要花 1.1 秒，其中大部分时间花在排队上。

设线程数 T：产能 = T/0.1 = 10T QPS，队列 = 10T 个 → 排队 10T ÷ 10T = 1.0 秒，加干活 0.1 秒 = **1.1 秒**。对上了。

同一本书还给了一条更直接的建议：

> 对于流量比较平稳的系统，队列长度通常应该**小于线程池大小的 50%**，这样服务器在扛不住时会尽早开始拒绝请求。

**小于 50%**。不是 10 倍。

```bash
python3 demos/demo05_metastable.py
```

## 最后一个，也是最反直觉的

「那我流量降下来不就好了？」

不一定。看这个模拟（`demo05` 的第二部分）：

- 服务器产能 100 QPS
- 日常流量 80 QPS（利用率 80%，非常健康）
- 第 20~30 秒来了个 300 QPS 的尖峰，**只持续 10 秒**
- 之后流量立刻回到 80 QPS

```
【A. 无界队列 + 无限重试（大多数系统的默认状态）】
  时间段                       打到服务的QPS      有效产出QPS     白烧QPS      积压
  尖峰前   0-20s                     80           80         0       0
  尖峰中  20-30s                    658           29        71    2126
  尖峰后  30-40s                    372            0       100    7394
  1分钟后 60-80s                    239            0       100   12496
  2分钟后100-120s                   240            0       100   18097
```

尖峰过去 90 秒了，流量早就回到 80 了，**有效产出是 0**。

因为服务器 100% 的产能都花在处理「客户端已经放弃了的请求」上（那一列叫「白烧」）。它每处理完一个，结果都直接扔掉，因为对面早就重试了。于是所有人继续超时，继续重试，队列继续排满。

**这个循环自己养活自己。** 学术上叫**元稳定失效**（metastable failure），2021 年 HotOS 那篇[论文](https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s11-bronson.pdf)的定义是：

> 触发因素被移除之后，坏状态依然持续存在。

Google SRE 书里那句更狠：

> 一个服务在 10000 QPS 时是健康的，在 11000 QPS 时开始雪崩式失败。这时候把流量降到 9000 QPS，几乎肯定止不住雪崩。

OSDI '22 那篇[《Metastable Failures in the Wild》](https://www.usenix.org/system/files/osdi22-huang-lexiang.pdf)统计了 11 家公司的 22 起真实事故，结论是：

- **超过一半**的事故，维持它的因素是**重试**
- **超过 55%** 的事故，最终是靠**丢负载**（限流、拒绝请求）解决的，不是靠扩容

论文对「能不能靠自动扩容躲过去」的表态是很克制的：

> 自动扩容对大型系统和大放大系数来说代价极高……当前的自动扩容技术能否快得过元稳定失效的形成，**还需要进一步研究**。

翻译成人话：**别指望 HPA 救你**。HPA 的控制环是分钟级的，`1/(1-ρ)` 的发散是秒级的。

---

## 这一篇要你记住的

```
队列不会创造产能，它只借时间。
背压不会消灭排队，它只换地方。
重试不会提高成功率，它只放大流量。
只有扩容能提高产能 —— 但前提是，你得先把烧起来的正反馈掐掉。
```

出事时的正确顺序永远是：

1. **先掐正反馈** —— 关重试、丢负载、必要时重启清空队列
2. **再扩容**

反过来做，新扩的机器一上线就被同一股重试洪水打回坏状态，钱白花。
