# 01 · 秒杀、抢票、热点查询：快速失败 + 丢弃

> 适用场景：**用户不会等**。等了也是超时重试，压力反而翻倍。
> 核心判断：**拒绝一个人，比让一百个人一起等，服务的人更多。**

---

## 先跑一下，看数字

场景设定：

- 后端只能同时处理 **20 个请求**，每个请求耗时 **50ms** → 产能 = 20 ÷ 0.05 = **400 QPS**
- 洪峰来了 **1200 QPS**，是产能的 3 倍
- 用户等超过 **1 秒**就关页面走人

```bash
python3 demos/demo01_failfast.py
```

```
【全都排队（无保护）】共 3600 个请求
  成功拿到结果 :   577  (16.0%)   ← 这才是有效产出
  被明确拒绝   :     0          ← 用户 50ms 内就知道结果
  等到超时     :  3023          ← 白等 1 秒，什么也没拿到
  白干的活     :  3015          ← 占了后端坑位，产出却被丢掉
  P50 / P99    :  1001 / 1002 ms

【快速失败 + 丢弃】共 3600 个请求
  成功拿到结果 :  1186  (32.9%)   ← 这才是有效产出
  被明确拒绝   :  2414          ← 用户 50ms 内就知道结果
  等到超时     :     0          ← 白等 1 秒，什么也没拿到
  白干的活     :     0          ← 占了后端坑位，产出却被丢掉
  P50 / P99    :     0 / 51 ms
```

> 这个 demo 跑的是真实并发调度，每次运行数字会有小幅波动（几个百分点），但趋势和量级是稳定的。

有两个数字值得盯着看：

**第一，成功数从 577 涨到了 1186，翻了一倍。**

这个结果反直觉 —— 我明明拒绝了 2414 个人，怎么反而多服务了？

因为无保护的时候，后端那 20 个坑位被一堆「用户已经走了的请求」占着。请求在队列里排到队头时，已经过去 1 秒多，用户早关页面了。服务器辛辛苦苦查完数据库，返回给一个不存在的连接。这就是那一行「白干的活：3015」。

**这 3015 次白干，本来可以服务 3015 个还在等的人。**

**第二，P99 从 1002ms 掉到 51ms。**

拒绝一个请求几乎不花钱 —— 一次判断，一次 return。让人排队却要付出全额的等待成本。

## 核心代码只有三行

看 demo 里的实现，脱掉壳子就是这么点东西：

```python
class Server:
    def __init__(self):
        self.inflight = 0          # 当前正在干活的请求数

    async def handle(self):
        # ↓↓↓ 就这三行 ↓↓↓
        if self.inflight >= CONCURRENCY:
            return "rejected"      # HTTP 429，立刻返回
        # ↑↑↑ 就这三行 ↑↑↑
        self.inflight += 1
        try:
            return await self._work()
        finally:
            self.inflight -= 1
```

真的就这么简单。难的不是写，是**说服自己去写**——很多人心理上过不去「我居然主动拒绝用户」这一关。

## 但阈值填多少？这才是真问题

上面那个 `CONCURRENCY = 20` 是我拍脑袋定的。生产环境里你怎么定？

- 定小了：平时白白浪费产能
- 定大了：真过载时不起作用
- 而且今天的合理值，明天可能就不对了 —— 下游变慢、GC、冷缓存、换了台机器

这就是为什么工业级的方案几乎都在做同一件事：**让这个数字自己算出来**。

下面看三个不同流派怎么解这个问题。

---

## 流派一：Sentinel —— 用利特尔法则反推容量

**[alibaba/Sentinel](https://github.com/alibaba/Sentinel)** · 23.1k stars · Java
**[alibaba/sentinel-golang](https://github.com/alibaba/sentinel-golang)** · 3k stars · Go

Sentinel 的「系统自适应保护」核心只有一个函数，在 `sentinel-core/.../slots/system/SystemRuleManager.java`：

```java
private static boolean checkBbr(int currentThread) {
    if (currentThread > 1 &&
        currentThread > Constants.ENTRY_NODE.maxSuccessQps() * Constants.ENTRY_NODE.minRt() / 1000) {
        return false;   // 拒绝
    }
    return true;
}
```

翻译成人话：

```
估算容量 = 最近观测到的最大成功 QPS × 最小响应时间(毫秒) ÷ 1000
如果 当前并发数 > 估算容量，就拒绝
```

**`maxSuccessQps × minRt` 就是利特尔法则 L = λW。**

- λ = 我这台机器最好状态下每秒能完成多少个（maxSuccessQps）
- W = 一个请求在完全不堵的时候要多久（minRt）
- L = 那我同时最多应该有多少个在飞

这个数字是**实时量出来的**，不是配置文件里写死的。下游变慢了，minRt 上去，估算容量自动下调。

Go 版一模一样（`core/system/slot.go`）：

```go
func checkBbrSimple() bool {
    concurrency := stat.InboundNode().CurrentConcurrency()
    minRt := stat.InboundNode().MinRT()
    maxComplete := stat.InboundNode().GetMaxAvg(base.MetricEventComplete)
    if concurrency > 1 && float64(concurrency) > maxComplete*minRt/1000.0 {
        return false
    }
    return true
}
```

### 一个容易忽略的设计：这是两级判定

看完整的 `checkSystem()`：

```java
// load. BBR algorithm.
if (highestSystemLoadIsSet && getCurrentSystemAvgLoad() > highestSystemLoad) {
    if (!checkBbr(currentThread)) {
        throw new SystemBlockException(resourceWrapper.getName(), "load");
    }
}
```

注意那个外层 `if`：**只有当系统 load 已经超过阈值时，才启动 BBR 复核**。

平时门口不挤，随便进。只有开始堵了，才拿出这把尺子量一量。

（Java 版里只有 load 这一路会走 BBR，CPU 那一路是直接抛异常、不复核。Go 版把 Load 和 CpuUsage **两者**都接上了 `checkBbrSimple()` —— 这是两个版本少见的行为差异，迁移时要留意。）

[官方文档](https://sentinelguard.io/en-us/docs/system-adaptive-protection.html)明说了这个设计意图 —— 目标是「在合适的系统负载下**提高**吞吐量，而不是把 load 死死压在阈值以下」。这是从 TCP BBR 拥塞控制借来的思路。

### 还有一个细节，很多人第一次看会忽略

Sentinel 拒绝请求时抛的 `BlockException` 是**预分配的、不带堆栈的**异常。

为什么？因为过载时你可能每秒要拒绝 10 万个请求。如果每次拒绝都要生成一个完整 Java 堆栈，**光是"拒绝"这个动作本身就能把服务压垮**。

**快速失败的重点在「快速」，不在「失败」。** 这句话值得记下来。

同样的思路在别的项目里也能看到：Envoy 用无锁 CAS 判定，Netflix 返回 `Optional.empty()` 而不是抛异常。

### Go 生态的等价物

**[go-kratos/aegis](https://github.com/go-kratos/aegis)** 的 `ratelimit/bbr` 是 Sentinel 思路的 Go 实现（源码注释直言 "It is inspired by sentinel"）：

```go
func (l *BBR) maxInFlight() int64 {
    return int64(math.Floor(float64(l.maxPASS()*l.minRT()*l.bucketPerSecond)/1000.0) + 0.5)
}

func (l *BBR) Allow() (ratelimit.DoneFunc, error) {
    if l.shouldDrop() {
        return nil, ratelimit.ErrLimitExceed
    }
    atomic.AddInt64(&l.inFlight, 1)
    start := time.Now().UnixNano()
    return func(ratelimit.DoneInfo) {
        rt := int64(math.Ceil(float64(time.Now().UnixNano()-start) / float64(time.Millisecond)))
        if rt > 0 { l.rtStat.Add(rt) }
        atomic.AddInt64(&l.inFlight, -1)
        l.passStat.Add(1)     // 注意：只有真正跑完的才算 pass
    }, nil
}
```

它多了一个 Sentinel 没有的细节 —— **1 秒的「丢弃粘滞期」**：

```go
if time.Duration(now-prevDropTime) <= time.Second {
    // 刚开始丢弃不到 1 秒，即便 CPU 已回落也继续按 inflight 判定
    inFlight := atomic.LoadInt64(&l.inFlight)
    return inFlight > 1 && inFlight > l.maxInFlight()
}
```

这叫**滞回**（hysteresis）。没有它的话，CPU 在阈值附近抖动会导致「拒绝→放行→拒绝→放行」的反复横跳，比一直拒绝还糟。

默认参数：`Window: 10s`、`Bucket: 100`（100ms 一个桶）、`CPUThreshold: 800`（80%），并且支持 `WithCPUQuota` 适配容器 cgroup —— 在 K8s 里跑必须开这个，否则读到的是宿主机 CPU。

## 流派二：Netflix / Envoy —— 用延迟梯度当信号

**[Netflix/concurrency-limits](https://github.com/Netflix/concurrency-limits)** · 3.6k stars · Java

Netflix 的思路更激进：**不看 CPU，不看 load，只看延迟的变化趋势**。

灵感来自 TCP 拥塞控制（Vegas 算法）。核心公式在 `Gradient2Limit.java`：

```java
final double gradient = Math.max(0.5, Math.min(1.0, tolerance * longRtt / shortRtt));
double newLimit = estimatedLimit * gradient + queueSize;
newLimit = estimatedLimit * (1 - smoothing) + newLimit * smoothing;   // smoothing 默认 0.2
```

人话：

> 平时端一盘菜要 1 分钟（longRtt，长期基线），现在要 3 分钟了（shortRtt）——
> 说明后厨堵了。于是把「同时接待桌数」按 1/3 的比例往下调。
> 等延迟恢复，再慢慢调回来。

**没有人需要提前告诉它「你最多能扛多少并发」。它自己从延迟里学出来。**

有三个细节值得学：

```java
// ① gradient 下限锁死 0.5 —— 单次最多把 limit 砍一半，防止一个离群点触发雪崩式收缩

// ② 用平均 RTT 而不是最小 RTT。Javadoc 明确解释：
//    RPC 请求复杂度不均匀，用 min 会让基线偏低，导致 "excessive load shedding"

// ③ app-limited 保护
if (inflight < estimatedLimit / 2) {
    return (int) estimatedLimit;    // 没人打流量时不要把 limit 撑大
}
```

第三条特别实用：凌晨三点没流量，如果这时候还在往上调 limit，早上高峰一来就直接放行过量请求了。

Netflix 的 API 设计也很有意思 —— 拒绝时**不抛异常**：

```java
Optional<Limiter.Listener> acquire(ContextT ctx)
// 返回 Optional.empty() 表示超限
```

拿到 Listener 后必须调 `onSuccess()` / `onIgnore()` / `onDropped()` 之一归还。**强制调用方归还**，是采集 RTT 数据的前提。Servlet 适配层默认返回 **429**。

### Envoy 的版本

**[envoyproxy/envoy](https://github.com/envoyproxy/envoy)** · 28.3k stars 的 adaptive concurrency filter 是同一思路（`gradient_controller.cc`）：

```cpp
uint32_t GradientController::calculateNewLimit() {
  const auto buffered_min_rtt = min_rtt_.count() + min_rtt_.count() * config_.minRTTBufferPercent();
  const double raw_gradient = static_cast<double>(buffered_min_rtt) / sample_rtt_.count();
  const double gradient = std::max<double>(0.5, std::min<double>(2.0, raw_gradient));

  const double limit = concurrencyLimit() * gradient;
  const double burst_headroom = sqrt(limit);      // headroom = sqrt(limit)，写死的
  ...
}
```

Envoy 比 Netflix 多做一件事：**它会周期性地故意把并发压到很低，量一次「完全不堵时端菜要多久」**（minRTT 探测），拿这个当基线。

拒绝时的处理：

```cpp
decoder_callbacks_->sendLocalReply(config_->concurrencyLimitExceededStatus(),
                                   "reached concurrency limit", nullptr, std::nullopt,
                                   "reached_concurrency_limit");
```

默认 **503**，body 是固定的 `"reached concurrency limit"`。健康检查请求不参与采样也不会被拦 —— 这个细节很重要，否则过载时健康检查被拒，K8s 直接把 Pod 干掉，雪上加霜。

## 流派三：Google SRE —— 让客户端自己憋着

前两个流派都是**服务端**保护自己。Google SRE 书里的 [Client-Side Throttling](https://sre.google/sre-book/handling-overload/) 是**客户端**保护服务端：

```
p_reject = max(0, (requests − K × accepts) / (requests + 1))
```

- `requests` = 客户端在 2 分钟滑动窗口内发起的请求数
- `accepts` = 其中被后端接受的数量
- `K` 通常取 **2**

人话：

> 你打电话订餐，餐厅连续说"满了"。聪明的做法不是继续每秒打一次 ——
> 那只会让接电话的人也累死。
> 而是自己算：「我打了 100 次，只成功 30 次，成功率不到 1/2，
> 那接下来每 3 次里我主动少打 1 次。」

注意留了 **2 倍余量**。不是完全不打，是留一条细缝 —— 这样餐厅一恢复你能立刻发现。**全掐死就永远不知道对方好没好。**

因为书上的公式是张图片，我让人去 Google 自家的实现里核对了一遍。gRPC-Go 的 RLS balancer 里有个照着书实现的版本（`balancer/rls/internal/adaptive/adaptive.go`）：

```go
const (
    defaultDuration        = 30 * time.Second
    defaultBins            = 100
    defaultRatioForAccepts = 2.0    // 就是书里的 K
    defaultRequestsPadding = 8.0    // 书里分母的 "+1"，这里放大到 8
)

func (t *Throttler) ShouldThrottle() bool {
    randomProbability := randFunc()
    accepts, throttles := float64(t.accepts.sum(now)), float64(t.throttles.sum(now))
    requests := accepts + throttles
    throttleProbability := (requests - t.ratioForAccepts*accepts) / (requests + t.requestsPadding)
    if throttleProbability <= randomProbability {
        return false
    }
    t.throttles.add(now, 1)
    return true
}
```

工程化的两处改动值得注意：分母的 padding 从 1 改成 8（低 QPS 时降低误杀，并防止概率打到 100%），窗口从 2 分钟改成 30 秒。

## 那 Python 里我该用什么

先说个扫兴的：**Python 生态里没有 Sentinel 那种级别的自适应过载保护**。有几个半成品，但要么是限速不是限流，要么就得自己写。

我把常见的几个查了一遍，结论如下：

| 库 | 是什么 | 过载时的行为 | 适合本篇场景吗 |
|---|---|---|---|
| [slowapi](https://github.com/laurentS/slowapi) (2.0k) | FastAPI 的请求**速率**限流 | 抛 `RateLimitExceeded` → 429 | ✅ 但只能配死阈值 |
| [aiolimiter](https://github.com/mjpieters/aiolimiter) (772) | asyncio 漏桶 | **不拒绝，排队等待** | ❌ 这是整形不是丢弃 |
| [pybreaker](https://github.com/danielfm/pybreaker) (672) | 熔断器 | 开路时抛 `CircuitBreakerError` | ✅ 但解决的是另一个问题 |
| uvicorn `--limit-concurrency` | 硬阈值闸门 | 503 + `connection: close` | ⚠️ 有坑，见下 |

### uvicorn 的坑

`--limit-concurrency` 是唯一「开箱即用」的选项，但它的实现有几个你必须知道的地方（`uvicorn/protocols/http/h11_impl.py`）：

```python
if self.limit_concurrency is not None and (
    len(self.connections) >= self.limit_concurrency or len(self.tasks) >= self.limit_concurrency
):
    app = service_unavailable      # 把整个 app 换成一个直接回 503 的桩函数
    message = "Exceeded concurrency limit."
```

三个坑：

1. **判定发生在「请求头解析完之后」**。TCP 握手和 header 解析的成本一分没省。
2. **判据是「连接数 或 task 数」**。keep-alive 的空闲连接也算进 `len(self.connections)` —— 高连接数场景下极容易误杀。
3. 响应带 `connection: close`，被拒的连接会被直接关掉。

而且它是**纯静态阈值，没有任何自适应**。

顺便澄清一个常见误解：**`limit_concurrency` 是 uvicorn 的参数，不是 Starlette 的**。Starlette 里根本没有这个东西 —— 我让人下载了 wheel 全包 grep，`limit_concurrency` 零命中。Starlette 唯一的隐式并发闸门是 `run_in_threadpool()` 走的 anyio 默认线程限流器（40 个线程），而且**满了是排队不是拒绝**。

### 那就自己写一个

好消息是，把上面几个流派的精华抄进 60 行 Python 是完全可行的。FastAPI 中间件版：

```python
import time
from collections import deque
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

class AdaptiveLimiter:
    """
    Sentinel BBR 的极简 Python 版：
      估算容量 = 窗口内最大完成速率 × 最小 RT
      当前在飞的请求超过它，就拒绝
    """
    def __init__(self, window=10.0, min_limit=8, max_limit=2000):
        self.window = window
        self.min_limit, self.max_limit = min_limit, max_limit
        self.inflight = 0
        self.completions = deque()     # 每个完成时刻
        self.min_rt = float("inf")
        self._rt_reset_at = time.monotonic()

    def _capacity(self):
        now = time.monotonic()
        while self.completions and now - self.completions[0] > self.window:
            self.completions.popleft()
        if not self.completions or self.min_rt == float("inf"):
            return self.max_limit                      # 数据不够，先放行
        rate = len(self.completions) / self.window     # 完成速率 λ
        return max(self.min_limit,
                   min(self.max_limit, int(rate * self.min_rt) + 1))   # L = λW

    def try_acquire(self):
        if self.inflight >= self._capacity():
            return False
        self.inflight += 1
        return True

    def release(self, rt):
        self.inflight -= 1
        now = time.monotonic()
        self.completions.append(now)
        self.min_rt = min(self.min_rt, rt)
        # minRT 要周期性重置，否则一个偶然的极快请求会把基线永久拉低
        if now - self._rt_reset_at > 60:
            self.min_rt, self._rt_reset_at = rt, now


app = FastAPI()
limiter = AdaptiveLimiter()

@app.middleware("http")
async def shed_load(request: Request, call_next):
    if request.url.path in ("/healthz", "/metrics"):    # 健康检查永远放行
        return await call_next(request)
    if not limiter.try_acquire():
        return JSONResponse({"detail": "server busy"}, status_code=429,
                            headers={"Retry-After": "1"})
    start = time.monotonic()
    try:
        return await call_next(request)
    finally:
        limiter.release(time.monotonic() - start)
```

几个从上面项目里学来的、别漏掉的点：

- **健康检查路径必须绕过限流器**（Envoy 的做法）。不然过载时探针被拒 → Pod 被杀 → 剩下的机器更少 → 更过载。
- **minRT 要周期性重置**。一个偶然的超快请求（缓存命中）会把基线永久拉低，导致后面一直误杀。
- **返回 429 而不是 503**，并带 `Retry-After`。429 的语义是「你太快了」，503 是「我挂了」。前者能让规矩的客户端退避，后者往往触发上游熔断。

### Go 和 TypeScript

Go 直接用现成的，别自己写：

```go
import "github.com/go-kratos/aegis/ratelimit/bbr"

limiter := bbr.NewLimiter(bbr.WithCPUThreshold(800))   // 80%

func handler(w http.ResponseWriter, r *http.Request) {
    done, err := limiter.Allow()
    if err != nil {
        http.Error(w, "server busy", http.StatusTooManyRequests)
        return
    }
    defer done(ratelimit.DoneInfo{})
    // 干活
}
```

只想要静态阈值的话，标准库级别的选择是 `golang.org/x/time/rate`：

```go
lim := rate.NewLimiter(rate.Limit(1000), 200)   // 1000 QPS，突发 200
if !lim.Allow() {                                // 注意是 Allow() 不是 Wait()
    http.Error(w, "too many requests", 429)
    return
}
```

⚠️ **`Wait()` 是排队，`Allow()` 才是丢弃。** 同理，`uber-go/ratelimit`（4.7k stars）的 `Take()` **只会 sleep，永远不返回错误** —— 它是给「限制自己对下游的出流量」用的整形工具，不是保护自己的。别用错。

TypeScript（Node）没有 BBR 的成熟实现，自己数在飞的请求：

```ts
let inflight = 0;
const LIMIT = 100;

app.use((req, res, next) => {
  if (req.path === '/healthz') return next();
  if (inflight >= LIMIT) {
    res.set('Retry-After', '1').status(429).json({ error: 'server busy' });
    return;
  }
  inflight++;
  res.on('finish', () => inflight--);
  res.on('close',  () => inflight--);   // ← 客户端提前断开也要减，否则慢慢泄漏
  next();
});
```

那个 `res.on('close')` 是最容易漏的一行。客户端提前断开连接时 `finish` 不一定触发，计数只增不减，跑几个小时你的服务就"永远满载"了。

---

## 几条容易踩的

**1. 别在拒绝路径上做重活**

日志、埋点、生成堆栈、序列化详细错误对象 —— 过载时这些会变成压垮你的最后一根稻草。Sentinel 用预分配无堆栈异常，就是这个道理。拒绝时最多打个计数器。

**2. 限流器本身不能有锁竞争**

上面 Python 示例里的 `deque` 在 asyncio 单线程下是安全的。多线程（比如 gunicorn + 线程 worker）下需要换成原子操作或分片计数。Envoy 用的是无锁 CAS：

```cpp
while (current_outstanding < limit) {
    if (num_rq_outstanding_.compare_exchange_weak(current_outstanding, current_outstanding + 1, ...)) {
      return RequestForwardingAction::Forward;
    }
}
```

**3. 限流 ≠ 熔断 ≠ 排队**

这三个词经常被混着用，但做的是完全不同的事：

| | 干什么 | 代表 |
|---|---|---|
| **限流 / 丢弃** | 门口保安：「满了，明天请早」，**立刻拒绝** | Sentinel、`x/time/rate` 的 `Allow()`、uvicorn 503 |
| **熔断** | 供货商断货：连着 5 次进货失败，这周别再打电话了，**省得每次白等 30 秒超时** | pybreaker、Envoy circuit breaking |
| **排队 / 整形** | 叫号机：不拒绝任何人，**只是让你等** | aiolimiter、`uber-go/ratelimit`、`rate.Wait()` |

**排队不解决过载。** 队伍无限长的时候，等于所有人都超时，反而更糟（这就是第 00 篇讲的）。真正保命的是前两个。

**4. 拒绝之后的用户体验也要设计**

秒杀页面上「已抢完」是可接受的。API 返回一个空白 500 就不行。至少给：

- 明确的 429 状态码
- `Retry-After` 头
- 一个人能看懂的 message

**5. 客户端和服务端都要做**

服务端限流保护的是服务端。但如果客户端拿到 429 之后立刻重试，你只是把 1 次请求变成了 10 次。Google SRE 的客户端自适应节流就是干这个的 —— 这部分留到 [05](05-稳定超载的系统-扩容以及它救不了的情况.md) 详细讲。

---

## 一句话记住

> 产能是死的。你能选的只有「谁被拒绝」，不能选「有没有人被拒绝」。
> 快速失败是让这个选择变得便宜、可控、可观测。
