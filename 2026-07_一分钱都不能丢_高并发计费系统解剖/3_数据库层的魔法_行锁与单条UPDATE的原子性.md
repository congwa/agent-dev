# 第 3 章:数据库层的机制——行锁与单条 UPDATE 的原子性

> 第 2 章说"把算式交给数据库,由它排队"。本章回答两个刨根问题:
> **① `balance = balance - 3` 同样要先读再减,缝隙去哪了?**
> **② 数据库的行锁到底是怎么"加"上去的?**
> 以 PostgreSQL 为例(sub2api 使用的正是它)。本章偏原理,第一遍读不透可先跳到第 4 章,读完案例再回看。

---

## 3.1 缝隙没有消失,它被挪进了锁里

对比两种写法,关键差异在**"读"发生在哪一侧**:

```
应用层读-改-写(有缝):
  ① 应用 SELECT balance → 100        ← 读发生在应用侧
  ② 应用算 100 - 3 = 97               ← 缝隙在此,可能几毫秒,插得进人
  ③ 应用 UPDATE SET balance = 97      ← 写回一个"死值"

单条 UPDATE(无缝):
  应用只发一条 SQL,其中不含任何具体旧值
  数据库引擎执行时:锁行 → 锁内读 balance → 锁内算减法 → 锁内写回
  ← 读、算、写全部发生在同一行的锁保护之下
```

第一种写法里,`97` 是应用基于**可能已过期的快照**算出的死值,写回时无条件覆盖。
第二种写法里,SQL 文本是 `balance - 3` 这个**表达式**——它到达数据库时尚未求值,**求值时机是引擎已拿到该行的锁之后**。

> 缝隙没有被消灭,而是被压缩进"持锁期间"——持锁期间其他执行流进不来,缝里插不进任何人。
>
> 实用判据:**看写回的是表达式(`balance - $1`)还是应用算好的字面量(`97`)。前者安全,后者必有缝。**

## 3.2 逐帧:两个 UPDATE 撞在同一行

A 扣 3、B 扣 2,初始余额 100:

```
时刻  事务 A                             事务 B                       行状态
t1    UPDATE ... balance = balance - 3
      找到行,对该行加排他锁 ✓                                         100 [A持锁]
t2                                       UPDATE ... balance = balance - 2
                                         找到行,尝试加锁 → A 占着
                                         阻塞,排队等 ←←←              100 [B在等]
t3    锁内读 100 → 算 97 → 写新版本                                    97 [A持锁]
t4    COMMIT → 释放锁                                                  97
t5                                       被唤醒,拿到锁
                                         ★ 重新读最新值 = 97
                                           (不是它 t2 时看到的 100)
                                         算 97 - 2 = 95 → 写           95 [B持锁]
t6                                       COMMIT                        95 ✓
```

**t5 的"重新读最新值"是全部问题的答案。** B 被唤醒后,PostgreSQL 不会使用 B 排队前看到的旧快照,而是**基于 A 提交后的最新版本重新求值**——连 WHERE 条件也重新检查一遍。这个机制叫 **EvalPlanQual(EPQ 重验)**,是 READ COMMITTED 隔离级别下 UPDATE 的标准行为。

最终 100 - 3 - 2 = 95,分毫不差。无论多少并发,效果等价于全部串行执行。

### WHERE 里的守卫条件也在锁内重验

```sql
UPDATE users SET balance = balance - 3 WHERE id = 2 AND balance >= 3
```

余额 4 元,A、B 各扣 3 并发:

```
t1   A 锁行,验 WHERE: 4>=3 ✓,扣成 1,提交
t2   B 醒来拿锁,EPQ 用最新值重验 WHERE: 1>=3 ✗
     → 条件不满足 → 这条 UPDATE 影响 0 行
t3   B 的代码看到"影响 0 行",走余额不足的分支
```

B **不可能**基于旧值 4 通过检查、再把余额扣穿而不自知——**守卫和减法在同一把锁内,是一体的**。这条 SQL 等价于一个"条件版原子减法":满足谓词才减,判断与减之间无缝。

## 3.3 行锁的实现——没有锁表,锁写在行上

常见的想象是"内存里有张锁表,锁一行登记一条"。**PostgreSQL 不是这样。** 它的行锁直接写在**数据行自己的头部**——磁盘上那 23 字节的 tuple header 里。

### 行头结构

```
┌─────────┬─────────┬──────────────┬─────────┐
│  xmin   │  xmax   │  infomask    │  数据    │
│ 创建者   │ 删除者/  │  状态标志位   │ balance │
│ 事务ID   │ 锁持有者 │              │  =100   │
└─────────┴─────────┴──────────────┴─────────┘
```

- `xmin`:创建这行的事务 ID
- `xmax`:本义是"删除这行的事务 ID"——**被复用来当锁**:谁把自己的事务 ID 写进 xmax,谁就锁住了这行

**"加行锁"这个动作,物理上就是一次 `xmax = 当前事务ID` 的写入。** 没有中央登记处。

### 一条 UPDATE 穿过的四层锁

```
① 表级锁 ROW EXCLUSIVE(锁管理器内存中)
   含义:"要修改这张表的某些行"
   与其他 UPDATE 的同类锁完全兼容 → 并发 UPDATE 不在这层撞车,只挡 DDL

② 页级 buffer 锁(轻量锁,微秒级)
   只保护"读写这 8KB 内存页"的一瞬间

③ 行级:检查目标行的 xmax
   为空(或已完结的旧事务)→ 写入当前 xid ← ★ 这就是加行锁
   同时写一个新版本的行(MVCC:UPDATE 不原地改,而是造一个新 tuple)

④ 无需任何"保持锁"的动作
   xmax 会留在行上直到事务结束——释放锁也不需要回来擦除(见下)
```

### 撞锁的一方如何等待、如何唤醒

B(xid=1002)撞上 A(xid=1001)锁着的行:

```
t1   B 读行头,发现 xmax = 1001,且标志位显示"更新中"
t2   查询:事务 1001 还活着吗? → 活着 → 需要等
t3   ★ 等在哪里?不是等"行锁",而是——
     每个事务启动时都会给"自己的事务ID"加一把锁,提交/回滚时自动释放。
     B 尝试获取"事务1001"这把锁 → 必然阻塞
t4   A 提交 → A 的事务锁自动释放 → B 立刻被唤醒
t5   B 顺着旧行头的指针找到 A 写的新版本行(97)
     EPQ 重验 WHERE → 通过 → 把新版本行的 xmax 写成 1002 → 造自己的新版本(95)
```

精确表述:**PostgreSQL 里"等行锁"的实现是"等在持有者的事务锁上"**。这个间接一跳非常聪明——不管 A 锁了 100 万行,所有等待者都只等 A 那一把事务锁,A 提交的瞬间统一唤醒,无需逐行通知。

> 防插队细节:B 进入等待前会在锁管理器短暂登记一个真正的行级重量锁,用于给等待者排先来后到——否则 A 释放的瞬间,老等待者和新到请求一起哄抢,老等待者可能饿死。拿到行后这条登记立即删除,因此锁表里常驻的行锁记录始终≈0。

### 这样设计的两笔账

**内存账**:`UPDATE ... WHERE ...` 命中 500 万行时,若每个行锁都进内存锁表(每条几十字节),一条语句吃掉几百 MB。把锁摊到行头上,**锁 1 行和锁 5 亿行的内存成本相同:零增量**。(对比:MySQL InnoDB 的行锁在内存中,因此有锁内存的烦恼。)

**释放账**:提交时**不回头擦任何 xmax**,只在事务状态表(clog)里把 xid 标成"已提交"。后来者读到 xmax=1001 时自行查 clog:"1001 已完结?那这个锁标记是死的,视同不存在。"——**释放 100 万个行锁 = 写一个状态位,O(1)。**

代价:xmax 是磁盘上的字段,加锁 = 弄脏数据页 = 将来要刷盘。这是"锁在盘上换内存零成本"的交换。

## 3.4 三个重要推论

**① `SELECT ... FOR UPDATE` 用的是同一套机制。** 同样把 xid 写进 xmax,仅标志位不同。因此显式行锁和 UPDATE 的隐式行锁会互相阻塞——它们本来就是同一个东西。

**② 普通 SELECT 永远不碰锁。** MVCC 读走快照可见性判断(看 xmin/xmax 决定该行对当前快照是否可见),不获取任何行锁。因此**读不阻塞写、写不阻塞读,只有写和写才在行上排队**。B 更新期间,其他连接 SELECT 这行照样瞬间返回。

**③ 行锁持续到事务提交,不是语句结束。** xmax 一旦写上,要等 COMMIT 才失效。推论:**事务里 UPDATE 之后、COMMIT 之前的每一行代码,都在延长锁的持有时间**。这就是"事务内绝不夹网络调用"这条纪律的物理依据——夹一次 2 秒的 API 调用,同一用户的其他扣费就在 xmax 上睡 2 秒。

## 3.5 "所以底下还是锁?"——与应用层锁差三个量级

底下确实是锁。关键在**持有多久、锁内干什么**:

| | 应用层悲观锁 | 引擎内部行锁(单条 UPDATE) |
|---|---|---|
| 锁内做什么 | 网络往返、业务逻辑、甚至调上游 | 读一个值、一次减法、写一个值 |
| 持锁时长 | 毫秒~秒 | **微秒** |
| 死锁风险 | 有 | 单行单语句,几乎没有 |

同一用户的并发扣费确实在这一行上串行化了——但串行单元是微秒级的"读-减-写",单行每秒也能吞几千次;不同用户落在不同行,零竞争。

"扣费路径上没有锁"的准确表述是:**应用代码里没有显式锁,没有任何锁被跨语句、跨网络调用持有。锁被压缩到了物理下限,且锁内不做任何多余的事。**

## 3.6 同一原理的三个化身(呼应第 2 章)

"把读-改-写压进一个不可分割的执行单元",三层各有实现:

```
PostgreSQL:  单条 UPDATE          → 行锁 + EPQ 保证语句内原子
Redis:       Lua 脚本              → 单线程引擎,脚本执行期间不插入任何其他命令
Go 进程内:   atomic.AddInt64       → CPU 的 LOCK XADD 指令,硬件保证
```

原则统一:**不把"读"暴露给应用层。由持有串行化能力的那一层(引擎/单线程/CPU 指令)自己完成读-改-写;应用层只发"意图"(减 3),不发"结果"(=97)。**

---

## 本章要点

- `balance = balance - 3` 的缝隙被密封在引擎内部:先锁行,锁内读最新值、算、写;等待者醒来后**基于最新提交值重新求值**(EPQ),不用排队前的旧快照
- WHERE 守卫和 SET 在同一把锁内,"条件+减法"一体,无 TOCTOU
- 行锁的物理实现 = 把事务 ID 写进行头的 xmax;等锁 = 等在持有者的事务锁上;释放 = 提交时改一个状态位
- 行锁持续到 COMMIT → **事务内禁止夹慢操作**
- 读写互不阻塞(MVCC),只有写写排队,串行单元微秒级
