# 一分钱都不能丢：高并发计费系统解剖

> 几百个并发同时砸向同一行余额，如何做到不丢账、不重账、还能扛住？

> 本教程以开源项目 [Wei-Shaw/sub2api](https://github.com/Wei-Shaw/sub2api)(一个 AI API 网关,Go + PostgreSQL + Redis)为解剖对象,
> 系统讲解一个真实生产系统如何处理**扣款、账单、配额与并发竞争**。
> 面向没有并发编程经验的读者,每个知识点均回答两个问题:**为什么这样做?不这样做会发生什么?**

## 内容范围

- 并发场景下资金错乱的成因:丢失更新、TOCTOU、重复扣款、漏扣款
- 三种并发控制手段(锁 / CAS / 原子增量)及其选型顺序
- 数据库行锁与 MVCC 的物理机制(单条 UPDATE 为什么是原子的)
- 一个"不丢账、不重账、能扛高并发"的计费系统的完整设计
- 一批可直接复用的工程写法:幂等抢占、两段式扣费、RETURNING、WithoutCancel 等

## 选择 sub2api 作为标本的原因

sub2api 是一个把多个上游 AI 账号(Claude/OpenAI/Gemini/Grok)聚合成统一 API 出售的网关,天然集齐了计费系统的全部难题:

- **费用无法预知**——AI 按 token 计费,请求结束前不知道花多少钱
- **高并发热点行**——单个用户可能开几百并发,全部落在同一行余额上
- **一次性资源**——OAuth refresh token 用一次即作废,写错一次账号即报废
- **异步不可靠**——计费在后台执行,重试/重启/断线都会制造重复或丢失
- **多级缓存**——DB 是真账,Redis 是抄本,两本账必须能对上

此外,该项目的代码注释诚实记录了每个取舍(包括有意保留的漏洞),是少见的教学级标本。

## 全书主线

> 并发 bug 的万恶之源是"**基于过期的认知做写入**"。
> 所有解法——锁、CAS、原子增量、唯一约束——都是在用不同的成本回答同一个问题:
> **如何保证写入的那一刻,依据的是最新的认知。**
