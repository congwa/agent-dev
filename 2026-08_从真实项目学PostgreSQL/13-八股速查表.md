## 一、MVCC 与事务

**Q：Postgres 的 MVCC 和 MySQL InnoDB 有什么本质区别？**

Postgres 把**所有行版本都存在表里**（堆），UPDATE 产生新版本、旧版本变成死元组，需要 VACUUM 回收。InnoDB 是**原地更新 + undo log**，旧版本在 undo 段里。

代价的分配不同：Postgres 的痛点是**表膨胀 + 必须 VACUUM**，且二级索引存物理位置（ctid）所以行一挪索引就得改（除非 HOT）；InnoDB 的痛点是**回滚成本高 + 长事务导致 undo 链变长读放大**，二级索引存主键所以行挪了索引不用动。→ 第 1、2 篇

---

**Q：`xmin`、`xmax`、`ctid` 分别是什么？**

- `xmin`：创建这个行版本的事务号
- `xmax`：让这个版本失效的事务号（0 = 仍有效）
- `ctid`：物理地址 `(页号, 槽位号)`；旧版本的 `t_ctid` 指向新版本，形成版本链

实测能直接看到（第 1 篇）：

```
 lp | t_ctid | t_xmin | t_xmax
  1 | (0,2)  |   1054 |   1055     ← 逻辑上只有 1 行，物理上有 3 个版本
  2 | (0,3)  |   1055 |   1056
  3 | (0,3)  |   1056 |      0
```

---

**Q：快照是什么？READ COMMITTED 和 REPEATABLE READ 的区别在哪？**

快照 = `xmin:xmax:活跃事务列表`，定义"在我眼里哪些事务算已完成"。

**唯一区别是取快照的时机**：RC 每条语句取一个新快照，RR 整个事务共用第一条语句时取的快照。→ 第 2 篇

---

**Q：Postgres 有几个隔离级别？**

**三个**。`READ UNCOMMITTED` 被当作 `READ COMMITTED` 处理——因为 MVCC 的可见性判断要求"xmin 已提交"，**脏读在 Postgres 里物理上不可能发生**。

实测（第 4 篇）：

| | 不可重复读 | 幻读 | 写偏斜 |
|---|---|---|---|
| READ COMMITTED | 出现 | 出现 | 出现 |
| REPEATABLE READ | 没有 | **没有** | 出现 |
| SERIALIZABLE | 没有 | 没有 | 没有 |

⚠️ **Postgres 的 RR 顺便解决了幻读**，比 SQL 标准要求的强（因为用的是快照，不是间隙锁）。

---

**Q：什么是写偏斜？为什么 RR 挡不住？**

两个事务**读同一批数据、写不同的行**，各自都对，合起来违反跨行不变量。

RR 挡不住是因为它们没有更新同一行，快照机制根本没有介入的机会。

实测（第 4 篇，两张卡余额之和不能为负，各扣 150）：

```
READ COMMITTED   -> 两卡总额 -100  ❌
REPEATABLE READ  -> 两卡总额 -100  ❌
SERIALIZABLE     -> 一个事务被中止，总额 50  ✅
```

**✅ 最实用的解法不是 SERIALIZABLE，是反范式加一个汇总行，把跨行约束变成单行约束。**

---

**Q：SERIALIZABLE 的实现原理和代价？**

**SSI（可串行化快照隔离）**：照常用快照跑（读不阻塞），但记录读写依赖，提交时检测"危险结构"，发现就中止一个。

代价是冲突率随并发超线性增长。实测（第 4 篇）：

```
   2 并发: 重试率 46%
   4 并发: 重试率 65%
   8 并发: 重试率 75%
  16 并发: 重试率 89%
```

**用 SERIALIZABLE 必须配套重试循环，且必须把 `Commit()` 包进去**（40001 常常在提交时才抛）。

## 二、并发写正确性（核心）

**Q：`UPDATE t SET balance = balance - $1 WHERE id = $2 AND balance >= $1` 为什么是原子的？**

三层保证：

1. **读和写在同一条语句里**——`balance - $1` 中的 `balance` 是数据库执行时读的，不是应用传的过期值；
2. **同一把行锁**贯穿整个语句；
3. **EvalPlanQual**：等锁结束后，Postgres 会取**最新已提交版本**重新计算 `WHERE`，条件不满足就放弃这一行（返回 0 行）。

⚠️ **前提：条件必须写在 WHERE 里。** 实测（第 3 篇）：

```
[1] WHERE 里带 balance>=80    → 0 行，余额 50    ✅ 正确拒绝
[2] WHERE 里没带              → 1 行，余额 -30   ❌ 透支
```

---

**Q：什么是丢失更新？怎么复现？**

`SELECT` 读出来、应用算好新值、`UPDATE` 整行写回。两个事务读到同一个旧值，后写的覆盖先写的。

实测（第 3 篇，初始 1000，20 线程共扣 100 次）：

```
读-改-写            → 992   ❌ 丢了 8 次
SELECT FOR UPDATE   → 900   ✅
UPDATE SET c = c-1  → 900   ✅
```

---

**Q：`SELECT FOR UPDATE` 和原子 UPDATE 怎么选？**

都对，但性能差一倍。实测（第 3 篇，16 并发打同一行，1600 次扣款）：

```
[A] 单条原子 UPDATE            0.77s  (2084 次/秒)
[B] SELECT FOR UPDATE + UPDATE 1.49s  (1076 次/秒)
[C] SERIALIZABLE + 重试        5.71s  ( 280 次/秒)
```

B 慢的原因：两次往返 + 显式事务，**行锁从 SELECT 一直持有到 COMMIT**。

📌 **能用一条 UPDATE 表达的，绝不拆成 SELECT + UPDATE。**

---

**Q：为什么"先 SELECT 查重，再 INSERT"在并发下必然失败？**

未提交的 INSERT 对别的事务**不可见**。N 个并发事务的 SELECT 全都看到"没有"，全都往下走。

实测（第 4 篇，8 个并发，用 Barrier 保证同时完成查重）：

```
[B1] 有唯一索引    → 被数据库挡下 7 个，只扣一次   ✅
[B2] 无唯一索引    → 8 个全通过，重复扣款 8 次     ❌
```

注意 B1 里应用层的 SELECT **一次都没起作用**，全靠唯一索引拦住。

---

**Q：`ON CONFLICT DO NOTHING` 比捕获 duplicate key 异常好在哪？**

捕获异常会让**整个事务进入 aborted 状态**，后续语句全报 `current transaction is aborted`，必须用 SAVEPOINT 才能继续。`ON CONFLICT` 不会。

在"幂等键 + 副作用同事务"的设计里，这个区别是决定性的。→ 第 6 篇

---

**Q：唯一索引和 NULL 的坑？**

`NULL != NULL`，所以 `UNIQUE(email, deleted_at)` **完全挡不住**软删除表里的重复邮箱。

```sql
-- ✅ 部分唯一索引
CREATE UNIQUE INDEX ON users(email) WHERE deleted_at IS NULL;
-- ✅ 或者 PG 15+
CREATE UNIQUE INDEX ON users(email, deleted_at) NULLS NOT DISTINCT;
```

## 三、锁

**Q：Postgres 有哪几种行锁？**

`FOR UPDATE` > `FOR NO KEY UPDATE` > `FOR SHARE` > `FOR KEY SHARE`。

实测冲突矩阵（第 5 篇）：关键是 **`FOR KEY SHARE`（外键检查加的）不阻塞 `FOR NO KEY UPDATE`（普通 UPDATE）**，所以 PG 9.3+ 上**外键不会阻塞父表普通列的更新**。

---

**Q：死锁怎么产生，怎么根治？**

加锁顺序不一致。实测（第 5 篇）：

```
T1 按 1→2，T2 按 2→1  → deadlock detected
两边都按 id 升序        → 都成功
```

**根治只有一个办法：全局统一加锁顺序（通常按主键升序）。** 外加 `40P01` 重试和 `lock_timeout` 兜底。

---

**Q：为什么一次 `ALTER TABLE` 能让整张表停摆？**

**Postgres 的锁队列是 FIFO 的。** 一个拿不到锁的强锁请求会堵在队首，**后面所有本来无冲突的请求也得排队**。

实测（第 5 篇）：一个长查询 → ALTER 排队 → 一条本该 1ms 的 SELECT 被连坐 1.5 秒。真实场景是几分钟，然后连接池打满，全站不可用。

**✅ 解法：`SET LOCAL lock_timeout = '5s'`，抢不到就退出重来。**

---

**Q：advisory lock 是什么？有什么坑？**

锁一个 64 位整数，不关联任何表，语义自定义。典型用途：定时任务防重复、迁移互斥。

三个坑：

1. **连接池传染**：会话级锁不释放，连接还回池里，下一个人莫名持有它 → **优先用 `pg_advisory_xact_lock`（事务级，自动释放）**；
2. `hashtext()` 会碰撞；
3. **不写 WAL、不复制**，failover 后全部消失 → **不能当分布式锁用，不能靠它保证"钱只扣一次"**。

→ 第 5 篇

---

**Q：`SKIP LOCKED` 解决什么问题？**

多个 worker 从同一张表抢任务时不互相阻塞。实测（第 7 篇，8 worker 抢 64 个任务）：

```
[A] FOR UPDATE SKIP LOCKED   0.44s   重复执行 0 次
[B] FOR UPDATE               3.31s   重复执行 0 次     ← 并发度退化为 1
[C] 不加行锁                 3.48s   重复执行 161 次   ❌
```

## 四、索引

**Q：复合索引的列顺序怎么定？**

**等值列在前，范围列在后。** 范围条件之后的列全部失效。

实测（第 8 篇，同一条查询）：

```
(user_id, created_at)  → 0.078 ms
(created_at, user_id)  → 4.101 ms     ← 反了，慢 50 倍
```

完整规则：等值列 → 范围列 → 只用于 ORDER BY 的列 → `INCLUDE` 只输出的列。

---

**Q：什么是覆盖索引 / Index Only Scan？它的隐藏依赖是什么？**

`INCLUDE (col)` 把额外的列塞进索引，查询不用回表。

**隐藏依赖：可见性映射表（VM），而 VM 是 VACUUM 维护的。** 索引项里没有 xmin/xmax，只有当目标页被标记"全可见"时才能跳过回表。

**看到 `Index Only Scan` 但 `Heap Fetches` 很大 = 这张表该 VACUUM 了。** → 第 8 篇

---

**Q：部分索引有多大收益？**

**收益 ≈ 被排除的行的比例。** 实测（第 7、8 篇）：

```
队列表（排除 99.99%）:  全量索引 56 MB  vs  部分索引 48 kB    ← 1200 倍
软删除（排除 2%）:      30 MB  vs  30 MB                      ← 没差别
```

但软删除场景仍然值得加——因为**部分唯一索引是不可替代的**（NULL 问题）。

---

**Q：哪些写法会让索引失效？**

实测数据（第 8 篇，50 万行）：

| 写法 | 失效原因 | 解法 | 效果 |
|---|---|---|---|
| `WHERE lower(email) = ?` | 列上套函数 | 表达式索引 | 124.7ms → 0.048ms |
| `WHERE id::text = ?` | 列被隐式转换 | 改成常量侧转换 | — |
| `WHERE email LIKE 'abc%'` | 非 C collation | `text_pattern_ops` | 40.9ms → 3.2ms |
| `WHERE email LIKE '%abc%'` | B-tree 没有起点 | `pg_trgm` GIN | 47.9ms → 18.1ms |
| 匹配 25% 的行 | 选择性太差 | **索引救不了** | 86ms → 58ms（只快 1.5x）|

---

**Q：GIN、BRIN、B-tree 怎么选？**

- **B-tree**：99% 的场景
- **GIN**：一个字段里有多个可检索值（JSONB `@>`、数组、全文、trgm）
- **BRIN**：物理顺序和列值顺序天然一致的超大表（追加写的时间列）。实测 100 万行：**BRIN 24 kB vs B-tree 30 MB**

---

**Q：怎么找出该删的索引？**

```sql
SELECT s.indexrelname, pg_size_pretty(pg_relation_size(s.indexrelid)), s.idx_scan
FROM pg_stat_user_indexes s JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0 AND NOT i.indisunique AND NOT i.indisprimary
ORDER BY pg_relation_size(s.indexrelid) DESC;
```

⚠️ 统计从上次 `pg_stat_reset()` 开始累计，要确认周期够长；**别删唯一索引**（它在做约束）。

## 五、VACUUM 与膨胀

**Q：VACUUM 和 VACUUM FULL 的区别？**

| | VACUUM | VACUUM FULL |
|---|---|---|
| 空间 | 标记可复用，**文件不缩小** | 真正释放 |
| 锁 | ShareUpdateExclusive（不阻塞读写） | **AccessExclusive（阻塞一切）** |
| 额外磁盘 | 不需要 | 需要一份完整副本 |

**生产上用 `pg_repack`，不用 `VACUUM FULL`。** 索引膨胀用 `REINDEX CONCURRENTLY`。

实测（第 9 篇）：5 轮全表 UPDATE 后表从 27MB → 162MB，VACUUM 后仍是 162MB，VACUUM FULL 后回到 27MB。

---

**Q：什么会拖住 VACUUM？**

实测（第 9 篇）：

```
READ COMMITTED  只读的空闲事务   → 不拖
READ COMMITTED  写过数据的空闲事务 → 拖（持有 XID）
REPEATABLE READ 哪怕全程只读     → 拖（持有快照）
```

四个嫌疑人：**长事务 / idle in transaction、未消费的复制槽、残留的 prepared transaction、autovacuum 参数太保守。**

⚠️ 回收水位线是**全局的**——一个连接卡住，全库所有表都回收不了。

---

**Q：什么是 HOT？什么时候失效？**

UPDATE 时如果**没改任何被非摘要索引（B-tree/GiST/GIN/hash）引用的列**且**新版本能塞进同一页**，就不动任何索引。（PG 16 起，只被 BRIN 覆盖的列被改仍可走 HOT。）

实测（第 2 篇，同一张表 UPDATE 5000 次）：

```
balance 上无索引: HOT 比例 99.5%,  主键索引 16 kB
balance 上有索引: HOT 比例  0%,    主键索引 56 kB（+ 额外 128 kB 的新索引）
```

📌 **给高频更新的列建索引，代价是三重的**：HOT 归零、新索引膨胀、主键索引也跟着膨胀。

---

**Q：事务号回卷是什么？为什么可怕？**

XID 是 32 位，可见范围是前后各 2³¹ ≈ 21.47 亿。太老的行版本会从"可见"翻转成"来自未来所以不可见"——**数据凭空消失**。

VACUUM 的 freeze 负责防止它。失控的后果：

```
2 亿代：           autovacuum 强制全表 freeze（autovacuum_freeze_max_age）
16 亿代：          进入紧急模式，跳过索引清理、不限速（PG14+ vacuum_failsafe_age）
剩 4000 万个事务： 日志开始刷 WARNING: must be vacuumed within N transactions
剩  300 万个事务： 数据库【拒绝分配新事务号】，必须停服进单用户模式修复
```

监控：`SELECT datname, age(datfrozenxid) FROM pg_database;`

---

**Q：为什么 `count(*)` 慢？**

MVCC 下不同事务看到的行数不同，**不存在全局行数**可以维护，必须逐行做可见性判断。

实测（第 9 篇，300 万行）：`count(*)` 0.09~0.16s vs `reltuples` 估算 0.0008s。

分页别用 `OFFSET`（代价随页数线性增长），用游标分页 `WHERE id < $last ORDER BY id DESC LIMIT n`。

---

**Q：什么是 TOAST？为什么"别写 SELECT *"？**

一行不能跨 8KB 页，超过约 2KB 的字段会被压缩、切片存到影子表。

实测（第 9 篇）：主表 296 kB，TOAST 表 39 MB。

```
SELECT count(small)     → 37 个 buffer,    0.876 ms
SELECT sum(length(big)) → 15060 个 buffer, 102.839 ms    ← 117 倍
```

**"别写 SELECT \*"的真正理由在 TOAST，不是"多传几个字段"。**

顺带：查磁盘占用要用 `pg_total_relation_size`，TOAST 藏在里面。

## 六、连接与配置

**Q：连接池该配多大？**

`CPU 核数 × 2 ~ 4`。实测（第 10 篇，2 核机器）：

```
   2 个连接: 5121 查询/秒   ← 峰值
  64 个连接: 2929 查询/秒   ← 比峰值低 43%
```

**宁可让应用排队，不要让数据库过载。**

建连接的成本：**5.38ms vs 复用连接的 0.106ms，51 倍**（还是本机 unix socket）。

---

**Q：Postgres 有哪三个默认为 0（无限）的关键超时？**

```
statement_timeout                     → 单条语句最长执行时间
lock_timeout                          → 等锁最长时间
idle_in_transaction_session_timeout   → 事务开着但不执行语句的最长时间
```

**这三个不配，等于给数据库拆了保险丝。**

```sql
ALTER DATABASE mydb SET statement_timeout = '60s';
ALTER DATABASE mydb SET lock_timeout = '10s';
ALTER DATABASE mydb SET idle_in_transaction_session_timeout = '60s';
```

---

**Q：PgBouncer 的 transaction 模式下不能用什么？**

`SET`（不带 LOCAL）、**会话级 advisory lock**、`LISTEN/NOTIFY`、临时表、`WITH HOLD` 游标、SQL 形式的 `PREPARE`/`DEALLOCATE`。

⚠️ 协议级的**服务端预备语句从 PgBouncer 1.21 起已经支持**（需设 `max_prepared_statements`），旧版本才需要在驱动层关掉。

症状是**低频随机报错**，极难排查。→ 第 10 篇

---

**Q：SSD 上必须改的一个参数？**

`random_page_cost`：默认 4.0（给机械盘的），SSD 上应设 **1.1**。

不改的后果：优化器系统性低估索引扫描的价值，表现为"我明明建了索引，为什么走全表扫描"。

---

**Q：`work_mem` 为什么危险？**

它是**每个排序/哈希节点**的上限，不是每连接一份。

```
最坏内存 ≈ 连接数 × 每查询节点数 × (并行 worker + 1) × work_mem
```

100 连接 × 5 节点 × 64MB = 32 GB（还没算并行）。另外哈希类节点的上限是 `work_mem × hash_mem_multiplier`（默认 2.0）。

**全局设小（16~32MB），需要时 `SET LOCAL` 调大。**

## 七、DDL 与迁移

**Q：在线 DDL 的核心原则？**

**风险 = 锁级别 × 持有时长。** 全部技巧是把"长时间的强锁"拆成"瞬间的强锁 + 长时间的弱锁"。

实测（第 11 篇，521 MB 表）：

```
ADD CHECK（AccessExclusiveLock 全程）        1.50s  阻塞一切
ADD CHECK NOT VALID + VALIDATE CONSTRAINT   1.26s  几乎不阻塞
```

```
CREATE INDEX             业务 UPDATE 最长被卡 2115 ms
CREATE INDEX CONCURRENTLY 业务 UPDATE 最长被卡  183 ms
```

---

**Q：哪些 ALTER 会重写全表？**

实测（第 11 篇，200 万行）：

```
ADD COLUMN（无默认值 / 常量默认值）           0.00s  ✅ PG11+
ADD COLUMN DEFAULT gen_random_uuid()        8.45s  ❌ 易变函数必须重写
ALTER COLUMN TYPE int→bigint                3.87s  ❌
RENAME COLUMN / DROP COLUMN                 0.00s  ✅ 只改元数据
```

---

**Q：什么是扩展-收缩（expand-contract）模式？**

滚动发布时新旧版本代码共存，所以破坏性变更要拆成 3 次发布：

```
扩展: 加新结构，代码同时读写新旧
迁移: 回填数据，代码切到新结构
收缩: 删旧结构
```

判断标准：**"这个迁移跑完后，应用回滚到上个版本还能工作吗？"** 不能 → 需要拆。

---

**Q：批量数据迁移怎么做？**

**分批 + 每批独立事务 + 每批之间 sleep。**

`UPDATE big_table SET x = y`（1 亿行）的后果：几十分钟的锁 + 表膨胀一倍 + WAL 洪流 + 自己就是那个拖住 VACUUM 的长事务 + 超时后全部回滚白干。

## 八、幂等与队列

**Q：幂等的正确实现？**

```sql
BEGIN;
  INSERT INTO dedup(request_id, api_key_id, fingerprint)
  VALUES (...) ON CONFLICT (request_id, api_key_id) DO NOTHING
  RETURNING id;                  -- 0 行 = 重放，直接返回
  -- 抢到了才执行副作用
  UPDATE users SET balance = balance - $1 WHERE ...;
  INSERT INTO usage_logs ...;
COMMIT;                          -- 幂等键和副作用【原子提交】
```

四个要点：**唯一索引兜底**、**幂等键和副作用同事务**、**带内容指纹防同 ID 不同内容的重放攻击**、**幂等表要窄 + 归档 + BRIN**。→ 第 6 篇

---

**Q：outbox 模式解决什么？**

双写问题：改数据库和发消息没有共同的事务。把"要发的消息"也写进数据库的同一个事务，再由独立 worker 投递。

**保证 at-least-once，不保证 exactly-once → 所以消费端必须幂等。幂等 + at-least-once = 事实上的 exactly-once。**

---

**Q：为什么不能用自增 id 当消费水位线？**

**序列号是非事务的。** id 在 INSERT 时分配，不是 COMMIT 时。慢事务可能持有小 id 却在很多大 id 之后才提交。

实测（第 6 篇）：

```
慢事务拿到 id=1（未提交）→ 快事务拿到 id=2 并提交
→ 消费者看到 [(2,...)]，把水位线推进到 2
→ 慢事务提交，id=1 出现，但【永远不会被消费】
```

解法：加宽限期（`created_at < NOW() - 10s`）、或者用 `WHERE processed_at IS NULL` 而不是水位线。

顺带：**序列不回滚**，ROLLBACK 也消耗序列号，所以 `bigserial` 主键必有空洞，不能当业务编号用。

---

**Q：任务队列的完整要素？**

```
FOR UPDATE SKIP LOCKED       worker 之间不阻塞
CTE + UPDATE + RETURNING     一次往返完成领取
claimed_at 租约               worker 崩溃后能被重领
available_at + 指数退避       延迟/定时/重试三合一
部分索引 WHERE state='available'   索引大小 = 队列实际长度（48kB vs 56MB）
分批删除 / 分区 DROP          清理不影响线上
LISTEN/NOTIFY + 轮询兜底      低延迟 + 不丢
任务本身幂等                  兜住所有 at-least-once 场景
```

## 九、类型

**Q：钱为什么不能用 float？**

实测（第 12 篇）：从 100 扣 1000 次 0.01 → `float8` 得到 `89.99999999999488`，`numeric` 得到 `90.000000`。

⚠️ numeric 也有坑：`numeric(20,2)` 扣 `0.004` 会四舍五入成 0——**AI 按 token 计费至少要 `numeric(20,6)`**。

---

**Q：`timestamp` vs `timestamptz`？**

**同样 8 字节**，`timestamptz` 存绝对时刻并自动做时区换算，`timestamp` 存一串没有时区含义的数字。

**没有任何理由用 `timestamp`。**

---

**Q：UUID 做主键有什么代价？**

实测（第 12 篇，各插 100 万行）：

```
bigserial:  插入 3.17s   主键索引 21 MB   叶页密度 90.06%
uuid v4:    插入 7.91s   主键索引 39 MB   叶页密度 69.92%
```

**慢 2.5 倍，索引大 86%。** 原因是随机键破坏 B-tree 的插入局部性，页分裂后各占一半。

需要分布式生成 → 用 **UUID v7**（时间有序）。需要防遍历 → 内部 bigint + 外部单独的 public_id。

---

**Q：列顺序会影响表大小吗？**

会。实测（第 12 篇，30 万行）：

```
小列穿插大列 (bool,bigint,bool,bigint,bool,bigint): 22 MB
大列在前小列在后 (bigint,bigint,bigint,bool,bool,bool): 17 MB    ← 省 23%
```

原因是内存对齐填充。**按对齐宽度从大到小排列。**

## 十、写代码时的 checklist

```
□ 条件更新有没有把业务约束写进 WHERE？（不是写在应用代码里）
□ 有没有把 SELECT + UPDATE 拆开？能不能合成一条？
□ 会被重复投递的操作有没有幂等键 + 唯一索引？
□ 幂等键和副作用在同一个事务里吗？
□ 事务里有没有网络 I/O？（HTTP、Redis、RPC）→ 一律挪出去
□ 多行加锁的顺序统一了吗？（按主键升序）
□ 用了 RR/SERIALIZABLE 的话，40001 重试写了吗？包含 Commit 了吗？有退避吗？
□ 新加的索引：列顺序对吗？能用部分索引吗？会不会破坏 HOT？
□ 新加的查询：EXPLAIN (ANALYZE, BUFFERS) 看过吗？
□ 迁移脚本：幂等吗？CONCURRENTLY 了吗？NOT VALID 了吗？lock_timeout 了吗？
□ 应用回滚到上个版本后，这个 schema 还能用吗？
□ 批量数据变更分批了吗？每批独立事务吗？
□ 金额用 numeric 且标度够吗？时间用 timestamptz 吗？
□ 大字段会不会触发 TOAST？查询有没有写 SELECT *？
□ 连接池大小 × 实例数 < max_connections × 0.8 吗？
□ statement_timeout / lock_timeout / idle_in_transaction_session_timeout 配了吗？
```

## 十一、必备的排查 SQL（背下来）

```sql
-- 谁在等锁，被谁堵着
SELECT pid, state, wait_event_type, pg_blocking_pids(pid), left(query,60)
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- 最长的事务（长事务是万恶之源）
SELECT pid, now()-xact_start AS age, state, left(query,80)
FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 10;

-- 回收水位线被钉住多远
SELECT max(age(backend_xmin)) FROM pg_stat_activity WHERE backend_xmin IS NOT NULL;

-- 死元组最多的表
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

-- 最耗时的查询（按【总耗时】排序，不是平均）
SELECT round(total_exec_time::numeric,1), calls, round(mean_exec_time::numeric,2), left(query,80)
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;

-- 复制槽积压（会撑爆磁盘 + 拖住 VACUUM）
SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
FROM pg_replication_slots;

-- 事务号年龄（接近 15 亿要紧急处理）
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;

-- 最大的表（含 TOAST 和索引）
SELECT relname, pg_size_pretty(pg_total_relation_size(relid))
FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 10;

-- 从没被用过的索引
SELECT s.indexrelname, pg_size_pretty(pg_relation_size(s.indexrelid)), s.idx_scan
FROM pg_stat_user_indexes s JOIN pg_index i ON i.indexrelid=s.indexrelid
WHERE s.idx_scan=0 AND NOT i.indisunique AND NOT i.indisprimary
ORDER BY pg_relation_size(s.indexrelid) DESC;
```

## 十二、如果只记住十句话

1. **UPDATE 不改原地，它写新版本。** 所有膨胀、VACUUM、HOT、索引问题都由此派生。
2. **`UPDATE ... SET c = c - $1 WHERE ... AND c >= $1` 是原子的**，靠的是行锁 + EvalPlanQual 重新验证 WHERE。
3. **业务约束必须写在 WHERE 里**，写在应用代码里的判断数据库帮不了你。
4. **数据库约束（唯一索引、CHECK）是唯一可靠的兜底**，应用层"先查再插"在并发下必然漏。
5. **长事务是头号杀手**：钉住回收水位线 → 全库膨胀 → 变慢 → 连接堆积 → 不可用。
6. **锁队列是 FIFO 的**：一个拿不到锁的 DDL 会把整张表堵死，所以必须配 `lock_timeout`。
7. **索引是有序结构**：等值列在前、范围列在后、能覆盖就 INCLUDE、能部分就 WHERE。
8. **在线 DDL 的全部技巧**是把"长时间的强锁"拆成"瞬间的强锁 + 长时间的弱锁"（`CONCURRENTLY` / `NOT VALID`）。
9. **幂等 + at-least-once = 事实上的 exactly-once**，两个缺一不可。
10. **Postgres 的默认超时全是无限**，`statement_timeout` / `lock_timeout` / `idle_in_transaction_session_timeout` 不配等于拆保险丝。
