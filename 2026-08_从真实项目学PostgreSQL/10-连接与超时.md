# 第 10 篇 · 连接、连接池、超时三件套

> 这一篇讲的东西不涉及任何"高级特性"，但它是**生产事故里出现频率最高的一类问题**。

---

## 一、Postgres 的连接很贵

第 1 篇提过：**一个连接 = 一个操作系统进程**（postmaster fork 出来的 backend）。

实测（`labs/exp24_conn.py`，本机 unix socket）：

```
  每次「新建连接 + 一条 SELECT 1 + 关闭」: 5.38 ms
  复用连接，每条 SELECT 1:                 0.106 ms
  → 建连接的固定开销约是一次简单查询的 51 倍
```

**51 倍**——而且这还是本机 unix socket。跨网络还要加上 TCP 握手、TLS 握手、认证往返，通常是 20~100 ms。

**❌ 每次请求都新建连接会怎样**：一个本来 5ms 的接口变成 50ms，而且 QPS 一高，postmaster 的 fork 就成了瓶颈，CPU 全花在创建进程上。

---

## 二、连接数不是越多越好（这是反直觉的部分）

实测（同一台机器，**2 核 CPU**，每个查询是一次轻量 CPU 计算）：

```
   1 个并发连接:    2526 查询/秒
   2 个并发连接:    5121 查询/秒     ← 峰值
   4 个并发连接:    4460 查询/秒
   8 个并发连接:    4788 查询/秒
  16 个并发连接:    4345 查询/秒
  32 个并发连接:    3167 查询/秒
  64 个并发连接:    2929 查询/秒     ← 比峰值低 43%
```

**吞吐在核数附近达到峰值，之后单调下降。** 64 个连接的吞吐比 2 个连接还低 43%。

原因：

1. **CPU 就那么多核**。32 个进程抢 2 个核，只是在做上下文切换；
2. **每个 backend 都有私有内存**（`work_mem` 是**每个排序/哈希节点**分配的，不是每连接一份——一个复杂查询可能同时用好几份）；
3. **锁竞争、LWLock 争用**随连接数上升；
4. **缓存局部性变差**。

### ❓ 问题：连接池该配多大？

**✅ 经验公式**（来自 PgBouncer/HikariCP 社区的长期实践）：

```
连接数 ≈ CPU核数 × 2 + 有效磁盘轴数
```

对现代 SSD 服务器，通常就是 **CPU 核数 × 2 ~ 4**。一台 16 核的机器，**32~64 个连接**通常就是最优，而不是 500。

然后倒推每个应用实例的池大小：

```
单实例 MaxOpenConns = 数据库总连接预算 / 应用实例数
```

sub2api 的默认配置是 `database.max_open_conns = 256`（`internal/config/config.go`），并且做了校验：

```go
if c.Database.MaxOpenConns <= 0 {
    return fmt.Errorf("database.max_open_conns must be positive")
}
if c.Database.MaxIdleConns > c.Database.MaxOpenConns {
    return fmt.Errorf("database.max_idle_conns cannot exceed database.max_open_conns")
}
```

**⚠️ 但 256 是"单实例上限"，不是推荐值。** 如果你部署 10 个副本，那就是 2560 个连接——远超任何单机 Postgres 的承受能力。**多副本部署时必须往下调，或者中间加 PgBouncer。**

**❌ 池子配太大会怎样**：

- 数据库端 `max_connections` 被打满 → `FATAL: sorry, too many clients already`（实测见第 1 篇）；
- 即使没打满，吞吐也会下降（上面的曲线）；
- 内存被 N 个 backend 的私有内存吃光 → OOM Killer 干掉 postmaster → **整个数据库重启**。

**❌ 池子配太小会怎样**：应用侧大量 goroutine 卡在等连接上，接口 P99 飙升。但这个问题**比池子太大好得多**——它是可观测的（应用侧的等待时间），而且不会搞垮数据库。

📌 **原则：宁可让应用排队，不要让数据库过载。**

## 三、连接的生命周期：三个容易忽略的参数

sub2api 的 `db_pool.go`：

```go
db.SetMaxOpenConns(settings.MaxOpenConns)
db.SetMaxIdleConns(settings.MaxIdleConns)
db.SetConnMaxLifetime(settings.ConnMaxLifetime)   // 默认 30 分钟
db.SetConnMaxIdleTime(settings.ConnMaxIdleTime)   // 默认 5 分钟
```

文件开头的包注释解释了**为什么要设 lifetime**，这段话信息量很大：

```go
// DB pool lifetimes are clamped here because lib/pq starts watchCancel
// goroutines for context-aware queries. If a cloud proxy silently drops idle
// TCP without RST/FIN, those goroutines can block in Read until database/sql
// retires the connection.
```

翻译：**云上的负载均衡器/NAT 网关会静默丢弃空闲 TCP 连接，不发 RST 也不发 FIN。** 客户端不知道连接已经死了，下次用它时会卡住，直到 TCP 超时（可能是几分钟到十几分钟）。

**这是云环境部署数据库应用的头号玄学问题**，表现为"服务跑一晚上，早上第一个请求超时"。

**✅ 三层防御**：

| 参数 | 建议值 | 作用 |
|---|---|---|
| `SetConnMaxLifetime` | 30 分钟（**必须短于 LB 的空闲超时**） | 主动退休老连接，绕开静默断连 |
| `SetConnMaxIdleTime` | 5 分钟 | 空闲连接自动关闭，释放数据库资源 |
| TCP keepalive | 60 秒 | 让 OS 层探测死连接 |

```
# 连接串里加
postgres://...?connect_timeout=5&keepalives=1&keepalives_idle=60&keepalives_interval=10&keepalives_count=3
```

⚠️ **云负载均衡器的默认空闲超时通常是 350 秒（AWS NLB）或 4 分钟**。`ConnMaxLifetime` 和 `ConnMaxIdleTime` 都要设得比它短。

## 四、超时三件套（默认值全是"无限"）

这是 Postgres 少数几个**默认值不适合生产**的地方：

```sql
SHOW statement_timeout;                      -- 0  （无限）
SHOW lock_timeout;                           -- 0  （无限）
SHOW idle_in_transaction_session_timeout;    -- 0  （无限）
```

实测确认（`labs/exp12_conn.py`）：

```
  max_connections                        = 100
  statement_timeout                      = 0
  lock_timeout                           = 0
  idle_in_transaction_session_timeout    = 0
  deadlock_timeout                       = 1s
  default_transaction_isolation          = read committed
```

### 各管什么

| 参数 | 管什么 | 不设的后果 |
|---|---|---|
| `statement_timeout` | **单条语句**的最长执行时间 | 一条写错的查询能跑几小时，占着连接、占着快照、拖住 VACUUM |
| `lock_timeout` | **等锁**的最长时间 | DDL 排队把整张表堵死（第 5 篇实测：连坐 1.5s，真实场景是几分钟） |
| `idle_in_transaction_session_timeout` | 事务开着但**不执行语句**的最长时间 | 忘了 COMMIT 的连接永久钉住回收水位线（第 9 篇） |

### ✅ 推荐配置

**数据库级兜底**（保证任何人、任何客户端都受约束）：

```sql
ALTER DATABASE mydb SET statement_timeout = '60s';
ALTER DATABASE mydb SET lock_timeout = '10s';
ALTER DATABASE mydb SET idle_in_transaction_session_timeout = '60s';
```

**按角色细分**（不同工作负载不同容忍度）：

```sql
-- 在线业务：严格
ALTER ROLE app_web SET statement_timeout = '10s';
-- 后台报表：宽松
ALTER ROLE app_report SET statement_timeout = '30min';
-- 迁移执行器：允许长时间的 DDL，但抢锁要快速失败
ALTER ROLE app_migrator SET statement_timeout = '2h';
ALTER ROLE app_migrator SET lock_timeout = '5s';
```

**语句级精调**（sub2api 的迁移脚本就是这么做的）：

```sql
BEGIN;
  SET LOCAL lock_timeout = '5s';
  SET LOCAL statement_timeout = '10min';
  ALTER TABLE ...;
COMMIT;
```

⚠️ `SET LOCAL` 只在当前事务内生效，事务结束自动恢复——**这正是你想要的**，不会污染这个连接的后续使用（在连接池场景下极其重要）。

### ❌ 反例：只在应用层设超时

```go
ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
rows, err := db.QueryContext(ctx, "SELECT ...")
```

这只让**你的 Go 程序**放弃等待。数据库那边：

- `database/sql` 会尝试发一个 cancel 请求（**新建一个连接**去发），但这是"尽力而为"；
- 如果 cancel 没送到、或者语句已经进入某个不可中断的阶段，**查询会继续在数据库里跑到底**；
- 于是出现"应用侧已经超时返回 504 了，数据库里还有 200 个僵尸查询在烧 CPU"。

📌 **应用侧超时和数据库侧超时都要有，数据库侧的才是真正的止损线。**

## 五、PgBouncer：什么时候需要，以及它的三个模式

当应用实例很多（比如 Kubernetes 里 50 个 Pod × 每个 20 连接 = 1000 连接），单靠应用池不够，需要在中间加一层。

| 模式 | 复用粒度 | 能支持的功能 | 复用率 |
|---|---|---|---|
| `session` | 一个客户端连接绑一个后端连接，直到断开 | 全部 | 低（几乎等于不池化） |
| **`transaction`** | **每个事务结束就归还** | **不支持**会话级状态 | **高（推荐）** |
| `statement` | 每条语句结束就归还 | 不支持多语句事务 | 最高（很少用） |

### ⚠️ `transaction` 模式下不能用的东西

这是最容易踩的坑，因为它**不会报错，只会行为诡异**：

| 功能 | 为什么坏 |
|---|---|
| SQL 形式的 `PREPARE` / `DEALLOCATE` | 预备语句绑在后端连接上，下次事务可能换了个连接 → `prepared statement "xxx" does not exist` |
| `SET`（不带 LOCAL） | 设置留在了某个后端连接上，随机影响别人 |
| **会话级 advisory lock** | 锁留在某个后端连接上，**永远不会释放**（第 5 篇的陷阱） |
| `LISTEN` / `NOTIFY` | 监听绑在后端连接上，收不到通知 |
| 临时表 | 下个事务换连接就没了 |
| `WITH HOLD` 游标 | 同上 |

**✅ 对应的做法**：

- **预备语句**：**PgBouncer 1.21+（2023）已经支持** transaction 模式下的协议级预备语句（extended protocol），只要把 `max_prepared_statements` 设为非 0 即可。旧版本或者不想开这个特性的话，在驱动层关掉：
  - Go + pgx：`DefaultQueryExecMode: pgx.QueryExecModeSimpleProtocol`（或 `QueryExecModeExec`）
  - Java + JDBC：`prepareThreshold=0`
  - Python + psycopg3：`prepare_threshold=None`
  - Node + node-postgres：默认就不用服务端预备语句
  - ⚠️ 无论哪个版本，**SQL 形式的 `PREPARE` / `DEALLOCATE` 语句都不支持**。
- **一律用 `SET LOCAL`**，不用 `SET`
- **advisory lock 一律用 `pg_advisory_xact_lock`**（事务级）
- **LISTEN/NOTIFY 走独立的直连**，绕过 PgBouncer

**❌ 不知道这些限制就上 PgBouncer 会怎样**：上线后随机出现 `prepared statement does not exist`、定时任务偶尔重复执行（advisory lock 失效）、某些请求看到了别人的 `SET` 参数。这类问题的共同特征是**低频、随机、无法复现**，排查成本极高。

## 六、还有哪些参数值得一开始就配好

```
# ===== 内存 =====
shared_buffers = 机器内存的 25%        # 默认 128MB，几乎总是太小
effective_cache_size = 机器内存的 75%  # 这只是给优化器的提示，不实际分配
work_mem = 16MB ~ 64MB                 # ⚠️ 是【每个排序/哈希节点】一份，不是每连接一份
                                       #    并发 × 每查询的节点数 × work_mem 可能爆内存
maintenance_work_mem = 1GB             # VACUUM / CREATE INDEX 用，调大能显著加速

# ===== WAL / checkpoint =====
max_wal_size = 8GB                     # 默认 1GB，太小会导致频繁 checkpoint → FPI 暴增
checkpoint_timeout = 15min
checkpoint_completion_target = 0.9
wal_compression = on                   # 压缩 FPI，通常划算

# ===== 计划器 =====
random_page_cost = 1.1                 # 默认 4.0 是给机械盘的；SSD 上必须调到 1.1
effective_io_concurrency = 200         # SSD

# ===== 可观测性（强烈建议全开）=====
shared_preload_libraries = 'pg_stat_statements'
pg_stat_statements.track = all
track_io_timing = on
log_min_duration_statement = 1000      # 记录超过 1 秒的慢查询
log_lock_waits = on                    # 记录锁等待（排查第 5 篇那类问题的关键）
log_autovacuum_min_duration = 0        # 记录所有 autovacuum 活动
log_checkpoints = on
log_temp_files = 0                     # 记录所有落盘的临时文件（work_mem 不够的信号）
```

### ❓ 问题：`random_page_cost = 4.0` 会怎样？

这是**给机械硬盘设计的默认值**——它告诉优化器"随机读比顺序读贵 4 倍"。

在 SSD 上随机读和顺序读差别很小（1.1 倍左右）。如果不改：

**❌ 优化器会系统性地低估索引扫描的价值**，倾向于选择顺序扫描。表现为"我明明建了索引，为什么还走全表扫描"。

**这可能是单个参数里最容易被忽略、收益最大的一项。**

### ❓ 问题：`work_mem` 为什么危险？

它是**每个排序/哈希操作**分配的上限，不是每个连接、更不是全局。

一个有 3 个排序节点 + 2 个 hash join 的复杂查询，可能同时占用 **5 份 work_mem**。如果再乘以并行 worker 数……

```
最坏情况内存 ≈ 连接数 × 每查询节点数 × (并行 worker 数 + 1) × work_mem
```

100 个连接 × 5 个节点 × 64MB = **32 GB**（还没算并行）。

⚠️ 两个额外的放大因素：**并行查询里每个 worker 各自拿一份 `work_mem`**；**哈希类节点（Hash Join / HashAgg）的上限是 `work_mem × hash_mem_multiplier`**（PG 13+，默认 2.0）。

**✅ 做法**：全局设小（16~32MB），需要大内存的会话单独调：

```sql
SET LOCAL work_mem = '512MB';   -- 只给这个报表查询
```

**监控信号**：日志里的 `temporary file` 记录说明 work_mem 不够，排序落盘了。

## 七、连接问题的排查清单

```sql
-- 1. 连接数分布：谁占着连接
SELECT usename, application_name, client_addr, state, count(*)
FROM pg_stat_activity
GROUP BY 1,2,3,4 ORDER BY count(*) DESC;

-- 2. idle in transaction 的连接（重点关注）
SELECT pid, usename, application_name,
       now()-state_change AS 空闲了多久, left(query,80) AS 最后一条语句
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY state_change;

-- 3. 还剩多少连接额度
SELECT (SELECT setting::int FROM pg_settings WHERE name='max_connections') AS 上限,
       count(*) AS 已用,
       (SELECT setting::int FROM pg_settings WHERE name='max_connections') - count(*) AS 剩余
FROM pg_stat_activity;

-- 4. 正在等待的连接在等什么
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity WHERE wait_event IS NOT NULL
GROUP BY 1,2 ORDER BY 3 DESC;
```

**应用侧同样要暴露池的指标**（Go 的 `db.Stats()`）：

```go
s := db.Stats()
// s.InUse         正在使用的连接
// s.Idle          空闲连接
// s.WaitCount     ← 累计有多少次请求需要等连接
// s.WaitDuration  ← 累计等待时长
// s.MaxIdleClosed / s.MaxLifetimeClosed
```

📌 **`WaitCount` 持续增长 = 池子太小或者有慢查询占着连接不放。** 这是最有价值的一个指标，一定要接进监控。

## 八、本篇小结

| 项 | 推荐值 | 不做的后果 |
|---|---|---|
| 连接池大小 | CPU 核数 × 2~4 | 太大 → 吞吐下降 43% + OOM；太小 → P99 升高（可接受） |
| `ConnMaxLifetime` | 30 分钟，短于 LB 空闲超时 | 云上静默断连，"早上第一个请求超时" |
| `statement_timeout` | 10~60s（按角色分） | 慢查询占连接、拖住 VACUUM |
| `lock_timeout` | 5~10s | DDL 排队堵死整张表 |
| `idle_in_transaction_session_timeout` | 60s | 长事务钉住回收水位线 → 全库膨胀 |
| `random_page_cost` | SSD 上设 1.1 | 优化器不爱走索引 |
| `work_mem` | 全局小，按需调大 | 并发高时 OOM |
| `shared_buffers` | 内存 25% | 缓存命中率低 |
| `pg_stat_statements` | 必开 | 出问题时没有任何线索 |
| PgBouncer transaction 模式 | 禁用服务端预备语句、只用 `SET LOCAL`、只用事务级 advisory lock | 随机报错、锁泄漏、定时任务重复执行 |

📌 **一句话**：**Postgres 的默认超时全是"无限"，这是留给你自己配的**——`statement_timeout`、`lock_timeout`、`idle_in_transaction_session_timeout` 这三个参数不配，等于给数据库拆了保险丝。
