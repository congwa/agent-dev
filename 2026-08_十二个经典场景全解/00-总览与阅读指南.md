## 0. 先说清楚：这套文档和之前那套秒杀文档什么关系

你之前读的那套是**秒杀系统源码拆解** —— 5 个 GitHub 真实项目 + 1 篇总览。

那套文档的作用是**打通任督二脉**：让你第一次搞明白，"高并发"这三个字背后到底在干什么事。

但秒杀只是一个场景。而且说实话，它是**最简单的那类** —— 库存就是一个数字，减到 0 为止。

这套文档要做的事是**把视野打开**：

## 4. 五个心法（全系列最重要的一章）

读完 12 篇，你会发现一件事：**这些看起来八竿子打不着的系统，翻来覆去就在用同几招。**

如果这份文档你只能记住一页，记这一页。

---

### 心法 ① 漏斗：越贵的计算，越靠后

```
   ████████████████████████  10,000,000   便宜的过滤
              │
              ▼
        ████████████          10,000      稍贵一点
              │
              ▼
           ██████             1,000       更贵
              │
              ▼
             ██               10          最贵的计算
```

**核心规则：把最便宜的过滤放在最前面，让最贵的计算只处理最少的数据。**

| 出现在 | 怎么用的 |
|---|---|
| 秒杀（你已读） | CDN → 按钮置灰 → 网关限流 → 本地售罄标记 → Redis 扣减 |
| **11 推荐系统** | 召回（千万→几千）→ 粗排（→几百）→ 精排（→几十）→ 重排（→10） |
| **08 网约车派单** | GeoHash 先粗筛附近的车，再做精确的最优匹配 |
| **12 布隆过滤器** | 先用 12KB 内存挡掉不存在的 key，再查数据库 |

**最精彩的对照**（详见 11 篇开头）：

```
      秒杀漏斗                  推荐漏斗
      ────────                  ────────
   10万请求 → 1000          1000万候选 → 10

   丢掉的请求               丢掉的候选
   本来就不该处理            本来可能是好的

   丢是为了【减少负载】       丢是因为【算不起】

        ✅ 必须丢                ⚠️ 不得不丢
```

**形状一样，含义完全相反。** 想通这一点，你就理解漏斗了。

### 心法 ② 削峰：把尖峰摊成平缓

```
   削峰前                        削峰后
                                 
      ▲                             ▲
      █                             │
      █                             │
      █                        ▄▄▄▄▄▄▄▄▄▄▄▄
   ▁▁▁█▁▁▁                     ▔▔▔▔▔▔▔▔▔▔▔▔
      ↑                             
   一瞬间全来了                  同样的总量，摊平了
   系统扛不住                    系统轻松处理
```

**核心规则：总量不变，把"瞬时的高"变成"持续的平"。** 手段是加一层缓冲（队列）。

| 出现在 | 怎么用的 |
|---|---|
| 秒杀（你已读） | Redis 扣减成功后扔 MQ，消费者慢慢建订单 |
| **05 Feed 流** | 明星发帖的 1 亿次扩散，扔 MQ 异步慢慢推 |
| **06 直播弹幕** | 不是来一条推一条，攒 1 秒打包推一次 |
| **08 网约车派单** | 攒 2 秒的订单批量匹配 |
| **01 12306 候补** | 把"抢"变成"排队 + 异步撮合"，从根上消解洪峰 |

**注意 08 和 06 的区别**：都是攒批，但目的不同 —— 弹幕攒批是为了**省带宽**，派单攒批是为了**求最优解**。同一招，两种用法。

### 心法 ③ 打散热点：一个变 N 个

```
   热点集中                      热点打散
   ────────                      ────────
                              
   所有请求 ──▶ ┃ 一个点 ┃      请求 ─┬─▶ ┃分片0┃
                    ↑               ├─▶ ┃分片1┃
                 挤爆了              ├─▶ ┃分片2┃
                                    └─▶ ┃分片3┃
                                      每个都很轻松
```

**核心规则：当一个点扛不住时，先想能不能把它拆成 N 个。**

| 出现在 | 怎么用的 |
|---|---|
| 秒杀（你已读） | 库存分片：1000 个库存拆成 10 份，每份 100 |
| **07 撮合引擎** | 按股票代码分片，每只股票一个独立的单线程引擎 |
| **02 微信红包** | SET 化：按用户 ID 哈希到不同的独立业务单元 |
| **06 弹幕** | 大房间分片到多台网关机 |
| **12 一致性哈希** | 让分片在扩容时不全部失效 |

**07 撮合引擎最有意思**：它不能用多线程（会变慢），但可以分片 —— **"不能并发"和"不能扩容"是两回事。**

### 心法 ④ 精度换性能：接受"差不多对"

```
   要 100% 精确           接受 99.2% 精确
   ─────────────         ────────────────
                        
   ████████████████       ▏
   800 MB 内存            12 KB 内存
                        
                        便宜了 6 万倍
```

**核心规则：先问"到底需不需要 100% 精确"。绝大多数时候不需要，而这个"不需要"能换来数量级的提升。**

| 出现在 | 牺牲了什么 | 换来了什么 |
|---|---|---|
| **12 HyperLogLog** | 0.81% 误差 | 内存 800MB → 12KB |
| **12 布隆过滤器** | 少量假阳性 | 内存降低几十倍 |
| **12 一致性哈希** | 分布不完全均匀 | 扩容时缓存不失效 |
| **04 限流器本地批发** | 可能轻微超限 | 99% 请求不走网络 |
| **08 GeoHash** | 格子边界不精确 | 二维查询变一维，O(1) |
| **11 向量召回 ANN** | 不是绝对最近邻 | 千万级检索从小时级到毫秒级 |
| **01 12306 余票显示** | 显示"有"点进去没了 | 查询 QPS 提升几百倍 |

最后一条特别有意思：**"余票不准"不是 bug，是故意的设计。**

### 心法 ⑤ 承认做不到：把"发现并修复"做到极致

```
   理想主义                     工程现实
   ────────                     ────────
                              
   保证永远不出错          →     承认一定会出错
        ↓                            ↓
   （做不到，或者代价            把【发现问题】和
     大到无法接受）              【修复问题】做到极致
                                     ↓
                                  实际更可靠
```

**核心规则：当"保证不出错"的代价高到离谱时，改为"允许出错 + 保证能发现 + 保证能修复"。**

| 出现在 | 承认了什么做不到 | 怎么兜底 |
|---|---|---|
| **10 支付对账** | 跨公司没法做分布式事务 | T+1 对账，逐笔比对，差异分类处理 |
| **09 IM 消息** | 推送永远不可靠 | 客户端上报 seq 水位，服务端补发缺口 |
| 秒杀（你已读） | Redis 和 MySQL 没法强一致 | 定时对账 job，以 MySQL 为准修正 |
| **10 本地消息表** | 远程调用不可靠 | 转化为可靠的本地写 + 异步重试 |
| **07 撮合引擎** | 内存数据会丢 | 先写输入日志，宕机后重放恢复 |

**这是整套文档里最"成年人"的一条。** 新手总想找一个"永远正确"的方案；工程师知道那个方案不存在，于是把精力放在**出错之后怎么办**上。

## 8. 小白词典

按拼音排序。看到不懂的词回来查。

### A–G

| 术语 | 一句话解释 |
|---|---|
| **ACK** | "我收到了"的回执。发出去不算送达，对方回了 ACK 才算 |
| **ANN（近似最近邻）** | 找"差不多最像的"而不是"绝对最像的"，快几个数量级 |
| **B+ 树** | 数据库索引用的树结构。数据都在叶子上，叶子之间用链表连起来，适合范围查询 |
| **背压（Backpressure）** | 下游处理不过来时，让上游**慢下来**。注意：和"丢弃"是两回事 |
| **幂等** | 同一个操作做 1 次和做 100 次，结果一样。分布式系统的必修课 |
| **布隆过滤器** | 用一点点内存判断"这个东西一定不存在"。说不存在一定对，说存在可能错 |
| **CAS** | Compare-And-Swap，"如果值还是我看到的那个，就改成新的"。无锁并发的基础 |
| **CDN** | 内容分发网络。把图片、JS 这些静态文件放到离用户最近的机房 |
| **重排（Re-ranking）** | 推荐漏斗的最后一级。不看单个物品好不好，看这一组搭配好不好 |
| **粗排** | 推荐漏斗第二级。用轻量模型从几千筛到几百 |
| **冲正** | 支付里的"撤销一笔错误记账" |
| **Embedding（向量化）** | 把物品变成一串数字。相似的物品，数字也接近 |
| **二倍均值法** | 红包拆分算法：每次随机范围是 `剩余金额/剩余人数 × 2` |
| **二分图匹配** | 左边一堆订单、右边一堆司机，怎么配对总成本最低 |
| **发号器** | 专门生成全局唯一递增数字的服务 |
| **分布式锁** | 多台机器抢同一把锁。通常用 Redis 或 ZooKeeper 实现 |
| **分层时间轮** | 秒轮→分轮→时轮，像钟表的时分秒针互相进位 |
| **GeoHash** | 把二维经纬度变成一维字符串。前缀相同 = 位置相近 |
| **归并排序** | 把多个已排好序的列表合成一个有序列表 |

### H–P

| 术语 | 一句话解释 |
|---|---|
| **哈希槽（Hash Slot）** | Redis Cluster 的分片方式，固定 16384 个槽 |
| **HyperLogLog** | 用 12KB 内存统计上亿个不重复元素，误差 0.81% |
| **回调（Callback）** | 第三方处理完了主动来通知你。支付里的核心机制 |
| **假阳性（False Positive）** | 说"有"但实际"没有"。布隆过滤器的固有缺陷 |
| **降级** | 出问题时提供一个简化版服务。比如推荐挂了就返回热门榜 |
| **精排** | 推荐漏斗第三级。用重模型从几百筛到几十，最贵的一级 |
| **令牌桶** | 限流算法。匀速生成令牌，能攒着，所以**允许突发** |
| **漏桶** | 限流算法。水匀速流出，所以**强制匀速**，不允许突发 |
| **LSM 树 / B+ 树** | 两种存储引擎的索引结构，前者写快，后者读快 |
| **MQ（消息队列）** | 一根"传送带"。生产者扔进去，消费者慢慢取，用来削峰和解耦 |
| **命中率** | 缓存里能找到的比例。90% 命中意味着只有 10% 要去查数据库 |
| **NTP** | 网络时间同步协议。它把时钟往回调的时候，雪花算法就出事了 |
| **QPS / TPS** | 每秒查询数 / 每秒事务数。衡量系统能扛多少 |
| **CTR / CVR** | 点击率 / 转化率。推荐系统精排预测的目标 |

### Q–Z

| 术语 | 一句话解释 |
|---|---|
| **RT（响应时间）** | 一个请求从发出到收到结果花了多久 |
| **Saga** | 长事务拆成多个本地事务，每个都配一个"反悔操作"用于回滚 |
| **SET 化** | 把整个业务栈（不只是数据库）按用户切成多个独立单元 |
| **seq 号** | 会话里的消息序号，单调递增。IM 的灵魂 |
| **删除标记（Tombstone）** | 不真删数据，只打个"已删除"的标记 |
| **事件溯源（Event Sourcing）** | 不存"当前状态"，只存"发生过的所有事件"。要状态就重放一遍 |
| **事务消息** | 保证"本地操作成功"和"消息发出去"这两件事同时成功或同时失败 |
| **双塔模型** | 用户特征和物品特征分开算成两个向量，最后算一下相似度。快在物品向量可以离线算好 |
| **水位（Watermark）** | "我已经处理到哪儿了"的标记 |
| **削峰填谷** | 用队列把瞬间的高峰摊平到后面的时间里 |
| **雪花算法（Snowflake）** | 64 位分布式 ID：时间戳 + 机器 ID + 序列号 |
| **一致性哈希** | 把机器和数据都映射到一个环上，扩容时只影响相邻一段 |
| **有界队列** | 容量有上限的队列。**无界队列是背压的头号杀手** |
| **召回（Recall）** | 推荐漏斗第一级。从千万级粗筛到几千，宁可错选不可漏选 |
| **长款 / 短款** | 对账术语。第三方有我没有 = 长款；我有第三方没有 = 短款 |
| **状态机** | 规定"从哪个状态只能跳到哪些状态"，防止状态乱跳 |
| **重放（Replay）** | 把历史事件按顺序再执行一遍，用来恢复状态 |
| **虚拟节点** | 一台物理机在哈希环上放 150 个点，让数据分布更均匀 |
| **熔断（Circuit Breaker）** | 下游一直失败就先别调了，过一会儿再试探 |
| **429 Too Many Requests** | HTTP 状态码，"你请求太频繁了"。配 `Retry-After` 告诉对方多久后再来 |

## 9. 读完之后往哪走

先说句实在话：**这 12 篇加起来五万多行，别想一口气读完。**

正确的姿势是：

1. **先按路线 A 或 B 挑 3~4 篇读透**，读完能给别人讲明白
2. **剩下的当字典用** —— 工作中遇到类似问题再回来翻
3. **心法那一章（第 4 节）多读几遍** —— 那是能迁移到任何新场景的东西

### 判断自己学会了没有

不是"看懂了"，而是**能不能回答这三个问题**：

```
   拿到一个新场景，你能不能说出：

   ① 它的【签名难题】是什么？
      （最核心的那一个矛盾，不是一堆问题）

   ② 它在用哪几个【心法】？
      （漏斗 / 削峰 / 打散 / 精度换性能 / 承认做不到）

   ③ 它的【取舍】是什么？
      （放弃了什么，换来了什么）
```

**能回答这三个，你就不是在背方案了，你是在做设计。**

### 延伸主题

学完这套之后，值得继续挖的方向：

| 方向 | 为什么 |
|---|---|
| **分布式共识**（Raft / Paxos） | 前面所有场景都在"绕开"强一致，这个方向是正面解决它 |
| **流式计算**（Flink） | 11 推荐系统里的实时特征、风控、实时大屏都靠它 |
| **存储引擎**（LSM 树 / B+ 树） | 12 篇里反复出现"为什么这样存更快"，源头在这里 |
| **可观测性**（链路追踪 / 指标 / 日志） | 系统建好之后，怎么知道它在正常工作 |
| **混沌工程** | 主动注入故障，验证你的"承认做不到 + 兜底"到底管不管用 |
