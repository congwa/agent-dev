## 1. 谣言粉碎："2000 万行"从哪来，为什么是错的

### 1.1 手册原文根本不是这么说的

"单表 2000 万行就要分表"十年来被归到《阿里巴巴 Java 开发手册》头上。手册原文：

> 15.【推荐】单表行数超过 **500 万行**或者单表容量超过 **2GB**，**才推荐**进行分库分表。
> 说明：如果预计三年后的数据量根本达不到这个级别，**请不要在创建时就分库分表**。

三个被普遍忽略的点：

1. 数字是 **500 万 / 2GB**，不是 2000 万；
2. 级别是**【推荐】**，不是【强制】；
3. "**才**推荐"三个字是反向表述——手册本意是**劝你别过早分表**。

一句劝退的话，传着传着变成了动员令。

### 1.2 "2000 万"的真实来历：一道 B+ 树算术题

```
  一个 16KB 的索引页，每条目录项约 14 字节
       → 每页能放 16384 / 14 ≈ 1170 个"指路牌"

  三层 B+ 树能索引的行数：
       1170 × 1170 × 16 ≈ 2190 万行
       （假设每行约 1KB，叶子页放 16 行）
```

数学是对的，**但拿它当阈值是错的**，两个原因：

- 超过 2190 万只是树从三层变四层，查询**多访问一个页**而已——不是悬崖，是缓坡。
- 它对行大小极度敏感：行从 0.9KB 变 5KB，"容量"就从 2140 万掉到 285 万。同一个公式能算出你想要的任何数。

### 1.3 真做过实验的证据：拐点跟着内存走，不跟行数走

2023 年有人在 MySQL 8.0.25 上做了可复现实测（9 张表，10 万 ~ 6000 万行，[原文](https://yishenggong.com/2023/05/22/is-20m-of-rows-still-a-valid-soft-limit-of-mysql-table-in-2023/)，第三方实测）：

| innodb_buffer_pool_size | 延迟拐点出现的行数 |
|---|---|
| 11 GB | 5000 万行 |
| 7 GB | 3000 万行 |
| 3 GB | 2000 万行 |

**拐点取决于"表（热数据+索引）能不能装进 buffer pool"，不是某个固定行数。** 索引查找命中缓存 0.5ms，未命中走磁盘 4~6ms，差 8~12 倍——所谓"大表变慢"，慢的从来是磁盘，不是行数本身。

"2000 万"之所以看着灵验，是因为 816B × 2000 万 ≈ 16GB，**恰好是那个年代服务器内存装不下的临界点**。换台 256GB 内存的机器，这个数就废了。

> 该用的判据（背这三条，忘掉 2000 万）：
> 1. 热数据 + 索引是否超出 buffer pool？（看命中率）
> 2. 单实例是否逼近 2~3TB？（备份 / DDL 时长还能忍吗）
> 3. 写 QPS 是否到了单机上限？（读的问题另有解法）

## 2. 分之前必须先做的 6 件事（严格按序）

分库分表是**第七招**。前六招每一招都比它便宜，而且多数团队做完前三招就够了：

| 顺序 | 做什么 | 为什么有效 / 真实限制 |
|---|---|---|
| 0 | SQL + 索引优化、数据类型瘦身 | Percona 列为第一步。能用 int 别用 bigint |
| 1 | **冷热分离 / 归档** | 被严重低估。Percona 原话："保持数据量小的最好办法是少存数据" |
| 2 | 加内存 / 换 NVMe | 由 1.3 节实验直接推出：3GB→11GB，拐点从 2000 万挪到 5000 万。**最便宜的"分库分表替代品"** |
| 3 | 读写分离 | ⚠️ **不解决写瓶颈**——每笔写仍然全量落在 primary，副本只是把写入量复制了一份，不是分摊 |
| 4 | MySQL 分区表 | ⚠️ 最致命的限制见下 |
| 5 | 垂直拆分（拆字段 / 拆库） | 行变窄 → B+ 树变矮 → buffer pool 装得下更多行 |
| 6 | 评估分布式数据库 | 2026 年天平明显倾斜，见第 7 节 |

### 分区表最致命的限制

MySQL 官方原文（[手册 §分区限制](https://dev.mysql.com/doc/refman/en/partitioning-limitations.html)）：

> "All columns used in the partitioning expression must be part of every unique key that the table may have."

后果：想按 `create_time` 给订单表分区，主键就必须变成 `(order_id, create_time)`——于是 `order_id` 单独**无法再保证唯一**，业务唯一约束直接失效。而且分区表仍然是一个 mysqld 进程，CPU、IOPS、容量、单点故障，一个都没解决。

分区表真正的价值在别处：**RANGE 分区 + `DROP PARTITION` 秒级删历史数据**。它是第 1 招"冷热分离"的最佳搭档，不是分库分表的替代品。

## 3. 分片键与基因法 ⭐（本篇核心）

### 3.1 难题：一张订单表有三个查询维度

```
  买家：  "我的订单"        →  按 user_id 查
  详情页："订单号 XXX"      →  按 order_id 查
  商家：  "我店铺的订单"    →  按 seller_id 查
```

按任何一个维度分片，另外两个维度就退化成**全分片广播**（16 个库每个都查一遍再合并）。这是分库分表真正的难点——不是"怎么分"，是"分完怎么查"。

### 3.2 基因法：把路由信息藏进雪花 ID 的低位

核心原理只有一句数学：**对 2ⁿ 取模 ≡ 取二进制低 n 位。**

分 16 库为例：

```
  1.  16 = 2⁴          →  需要 4 bit "基因"
  2.  gene = user_id % 16          （即 user_id 的低 4 位）
  3.  用雪花算法生成 60 bit 的 seq
  4.  order_id = (seq << 4) | gene   ← 上一篇 Grafana 的"位打包"技巧
```

于是得到一个恒等式：

```
  order_id % 16  ==  user_id % 16
```

**按 user_id 查和按 order_id 查，都是一次命中同一个分片**——不需要索引表，不需要广播。

> 💡 这就是雪花算法和分库分表的真正结合点。基因法要求你**能控制 ID 的低位比特**，所以必须自己生成 ID（雪花变体），**绝对不能用 UUID**——上一篇决策表里那行"基因法必须雪花"，原因在此。
> 雪花在这里不只是发号器，它是**路由信息的载体**。第 12 篇 4.8 节说雪花和取模分表"天然打架"，基因法的回答是：别让它们打，让 ID 出生时就带上分片的户口。

附带的好处：同一用户的所有订单写操作**全落在同一分片**——跨分片分布式事务问题直接消失（对照第 10 篇支付对账里为了跨系统一致性付出的代价，你会体会到"根本不产生分布式事务"有多值钱）。

### 3.3 基因法的代价（多数文章不提）

- 4 bit 基因意味着**最多 16 库**。想扩到 32 库需要 5 bit，但历史 order_id 已经定型，改不了。所以要**一开始就预留足够多的 bit**——比如预留 10 bit（1024 个逻辑分片），再把逻辑分片映射到少量物理库。
- 它只能解决**一个**额外维度。买家 + 订单号解决了，**卖家维度还是没救**。

淘宝的做法是两招叠加（第三方架构分享，未经阿里官方文档确认）：拆**买家库 + 卖家库**（异步同步两份数据），同时在订单号里嵌入卖家 id 末 2 位 + 买家 id 末 2 位。

### 3.4 一条价值最高但常被忽略的原则：前台后台分离

> C 端查询用基因法保极致性能；**运营 / 客服 / BI 单独建 ES / ClickHouse，彻底不碰在线库。**

因为大多数"跨库 JOIN、跨库聚合、深分页跳页"的需求，追根究底**都来自后台**。把后台流量分离出去，一半难题自动消失。这和第 11 篇推荐系统"四级漏斗各干各的"是同一个思想：不同的查询模式，就该给不同的存储。

## 4. 分完之后最难的：深分页

### 4.1 为什么深分页在分片后会爆炸

ShardingSphere 官方文档的例子：

```sql
SELECT * FROM t_order ORDER BY id LIMIT 1000000, 10
```

在 2 个分片下必须改写成 `LIMIT 0, 1000010` 发给**每个**分片——要传输 200 多万条数据才能取到 10 条。

为什么不能各分片取 `LIMIT 500000, 5`？因为**无法预知全局第 100 万名在各分片排第几**——极端情况下前 1000010 条可能全来自同一个分片。这是正确性要求，不是实现偷懒。

### 4.2 四种方案

| 方案 | 精确? | 性能 | 现实评价 |
|---|---|---|---|
| 全局视野法（各分片 `LIMIT 0, X+Y`） | ✅ | 随页深平方级下降 | ShardingSphere 默认行为 |
| **禁止跳页（keyset 分页）** | ✅ | **与页深无关，恒定** | ⭐ 实际最该用的 |
| 各分片取 X/N | ❌ | 好 | 用精度换性能（第 12 篇的老朋友），统计报表可用 |
| 二次查询法 | ✅ | 与页深无关 | 需 2 次往返；**没有任何主流中间件内置**，更多活在面试题里 |

推荐方案一句话：**记住上一页的最大值**，下一页查 `WHERE time > $last_max LIMIT 10`。每个分片每次只返回一页的量，翻到第几万页都一样快。代价是产品上砍掉"跳到第 N 页"——想想你自己上一次点"第 5000 页"是什么时候。

（对照：第 6 篇弹幕"主动丢弃是一种设计"——这里"主动砍掉跳页"同样是设计，不是妥协。）

## 5. 扩容：双倍扩容法

简单取模 `id % N` 的致命问题：8 库扩到 9 库，约 **8/9 的数据要搬家**。

但如果 N 是 2 的幂，有个漂亮的性质：

> `id % 2N` 的结果只可能是 `id % N` 或 `id % N + N`。
> 也就是说，**原 A 库的数据只会去 A 或新库 A2，绝不会跑到 B 去**。

于是可以用「主从复制」代替「数据迁移」，2 库 → 4 库全程不停服：

```
  1. 给 A 挂从库 A2，给 B 挂从库 B2，等复制追平
  2. 原子切换路由：  id%2==0 → A     变为
                     id%4==0 → A， id%4==2 → A2
  3. 断开主从（A2 / B2 提升为独立主库）
  4. 后台异步 DELETE 清掉各库里不属于自己的那一半
```

A2 本来就是 A 的完整副本——**数据早就在那儿了，只需要改路由规则，零迁移**。

> 💡 这就是为什么分片数一定要选 2 的幂：不是为了好看，是为了给双倍扩容留后路。（和 3.3 节"基因 bit 预留"是同一件事的两面。）

### ⚠️ 坑 1：ShardingSphere 官网 `document/current/` 不是稳定版文档


## 7. 2026 年的一个重要现实：手写分库分表的机会成本

Bolt（欧非 2 亿+ 用户，数百 TB）2026 年从分片 MySQL 迁到了 TiDB（[PingCAP 官方案例](https://www.pingcap.com/case-study/)，注意这是厂商单方叙述）。触发原因全是"分库分表也解决不了"的运维痛点：

- TB 级表加索引要**一周**；
- 单线程备份拖垮 RTO；
- 吞吐翻倍，成本涨 3 倍。

关键细节：他们**先上了 Vitess，然后放弃了**——理由是 MySQL 特性缺失、跨分片 DDL 同步失败、需要人工 rebalance。迁到 TiDB 后：加索引 1 周 → 22 分钟，存储成本降近 50%。

> 手写分库分表在 2026 年的机会成本，已经比 2019 年高得多。第 2 节的第 6 招（评估分布式数据库）应该被更早、更认真地对待——尤其当你团队没有专职 DBA 的时候。
> （但也别忘了第 13 篇第 4 节：分布式数据库上"时间有序主键 = 写热点"，换引擎的同时 ID 方案要跟着换。）

## 8. 动手清单与一句话总结

### 判断该不该分

看 **buffer pool 命中率**，不看行数。

### 动手顺序（别跳）

```
  慢SQL/索引 → 冷热分离+归档 → 加内存 → 读写分离(只解决读)
    → 垂直拆分 → 评估 TiDB/OceanBase → 最后才手写分库分表
```

### 真要分的九条

1. 分片键让 **90% 的查询落单分片**（做不到就换分片键，不是换中间件）
2. **基因法**吃下第二查询维度——ID 必须雪花变体，不能 UUID
3. 基因 bit **一开始就预留够**（建议 10 bit / 1024 逻辑分片）
4. 分片数取 **2 的幂**（给双倍扩容留后路）
5. 运营 / 客服 / BI 的复杂查询全部扔给 **ES / ClickHouse**，不碰在线库
6. 分页默认**禁止跳页**（keyset 分页）
7. 靠分片键对齐**消灭**分布式事务，而不是引入 Seata 去"解决"它
8. 跨分片 JOIN 靠绑定表 + 广播表，解不了的回到第 5 条
9. 中间件选 ShardingSphere 5.5.3+，别碰 MyCat

### 一句话总结

> **分库分表的最高境界是不分；不得不分的时候，让每个查询天生知道自己该去哪个分片——这件事在 ID 出生那一刻（基因法）就该决定，而不是在查询发出的时候。**
