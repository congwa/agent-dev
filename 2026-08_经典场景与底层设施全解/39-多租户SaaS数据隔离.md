# 《多租户 SaaS 数据隔离》三种隔离模式，三种死法（小白版）

> 一句话结论：**共享表 + 租户 ID 模式的头号风险不是越权，是索引**——`tenant_id` 一旦要做最左前缀，全部既有索引都要重建；越权反而是拦截器能兜住的。而**独立库模式一定先死在连接池上**，不是死在存储成本上：租户数 × 池大小 × 应用实例数是乘法关系。最后一条：**多租户隔离和数据行权限在实现层是同一个东西**——MyBatis-Plus 的 `TenantLineInnerInterceptor` 直接继承 `BaseMultiTableInnerInterceptor`，租户隔离只是"一条恒为真的行权限规则"。

## 0. 开场：一个租户导出报表，把所有租户都拖慢了

### 0.1 事故当天

你在一家做 SaaS CRM 的公司。产品卖给企业，一家企业就是一个"租户"。目前 200 个付费租户，客户表 `t_customer` 一共两千万行，所有租户的数据混在同一张表里，靠一个 `tenant_id` 字段区分。

下午三点十七分，值班群炸了。所有租户的接口 P99 从 80ms 涨到 4 秒多，持续了十一分钟。查下来只有一件事：租户 T-007 的一个运营点了"导出全部客户"。

```
        平常的下午三点                          那天的三点十七分
  ─────────────────────────────        ─────────────────────────────
  199 个租户各查各的                    ┌──────────────────────────┐
  每次扫几百到几万行                    │ T-007 的导出：一条 SQL   │
  数据库 CPU 30%                        │ 扫了 800 万行            │
  P99 = 80ms                            │ 排序、回表、拉满磁盘 IO  │
                                        └──────────────────────────┘
                                        数据库 CPU 98%
                                        P99 = 4200ms   ← 199 个无辜租户
                                        客服工单 ×23
```

T-007 是你们最大的客户，一家有八百多万条客户记录的连锁品牌，一个租户占了全库 40% 的数据。他导他自己的数据，一行都没越权，**流程完全合规，但把另外 199 家拖下水了**。

这就是多租户的第一课：**数据隔离不只是"看不到别人的数据"，还包括"别人的重活不能砸到我头上"。** 前者叫逻辑隔离，后者叫资源隔离，绝大多数人只想到了前者。

### 0.2 最朴素的做法：加个字段，每条 SQL 带上它

谁都会写。所有业务表加一列，然后每条 SQL 都手动带上它：

```sql
ALTER TABLE t_customer ADD COLUMN tenant_id BIGINT NOT NULL DEFAULT 0;

SELECT * FROM t_customer WHERE tenant_id = #{tenantId} AND status = 1;
UPDATE t_customer SET name = #{name} WHERE id = #{id} AND tenant_id = #{tenantId};
```

上线，跑通，收工。这方案能活多久？取决于三个死穴哪个先发作。

### 0.3 死穴一：总有一条 SQL 会漏

一个中等规模的 SaaS，光 Mapper XML 就几百个方法，再加上定时任务、报表、运维脚本、数据修复的临时 SQL。**只要有一条漏写 `AND tenant_id = ?`，就是一次跨租户数据泄露。** 而且它在测试环境**永远测不出来**——测试库里通常只有一个租户的数据，漏写租户条件的 SQL 查出来和写了一模一样。它只在生产、只在第二个租户接入之后、只在某个特定页面才现形。

这个死穴看着最吓人，其实是**三个里最容易解的**——第 2 节的拦截器一次性兜住全部 Mapper。真正解不掉的是漏在拦截器外面的那些（第 5 节）。

### 0.4 死穴二：索引全废了（这才是真的）

假设你把 SQL 全改对了。你库里现有的索引是单租户时代的遗产：`idx_phone(phone)`、`idx_email(email)`、`idx_status_created(status, created_at)`……现在看这条最普通的查询：

```sql
SELECT * FROM t_customer
WHERE tenant_id = 7 AND status = 1 ORDER BY created_at DESC LIMIT 20;
```

`idx_status_created(status, created_at)` 是按 `status` 排的，`tenant_id` 不在最左边。数据库要么扫遍所有租户的 `status=1` 的行再逐行过滤租户，要么干脆全表扫。**索引还在，但它索引的是一个不再存在的世界。**

正确的索引应该是 `(tenant_id, status, created_at)`。于是问题变成一道算账题：

```
   业务表 12 张 × 平均 4 个二级索引 = 48 个索引
        → 全部要在最左边插进 tenant_id，全部重建
        → 两千万行的表建一个复合索引，量级在分钟级
          （具体耗时取决于硬件与表宽，此处只给量级）
        → 48 次重建 = 一整个维护窗口
          期间要不要锁表，是另一篇的题（PG 系列第 11 篇）
```

这就是本篇一句话结论的前半句：**头号风险不是越权，是索引。** 越权是"写代码时忘了一句话"，索引是"整个库的物理结构要推倒重来"，后者贵一个数量级。第 3 节整节讲它。

### 0.5 死穴三：资源是共享的，开场那件事没解

就算 SQL 全对、索引全建好，T-007 那条导出还是会扫 800 万行、还是会占满 IO。共享表模式下 CPU、内存、磁盘带宽、连接、锁——全是共享的。**逻辑上你隔离了，物理上一点没隔离。**

这一条共享表模式解不掉，只能缓解（限流、导出走异步、给大租户单独派机器）。真要物理隔离就得换模式，这就是第 1 节要摆开的三种模式。

### 0.6 三个死穴，就是本篇的路线图

| 死穴 | 症状 | 谁来解 | 在第几节 |
|---|---|---|---|
| 漏写租户条件 | 跨租户数据泄露，测试环境测不出 | SQL 自动改写拦截器 | 第 2 节 + 第 5 节的漏网清单 |
| 索引失效 | 加了 `tenant_id` 反而更慢，执行计划乱跳 | 索引重建 + 应对数据倾斜 | 第 3 节（主菜） |
| 资源不隔离 | 一个租户的大查询砸到所有人 | 换模式，或者给大租户单独拆出去 | 第 1 节 + 第 4 节 |

三个死穴不是三选一，是层层递进：治好前一个才看得见后一个。

## 1. 三种模式先摆开：独立库、独立 schema、共享表加租户 ID

先把地图画出来。多租户隔离在业界基本就三种模式，从"最隔离最贵"到"最省最挤"。

### 1.1 模式 A：一个租户一个库

```
   请求（租户 7）   ┌──────────────┐
  ────────────────▶│ 应用：按 tenant_id 选数据源 │
                   └──┬───────┬───────┬─────────┘
             ┌────────┘       │       └────────┐
             ▼                ▼                ▼
      ┌────────────┐   ┌────────────┐   ┌────────────┐
      │  db_t001   │   │  db_t007   │   │  db_t200   │  ← 结构相同
      │ t_customer │   │ t_customer │   │ t_customer │     数据全分开
      └────────────┘   └────────────┘   └────────────┘
        200 个租户 = 200 个库（甚至 200 个实例）
```

Java 生态做这件事的主力零件是 `baomidou/dynamic-datasource`（5,178 star）——按上下文动态切数据源。这里有一条**时效提醒**：该仓库最后一次提交是 **2026-04-28，已经近 3 个月没有提交**（2026-08-05 实测）。它不是不能用，成熟组件停更很正常，但如果你打算把它放在核心链路上，选型评审时要把这条摆出来说清楚，别让它成为三年后没人敢升级的那个依赖。

### 1.2 模式 B：一个租户一个 schema

```
   请求（租户 7）   ┌────────────────────────────────┐
  ────────────────▶│ 应用：连接后先 SET search_path  │
                   └───────────────┬────────────────┘
                                   ▼
              ┌──────────────────────────────────────┐
              │  同一个数据库实例                      │
              │  ┌──────────┐ ┌──────────┐           │
              │  │ schema_1 │ │ schema_7 │  ···      │
              │  │t_customer│ │t_customer│           │
              │  └──────────┘ └──────────┘           │
              │  共享同一个连接池 / 同一份内存 CPU      │ ← 关键差别
              └──────────────────────────────────────┘
```

PostgreSQL 的 `search_path` 让这个模式特别自然（MySQL 里 schema 约等于 database，界限更模糊）。它的卖点是：**结构上像独立库，连接上像共享表**——这正好躲过第 4 节那道乘法题。代价是 DDL 变更要在 200 个 schema 里各跑一遍，而且系统表会膨胀（200 schema × 12 表 = 2400 张表的元数据）。

### 1.3 模式 C：共享表 + 租户 ID

```
              ┌────────────────────────────────────┐
              │  同一个库，同一张表 t_customer        │
              │  ┌───────────┬──────┬────────────┐  │
              │  │ tenant_id │ id   │ name       │  │
              │  ├───────────┼──────┼────────────┤  │
              │  │     1     │ 1001 │ 张三        │  │
              │  │     7     │ 1002 │ 李四        │  │ ← T-007 的 800 万行
              │  │    200    │ 1004 │ 赵六        │  │    也全在这张表里
              │  └───────────┴──────┴────────────┘  │
              └────────────────────────────────────┘
              每条 SQL 都必须带 tenant_id。谁来保证？→ 第 2 节
```

三个模式的架构图摆完，现在上对照表。

### 1.4 六个维度的对照表

| 维度 | A 独立库 | B 独立 schema | C 共享表 + 租户 ID |
|---|---|---|---|
| **隔离强度** | 最强。物理隔离，连库都连不上别人的 | 中。逻辑隔离，同实例内资源共享 | 最弱。全靠应用层一句 `WHERE` |
| **成本** | 最贵。库数量 = 租户数，连接池是乘法（第 4 节） | 中。一个实例装几百 schema | 最省。多一个租户 = 多几行数据 |
| **扩容方式** | 加租户 = 建库 + 注册数据源；可按租户搬迁到不同实例 | 加租户 = 建 schema；搬迁要 dump/restore | 加租户 = INSERT；扩容靠分库分表（第 14 篇） |
| **备份恢复** | 最舒服。单租户恢复 = 恢复一个库，五分钟的事 | 中。可按 schema 导出 | 最难。"只恢复 T-007 昨天的数据"= 从全库备份里捞出一个租户再回灌 |
| **单租户定制** | 可以。给大客户加个字段、加个索引都行 | 可以，但 DDL 要小心不同 schema 结构漂移 | 基本不行。加字段全租户一起加，只能靠扩展 JSON 列 |
| **跨租户统计** | 最难。"全平台今日订单数"要连 200 个库聚合 | 中。同实例内可以跨 schema 查 | 最简单。`GROUP BY tenant_id` 一条 SQL 搞定 |

请特别注意最后两行——它们的方向是**相反的**：

```
              A 独立库    B schema    C 共享表
   备份恢复    ●●●●●      ●●●○○       ●○○○○     ← 越隔离越好做
   跨租户统计  ●○○○○      ●●●○○       ●●●●●     ← 越隔离越难做
   运维成本    ●○○○○(贵)  ●●●○○       ●●●●●(省)
```

所以没有"更好的模式"，只有"你更怕哪一件事"。怕数据泄露和噪声邻居 → 往左；怕运维成本和跨租户报表 → 往右。

一个额外的观察：PHP 生态的 `archtechx/tenancy`（4,381 star，2026-08-05 实测）把这三种模式的边界讲得特别干净，Laravel 用户可以直接拿来当模式对照的教材读（**具体源码路径本次未核实，以官方仓库为准**）。

### 1.5 真实世界的答案通常是"混着来"

一个跑了三年的 SaaS，架构往往长这样：

```
   长尾租户 180 家（各几千行）  → 共享表 + tenant_id，全塞一个库
   腰部租户  19 家（各几十万行）→ 共享表，但按租户分了库（第 14 篇）
   头部 T-007 1 家（800 万行） → 独立库、独立实例，甚至独立部署
```

**模式不是选一次，是一条随租户成长的迁移路径。** 开场那个事故的终局解法就在这张图里：把 T-007 搬出去。而"能不能搬"取决于你第一天有没有把 `tenant_id` 设计成一个干净的分片键——这就接到第 14 篇了，第 6 节还会再说。

## 2. 共享表模式的 SQL 改写（本篇主菜之一）

### 2.1 思路：不靠人记，靠机器改

死穴一（总有一条 SQL 漏写）的正解只有一个方向：**别让人写这句话。** 让框架在 SQL 执行前，把 `tenant_id` 条件自动塞进去。

Java 生态最常见的实现是 MyBatis-Plus 的 `TenantLineInnerInterceptor`（`baomidou/mybatis-plus`，17,435 star，最后提交 2026-08-03，2026-08-05 实测）。它的位置在这里：

```
   你的 Mapper 方法
        │  select * from t_customer where status = 1
        ▼
   ┌──────────────────────────────────────────┐
   │ TenantLineInnerInterceptor                │
   │  1. 把 SQL 字符串解析成语法树（AST）        │
   │  2. 在语法树上找到每个表引用                │
   │  3. 往 WHERE 里 AND 一个 tenant_id 条件    │
   │  4. 语法树重新序列化回 SQL 字符串           │
   └──────────────────────────────────────────┘
        │  select * from t_customer
        ▼  where status = 1 and t_customer.tenant_id = 7
   真正发给数据库的 SQL
```

注意第 1 步和第 4 步：它**不是字符串拼接**，是把 SQL 解析成抽象语法树再改。这一点很重要——字符串拼接遇到子查询、UNION、带括号的复杂条件必然出错，只有在语法树上动手才可能改对。

### 2.2 四类语句全量改写，不只是 SELECT

很多人对这个拦截器最大的误解是"它给查询加了个 where"。源码里它重写的是四个方法：`processSelect` / `processInsert` / `processUpdate` / `processDelete`（已读源码）。四类改写的形状完全不同：

```
  ┌─────────┬───────────────────────────┬────────────────────────────────────┐
  │ 语句类型 │ 你写的                     │ 改写后                              │
  ├─────────┼───────────────────────────┼────────────────────────────────────┤
  │ SELECT  │ select * from t_customer  │ select * from t_customer            │
  │         │ where status = 1          │ where status = 1 AND tenant_id = 7  │
  │         │                           │ ← 加过滤条件                         │
  ├─────────┼───────────────────────────┼────────────────────────────────────┤
  │ INSERT  │ insert into t_customer    │ insert into t_customer              │
  │         │   (name) values (?)       │   (name, tenant_id) values (?, 7)   │
  │         │                           │ ← 加列 + 加值，不是加 where！        │
  ├─────────┼───────────────────────────┼────────────────────────────────────┤
  │ UPDATE  │ update t_customer         │ update t_customer set name=?        │
  │         │ set name=? where id=?     │ where id=? AND tenant_id = 7        │
  │         │                           │ ← 防止改到别人的行                   │
  ├─────────┼───────────────────────────┼────────────────────────────────────┤
  │ DELETE  │ delete from t_customer    │ delete from t_customer              │
  │         │ where id=?                │ where id=? AND tenant_id = 7        │
  │         │                           │ ← 防止删到别人的行                   │
  └─────────┴───────────────────────────┴────────────────────────────────────┘
```

**只做 SELECT 会死在哪？** 两处，都是重伤：**INSERT 不补 `tenant_id`**，新数据全部落成默认值 0，事后要靠人肉修数据判断这行属于谁——这是无法恢复的信息丢失；**UPDATE / DELETE 不加条件**，一个 `where id = 1002` 就能改到别人的行，而 id 通常是全局自增或雪花 ID（[第 13 篇](./13-雪花算法真实项目调研.md)），**猜一个 id 就能跨租户改数据**。SELECT 越权只是看到，UPDATE 越权是能改。

一句话记住：**租户隔离不是读隔离，是读写全隔离。**

### 2.3 它和数据行权限是同一个基类

`TenantLineInnerInterceptor` 继承自 `BaseMultiTableInnerInterceptor`（已读源码）。而[第 36 篇《权限系统》](./36-权限系统.md)讲的数据行权限拦截器，继承的是**同一个基类**。

```
          ┌────────────────────────────────────────────┐
          │  BaseMultiTableInnerInterceptor             │
          │  · 解析 SQL 成语法树                        │
          │  · 遍历所有表引用（含 join / 子查询）        │
          │  · 把"某张表该加什么条件"交给子类决定        │
          └──────────┬────────────────────┬────────────┘
                     │                    │
        ┌────────────▼─────┐   ┌──────────▼──────────────┐
        │ 租户隔离          │   │ 数据行权限（第 36 篇）    │
        │ tenant_id = 当前  │   │ dept_id IN (我管的部门)  │
        │ 恒为真，谁都不能豁免│   │ 因人而异，超管可以豁免    │
        └──────────────────┘   └─────────────────────────┘
```

这张图就是本篇一句话结论的第三段：**多租户隔离在实现层就是一条特殊的行权限规则**——特殊在它对所有人恒定生效、不因角色而变。想通这一点，第 7 节那道优先级题就有答案了。

💡 顺带一提，这也解释了为什么芋道（`YunaiV/ruoyi-vue-pro`，38,524 star，最后提交 2026-07-31，2026-08-05 实测）把这两件事做成两个平行的 starter：`yudao-spring-boot-starter-biz-tenant` 和 `yudao-spring-boot-starter-biz-data-permission`（pom 已核实）。**同源、同基类、但生命周期和豁免规则不同，所以拆成两个包。**

### 2.4 忽略表白名单：不是所有表都有租户

有几类表天生不属于任何租户，给它们加 `tenant_id = 7` 会直接查空：

```
  需要加租户条件（业务表）
    t_customer / t_order / t_contract / t_task ...
  必须忽略（全局表）
    ① t_tenant     租户表本身   ← 加了就查不到租户列表
    ② t_dict_data  全局字典     ← 省市区、行业分类
    ③ t_config     系统配置     ← 平台级开关
    ④ t_admin_user 平台管理员   ← 运营后台的账号
    ⑤ t_job_log    任务日志     ← 平台维度
```

MyBatis-Plus 里通过实现 `TenantLineHandler` 的忽略表方法来配置白名单（接口与方法名以官方仓库为准）。这里最容易踩的坑是**白名单配反了**：

- **少配一张全局表** → 页面数据为空，一眼能发现，属于良性故障；
- **多配一张业务表** → 那张表**彻底没有租户隔离**，而且页面一切正常，谁也发现不了。

⚠️ 所以白名单这份配置必须走 code review，并且最好写成"默认全部拦截、显式列出豁免"，绝不能写成"匹配某个前缀就豁免"这种模糊规则。一个 `t_sys_*` 的前缀规则，某天有人建了张 `t_sys_customer_tag` 业务表，隔离就悄悄破了。

### 2.5 多表 join 时，条件加在哪张表上

这是共享表模式最微妙的一处。看 `SELECT c.name, o.amount FROM t_customer c JOIN t_order o ON o.customer_id = c.id WHERE o.status = 'PAID'` 这条——租户条件加在哪张表上？三种加法，结果不一样：

```
  ① 只加主表   ... AND c.tenant_id = 7
     ┌──────────────────────────────────────────────────┐
     │ 看似对：c 被限制了，join 出来的 o 也就被限制了。   │
     │ 但它依赖一个假设：o.customer_id 一定指向同租户的 c │
     │ 一条脏数据就能破掉。而且 o 这一侧的索引用不上。    │
     └──────────────────────────────────────────────────┘
  ② 只加从表   ... AND o.tenant_id = 7
     ┌──────────────────────────────────────────────────┐
     │ 同样的问题镜像一遍。LEFT JOIN 时更危险：条件写在   │
     │ WHERE 里会把 LEFT JOIN 悄悄打成 INNER JOIN。      │
     └──────────────────────────────────────────────────┘
  ③ 每张表都加 ... AND c.tenant_id = 7 AND o.tenant_id = 7
     ┌──────────────────────────────────────────────────┐
     │ 不依赖任何数据完整性假设，且两张表各自都能走       │
     │ (tenant_id, ...) 索引。代价只是 SQL 变长。        │
     └──────────────────────────────────────────────────┘
```

**正确答案是 ③，而且理由主要是性能，不是安全。** 加法 ① 在逻辑上大部分时候也对，但它让 `t_order` 那一侧失去了走 `(tenant_id, status)` 索引的机会——数据库不会自己推导出"c 是租户 7 所以 o 也是租户 7"。冗余条件在这里是**给优化器的礼物**，不是废话。

⚠️ 所以接入拦截器之后第一件事：开 SQL 日志，挑十条最复杂的 SQL（带 `UNION` / 子查询 / `WITH` / `LEFT JOIN` 的）单独看改写结果。改写引擎能不能正确处理这些语法，取决于它的解析器覆盖到了哪里——**改写引擎的能力边界，就是你的安全边界。**

## 3. 真正的杀手是索引（本篇主菜之二）

### 3.1 加 tenant_id 前后，索引的形状变了

先复习一句[PostgreSQL 系列第 08 篇《索引》](../2026-08_从真实项目学PostgreSQL/08-索引.md)的核心结论：**B-tree 索引是按列顺序层层排序的，列顺序决定了哪些 WHERE 能用上它。** 复合索引 `(a, b)` 能服务 `WHERE a=?` 和 `WHERE a=? AND b=?`，但服务不了 `WHERE b=?`。

现在把这条结论套到多租户上：

```
   ── 旧索引 (status, created_at) ──────────────────────────
              [ status ]
             ╱          ╲
        status=0        status=1
                           │  按 created_at 排
                     ┌──┬──┬──┬───┬──┬──┐
                     │t7│t1│t7│t99│t7│t3│ ← 各租户的行交错在一起
                     └──┴──┴──┴───┴──┴──┘
   查询 tenant_id=7 AND status=1 ORDER BY created_at LIMIT 20
   → 沿 status=1 这一支扫，扫一行判断一次 tenant_id
   → 小租户 T-133 只占 0.001%，要扫几万行才凑够 20 条

   ── 新索引 (tenant_id, status, created_at) ────────────────
              [ tenant_id ]
        ╱          │           ╲
      t1          t7           t200
                   │
              [ status ] → 按 created_at 排，这一支里只有 t7 的行
             ┌──┬──┬──┬──┬──┐
             │  │  │  │  │  │  ← 同租户的行物理相邻
             └──┴──┴──┴──┴──┘
   → 直接跳到 t7 那一支，顺着扫 20 行就停。
     扫描量和其他 199 个租户的数据量完全无关。
```

看懂这张图，就懂了为什么 `tenant_id` **必须放在最左边**而不是随便加在后面：它是所有查询的公共前缀，是把一张两千万行的表在物理上切成 200 个连续区间的那把刀。

### 3.2 算一笔重建的账

问题在于，这不是"加一个索引"，是"改掉所有索引"：

```
   改造前                       改造后
   idx_phone(phone)        →   (tenant_id, phone)
   idx_email(email)        →   (tenant_id, email)
   idx_status_created(...) →   (tenant_id, status, created_at)
   idx_owner(owner_id)     →   (tenant_id, owner_id)
        × 12 张业务表
   ──────────────────────────────────────────────────────
   = 48 个索引，每一个都是 DROP + CREATE
     两千万行的表建一个复合索引：分钟级
     48 个 × 分钟级 = 一个完整的维护窗口
     期间磁盘占用翻倍（旧索引还在、新索引在建）
     期间要不要锁写？→ PG 系列第 11 篇《在线 DDL》
```

这就是为什么本篇的一句话结论把索引排在越权前面。越权是一次 code review 加一个拦截器；索引是一次跨越整个维护窗口的物理重构，而且**表越大越贵、上线越晚越贵**。

⚠️ 给还没开始做多租户的读者一句最实在的建议：**如果你的产品有一丝可能走 SaaS，第一天就把 `tenant_id` 放进每个复合索引的最左边**，哪怕现在只有一个租户、这一列全是 1。一列全是 1 的索引前缀，代价是每个索引项多几个字节；三年后再加，代价是 48 次重建加一个通宵。

### 3.3 唯一索引也要跟着改

一个特别容易漏的点：所有业务唯一约束都要变成"租户内唯一"。

```sql
-- 单租户时代
UNIQUE KEY uk_phone (phone)
-- 多租户时代
UNIQUE KEY uk_tenant_phone (tenant_id, phone)
```

不改会怎样？租户 A 的客户用了 `138xxxx0001`，租户 B 就再也录不进这个手机号了，报错还是"手机号已存在"。**这是一个业务上完全说不通、但在库里完全说得通的报错。** 同类的还有编号唯一（订单号、合同号）、名称唯一（部门名、角色名）、账号唯一（同一个邮箱在不同租户下是不是同一个人——这条要产品拍板，技术上两种都能做）。

### 3.4 数据倾斜：统计信息骗了优化器

索引建好了，还有第二个坑，而且更隐蔽。

回到开场的数据分布：

```
   200 个租户，2000 万行 t_customer

   T-007   ████████████████████████████████████  800 万行（40%）
   T-012   ██████                                140 万行
   T-033   ███                                    70 万行
   中位数租户                                     1.2 万行
   T-133   ·                                        200 行
           └────────────────────────────────────────────┘
             最大租户 / 最小租户 = 40000 倍
```

数据库优化器怎么估算 `WHERE tenant_id = ?` 会命中多少行？靠统计信息。如果它只记住了"这一列有 200 个不同值"，默认假设就是**均匀分布**——于是估错，而**误差导致的计划选择才致命**：

```
   优化器的估算：2000 万 ÷ 200 = 每租户 10 万行
   ┌──────────┬───────────┬──────────┬────────────┐
   │ 租户      │ 优化器估算 │ 实际行数  │ 误差        │
   ├──────────┼───────────┼──────────┼────────────┤
   │ T-007    │ 10 万      │ 800 万    │ 低估 80 倍  │
   │ T-133    │ 10 万      │ 200      │ 高估 500 倍 │
   └──────────┴───────────┴──────────┴────────────┘

   t_customer JOIN t_order，优化器以为左表 10 万行
      → 选 Nested Loop（左表每行去右表查一次），10 万次，能接受
   实际左表 800 万行
      → 800 万次索引查找 → 本该 200ms 的查询跑了 40 秒
      → 这就是开场那条导出 SQL 的真身
```

反过来对 T-133（200 行的小租户），优化器高估到 10 万行，可能选了 Hash Join、建了个完全没必要的哈希表。**同一条 SQL 模板，在不同租户下需要的其实是不同的执行计划**——这是共享表模式独有的病。

### 3.5 三个能用的应对

```
   ① 提高统计信息精度（最便宜，先试它）
      让优化器记住"最常见值"的分布（PG 的 MCV 列表 / MySQL 的直方图），
      把 T-007 这种大值单独记下来。大部分情况这一招就够。

   ② 给超大租户建部分索引（PostgreSQL）
      CREATE INDEX idx_t007_created ON t_customer(created_at)
        WHERE tenant_id = 7;
      索引里只有 T-007 的行，体积小、层数浅。这正是 PG 系列第 08 篇
      最推荐的那一招——租户天然就是一个"稳定的过滤条件"。

   ③ 把大租户搬出去（回到第 1.5 节的分层架构）
      T-007 单独一个库之后，剩下 199 个租户的分布重新变均匀，
      优化器立刻就聪明了。治本，但最贵。
```

💡 注意 ② 和 ③ 之间的联系：**部分索引是"穷人版的独立库"**——它在同一张表里为大租户单独辟了一块物理空间，让它的查询不再被其他租户的数据稀释。两者的思路是一样的，只是隔离的粒度从"库"降到了"索引"。

### 3.6 为什么这个坑在测试环境永远复现不出来

```
   测试库                             生产库
   ──────────────────                ──────────────────
   3 个租户，各 1000 行                200 个租户，最大 800 万最小 200 行
   分布均匀，全表 3000 行              倾斜 4 万倍，全表 2000 万行
        │                                  │
        ▼                                  ▼
   任何执行计划都是毫秒级              计划选错 = 40 秒，且只有大租户中招
```

**多租户的性能问题本质上是数据分布问题，而数据分布是测试环境最难仿真的东西。** 想提前发现，唯一的办法是把生产的行数分布（不是数据本身）灌进压测环境。

## 4. 独立库模式：连接池的乘法

### 4.1 先算这道乘法题

很多人选独立库模式时算的是存储账："200 个库，每个几 GB，磁盘够。" 这笔账算得没错，但算的不是要命的那一笔。

要命的是这个：

```
   ┌──────────────────────────────────────────────────────────┐
   │                    连接数的算账                            │
   │    租户数    ×    每租户池大小   ×   应用实例数            │
   │      200     ×        10        ×       8                 │
   │    ─────────────────────────────────────────              │
   │                  = 16000 个连接                           │
   │                                                           │
   │    而 PostgreSQL 的 max_connections 默认 100              │
   │    （具体默认值以官方文档为准）→ 超了 160 倍               │
   └──────────────────────────────────────────────────────────┘

   而且这三个数任何一个都会自然增长，且是相乘：
   租户 200 → 400     16000 → 32000
   实例   8 → 16      32000 → 64000
   池大小 10 → 20     64000 → 128000
   ────────────────────────────────────────────────
   业务量涨 8 倍听起来很正常，但绝对值已经到了
   任何单机数据库都接不住的量级
```

而共享表模式呢？**8 个实例 × 10 = 80 个连接，和租户数无关。** 这就是本篇一句话结论的第二段：**独立库模式一定先死在连接池上，不是死在存储成本上。**

### 4.2 为什么连接这么贵

回接[PostgreSQL 系列第 10 篇《连接与超时》](../2026-08_从真实项目学PostgreSQL/10-连接与超时.md)的两条结论：**Postgres 的连接很贵**（每个连接是一个独立的操作系统进程，即使全程 idle 也占内存、占进程表），以及更反直觉的那条——**连接数不是越多越好**，超过某个点吞吐反而下降。独立库模式是这两条的最凶放大器，因为它造出来的连接绝大部分是闲着的：

```
   200 个租户的连接池，同一时刻的真实使用情况
   活跃租户（正在有人操作）  约 20 个   ████
   闲置租户（今天没人登录）  约 180 个  ████████████████████████████
                                        ↑ 照样各开着 10 条连接
                                          1800 条全程 idle，全程占资源
```

**你为 90% 不干活的租户，预付了 90% 的连接成本。**

### 4.3 三种拆法

这道乘法题只能从三个因子上各拆一刀：

```
                  200 × 10 × 8 = 16000
                   │     │     │
      ┌────────────┘     │     └──────────────┐
      ▼                  ▼                    ▼
  ┌──────────┐    ┌───────────┐       ┌─────────────┐
  │ 拆租户数  │    │ 拆池大小   │       │ 拆实例数     │
  │ 池懒加载  │    │ 每租户池   │       │ 把池挪出应用 │
  │ 只给活跃  │    │ 设 2~3    │       │ 所有实例共用 │
  │ 租户开池  │    │ 而不是 10 │       │ 一个外部池   │
  │ 200 → 20 │    │ 10 → 3    │       │ 8 → 1       │
  └──────────┘    └───────────┘       └─────────────┘
      └──────────────────┴────────────────────┘
                         ▼
            20 × 3 × 1 = 60 个连接，降了 260 倍
```

三刀各有代价：

| 拆法 | 做法 | 代价 |
|---|---|---|
| 池懒加载 | 租户首次请求时才建池，一段时间无请求就关掉 | 冷启动的第一个请求要等建连接（几十到几百毫秒）；LRU 抖动时反复建连 |
| 缩小池 | 每租户池设 2~3 | 单租户并发上限降低，突发流量要排队。但对长尾租户完全够用 |
| 池外置 | 应用不直连数据库，中间挂一个连接池代理 | 多一跳、多一个要运维的组件；事务模式下有些会话级特性不能用 |

**实践中三刀通常一起下**，而第三刀是效果最大的那一刀。

### 4.4 supavisor 存在的全部理由

`supabase/supavisor`（2,249 star，最后提交 2026-08-03，2026-08-05 实测）是专门为多租户场景写的 Postgres 连接池代理（Elixir）。它的 README 给了两个实测数字（README 已核实）：单个 **16 核 64GB** 节点扛 **25 万个 idle 连接**，集群规模下 **100 万连接**。把这两个数字和 4.1 节那道乘法题放在一起看：

```
   ── 没有代理 ──────────────  ── 有代理 ────────────────────
   8 个应用实例                8 个应用实例
   各持 200 租户 × 10 的池          │ 16000 条"客户端连接"（廉价）
        │                          ▼
        ▼ 16000 条连接        ┌──────────────────────┐
   ┌──────────────────┐      │  supavisor / 池代理   │
   │  PostgreSQL 实例  │      │  25 万 idle 连接      │
   │  进程数爆炸       │      │  一台 16C64G 就够      │
   │  内存吃光         │      │  每租户独立池          │
   │  max_conn = 100  │      └──────────┬───────────┘
   └──────────────────┘                 │ 几十条真连接（昂贵）
                                        ▼
                              ┌──────────────────┐
                              │  PostgreSQL 实例  │ ← 舒服
                              └──────────────────┘
```

**这就是这类组件存在的全部理由：把"连接"这个东西从数据库实例里挪出来，让昂贵的那一端不再和租户数成正比。** supavisor 还给每个租户维护独立的池（README 已核实），这样一个租户把自己的池打满，不会挤掉别的租户的配额——**连接层的隔离，和第 3 节讲的存储层隔离是同一个思路的不同层次**。

💡 PG 系列第 10 篇讲过 PgBouncer 的三种模式（session / transaction / statement），那些取舍在这里原样适用，本篇不复读。要补充的只有多租户特有的一条：**如果你走的是"独立 schema"模式（第 1.2 节），连接是共享的，你在事务池模式下必须小心 `search_path` 这类会话级状态**——连接被换给另一个租户时，会话状态可能还留着上一个租户的值。这是 schema 模式最阴的一个坑。

## 5. 越权的真实入口：没走 ORM 的那条 SQL

### 5.1 拦截器兜住的和兜不住的

第 2 节把拦截器夸了一通。现在说它的边界。

```
                      ┌──────────────────┐
                      │    你的数据库      │
                      └────────▲─────────┘
        ┌──────────────────────┼──────────────────────┐
        │              │              │               │
  ┌─────▼──────┐ ┌─────▼──────┐ ┌─────▼──────┐ ┌──────▼──────┐
  │ Mapper     │ │ 原生 JDBC   │ │ 报表/BI     │ │ 存储过程     │
  │  ↓ 拦截器✓ │ │ 手写 SQL    │ │ 直连生产库  │ │ DBA 的窗口   │
  │ 自动加条件 │ │ 拦截器 ✗    │ │ 拦截器 ✗   │ │ 拦截器 ✗     │
  └────────────┘ └────────────┘ └────────────┘ └─────────────┘
   唯一被系统性              这三条全是人写的、一次性的、
   保护的路径                没人 review 的
```

**（以下判断为推论，未实测验证）**：真实发生的跨租户数据泄露，我认为绝大多数不是出在 Mapper 上，而是出在这些旁路上。理由很直接——Mapper 那条路上有拦截器兜底，是全系统唯一被系统性保护的路径；而旁路是人写的、一次性的、没人 review 的。**安全的木桶效应在这里体现得特别纯粹：你的隔离强度等于最弱的那条数据访问路径。**

### 5.2 六个高危旁路

| 编号 | 旁路 | 典型长相 |
|---|---|---|
| ① | 报表 / BI 直连 | 数据分析师拿只读账号连生产库跑聚合 |
| ② | 定时任务 | 原生 JDBC 扫全表，"反正是后台任务" |
| ③ | 数据导出 / 导入 | 导出走了拦截器，导入的批量 INSERT 没走 |
| ④ | 存储过程 / 函数 | 逻辑在库里执行，应用层拦截器根本看不见 |
| ⑤ | 缓存 | 缓存 key 忘了拼 `tenant_id`（见 5.3） |
| ⑥ | MQ 消费者 | 消费时上下文里没有 `tenant_id`，取了默认值 |

第 ② 和第 ⑥ 有一个共同的根因：**定时任务和 MQ 消费者没有"当前登录用户"**。拦截器通常从一个 ThreadLocal 上下文里读 `tenant_id`，而那个上下文是登录或请求进来时塞进去的——定时任务的线程里它是空的。

于是框架面临一个选择：

```
   上下文里没有 tenant_id 时，拦截器该怎么办？
   选项 A：不加条件放行 → 定时任务扫到全部租户 → 静默越权，最危险
   选项 B：抛异常拒绝   → 定时任务全挂         → 吵，但安全

   正确做法：默认选 B，再为定时任务显式提供
   "遍历租户、逐个切上下文执行"的封装。
```

芋道的租户 starter 就提供了这类"在指定租户上下文中执行一段逻辑"的封装能力（**具体类名与方法名未核实，以官方仓库为准**）。这个封装是独立库/共享表两种模式都需要的基础设施——**没有它，你的后台任务就是隔离体系上一个长期敞开的洞。**

### 5.3 缓存这条最容易忘

单独拎出来说，因为它太常见了：

```
   ✗  String key = "customer:" + customerId;
      → 租户 A 先访问，缓存了自己的数据
      → 租户 B 访问同一个 customerId（雪花 ID 猜得到）
      → 直接命中缓存，拿到 A 的数据
      → 数据库层所有隔离都完好无损，但数据还是漏了
   ✓  String key = "t:" + tenantId + ":customer:" + customerId;
```

**缓存是拦截器彻底管不到的一层**——它压根不是 SQL，所以缓存 key 的租户前缀只能靠规范和 code review。这条同样适用于本地缓存、`@Cacheable` 注解、以及各种"我就缓存一下配置"的小 Map。

### 5.4 自查清单

⚠️ 接手或评审一个多租户系统时，挨条问下去：

1. 全局搜一遍 `JdbcTemplate` / `EntityManager.createNativeQuery` / 原生连接的用法，每一处都问："这里的租户条件谁加的？"
2. 所有定时任务：上下文里的 `tenant_id` 从哪来？没有的时候是放行还是抛异常？
3. 所有 MQ 消费者：消息体里带 `tenant_id` 吗？消费前有没有切上下文？
4. 所有缓存 key（含本地缓存、注解缓存）：有没有租户前缀？
5. 忽略表白名单：逐条念一遍，确认每一张都真的是全局表，且规则是"显式列举"而非"前缀匹配"。
6. 报表 / BI 用的只读账号：它连的是全库还是只有该租户的视图？有没有人用它跑过跨租户的 SQL？
7. 库里有没有存储过程 / 触发器？它们里面的 SQL 有没有租户条件？
8. 文件存储（附件、导出文件）的路径里有没有租户隔离？对象存储的签名 URL 会不会被猜到？
9. 全文检索 / ES 索引：是每租户一个索引，还是共享索引靠 filter？filter 谁加的？
10. 有没有"超级管理员可以看所有租户"的功能？它的入口是不是收敛到了唯一一处？

**十条里答不上来的每一条，都是一次潜在的通报。** 第 1、2、3 条是最高频的三个。

## 6. 中外路线相反：数据库层 vs 应用层

### 6.1 两条路线

同一件事——"保证每条 SQL 只碰到本租户的数据"——业界有两条完全不同的实现路线，而且中英文生态的偏好几乎是相反的。

```
   路线甲：数据库层                路线乙：应用层
   （英文生态更常见）               （中文生态压倒性主流）
   ─────────────────────          ─────────────────────────
   应用                            应用
    │ 原样的 SQL                    │ 原样的 SQL
    ▼                              ▼
   ┌────────────────────┐         ┌────────────────────┐
   │ PostgreSQL RLS 或   │         │ MyBatis 拦截器      │
   │ Citus 分布式分片     │         │ 在语法树上改写 SQL   │
   └─────────┬──────────┘         └─────────┬──────────┘
             ▼                              ▼ 改写后的 SQL
   数据库自己保证只返回本租户        ┌────────────────────┐
                                   │ 普通数据库，一无所知 │
                                   └────────────────────┘
```

**根本差别是"信任边界画在哪"**：路线甲把边界画在数据库里，任何人用任何方式连进来都受约束；路线乙把边界画在应用里，绕过应用就绕过了一切（第 5 节讲的正是这个）。

### 6.2 两条路线的失败模式完全不同

| | 路线甲：数据库层 | 路线乙：应用层改写 |
|---|---|---|
| **典型代表** | PostgreSQL RLS、`citusdata/citus`（12,666 star，2026-08-05 实测） | MyBatis-Plus 拦截器、`apache/shardingsphere`（20,771 star，2026-08-05 实测） |
| **头号失败模式** | **分片键/策略选错**——上线后改不动 | **漏网 SQL**——总有一条没经过改写 |
| **失败什么时候暴露** | 数据量涨上来之后，跨分片查询开始爆炸 | 第二个租户接入之后，某个冷门页面 |
| **失败的修复代价** | 极大。要重分布数据，等于一次数据迁移 | 中。找到那条 SQL，补上条件 |
| **失败会不会静默** | 不会。性能崩了大家都看得见 | **会**。数据泄露可以静默很久 |
| **谁能绕过** | 几乎没人（除非用超级用户） | 任何不走 ORM 的路径 |

**两种失败一个吵一个静。** 路线甲失败时你会被性能曲线揍醒；路线乙失败时你可能是被客户的截图告知的。

### 6.3 分片键选错，就是第 14 篇那道题

Citus 这类方案的做法，是把 `tenant_id` 当作**分布列（distribution column）**，让同一个租户的所有表的所有行都落在同一个分片上（**具体源码路径与配置项本次未核实，以官方仓库为准**）。

看出来了吗——**这就是[第 14 篇《分库分表》](./14-分库分表.md)讲的分片键问题，只是分片键被业务天然指定成了 `tenant_id`。**

```
   第 14 篇的经典困境（分片键只有一个，查询路径有两条），
   在多租户场景下一半变轻、一半变重：
   ┌──────────────────────────────────────────────────┐
   │ 好消息：分片键不用选，就是 tenant_id；99% 的查询   │
   │         天然带这个条件；同租户的表落同一分片，     │
   │         join 不跨分片。                           │
   │ 坏消息：分片彻底不均。T-007 占 40% 数据，它那个    │
   │         分片是个巨无霸。第 14 篇的"双倍扩容法"     │
   │         救不了你——再怎么扩，一个租户也切不开。     │
   └──────────────────────────────────────────────────┘
```

**这是多租户分片和普通分片最本质的区别**：普通分片按用户 ID 哈希，天然均匀；租户分片按租户，天然倾斜，而且倾斜度会随着大客户签约越来越极端。所以租户分片必须支持**按租户手工搬迁分片**（把 T-007 单独挪到一台专属机器上），而不能只靠哈希取模。

### 6.4 PG RLS：把规则写进数据库

PostgreSQL 的行级安全（Row Level Security）是路线甲更轻量的一个选择：给表建一条策略，之后**所有**访问这张表的 SQL 都自动受约束，不管来自应用、psql 命令行还是 BI 工具。

它最吸引人的地方正是第 5 节那份自查清单的解药：**旁路也被挡住了。** 报表直连？受策略约束。DBA 手敲的 SQL？受策略约束（除非用超级用户）。

那为什么中文生态用得不多？我能给的诚实回答是三条观察，不是定论：

1. **它绑死 PostgreSQL**。中文生态的 SaaS 基础盘仍以 MySQL 为主，MySQL 没有等价能力。
2. **策略的租户上下文要靠会话变量传递**，而会话变量在连接池（尤其是事务级复用的池）下的正确性需要额外小心——这和 4.4 节末尾那个 `search_path` 的坑是同一类问题。
3. **性能。** RLS 相当于给每条查询附加了一个条件，在大表和复杂查询下的开销、以及它和执行计划的相互作用，**本次没有做实测（未实测）**，我不能给你数字。网上流传的各种"RLS 慢多少"的说法我也建议你一律当作待验证的传闻——**这正是应该在自己的数据分布上跑一遍才敢下结论的题**。

**所以本节的结论不是"选哪条路线"，而是：这两条路线可以叠加。** 应用层改写负责日常业务（性能可控、错误信息友好），数据库层 RLS 负责兜住旁路（哪怕只给报表账号加）。安全上的纵深防御，本来就不该只有一层。

## 7. 租户维度和数据权限维度叠加时谁优先

### 7.1 一个真实的模块

芋道的 `yudao-module-bpm`（审批流模块）在 pom 里**同时依赖了 tenant 和 data-permission 两个 starter**（pom 已核实，2026-08-05）。这不是巧合——审批流是最典型的两个维度叠加的场景：

```
   一张报销单的可见性，要同时满足两个条件
   ┌───────────────────────────────────────────────────┐
   │ 维度一 租户：这张单子属于哪家公司？                  │
   │              别家公司的人绝对不能看见（硬边界）       │
   │ 维度二 数据权限：同一家公司内谁能看见？               │
   │              我提的 / 我审的 / 我管的部门提的（软边界）│
   └───────────────────────────────────────────────────┘
   最终 SQL：
   SELECT * FROM bpm_task WHERE ...业务条件...
     AND tenant_id = 7              ← 租户拦截器加的
     AND dept_id IN (101, 102, 103) ← 数据权限拦截器加的
```

两个条件都是 `AND`，看起来没有优先级问题。**但优先级问题出现在"豁免"的时候。**

### 7.2 优先级的真相：谁能被忽略

第 2.3 节那张继承图给了答案：两个拦截器同基类，但**豁免规则完全不同**。

```
   谁可以被忽略？
   ┌──────────────────┬────────────────┬────────────────────┐
   │ 角色              │ 数据权限条件    │ 租户条件            │
   ├──────────────────┼────────────────┼────────────────────┤
   │ 普通员工          │ 生效           │ 生效                │
   │ 部门主管          │ 生效（范围更大）│ 生效                │
   │ 租户内超级管理员   │ 可忽略 ✓       │ ✗ 不可忽略          │
   │ 平台运营（跨租户） │ 可忽略 ✓       │ 特批可忽略（见 7.3）│
   └──────────────────┴────────────────┴────────────────────┘
                        软边界：业务规则   硬边界：安全边界
                        由角色配置决定     只有平台侧能碰
```

**这张表就是优先级的全部内容**：租户条件比数据权限条件"硬"一级。

最容易出事的是第三行。系统里通常有一个"忽略数据权限"的开关（注解或者上下文标记），给租户的超管、或者给某些必须全量查询的场景用。**危险在于：如果这个开关的实现是"跳过整个 MyBatis 拦截器链"，那它会顺手把租户条件也跳过。**

```
   ✗ @IgnoreDataPermission        // 意图：这个方法不做数据权限过滤
     public List<Task> listAll()  // 实际：整条拦截器链被跳过，租户条件也没了
     → 租户 A 的超管看到了全平台 200 个租户的数据
     → 而且因为他"本来就是超管"，日志里看不出任何异常

   ✓ 两个拦截器各自独立判断自己要不要生效：
     · 数据权限拦截器：看到忽略标记 → 不加条件
     · 租户拦截器：无视这个标记     → 照常加 tenant_id = 7
```

**一句话记住：忽略数据权限，绝不等于忽略租户。** 这两个开关必须是两个开关，而且租户那个开关的权限级别要高得多。

### 7.3 平台侧的跨租户操作，收敛到一处

那"平台运营要看全部租户"这个真实需求怎么办？

```
   跨租户能力只在一个地方存在：

   租户端应用（tenant-app）        平台端应用（admin-app）
   ┌──────────────────────┐      ┌──────────────────────┐
   │ 租户拦截器：强制开启   │      │ 租户拦截器：可显式指定 │
   │ 无任何绕过入口         │      │ tenant_id 或跨租户查  │
   │ 200 个租户的用户都登这 │      │ 只有平台员工能登录     │
   │                      │      │ 独立鉴权 + 全量审计    │
   └──────────────────────┘      └──────────────────────┘
   两个应用可以共用代码，但入口、鉴权、审计必须分开
```

关键在于**跨租户能力是一个部署单元的属性，不是一个用户角色的属性**。把它做成角色（"超管可以跨租户"），意味着任何一次角色配置失误都是一次全平台泄露；把它做成独立应用，攻击面从"一个角色配置"缩小成"一个部署入口"。

💡 这条和[第 37 篇《审批流与工作流引擎》](./37-审批流与工作流引擎.md)有一处直接联动：审批流里"审批人是怎么算出来的"依赖数据权限（候选人范围受部门树约束），而候选人查询本身又受租户约束。**两个维度的叠加顺序在这里必须是：先租户后数据权限**——先把范围锁死在本租户，再在租户内按部门算候选人。反过来（先算部门再限租户）在部门 ID 跨租户重复时会出诡异结果。而[第 36 篇](./36-权限系统.md)讲的那些数据域算法（部门树、上下级、自定义范围），全部是在"租户已经锁定"这个前提下才成立的。

## 8. 反直觉结论

**一、共享表模式最贵的不是拦截器，是索引重建。**

依据：拦截器是一次性接入，一天的工作量；而 12 张业务表 × 4 个二级索引 = 48 个索引全部要在最左边插进 `tenant_id`，两千万行的表每个索引重建是分钟级，加起来是一个完整的维护窗口，还要处理在线 DDL 的锁问题（第 3.2 节）。**而且这笔账随时间只涨不跌**——第一天加是免费的，第三年加是通宵的。

**二、独立库模式会死在连接池上，而不是磁盘上。**

依据：`200 租户 × 10 池大小 × 8 实例 = 16000 连接`，是三个都会自然增长的因子相乘；而 PostgreSQL 的 `max_connections` 默认 100（具体默认值以官方文档为准），且[PG 系列第 10 篇](../2026-08_从真实项目学PostgreSQL/10-连接与超时.md)论证过连接数超过某个点后吞吐反而下降。存储是加法，连接是乘法——**乘法总是先爆**。而 `supabase/supavisor` 的 README 实测数字（单 16 核 64GB 节点 25 万 idle 连接、集群 100 万连接，2026-08-05 实测）恰恰说明了这个问题有多普遍：需要一个专门的组件，专门解决它。

**三、多租户隔离和数据行权限是同一个东西的两种参数。**

依据：`TenantLineInnerInterceptor` 继承 `BaseMultiTableInnerInterceptor`（已读源码），和第 36 篇的数据行权限拦截器同基类。差别只在两点：条件是否因人而变（租户不变，权限变）、是否允许豁免（租户不许，权限允许）。**想不通"多租户该怎么设计"的时候，把它当成一条恒为真、且谁都不能关闭的行权限规则，答案立刻就清楚了。**

**四、越权不在 ORM 里，在没走 ORM 的那条路上。**（此为推论，未实测验证）

依据：走 Mapper 的路径有拦截器系统性兜底，是全系统唯一被保护的路径；而定时任务、报表直连、存储过程、缓存 key、MQ 消费者这些旁路是一次性代码，没人 review。**隔离强度等于最弱的那条数据访问路径**，而拦截器恰恰对最弱的那几条完全无能为力。这也是 PG RLS 这类"把规则写进数据库"的方案在架构上更优雅的原因（虽然它的性能本次未实测）。

**五、大租户不是"好消息"，是架构上的定时炸弹。**

依据：一个占全库 40% 数据的租户会同时引爆三件事——统计信息失真导致执行计划选错（第 3.4 节）、共享资源被单租户占满（开场事故）、分片彻底不均且无法通过扩容缓解（第 6.3 节）。**签下最大的那个客户的那一天，就是你的多租户架构开始需要分层的那一天**（第 1.5 节）。销售在庆祝，架构师应该在排期。

## 9. 一句话总结、小白词典、和前几篇的对照

### 一句话总结

> **多租户隔离要同时解三道题，而它们的难度顺序和直觉相反：越权最好解（一个继承自行权限基类的拦截器，把 select/insert/update/delete 四类全量改写就兜住了），索引第二难（`tenant_id` 进最左前缀 = 全部既有索引重建，且越晚越贵），资源隔离最难（共享表根本解不掉，只能靠把大租户搬出去）；而你一旦为了资源隔离转向独立库，立刻会撞上 `租户数 × 池大小 × 应用实例数` 这道乘法题——所以真实世界的答案从来不是三选一，是一条随租户体量分层的迁移路径。**

### 小白词典

| 词 | 一句人话 |
|---|---|
| **租户（tenant）** | 一个客户组织。同一套代码同一套部署，服务很多家公司，一家就是一个租户 |
| **共享表 + 租户 ID** | 所有租户挤一张表，靠一列 `tenant_id` 区分。最省钱，隔离最弱 |
| **独立 schema** | 一个租户一套表，但在同一个数据库实例里。结构上像独立库，连接上像共享表 |
| **独立库** | 一个租户一个库甚至一个实例。隔离最强，然后死在连接池上 |
| **SQL 改写** | 框架把你写的 SQL 解析成语法树，偷偷加上 `AND tenant_id = ?` 再发给数据库。不是字符串拼接 |
| **`TenantLineInnerInterceptor`** | MyBatis-Plus 干这件事的类，四类语句全改；它和数据行权限拦截器是同一个爹 |
| **忽略表白名单** | 那些不属于任何租户的全局表（字典、配置、租户表自己），必须显式豁免。少配了页面空白，多配了隔离破洞 |
| **最左前缀** | 复合索引 `(a,b,c)` 只能服务以 a 开头的条件。所以 `tenant_id` 必须放最左边，否则索引形同虚设 |
| **数据倾斜** | 一个租户占 40%、另一个占 0.001%。优化器按均匀分布估算，于是估错 80 倍，于是选错执行计划 |
| **部分索引** | 只给满足某条件的行建索引，比如"只给 T-007 建"。穷人版的独立库 |
| **连接池乘法** | `租户数 × 池大小 × 实例数`。三个因子都会涨，相乘就是 16000 |
| **池代理** | 把连接池从应用里挪出来放中间（PgBouncer / supavisor），让数据库只见到几十条连接 |
| **RLS（行级安全）** | 把过滤规则写进数据库本身，连 psql 命令行都绕不过。代价是绑死 PostgreSQL |
| **旁路** | 所有不经过 ORM 的数据访问：报表直连、定时任务、存储过程、缓存。越权的真实入口 |

### 和前几篇的对照

1. **vs [第 36 篇《权限系统》](./36-权限系统.md)**：同样是往 SQL 里塞一个 `WHERE`，同样继承 `BaseMultiTableInnerInterceptor`，但两者的性质相反——数据行权限是**软边界**（条件因人而变、超管可以豁免、错了是业务问题），租户隔离是**硬边界**（条件恒定、谁都不能豁免、错了是安全事故）。差别在于：那篇的难点是"数据域怎么算"（部门树、上下级、自定义范围），本篇的难点是"算出来之后索引扛不扛得住"。第 7.2 节那张豁免表是两篇的接缝：**忽略数据权限的开关，绝不能顺手忽略租户。**

2. **vs [第 14 篇《分库分表》](./14-分库分表.md)**：同样要选分片键，但多租户把这道题一半变简单、一半变更难。简单在于分片键不用选——就是 `tenant_id`，而且 99% 的查询天然带这个条件，同租户的表落同一分片所以 join 不跨片；更难在于**分片必然不均**，第 14 篇的"双倍扩容法"在这里失效，因为一个占 40% 数据的租户你再怎么扩容也切不开，只能整体搬迁。差别在于：普通分片追求均匀，租户分片必须接受不均并为此准备搬迁能力。

3. **vs [PostgreSQL 系列第 08 篇《索引》](../2026-08_从真实项目学PostgreSQL/08-索引.md)**：那篇讲的是"B-tree 的形状决定了 WHERE 该怎么写"，本篇是这条结论最昂贵的一次应用——`tenant_id` 进最左前缀不是加一个索引，是**推翻全部既有索引重建一遍**。而那篇最推荐的"部分索引"在这里找到了最自然的用武之地：租户天然是一个稳定的过滤条件，给超大租户单开部分索引，等于在同一张表里为它辟出一块专属空间。差别在于：那篇教你怎么建对索引，本篇告诉你建错了要付多少钱去改。

4. **vs [PostgreSQL 系列第 10 篇《连接与超时》](../2026-08_从真实项目学PostgreSQL/10-连接与超时.md)**：那篇的两条结论（Postgres 连接很贵、连接数不是越多越好）在本篇被放大到了极致——独立库模式让连接数和**租户数成正比**，而且制造出来的连接 90% 是闲的。那篇讲 PgBouncer 三种模式的取舍，本篇补上一条多租户特有的坑：**schema 模式下事务级连接复用会串 `search_path`**，上一个租户的会话状态可能留给下一个租户。

5. **vs [第 37 篇《审批流与工作流引擎》](./37-审批流与工作流引擎.md)**：同样面对"这条数据谁能看见"，那边是流程内的可见性（审批人、抄送人、发起人），本篇是流程外的硬边界。芋道的 `yudao-module-bpm` 同时依赖 tenant 和 data-permission 两个 starter（pom 已核实）这件事本身就是结论：**两个维度必须按"先租户后数据权限"的顺序叠加**——先把范围锁死在本租户，再在租户内算候选人；反过来在部门 ID 跨租户重复时会出诡异结果。

6. **vs [第 28 篇《分布式调度》](./28-分布式调度.md)**：同样是后台任务，那篇操心的是"不重不漏"，本篇给它加了一个那篇没提的约束——**定时任务的线程里没有租户上下文**。第 5.2 节讲的正是这个：拦截器读不到 `tenant_id` 时如果选择"放行"，你的每一个定时任务都是一次全租户越权。所以多租户系统里的任务框架必须提供"遍历租户、逐个切上下文执行"的封装，这是那篇的分片广播之外，多租户额外要求的一层。

7. **vs [第 15 篇《缓存三兄弟与缓存一致性》](./15-缓存三兄弟与缓存一致性.md)**：那篇操心的是缓存和数据库对不对得上，本篇提醒的是一件更基础的事——**缓存 key 忘了拼租户前缀，数据库层所有隔离做得再好也白搭**（第 5.3 节）。这是本系列里少见的"上层组件能一票否决下层所有努力"的例子：SQL 改写、索引、RLS 全都管不到一个字符串 key 怎么拼。
