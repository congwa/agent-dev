# 《已读回执与万人群消息》5000 人的群，一条消息要维护 5000 份已读状态？（小白版）

> 一句话结论：**钉钉那个"已读 4999/未读 1"，背后并不存在 4999 条已读记录——生产级 IM 根本不记"谁读了哪条消息"，它只给每个成员存一个数字（已读水位线），"这条消息谁读了"是在你点开明细的那一刻现算出来的。更反直觉的是：已读回执这个看起来最轻的小功能，是 IM 里写压力最大的功能之一——不少产品把它做成"可关闭"，客观效果就是给自己装了一个泄压阀。**
> 难度：★★★★☆
> 阅读前提：本篇是[第 9 篇《IM 消息可靠投递》](./09-IM消息可靠投递.md)的直接续集。那篇讲"一条消息怎么可靠送到你手上"，本篇讲"送到之后，'看没看过'这件事怎么管"。seq 是那篇的主角，本篇它还要再立一功。
> 写作时间：2026-08-05。文中提到的具体产品行为（钉钉 / 微信 / WhatsApp 等）以公开可观察的产品表现为准；未经一手核实的说法在文中已标注。
> 读完你会懂：
> 1. "已读 4999"这个数字的真实来历——为什么它不是查了 4999 条记录，而是一次 count 现算
> 2. 已读水位线怎么把存储从 O(消息数 × 成员数) 打到 O(成员数)，以及它付出的语义代价（你的"已读"其实不等于"看过"）
> 3. 未读角标为什么是一条减法，而不是一次遍历
> 4. 为什么群越大、已读功能越少——万人群不显示明细不是抠门，直播式大群连消息都要丢
> 5. IM 群聊的写扩散/读扩散，和第 5 篇微博 Feed 的推拉，为什么是同一道题的两次出现
> 6. 4999 个客户端几秒内同时上报已读的"回执风暴"怎么泄洪——攒批、节流、有界队列、丢了不修

## 0. 开场：已读 4999，未读 1

### 0.1 盯着那行灰色小字看 30 秒

晚上 19:47，你在公司那个 5000 人的钉钉大群里摸鱼。老板突然发了一句：

> "明天全员 9 点开会，收到请回复。"

你盯着这条消息旁边那行灰色小字，看它跳动：

```
   19:47:03   已读 132
   19:47:10   已读 1874
   19:47:25   已读 4102
   19:48:40   已读 4999 / 未读 1
                        ▲
                        └── 全公司都知道有一个人还没看
                            （祈祷那个人不是你）
```

点开"未读 1"，还能看到那个倒霉蛋的名字。

现在把产品滤镜摘掉，问一个纯技术问题：

> **这个数字是怎么来的？服务器是不是给这条消息记了 4999 条"某某某已读"？**

小白的直觉答案：是啊，不然呢？谁读了就记一笔，数一下有几笔，不就是已读人数吗。

这个直觉答案，就是本篇的靶子。它不是错在"不能用"，是错在**用了就得给它陪葬一个数据库**。下面先按这个直觉把系统搭出来，亲眼看它爆炸。

### 0.2 本篇和第 9 篇的分工

[第 9 篇](./09-IM消息可靠投递.md)已经在第 14 节算过"群聊已读是 N² 灾难"这笔账，但它只算到"这事很贵、微信干脆不做"就收手了。本篇接着往下走：

```
   本篇回答：  真要做，怎么做到不破产
              —— 以及做到一半为什么要主动收手（万人群）
```

## 1. 朴素做法：给每条消息发一张签到表

### 1.1 方案：一条消息一张签到表

最直白的建模：已读是一个事件，事件就记一行。

```sql
CREATE TABLE message_read_receipt (
    msg_id   BIGINT,      -- 哪条消息
    user_id  BIGINT,      -- 谁读了
    read_at  BIGINT,      -- 什么时候读的
    PRIMARY KEY (msg_id, user_id)
);
```

每条消息就像会议室门口贴了一张签到表，谁看了谁签个名：

```
   msg_id = 888  "明天全员 9 点开会"
   ┌────────────────────────────────────┐
   │  签到表（每人一行）                │
   │    user_1001   19:47:03            │
   │    user_1002   19:47:03            │
   │    user_1003   19:47:04            │
   │    ...                             │
   │    user_5999   19:48:40            │
   │                                    │
   │  已读人数 = COUNT(*) = 4999        │
   │  未读的人 = 群成员 − 签过名的人    │
   └────────────────────────────────────┘
```

逻辑无懈可击，查询也好写。小群里它完全能跑。问题出在规模上——下面算三笔账。

### 1.2 第一笔账：存储

一个 5000 人的群，一天 1000 条消息（大群里这不算话痨，摸鱼群轻松翻倍）：

```
   每条消息的签到行数：最多 5000 行
   一天的签到行数：    1000 条消息 × 5000 人
                     = ★ 500 万行 / 天 / 群 ★

   对比消息本身：      1000 行 / 天

   ★★ 已读记录是消息本身的 5000 倍 ★★

   一年：500 万 × 365 ≈ 18 亿行（还只是这一个群）
   如果全平台有 10 万个这种量级的活跃大群……
   自己乘一下，数字会大到失去意义
```

这里有个跨篇的冷笑话。[第 14 篇](./14-分库分表.md)刚讲过，《阿里巴巴 Java 开发手册》的原文是"单表超过 **500 万行**才推荐分库分表"，而且本意是劝你别分。这张签到表**一个群一天**就制造 500 万行——等于每天早上给你生产一张"该分表了"的表。第 14 篇教你的第一招是"少存数据"，这张表是反着来的教科书案例：存了一堆**根本没人会逐行去查**的数据。

### 1.3 第二笔账：写入

存储还只是慢性病，写入是急性的：

```
   老板 19:47 发出消息
        │
        ▼
   19:47:03 ~ 19:48:40 之间
   4999 个人陆续点开
        │
        ▼
   每人点开 → INSERT 一行签到记录
   而且不是只签这一条——
   你点开会话时往上翻了 50 条没读的消息，
   按"每条消息一个事件"的模型，要 INSERT ★ 50 行 ★
```

消息本身一天写 1000 行，已读签到一天写 500 万行。**你的数据库 99.98% 的写入量在伺候一个灰色小字。**

### 1.4 第三笔账：推送（第 9 篇的旧账）

签过名还得通知别人。"谁读了要让发送者看到"，如果做成实时推送给全群，就是[第 9 篇 14.2 节](./09-IM消息可靠投递.md#142-群聊已读n-的账)算过的 N²：500 人群一条消息 249,500 次已读推送，5000 人群约 2500 万次。那笔账那边算得很细，这里不重复。

### 1.5 死亡诊断书

```
   ┌─────────────────────────────────────────────────────┐
   │  朴素签到表的病根只有一个：                         │
   │                                                     │
   │     把"已读"当【事件】存 —— 发生一次，记一行        │
   │                                                     │
   │  于是三个成本全部正比于  消息数 × 成员数：          │
   │     存储  O(M × N)                                  │
   │     写入  O(M × N)                                  │
   │     推送  O(M × N²)（如果还要实时广播）             │
   │                                                     │
   │  而群聊场景 M 和 N 都大，乘起来就是天文数字         │
   └─────────────────────────────────────────────────────┘
```

出路也只有一个方向：**别把已读当事件存，把它当状态存。** 讲这个状态长什么样之前，先花 30 秒复习一个老朋友。

## 2. 前置复习：09 篇的会话级 seq

一句话版本：

> **每个会话（单聊或群）内部，服务端给每条消息分配一个连续递增的整数：1, 2, 3, 4……全会话共用一条号码线，不分谁发的。**

[第 9 篇第 7 节](./09-IM消息可靠投递.md#7-seq-号一个设计解决四个难题)用这一个整数一口气解决了丢失检测、去重、排序、多端同步四个难题，我们叫它"银弹时刻"。三条铁律（单调、连续、服务端分配）也在那边，此处不展开。

本篇你只需要记住 seq 的一个推论：

> **因为 seq 连续且单调，"我读到哪了"可以用一个数字完整描述。**

这句话就是下一节的全部。

## 3. 银弹第二次登场：已读水位线 ⭐（本篇核心）

### 3.1 每个成员，只存一个数

把签到表整个扔掉，换成这个：

```
   每个成员在每个群里，只存一个数字：

       max_read_seq  ——  "我读到第几条了"

   群成员状态表（一个 5000 人的群，永远只有 5000 行）：
   ┌───────────┬──────────────┐
   │  user_id  │ max_read_seq │
   ├───────────┼──────────────┤
   │  1001     │     890      │   ← 读到最新了
   │  1002     │     887      │   ← 还差 3 条
   │  1003     │     712      │   ← 一周没点开这个群
   │  ...      │     ...      │
   │  5999     │     890      │
   └───────────┴──────────────┘
```

这个数字叫**已读水位线**（read watermark）。水位这个词很形象：水面下（seq ≤ 水位）的全淹了——全读过；水面上的还露着——没读。

### 3.2 关键转变："这条消息谁读了"改成读时计算

签到表回答"seq=888 谁读了"，靠的是**写的时候记下来**。水位线回答同一个问题，靠的是**查的时候现算**：

```
   "seq=888 这条消息，谁读了？"

        =  群成员里，水位 ≥ 888 的人

   SELECT count(*) FROM group_member_state
   WHERE  group_id = ? AND max_read_seq >= 888;
                                            → 已读 4999

   SELECT user_id  FROM group_member_state
   WHERE  group_id = ? AND max_read_seq <  888;
                                            → 未读那 1 个人是谁
```

开头那个"已读 4999/未读 1"，来历就是这两条查询——**5000 行的小表上一次聚合**，配上索引毫秒级。而且通常只在有人**点开明细时**才查（第 9 篇 14.4 节的拉模式），平时连算都不算。

### 3.3 前后对比图（本篇最重要的一张图）

```
 ┌── 朴素签到表：写时记录 ──────────────────────────────────────────┐
 │                                                                  │
 │            成员1   成员2   成员3   ……   成员5000                 │
 │   seq=1     ✓       ✓       ✗             ✓      → 5000 个格子   │
 │   seq=2     ✓       ✗       ✗             ✓      → 5000 个格子   │
 │   seq=3     ✓       ✓       ✓             ✗      → 5000 个格子   │
 │    ⋮                     ⋮                              ⋮        │
 │   seq=1000  …                                    → 5000 个格子   │
 │                                                                  │
 │   每个格子 = 数据库里实实在在的一行                              │
 │   一天 = 1000 × 5000 = ★ 500 万行 ★，而且明天还有 500 万         │
 └──────────────────────────────────────────────────────────────────┘

 ┌── 已读水位线：读时计算 ──────────────────────────────────────────┐
 │                                                                  │
 │   群 timeline（消息只存这一份，一天 1000 行）：                  │
 │                                                                  │
 │   ──1──2──3──┄┄──886──887──888──889──890─▶  seq 数轴             │
 │                    ▲              ▲    ▲                         │
 │                    │              │    │                         │
 │        成员1003 的游标   成员1002 的游标  成员1001 的游标        │
 │           (712…画不下)      (887)         (890)                  │
 │                                                                  │
 │   每个成员 = 数轴上的一个游标（一个整数）                        │
 │   全群状态 = 5000 个整数，★ 永远是 5000 个 ★，和消息数无关       │
 │                                                                  │
 │   "seq=888 谁读了" = 数一数游标在 888 或右边的人 → 现算，不存    │
 └──────────────────────────────────────────────────────────────────┘
```

复杂度对账：

| | 签到表（事件） | 水位线（状态） |
|---|---|---|
| 存储 | O(消息数 × 成员数)，随时间无限涨 | **O(成员数)**，恒定 |
| 一次"读了 50 条" | 写 50 行 | **写 1 行**（更新一个数字） |
| "这条消息谁读了" | 读现成记录 | 一次 count 现算 |
| "已读"语义 | 精确到每条 | 只能表达"读到哪了"（前缀） |

注意右下角那格——水位线不是白捡的，它**换走了一部分语义**。第 4 节专门算这笔账。

### 3.4 写入量为什么也塌下来了

存储降维好理解，写入的降维更妙一点：

```
   签到表：   上报次数 ∝ 你【读了多少条消息】
   水位线：   上报次数 ∝ 你【打开了几次会话】

   你点开群，从 seq=838 一路刷到 890（看了 52 条）：
      签到表   → 52 次 INSERT
      水位线   → 报一次 { read_seq: 890 }，1 次 UPDATE

   一个数字覆盖一批消息 —— 这是水位线的"批量天赋"
```

第 9 篇 14.1 节在单聊里已经让这招露过一面（"B 报一次 read_seq=301，A 就知道 1~301 全已读"）。本篇把它扶正成主角，是因为**在群聊里它的收益乘了一个 N**：单聊省的是回执条数，群聊省的是 5000 人 × 回执条数。

### 3.5 为什么说这是 seq 的第二次收益

第 9 篇说 seq 是银弹，指它一个设计吃下四个难题。已读水位线不是一个新发明——**它是 seq 的连续性送的赠品**：

```
   seq 连续单调
       │
       ├── 于是"我读到哪"能用一个整数完整描述     ← 没有连续性就没有这句
       │
       ├── 于是"谁读了 seq=X"能用比大小算出来
       │
       └── 于是"我还有几条没读"能用减法算出来（第 4.4 节）

   如果消息 ID 是随机串（UUID / 雪花），
   "我读到 a3f2b1 了"对推断其他消息读没读【毫无帮助】
   —— 你就只能退回签到表
```

说白了：**朴素方案存 500 万行，不是因为工程师蠢，是因为没有 seq 这条数轴时，已读状态压根"压缩"不了。** 水位线是 seq 数轴上的一次无损压缩（对"前缀已读"语义而言无损）。

## 4. 水位线的前提与破绽：跳读、进群、角标

### 4.1 前提：已读必须"连续推进"

水位线只能表达一种形状的已读状态——**前缀**：

```
   能表达：   1~890 全读了                    ██████████░░░  ✓
   不能表达： 读了 1~10 和第 15 条，          ███░░░█░░░░░░  ✗
              中间 11~14 没读
```

一个整数只有一个刻度，表达不了中间有洞的形状。那现实里"有洞"的情况存在吗？存在，而且天天发生。

### 4.2 破绽：跳读

```
   你有 300 条未读（水位 = 590，最新 = 890）
   锁屏通知弹出老板那句话，你直接点通知进入会话
        │
        ▼
   会话定位到最新的 seq=890，你看了这一条
   中间 591~889 那 299 条，你【一个字都没看】
        │
        ▼
   但客户端上报的是  { read_seq: 890 }
   —— 那 299 条被四舍五入成"已读"
```

工程上的取舍，各家产品实际都是这么做的：

> **只要你打开会话、视图拉到了某个位置，该位置之前的全部视为已读。**

这不是偷懒，是一次清醒的语义收窄：

```
   产品字面语义：  已读 = 看过这条消息
   实际系统语义：  已读 = 这条消息曾经出现在你打开过的会话视图之前

   收窄换来的：    已读状态从 O(M×N) 压到 O(N)
   收窄丢掉的：    "他真的逐条看了吗"—— 本来也没有哪个系统能保证
                   （眼动仪都不行，看了≠走心）
```

💡 换个角度想：签到表那种"精确到每条"的语义，精确得很虚假——用户滚轮划过去算不算读？渲染在屏幕上 0.3 秒算不算读？**既然"读"本身就是个模糊概念，为模糊概念付出精确存储的代价，是纯亏。** 这和[第 12 篇](./12-小而美的五个算法.md)的主线一模一样：先问"这里的不准会不会伤到人"，不会，那就大方地不准，把省下的数量级装进口袋。

### 4.3 进群怎么初始化水位

新成员进群，他的 max_read_seq 填多少？

```
   选择 A：填 0
      → 角标显示"你有 88 万条未读"，吓死人
      → 已读统计里他永远拖后腿（进群前的消息他"未读"）

   选择 B：填 进群那一刻的最新 seq        ← 通用做法
      → 此前的消息一律视为"与他无关"
      → 角标从 0 开始涨，符合直觉
```

选 B 还有一个产品层的呼应：微信新成员本来就看不到进群前的历史消息（可观察的产品行为）；有些产品允许新成员看历史（部分社群类产品可配置，具体各家行为未逐一核实），但即便能看，也不会把历史算进他的"未读"。**"进群拉到最新即视为此前全部已读"，是水位线模型下最顺滑的初始化。**

### 4.4 未读角标：同一个数字的另一面

会话列表上每个群的红色角标数字，是小白最容易想歪的地方——直觉是"数一数有几条没读的消息"，也就是去遍历消息表。真实做法：

```
   unread = 群最新 seq − 我的 max_read_seq

   群 timeline 最新 seq = 890
   我的水位            = 712
   角标                = 890 − 712 = 178

   ★ 一条减法。零次消息表扫描。 ★
```

你的会话列表有 200 个会话？渲染全部角标 = 200 次减法。每个会话只需要两个整数（latest_seq 缓存在会话元数据里，read_seq 在成员状态里），所以 IM 客户端冷启动时那一排角标能瞬间画出来——它根本没碰消息数据。

这里有个坑，顺手说了：**撤回的消息 seq 不回收**（seq 铁律之一是连续分配，撤回只是把内容替换成"XX 撤回了一条消息"这个系统事件）。如果撤回做成"物理删除且 seq 留洞"，减法算出的角标就会虚高。所以主流实现里撤回是"内容置换"不是"删行"——保住 seq 数轴的连续性，比省那一行存储重要得多。

### 4.5 小结：水位线的适用边界

```
   水位线成立的三根柱子：
   ① seq 连续单调（第 9 篇的地基）
   ② 产品接受"前缀已读"语义（跳读四舍五入）
   ③ 已读只进不退（没有"标记为未读"…吗？）

   关于 ③：不少邮箱和 IM 有"标记未读"功能。
   实现上通常不是把水位倒回去（倒回去会连累角标和多端合并），
   而是给会话打一个独立的"手动未读"标志位 —— 水位线本身保持单调。
   （各家实现细节未逐一核实，但"水位保持单调"是多端合并能成立的前提，
    见第 8 节，倒退的水位会让 max 合并直接失效。）
```

## 5. 群越大，已读功能越少：退化是设计出来的

### 5.1 一个观察：已读功能是随人数"掉档"的

把市面上的 IM 按群规模排开，你会看到一条清晰的退化阶梯：

| 规模 | 已读功能形态 | 例子（可观察的产品行为） |
|---|---|---|
| 单聊 | 逐条已读状态（甚至"对方正在输入"） | 钉钉/WhatsApp 单聊 |
| 几十人小群 | 已读人数 + 点开看明细名单 | 钉钉/企业微信群 |
| 几百到几千人大群 | 只有人数、明细弱化，或干脆没有 | 各家行为不一，阈值未逐一核实 |
| 万人群 / 频道 | 无已读概念，只有"浏览量"级别的模糊计数 | Telegram 频道的 view 数 |
| 直播式聊天室 | 连消息本身都合并、抽样、丢弃 | 见[第 6 篇弹幕](./06-直播弹幕与广播.md) |

### 5.2 万人群不显示明细：算力能做，产品无意义

注意一个容易想反的点：有了水位线，**万人群的已读明细在算力上是做得起的**——1 万行的成员表做一次 count，不是什么难事。真正杀死这个功能的是产品判断：

```
   "已读 8734 / 未读 1266"
        │
        ├─ 发送者会因此做什么不同的决策吗？   基本不会
        ├─ 有人会翻 1266 人的未读名单吗？     翻到第 3 屏就放弃
        └─ 8734 个人的"已读"里有多少是跳读？  参考 4.2 节，一大半
                                              （数字越大，含金量越低）
```

这和[第 18 篇排行榜](./18-排行榜与计数系统.md)里"只做 Top 100，长尾根本没人看"是同款判断：**系统能算 ≠ 值得算。** 排行榜砍掉第 100 名之后的精确名次，已读明细砍掉大群的逐人名单，都是把资源从"没人消费的精确"上撤走。

万人群通常保留的是那条**减法角标**（第 4.4 节）——因为它 O(1)、因为"我有多少没看"对每个用户都有真实价值。已读功能的退化顺序，恰好就是"单位成本的用户价值"排序。

### 5.3 直播式超大群：消息本身先没了，已读无从谈起

再往上走一档，10 万人的直播间聊天区。这时候讨论"已读"已经是个假问题——**消息本身都送不全**：

```
   10 万人房间，每秒 1000 条发言
   如果每条都推给每个人：10 万 × 1000 = 1 亿次推送/秒

   第 6 篇弹幕的答案在这等着：
      合并推送（100ms 攒一批）＋ 分级（礼物可靠、闲聊尽力）
      ＋ 超过下发预算直接【丢弃】
```

一条消息连"必达"都放弃了，自然没有"已读"。回头看这条阶梯，它其实是同一个约束的连续谱：**人数 N 每上一个数量级，就要砍掉一层"每人一份"的东西**——先砍逐条已读记录（本篇），再砍已读明细（5.2），再砍消息必达（第 6 篇）。IM 的架构演化史就是一部"每人一份"的裁员史。

## 6. 消息本身怎么扩散：IM 群聊和微博 Feed 是同一道题

已读状态讲完了，往下挖一层：**消息本体**在群里是怎么存、怎么分发的。这层[第 9 篇第 11 节](./09-IM消息可靠投递.md#11-群聊读扩散-vs-写扩散)算过 100 倍成本差的大账（写扩散 3000 亿行/天 vs 读扩散 30 亿行/天），本篇不重算，补的是那篇没点破的一层窗户纸。

### 6.1 快速回放：两种扩散

```
   写扩散：发消息时复制 N 份，塞进每个成员自己的收件箱
           （写贵读贱 —— 读只看自己的箱子）

   读扩散：消息只存 1 份在群 timeline，成员各自按 seq 来取
           （写贱读贵？—— 等等，群聊的读真的贵吗，见 6.3）
```

### 6.2 窗户纸：这就是第 5 篇的推和拉

把[第 5 篇微博 Feed](./05-微博热点Feed流.md) 的推拉表格拿来，逐行换词：

| | 微博 Feed（第 5 篇） | IM 群聊（第 9 篇 + 本篇） |
|---|---|---|
| 一份内容发出 | 一条微博 | 一条群消息 |
| 内容的受众 | 粉丝列表 | 群成员列表 |
| 写扩散（推） | 写进每个粉丝的收件箱 | 写进每个成员的收件箱 |
| 读扩散（拉） | 打开 Feed 时去关注对象那里现拉 | 打开会话时按 seq 区间拉群 timeline |
| 爆炸点 | 大 V：千万粉丝 × 1 条 = 千万次写 | 大群：万人 × 1 条 = 万次写 |
| 实际选择 | 推为主，大 V 走拉（推拉结合） | 小群可写扩散，大群读扩散 |
| 用户的"读到哪" | 上次刷到的位置 | read_seq / 收到 seq 水位 |

**IM 群聊和微博 Feed 是同一道题的两次出现。** 粉丝关系和群成员关系在数据结构上是同一个东西：一个"内容源 → 接收者集合"的一对多映射。写扩散/读扩散的抉择、按规模分档的混合策略、连"水位线"这个概念本身（Feed 里你上次刷到哪，不也是一个游标吗），全都能一一对上。

### 6.3 那为什么两边的"默认答案"不一样

同一道题，微博默认写扩散（推为主），IM 群聊默认读扩散——方向相反。差别藏在**读扩散的读取成本**里：

```
   微博拉模式的一次读：
      你关注了 500 个人
      → 去 500 条 timeline 各取最新
      → ★ 500 路归并 ★ 排序出你的 Feed
      → 读很贵，所以微博宁可写扩散预先算好

   IM 群聊读扩散的一次读：
      你打开一个群
      → 去 ★ 1 条 ★ 群 timeline
      → WHERE seq > my_seq ORDER BY seq 顺序读一段
      → 单路顺序读，便宜到可以忽略
```

```
        读扩散的成本 ≈ 读取时要归并几路

   Feed：接收者自己聚合 N 个内容源  → 拉贵 → 偏向推
   群聊：会话本身就是聚合点，只有 1 个源 → 拉贱 → 偏向拉
                    ▲
                    │
        ★ 会话（conversation）天然是个聚合好的 timeline，
          这是 IM 比 Feed 幸运的地方 ★
```

💡 所以别背"IM 用读扩散"这种结论，背这个判据：**内容在读取端需要归并几路？一路，读扩散几乎白拿；几百路，读扩散会把打开动作拖死。** 第 5 篇大 V 走拉，是因为大 V 只占关注列表里的少数几路，归并压力可控——同一个判据的另一次应用。

顺带一提：业界公开分享里常说微信的消息同步采用每用户收件箱式的写扩散、群上限与此有关（第三方来源与技术大会分享，未经官方文档确认）。如果为真，它正好演示了判据的另一头——**肯为写扩散付钱，买到的是"每个用户只有一条同步 timeline"的多端同步简单性**。工程没有免费答案，只有明码标价。

## 7. 在线推、离线拉：消息同步的断点续传

### 7.1 分发的时机问题

存储模型定了（大群：群 timeline 一份），下一个问题是"怎么送到 5000 个成员手上"。成员分两种状态，待遇完全不同：

```
                张三在群里发言（服务端写入 timeline，seq=891）
                              │
             ┌────────────────┴────────────────┐
             ▼                                 ▼
        在线成员（有长连接）              离线成员（连接不在）
             │                                 │
        实时【推】过去                     什么都不做
        （最多再配一条厂商通道             （等他回来自己【拉】）
          的系统通知）
```

时序图，重点看右边那条离线的：

```
     手机(在线)              服务端                 电脑(离线两小时)
        │                      │                        ×
        │◀── 推 seq=891 ───────│                        ×
        │─── ACK ─────────────▶│                        ×
        │                      │                        ×
        │                      │              （电脑上线，建立长连接）
        │                      │◀── "我这个群的水位是 875，│
        │                      │     把之后的给我" ────────│
        │                      │                          │
        │                      │─── 返回 seq 876~891，    │
        │                      │    共 16 条 ────────────▶│
        │                      │                          │
        │                      │◀── "收到，水位更新 891" ─│
```

### 7.2 这就是断点续传

电脑上线时说的那句话，翻译一下就是下载工具的断点续传：

```
   下载器：  "这个文件我收到 875 MB 了，从第 876 MB 继续给"
   IM 端：   "这个会话我收到 seq 875 了，从 876 继续给"

   共同点：
   ① 用一个单调递增的偏移量描述进度（字节偏移 / seq）
   ② 断了随便断，重连从偏移量继续，不重传也不漏
   ③ 偏移量由接收方保管并上报 —— 服务端不用记"我给他发过什么"
```

第 ③ 点是省服务端状态的关键，也是[第 9 篇 7.6 节](./09-IM消息可靠投递.md#7-seq-号一个设计解决四个难题)多端同步的复用：**服务端不维护每个端的投递清单，每个端自带进度条。** 5000 人的群，服务端不需要 5000 份"发送进度"，因为进度分散在 5000 个客户端自己手里。

### 7.3 大群的"推"也要打折

万人群里，就算 8000 人同时在线，一条消息逐条推 8000 次长连接写也顶不住高峰。所以大群的在线推普遍退一步：

```
   小群：  推【消息本体】          → 收到即显示，最快
   大群：  推【通知信号】          → "你有新消息，最新 seq=903"
              │                       客户端收到信号后自己来拉一批
              ▼
           几百 ms 攒一次，批量下发（有新消息合并成一个信号）
```

推信号不推本体，配合攒批，下行量从"消息数 × 在线人数"降到"信号频率 × 在线人数"。这招你在[第 6 篇弹幕](./06-直播弹幕与广播.md)见过原型（合并推送），在第 9 篇 14.5 见过它用在已读数字上——同一把锤子，第三次出现。

## 8. 多端同步：取 max 就完事了吗

### 8.1 两条水位线，别搞混

第 9 篇第 12 节讲过"每个端一条独立水位线"，那说的是**收到水位**（recv_seq，同步进度）。本篇的**已读水位**（read_seq）和它不是一个东西，而且多端策略正好相反：

```
   ┌──────────────────────────────────────────────────────────┐
   │  收到水位 recv_seq  ——【每端一条】                       │
   │                                                          │
   │     手机 recv=891   电脑 recv=875   平板 recv=0(关机)    │
   │                                                          │
   │     各端下载进度本来就不同，必须分开记                   │
   │     （第 9 篇 12 节的地盘）                              │
   ├──────────────────────────────────────────────────────────┤
   │  已读水位 read_seq  ——【每人一条，所有端共享】           │
   │                                                          │
   │     "读没读过"是【人】的属性，不是设备的属性             │
   │     你在电脑上看了消息，手机上必须同步变已读             │
   │     （不然就是那个经典 bug：手机角标永远消不掉）         │
   └──────────────────────────────────────────────────────────┘
```

### 8.2 合并规则：max，以及为什么 max 够了

多端上报怎么合并成一条人级水位？一行代码：

```
   read_seq = max(read_seq, 上报值)
```

看它扛住三种乱局：

```
   场景 1：手机报 890，电脑随后报 875（电脑看的是旧位置）
       max(890, 875) = 890            ✓ 旧值迟到，无事发生

   场景 2：电脑的上报在网络里堵了 10 分钟才到
       乱序到达，max 不在乎先来后到    ✓ 乱序无害（交换律）

   场景 3：客户端不放心，同一个 890 报了 3 次
       max(890, 890) = 890            ✓ 重复无害（幂等）
```

数学上这三条分别叫幂等、交换、单调——一个只增不减的数配上 max 合并，**怎么折腾结果都对**。分布式领域给这类"随便合并都收敛"的结构起了个名字叫 CRDT，水位线取 max 是它最迷你的案例（一句话带过，展开就跑题了）。

### 8.3 这个性质值多少钱：它决定了已读可以走"烂"通道

第 9 篇 14.7 节说过已读回执可以丢、可以延迟。现在你知道**为什么敢**了：

```
   消息本体：  丢了 = 事故     → 必须 ACK + 重传 + seq 补拉（第 9 篇全篇）
   已读水位：  丢了 = 没事     → 下一次上报自带全量状态，直接覆盖

   因为水位是【状态】不是【事件】：
      事件丢了，那件事就没发生过，必须重传
      状态丢了，等下一个状态来就好 —— 每次上报都是完整的自我修复
```

这是"把已读当状态存"(第 3 节) 在传输层的第二次分红：存储上它省掉 500 万行，传输上它让整条已读链路**降级成尽力而为**——正是下一节泄洪方案敢往死里丢的底气。

## 9. 已读回执风暴：4999 个客户端同时开火

### 9.1 风暴长什么样

回到开场那一幕，这次站在服务端机房里看：

```
   19:47:00   老板发言，seq=888（1 条消息，1 次写入）
   19:47:01   5000 台手机同时弹通知、亮屏
   19:47:03 ~ 19:48:40
              4999 个人陆续点开会话
              每个客户端都想立刻上报 { read_seq: 888 }

              ┌─────────────────────────────────┐
              │   上行：≈ 4999 次已读上报        │
              │   全部挤在 100 秒内              │
              │   而且全平台不止这一个群在爆     │
              └─────────────────────────────────┘

   ★ 1 次消息写入，带出 ≈ 5000 次状态写入 ★
   写压力的大头不是消息，是那个灰色小字 —— 又见 1.3 节的比例
```

水位线已经把"每条消息一行"压成"每人一个数"，但**上报动作本身**还是 O(N) 的——5000 个人各自点开，就是 5000 次上报。这层要靠流量手段泄洪，分三段。

### 9.2 第一段：客户端攒批 + 节流

最便宜的削峰在源头：

```
   客户端已读上报策略（常见做法）：

   ① 进入会话不立刻报 —— 等 2~5 秒，攒着
   ② 停留期间持续阅读，水位一直在涨 —— 定时器到了才报【当前最大值】
        19:47:03 读到 888   ┐
        19:47:04 读到 889   ├── 攒批：只报一次 { read_seq: 890 }
        19:47:05 读到 890   ┘
   ③ 离开会话 / 切后台 —— 立刻补报一次（兜底，别让水位躺在内存里）

   效果：上报次数从"读了几条"退化成"每几秒最多一次"
         + 水位天然可合并（8.2 节），攒批零成本 —— 报最新值就行
```

注意 ③ 的兜底：攒批的风险是客户端崩溃时丢掉没上报的水位。丢了会怎样？角标多显示几条、已读数少 1，**下次打开会话自动修复**（8.3 节的自愈）。风险的代价小到可以不管——这就是为什么已读能攒批，而消息发送不能。

### 9.3 第二段：服务端有界队列 + 敢丢

上报到了服务端，进的不是消息那条"高可靠主干道"，是一条旁路：

```
        4999 个上报涌进来
              │
              ▼
   ┌─────────────────────────┐
   │ 立即 ACK，落入有界队列  │ ← 队列有长度上限
   │ 队列满？直接丢，不重试  │ ← 丢了等下次上报覆盖
   └───────────┬─────────────┘
               ▼
   ┌─────────────────────────┐
   │ 消费者按 (group, user)  │ ← 同一人的多次上报合并成一次
   │ 合并后批量 UPDATE       │    max 合并，攒 100ms 刷一批库
   └─────────────────────────┘
```

这两板斧都是[流量系列](../2026-08_流量扛不住了怎么办_六种真实做法/02-第三方webhook回调-立即ACK与有界队列.md)的现役装备："立即 ACK + 有界队列"对应 webhook 回调那篇的主方案；"超载直接丢"对应 [IoT 上报那篇](../2026-08_流量扛不住了怎么办_六种真实做法/03-IoT设备上报行情推送-丢弃与采样.md)的丢弃与采样——IoT 传感器读数和已读水位是同一类数据：**新值覆盖旧值、丢一帧无所谓的状态流**。那两篇讲的是通用手法，本篇是它们在 IM 里的对号入座。

### 9.4 第三段：下行聚合，只喂发送者

已读数字变了要通知谁？第 9 篇 14.5 节的两板斧直接搬来：**只推给发送者**（4999 个围观群众不需要实时知道彼此读没读），**几秒聚合一次只推数字**（"已读 4102"这种数字，每 5 秒刷一次和每 50ms 刷一次，用户体验没有区别）。开场那行会跳的灰色小字，跳动的节奏就是这个聚合窗口。

### 9.5 ⚠️ 反直觉主菜：已读回执是 IM 里写压力最大的功能之一

把三段泄洪全做完，回头看总账，依然吓人：

```
   一条群消息引发的写操作（5000 人群，全员看了）：

      消息本体：     1 次写入（读扩散，timeline 一行）
      已读水位：     ≈ 数千次上报 → 合并后仍是数千次 UPDATE 量级

   全平台放大（第 9 篇 14.6 的微信量级估算口径，估算值）：
      日消息量百亿级 × 平均群人数几十
      → 已读事件量级 ≈ 数千亿次/天，比消息本身【大一个数量级】
```

一个界面上最不起眼的功能，吃掉了系统里最大份额的写入。所以你会看到一个耐人寻味的产品现象：**WhatsApp 的蓝勾、iMessage 的已读回执，都提供关闭开关**（产品内可见的设置项）。对外的话术是隐私，这没错；但站在机房角度，每多一个关掉的用户，峰值写入就少一截——**隐私开关同时是个泄压阀**。至于当初做决策时技术占几成动机，没有一手资料，不替人家下结论；能下的结论是：一个可关闭的重成本功能，比一个不可关闭的，让架构师晚上睡得着得多。微信群聊干脆不做（第 9 篇 14.6 的技术账 + 产品账），是同一根算盘上更狠的一档。

## 10. 动手实验：60 行 Python 跑通水位线

纯标准库，复制下来 `python3` 直接跑。它把本篇的四个主角——水位线、读时计算、减法角标、max 合并——全塞进一个类里：

```python
# 已读水位线最小实现 —— 纯标准库，直接运行
import random

class Group:
    def __init__(self, members):
        self.latest_seq = 0                       # 群 timeline 最新 seq
        self.read_seq = {m: 0 for m in members}   # ★ 每人只存一个数字 ★

    def send(self):
        """发一条消息：seq 自增。消息本体只存一份（读扩散）。"""
        self.latest_seq += 1
        return self.latest_seq

    def report_read(self, member, seq):
        """已读上报：单调合并取 max —— 重复报/乱序报/报旧值，全都无害。"""
        self.read_seq[member] = max(self.read_seq[member], seq)

    def read_count(self, msg_seq):
        """"这条消息谁读了" = 读时计算，全程没存过任何已读记录。"""
        return sum(1 for s in self.read_seq.values() if s >= msg_seq)

    def unread_badge(self, member):
        """未读角标 = 一条减法，零次消息扫描。"""
        return self.latest_seq - self.read_seq[member]

if __name__ == "__main__":
    N = 5000
    g = Group(range(N))

    for _ in range(887):                  # 群里已经聊了 887 条
        g.send()
    for m in range(N):                    # 各人读到的位置参差不齐
        g.report_read(m, random.randint(800, 887))
    g.report_read(N - 1, 887)             # 装死那位其实早读完了 887 条

    boss = g.send()                       # 老板发言，seq=888
    print("老板消息 seq =", boss)
    print("发出瞬间：已读", g.read_count(boss), "/", N)

    for m in range(N - 1):                # 4999 人陆续点开，1 人装死
        g.report_read(m, boss)
    print("几秒之后：已读", g.read_count(boss), "/", N)
    print("装死那位的角标 =", g.unread_badge(N - 1))

    # 乱序 + 重复 + 旧值上报，验证 max 合并的免疫力
    g.report_read(0, 850)                 # 电脑迟到的旧上报
    g.report_read(0, 888)                 # 手机重复上报
    g.report_read(0, 888)                 # 再重复一次
    print("成员 0 被乱报三次后 read_seq =", g.read_seq[0])
```

运行输出（每次都一样——随机数只影响 800~887 的初始水位，不影响任何一行打印）：

```
老板消息 seq = 888
发出瞬间：已读 0 / 5000
几秒之后：已读 4999 / 5000
装死那位的角标 = 1
成员 0 被乱报三次后 read_seq = 888
```

对着输出数一下这个程序的状态量：5000 人的群，聊了 888 条消息，全部已读状态 = **一个 5000 项的 dict 加一个整数**。换成第 1 节的签到表，同样的信息要 400 多万行。把 `N` 和消息条数各改大 10 倍再跑一次，dict 还是那个 dict——这就是 O(成员数) 和 O(消息数 × 成员数) 的手感差别。

## 11. 反直觉结论

一篇看下来，值得带走的反直觉点集中报数：

1. **"已读 4999"背后没有 4999 条记录。** 它是 5000 行小表上的一次 count，而且多半只在你点开明细时才算。"写时记录"换成"读时计算"，是本篇最大的一次乾坤挪移。

2. **你的"已读"不是"看过"，是"打开过"。** 跳读的 299 条被四舍五入成已读（4.2 节）。系统层面的"已读"从来都是前缀语义——为一个本来就模糊的概念（"读"）付出精确存储，是纯亏。

3. **已读回执是 IM 里写压力最大的功能之一。** 界面上最轻的灰色小字，制造着比消息本体大一个数量级的事件量（9.5 节）。"可关闭的已读回执"客观上是个泄压阀，微信群聊不做已读是同一根算盘上更狠的一档。

4. **越"不可靠"的通道越配得上水位线。** 已读上报可以攒批、可以丢、可以乱序——不是它不重要，是 max 单调合并让任何丢失都能被下一次上报自愈（8.3 节）。状态流和事件流的可靠性要求，天生差一个等级。

5. **未读角标从不数消息。** 它是两个整数的减法。所以 200 个会话的角标能瞬间画出来，也所以撤回必须"置换内容"而不是"删行"——保数轴连续比省一行存储重要（4.4 节）。

6. **群越大，功能越少，这是设计不是偷懒。** 逐条已读 → 只有人数 → 没有已读 → 连消息都丢，每上一个数量级就裁掉一层"每人一份"的东西（第 5 节）。万人群不显示明细，卡住它的不是算力是产品判断——和排行榜只做 Top 100 同款。

## 12. 一句话总结 + 小白词典

> **已读回执的正解，是把"谁读了哪条"这个 O(消息数 × 成员数) 的事件海，压缩成每人一个整数的水位线——靠的是第 9 篇那条连续 seq 数轴；"谁读了"改成读时现算，"没读几条"改成一条减法，上报走可以随便丢的旁路。而当群大到一定程度，正解变成不做：算力买得起的功能，产品也未必付得起。**

### 小白词典

| 词 | 一句人话 |
|---|---|
| 已读水位线（read watermark） | "我读到第几条了"这一个数字；数字以下全算读过，以上全算没读 |
| max_read_seq | 水位线在数据库里的名字：每人每会话一个整数，只涨不跌 |
| 读时计算 | 不存"谁读了"，等有人问的时候用水位比大小现场算出来 |
| 前缀语义 | 水位线只能表达"1 到 X 全读了"，表达不了中间有洞——跳读会被四舍五入 |
| 未读角标 | 群最新 seq 减你的水位，一条减法，不数消息 |
| 写扩散 / 读扩散 | 一份内容是发的时候复制 N 份、还是存一份大家自己来取；群聊大了选后者 |
| 收件箱 / 群 timeline | 写扩散存的是"每人一个箱子"，读扩散存的是"全群共用一条消息轴" |
| 攒批 / 节流 | 客户端把几秒内的多次已读合成一次上报——水位可合并，只报最新值就行 |
| 单调合并 | 多端各报各的，服务端取 max；重复、乱序、丢失全都无害的合并方式 |
| 泄压阀 | 可关闭的重成本功能：用户每关一个，峰值写入少一截 |
