## 0. 先讲个故事：一亿条还款提醒

### 0.1 需求长什么样

你在一家银行的信用卡中心写代码。产品需求一句话：

> 每天早上 8 点，给当天到还款日的持卡人推一条提醒："您今天需要还款 XXX 元。"

持卡人总数一亿。每天到期的是其中一部分，但也是千万级。

这条提醒不是锦上添花。用户没收到提醒、忘了还款、产生逾期记录，会打客服电话骂人，闹大了会上监管投诉。所以它有两条底线：

- **不能漏**：该收到的人必须收到；
- **不能重**：一人一条，发两条用户会怀疑银行系统坏了，发十条会上热搜。

至于"8 点整"——说白了，8 点零 2 分发出去没有任何人在意。记住这个感觉，第 7 节要用它翻案。

### 0.2 最朴素的做法：一台机器 + crontab

谁都会写：

```
# crontab -e
0 8 * * *  /usr/bin/python3 /app/send_reminders.py
```

脚本里扫一遍"今日到期"表，逐个调推送接口。上线第一天，跑通了，提醒发出去了，收工。

这个方案能活多久？取决于三个死穴哪个先发作。

### 0.3 死穴一：单点 —— 挂了，而且是安静地挂

```
        计划中的一天                          实际的那一天
  ─────────────────────────           ─────────────────────────
  07:58  机器活着                      07:58  硬件故障，宕机
  08:00  cron 触发脚本                 08:00  （什么都没发生）
  08:00  开始逐条发提醒                08:30  （什么都没发生）
  ……     千万条陆续发出                ……    （一直什么都没发生）
                                       09:40  客服电话开始变多
                                       10:20  才有人想起来登那台机器
```

注意最毒的一点：**cron 不会向任何人报告"我没跑"**。机器挂了，没有报错、没有告警、没有日志——它安静得和正常的一天一模一样。你是从客服的投诉量曲线上，而不是从监控上，知道今天提醒没发的。

用户逾期了，损失是真金白银的违约金和征信记录。这个锅没法甩。

### 0.4 死穴二：容量 —— 8 点开跑，11 点才跑完

就算机器不挂，算笔账。单机发一条提醒要查库、组装文案、调推送接口，算它每秒处理 1 万条——这已经相当乐观。

```
  1 亿条 ÷ 1 万条/秒 = 10000 秒 ≈ 2 小时 47 分

  08:00 ─────────────────────────────────────────▶ 10:47
   │                                                 │
   第 1 个用户收到"8 点提醒"              最后一个用户收到"8 点提醒"
                                          （离还款截止时间又近了 3 小时）
```

排在队尾的用户，收到"早上 8 点提醒"时已经快 11 点了。提醒的价值随排队位置衰减——这不是"慢一点"的问题，是队尾那批用户约等于没被提醒。

### 0.5 死穴三：重复 —— 为了高可用部署两台，每人收到两条

死穴一的直觉解法：再加一台机器，同样的 crontab，互为备份。总不会两台同时挂吧？

```
        机器 A                              机器 B
   crontab: 0 8 * * *                  crontab: 0 8 * * *
        │                                    │
        │ 08:00:00 触发                      │ 08:00:00 触发
        ▼                                    ▼
   扫全表，给每人发一遍                 扫全表，给每人发一遍
        └──────────────────┬─────────────────┘
                           ▼
                   每个用户收到 2 条
          "您今天需要还款" ×2 —— 用户：银行系统是不是坏了？
```

两台机器互相不知道对方的存在，各自尽职尽责地把活干了一遍。**为了治"漏"，制造了"重"。**

这正是[第 16 篇《分布式锁》](./16-分布式锁.md)开场的那类事故：多个节点同时认为"这活归我"。第 16 篇给的是通用解法（锁），本篇会看到调度领域的整套专用解法——而且第 5 节你会发现，兜底的最后一招和第 16 篇阶梯的起点是同一个东西。

### 0.6 三个死穴，就是本篇的路线图

| 死穴 | 症状 | 谁来解 |
|---|---|---|
| 重复 | 部署多台 → 每人多条 | 阶梯一：quartz 集群（数据库行锁） |
| 单点 | 调度器自己挂了没人发令 | 阶梯二：中心化调度 + 调度器 HA |
| 容量 | 一亿条单机跑到 11 点 | 阶梯三：分片广播 |

三个阶梯不是三选一，是层层递进——每一级都在回答"上一级为什么还不够"。

## 1. 先分清两个问题：触发是时间问题，执行是分布式问题

动手之前先把题目切开。"每天早上 8 点给一亿人发提醒"这句话，其实是两个完全不同的问题粘在一起：

```
        "每天早上 8 点，给一亿个该还款的人各发一条提醒"
                            │
            ┌───────────────┴────────────────┐
            ▼                                ▼
    ① "每天早上 8 点"                 ② "给一亿个人各发一条"
      什么时候触发                      触发之后归谁执行
    ──────────────────                ──────────────────────
      时间管理问题                      分布式问题
      cron 表达式解析                   不重：别让人收到两条
      时间轮 / 优先队列                 不漏：别一台挂了全线沉默
      第 03 篇的地盘                    够快：别从 8 点发到 11 点
                                        本篇主讲
```

问题①，[第 03 篇《延迟任务与时间轮》](./03-延迟任务与时间轮.md)已经讲透了。一句话复习：**时间轮让"到期的任务自己走到指针面前"，检查到期的代价与任务总数无关**——宿管阿姨不翻本子，只开当前这一分钟的信箱。本篇不再展开。

问题②才是本篇的正题。从现在起，假设"8 点到了"这个信号已经有人喊出来了（谁喊的、用时间轮还是用扫表喊的，都不重要），剩下的全部问题是：**一屋子机器听到了喊声，谁上？怎么保证只上一个（或者按计划上 N 个）？上的那个挂了怎么办？**

说白了：03 篇管闹钟什么时候响，本篇管闹钟响了之后活儿归谁干。两篇拼起来才是一个完整的调度系统。

## 2. 阶梯一：quartz 集群 —— 所有节点抢同一把数据库锁

### 2.1 思路：两台会重复，是因为它们互相不认识

死穴三的根子：机器 A 和机器 B 之间没有任何通信，谁也不知道对方也在干。要治它，要么让它们互相商量，要么找一个双方都信的仲裁者。

quartz（Java 生态的老牌调度库）的集群模式选的是仲裁者：**共享数据库**。

> 以下机制描述基于 quartz 官方文档 Clustering 章节与源码公开资料，表名与默认值以官方文档为准。

### 2.2 机制：SELECT FOR UPDATE 抢一行

所有节点连同一个库，库里有一套 `QRTZ_*` 表存任务和触发器。关键的一张叫 `QRTZ_LOCKS`，里面就几行，充当集群级的锁。任何节点想触发任务，先抢锁：

```
     节点 A            节点 B            节点 C
  (业务+quartz)     (业务+quartz)     (业务+quartz)
        │                 │                 │
        │   SELECT * FROM QRTZ_LOCKS
        │   WHERE lock_name = 'TRIGGER_ACCESS' FOR UPDATE
        │                 │                 │
        └─────────────────┼─────────────────┘
                          ▼
                 ┌────────────────┐
                 │   共享数据库    │  同一行，同一时刻只有一个事务能锁住
                 │   QRTZ_* 表    │
                 └────────────────┘

  08:00:00  B 先锁到行 → 扫出到期的 trigger → 标记"这批我拿走了" → 提交放锁 → 执行
  08:00:00  A、C 在这行锁上排队 → 轮到自己时发现 trigger 已被标记 → 空手放锁
```

行锁是数据库最基础的排队机制——`FOR UPDATE` 拿不到锁会怎么等、等的时候发生什么，[PostgreSQL 系列第 05 篇](../2026-08_从真实项目学PostgreSQL/05-锁.md)整篇拆的就是它。quartz 集群本质上就是把"谁来触发"这个分布式共识问题，外包给了数据库的行锁。

效果立竿见影：

- **不重了**：同一个 trigger 只会被一个节点标记走，每人只收到一条；
- **不怕单点了**：B 挂了，A 和 C 还在抢锁，下一轮照常有人触发。

死穴三和死穴一，一把行锁全治了。代价呢？

### 2.3 坑 1：加机器不加产能

注意这个结构里谁在干活：**同一个任务，同一时刻，永远只有一个节点在跑。** 其他节点抢锁失败，转身回去待命。所以：

```
   节点数      1          3          10
               │          │          │
   任务吞吐    █          █          █            ← 还是那一个节点在跑
   锁竞争      █          ███        ██████████    ← 抢锁的人变多，数据库更忙

   你以为加的是产能，其实加的是排队的人。
```

10 个节点不会让一亿条提醒跑快 10 倍——它们只是让 `QRTZ_LOCKS` 那一行更抢手、数据库更忙。任务多的时候（几百个 job 密集触发），所有节点反复抢同一行锁，锁竞争随节点数上升，调度吞吐反而可能下降。

这和[流量系列第 00 篇"队列不会创造产能"](../2026-08_流量扛不住了怎么办_六种真实做法/00-接口超时把队列调大反而OOM-队列不会创造产能.md)是同款反直觉：把队列调大不会让消费变快，把抢锁的节点加多也不会让任务跑得更快。**产能在干活的那一端，不在排队的那一端。**

所以死穴二（容量）在这一级纹丝未动：一亿条还是一台跑，8 点开跑 11 点收工。

### 2.4 坑 2：调度和业务锁死在同一个进程里

quartz 是个库，嵌在你的业务进程里。这意味着：

- 业务代码发个版，调度节点跟着重启——重启窗口里的触发点就悬了（第 5.1 节的 misfire 就这么来的）；
- 想给调度扩容，得连业务一起扩；想给业务缩容，调度节点跟着少。

两件不相干的事被迫同进退。这是架构问题，加机器解决不了，得动结构——这就是阶梯二。

### 2.5 顺手记一个：集群节点的时钟必须同步

quartz 官方文档明确要求集群各节点用 NTP 之类的手段对时（以官方文档为准）。原因很直白："到期没到期"是每个节点看自己手表判断的，节点之间表差几十秒，就会出现"A 认为还没到点、B 认为早过点了"的错乱。

这里有个坑：**时钟问题的症状从来不指向时钟**——你看到的是任务偶发地早触发、晚触发、或被当成 misfire，排查半天代码，根子是某台机器的 NTP 没配。碰到调度系统的"灵异"问题，先对表。

## 3. 阶梯二：中心化调度 —— 发令的和干活的分家

### 3.1 把两种角色拆开

阶梯一坑 2 的答案：**发令的和干活的，不该是同一批进程。** 拆开，各自变成独立集群。这就是 XXL-Job 这类调度平台的模型（机制描述基于 XXL-Job 公开文档，细节以官方文档为准）：

```
              ┌──────────────────────────────────┐
              │         调度中心（admin）          │
              │   只干三件事：                     │
              │   1. 盯表：哪个任务到点了           │
              │   2. 挑人：按路由策略选执行器        │
              │   3. 发令：把触发请求发过去          │
              │   自己一行业务代码都不碰            │
              └──────┬─────────┬─────────┬───────┘
                     │         │         │   触发请求（带参数）
                     ▼         ▼         ▼
              ┌─────────┐ ┌─────────┐ ┌─────────┐
              │ 执行器 1 │ │ 执行器 2 │ │ 执行器 3 │  ← 业务进程，
              │  干活    │ │  干活    │ │  干活    │    启动时注册 + 定期心跳
              └─────────┘ └─────────┘ └─────────┘
```

执行器是嵌在业务进程里的一个小组件：启动时向调度中心注册"我在这，我能跑这些任务"，之后定期心跳报平安，收到触发请求才干活。

拆开之后，两边独立扩缩容：

- 执行器忙不过来 → 加执行器，注册上来就自动进入候选名单，调度中心无感知；
- 任务数量多、触发密集 → 加调度中心节点；
- 业务发版只重启执行器，调度中心岿然不动——发版窗口里到点的任务照常触发，只是那一下没有活着的执行器接（这个问题路由策略里的"故障转移"来兜，往下看）。

### 3.2 调度中心自己的 HA：还是那把数据库锁，但抢的人变少了

调度中心也不能是单点，否则死穴一换个位置复发。XXL-Job 的做法很朴素：多个 admin 节点同时部署，共享一个数据库，每轮触发前抢数据库锁，抢到的节点负责这一轮的扫表和触发（基于公开文档与源码资料，实现细节以官方文档为准）。

眼熟吗？**这就是阶梯一那招 SELECT FOR UPDATE。** 中心化调度并没有发明新的共识机制，它做的是一件更聪明的事：

💡 **把抢锁的人数从"整个业务集群"缩到"两三个调度节点"。** 阶梯一的锁竞争会随业务扩容线性恶化——业务加到 50 个节点，就有 50 个进程在抢那一行。拆出调度中心后，业务扩到 500 个节点也和锁无关，抢锁的永远只有那两三个 admin。锁竞争从"随规模增长的变量"变成了"常数"。

同一把锁，换个位置放，性质完全不同。架构里很多"高级方案"拆开看都是这样——不是用了更高级的原语，是把土办法放到了它撑得住的规模上。

### 3.3 路由策略：到点了，挑哪台执行器

调度中心发令前要挑人。XXL-Job 内置了一批路由策略（清单以官方文档为准），常用的这几个：

| 策略 | 挑人逻辑 | 适合什么 |
|---|---|---|
| 轮询 | 挨个来，雨露均沾 | 无状态任务的默认选择 |
| 随机 | 随机挑一台 | 同上 |
| 一致性哈希 | 同一个任务永远落到同一台执行器 | 执行器本地有缓存/状态，换机器就白攒了 |
| 故障转移 | 按顺序心跳探测，第一台活着的上 | 要求"只要还有一台活着就必须跑成" |
| 忙碌转移 | 先问"你忙吗"，空闲的才接 | 单次执行时间长、怕堆积的任务 |
| 分片广播 | 所有执行器一起上，各领一份 | 第 4 节的主菜 |

一致性哈希在这里再就业了——环怎么建、虚拟节点怎么摊匀，[第 12 篇 6 节](./12-小而美的五个算法.md)画过完整的图，这里只是换了个岗位：从"key 找缓存机器"变成"任务找执行器"，数学一模一样。

### 3.4 但容量死穴还在

到这里盘点一下：死穴三（重复）阶梯一治了，死穴一（单点）这一级治了——调度中心多节点选主，执行器挂一台还有故障转移。

死穴二呢？**纹丝未动。** 路由策略挑人挑得再精，也是把"发一亿条提醒"这个任务整个塞给某一台执行器。挑出来的那台机器看着同伴们空闲，自己从 8 点跑到 11 点。

问题不在挑人，在建模。这就是阶梯三。

## 4. 阶梯三：分片广播 —— 一个任务切成 N 片（本篇主菜）

### 4.1 换个脑子：不是"一个任务执行一亿次"

一亿条提醒，错误的建模是：

> 一个任务，里面循环一亿次。

只要这么建模，无论路由给谁，都是一台机器干全部的活。正确的建模是：

> **一个任务，切成 N 片，每片是全量的 1/N，N 台机器同时跑。**

分片广播（sharding broadcast）就是这个建模的调度平台原生支持：到点时，调度中心不再挑一台，而是**给所有在线执行器同时发触发请求**，每台带一份不同的参数——`shardIndex`（你是第几片，从 0 开始）和 `shardTotal`（一共几片，等于当前在线执行器数）：

```
                          调度中心
            "还款提醒"到点，路由策略 = 分片广播
                 │            │            │
        (index=0, total=3) (index=1, 3) (index=2, 3)   ← 同一个任务，三份参数
                 ▼            ▼            ▼
             执行器 0      执行器 1      执行器 2
          user_id%3==0   user_id%3==1  user_id%3==2
                 │            │            │
                 └────────────┴────────────┘
              三片互不重叠，拼起来恰好是全量
              10000 秒的活 ÷ 3 ≈ 56 分钟；32 台 → 约 5 分钟
```

任务代码里用这两个数自己算"哪些数据归我"：

```python
# XXL-Job 风格的分片任务（伪代码）
def send_reminder_job(ctx):
    i = ctx.shard_index      # 我是第几片
    n = ctx.shard_total      # 一共几片

    cursor = 0
    while True:
        users = db.query("""
            SELECT user_id, amount FROM repayment_due
            WHERE due_date = CURRENT_DATE
              AND MOD(user_id, %s) = %s      -- 只认领自己这一片
              AND user_id > %s               -- keyset 翻页，别用 OFFSET
            ORDER BY user_id
            LIMIT 1000
        """, n, i, cursor)
        if not users:
            break
        for u in users:
            mq.send("reminder_topic", u)     # 只生产消息，不直接调推送接口（4.4 节）
        cursor = users[-1].user_id
```

两个顺手的细节：翻页用 `user_id > cursor` 而不是 `OFFSET`，就是[第 14 篇 4.2 节](./14-分库分表.md)的 keyset 分页——翻到第几万页速度都不变；批大小 1000 是让每次事务小而快，挂了损失也小。

### 4.2 💡 这和分库分表是同一个数学

看一眼分片条件：`user_id % shardTotal == shardIndex`。再看一眼[第 14 篇](./14-分库分表.md)的分库路由：`user_id % 库数 == 库编号`。

**同一个式子。** 数据分片用它切存储，计算分片用它切任务。而且当两边对齐时，效果是乘起来的：

```
  不对齐（比如 3 个执行器 × 4 个分库）：
      执行器 0 ──┬── db_0 ──扫──▶ 只留 user_id%3==0 的，其余扔掉
                 ├── db_1 ──扫──▶ 同上
                 ├── db_2 ──扫──▶ 同上
                 └── db_3 ──扫──▶ 同上
      每台执行器都要连所有库、扫出来大部分丢弃 —— 跨库 + 浪费

  对齐（分片数 = 分库数，比如都是 32）：
      执行器 0 ───── db_0      库本来就是按 user_id%32 切的，
      执行器 1 ───── db_1      第 i 个库里的用户天生全是第 i 片的
      ……                       连 WHERE MOD(...) 都不用写
      执行器 31 ──── db_31     一对一直连，零跨库，零浪费
```

第 14 篇讲的是"让每个查询天生知道自己去哪个分片"，这里是它的批处理版：**让每片计算天生知道自己去哪个库。** 如果你的用户库已经按 `user_id % 32` 分了 32 个库，分片数就定 32，第 i 片直连第 i 库全量扫——这是分片广播的最优形态。

一个马上会撞到的现实问题：库有 32 个，执行器只有 8 台，`shardTotal` 是按在线机器数给的，对不齐怎么办？答案还是第 14 篇 3.3 节那招——**逻辑分片和物理资源解耦**。逻辑分片数固定按库数算（32），每台机器认领多个逻辑分片：

```
  8 台执行器 × 32 个逻辑分片（= 分库数）：

  执行器 i 认领的逻辑分片：i, i+8, i+16, i+24
      执行器 0 → db_0, db_8,  db_16, db_24
      执行器 1 → db_1, db_9,  db_17, db_25
      ……
      执行器 7 → db_7, db_15, db_23, db_31

  伪代码就一行循环：
      for shard in range(shard_index, 32, shard_total):
          process_db(shard)          # 每个逻辑分片仍然一对一直连分库
```

机器加到 16 台，每台领 2 片；加到 32 台，一台一片——**逻辑分片数不动，物理机器随便伸缩**。第 14 篇预留 10 bit 逻辑分片是同一个思想在存储侧的版本：把"切多少份"和"有多少资源"这两个变化频率完全不同的东西，拆成两层。

### 4.3 ⚠️ 反直觉：这里的取模扩容为什么毫无痛感

第 12 篇用一整节讲"简单取模是灾难"：缓存从 %10 变 %11，91% 的 key 落点改变，缓存雪崩；第 14 篇也说取模扩容要靠双倍扩容法精心迁移。可分片广播呢？执行器从 3 台加到 4 台，`shardTotal` 下一轮自动变 4，每片认领的用户集合大洗牌——**没有任何人在意。**

为什么同一个数学，那边是事故，这边是日常？

> **分片的痛苦程度 = 存量状态的多少。** 缓存分片痛，因为数据躺在旧机器上，落点一变就等于全丢了；数据库分片更痛，因为数据要物理搬家。而计算分片是每次触发时现算的——用户归哪片，是执行那一刻用当时的 `shardTotal` 临时算出来的，**没有任何存量状态需要搬**。切法变了，下一轮按新切法跑就是了。

这也顺手解了"漏"的一半：某台执行器宕机，下一轮广播时 `shardTotal` 自动减一，它那片被活着的机器重新瓜分——不会有哪片从此永远没人跑。至于"这一轮跑到一半挂了"怎么办，交给第 5.2 节的幂等 + 重试。

### 4.4 下游保护：分片不会给推送网关创造产能

一个必踩的坑：分片广播把生产速度提了 32 倍，可推送网关（或者短信通道、APNs）的消化速度一点没变。32 台机器同时全速调推送接口，等于自己人对下游发起了一场 8 点整的压测。

这是[流量系列第 00 篇](../2026-08_流量扛不住了怎么办_六种真实做法/00-接口超时把队列调大反而OOM-队列不会创造产能.md)的镜像版：队列不会创造产能，**分片也不会给下游创造产能**——它只是把生产端提速了。正确姿势在上面伪代码里已经埋了：

```
  分片任务（32 台并行）──▶ MQ ──▶ 推送服务按自己的消化速度拉
        生产：5 分钟灌完            消费：匀速发一小时也没关系
                  8 点的尖峰被 MQ 摊成缓坡
```

任务只负责"算出该给谁发"并写进 MQ，发送这个动作交给消费方按自己的节奏来。8 点这个时间点上真正发生的事，从"发一亿条"变成了"生产一亿条待发消息"——尖峰被削平。

顺带一句：分片这招不是 XXL-Job 独有。Elastic-Job 那一路用 ZooKeeper 做分片协调（公开资料），切分思想同款——分片是调度平台的通用招式，不是某家的专利。

## 5. 可靠性三件套：misfire、幂等、防双触发

架构搭到这，正常的日子已经跑得欢了。但调度系统的事故从来不出在正常的日子。三个高发点，每个配一道闸门。

### 5.1 misfire：错过的触发点怎么办

misfire（错过触发）：计划 8:00 触发，但那一刻调度器正在宕机、重启、或线程池满——没触发成。等它活过来，面对这个过期的触发点，有三种选择：

```
   每天 08:00 的还款提醒任务，调度器 07:55 宕机、08:40 恢复：

   07:55          08:00                  08:40
   ──┬──────────────┬──────────────────────┬─────────────────▶
    宕机       计划触发点（没人在，错过）      恢复，发现错过了
                                            │
                              ┌─────────────┼─────────────┐
                              ▼             ▼             ▼
                          ① 立即补跑     ② 跳过        ③ 合并
                          08:40 马上跑   这次算了      错过 N 次
                          这一次         等下个周期     只补 1 次
```

三种策略没有对错，只有和业务配不配：

| 策略 | 该用的业务 | 用错的后果 |
|---|---|---|
| 立即补跑 | 还款提醒（晚发 40 分钟强过不发）、账单生成 | 对"过时即无意义"的任务是白跑 |
| 跳过 | 幂等的全量同步类（"每 5 分钟同步一次配置"，错过的那次跑了也是重复劳动） | **账单生成敢跳过，就是漏了一天的账**——月底对账直接崩，参考[第 10 篇](./10-支付与对账.md)里"账对不上"要付出什么代价 |
| 合并 | 分钟级任务宕机 1 小时——补 1 次，别把 60 次全补了（用户不需要 60 条提醒） | 对"每次都必须执行"的计数、结算类任务会丢执行 |

拿还款提醒对号入座：**能合并（错过几次只补一条，用户只需要知道"今天要还款"这一件事），不能跳过（跳过等于没提醒，回到死穴一的投诉现场）。** 而账单生成恰好相反：一天都不能跳，但也不能合并——每天的账单是独立的一份。

misfire 还有个近亲，长得像但不是一回事：**上一轮还没跑完，下一轮又到点了**。misfire 是"调度器不在场"，这个是"执行器还没腾出手"：

```
   每 5 分钟一轮的任务，某轮跑了 12 分钟：

   08:00 开跑 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━▶ 08:12 才跑完
                    ▲               ▲
                  08:05           08:10        ← 这两轮到点时，人还没腾出来
                    │
        ┌───────────┼───────────────┐
        ▼           ▼               ▼
     ① 排队等     ② 丢弃后来的    ③ 掐掉前面的
     跑完一轮     这两轮不跑了    终止当前执行
     接着跑下轮   （防堆积）      让新一轮上
```

丢弃像不像[第 06 篇弹幕](./06-直播弹幕与广播.md)的"主动丢弃是一种设计"？同源。全量同步类任务选②最合适——反正下一轮是全量覆盖，堆着跑三轮纯属浪费。

quartz 里对应的是 misfireThreshold（错过多久才算 misfire）加每种 trigger 的 misfire instruction 枚举，XXL-Job 里叫调度过期策略，上面这个近亲叫阻塞处理策略——名字和默认值都以各自官方文档为准。你要做的不是背枚举，是先想清楚自己的业务属于上表哪一行，再去文档里找对应的开关。

### 5.2 执行幂等：跑一半挂了，重跑不能重复发

场景：分片 2 跑到第 300 万个用户时 OOM。调度平台的故障转移很尽职，把这一片换台机器重跑——那前 300 万人会收到第二条吗？

```
   没有幂等：                          有幂等（发送流水表兜底）：
   重跑 = 从头再发一遍                  重跑 = 从头再"过"一遍
   前 300 万人收到第 2 条               前 300 万人：INSERT 冲突 → 跳过
   客诉爆炸                            没发过的人：INSERT 成功 → 发出
                                       结果：每人恰好 1 条
```

闸门是一张发送流水表：

```sql
CREATE TABLE reminder_sent (
    user_id   BIGINT NOT NULL,
    biz_date  DATE   NOT NULL,
    sent_at   DATETIME,
    UNIQUE KEY uk_user_date (user_id, biz_date)
);
-- 发送前先占坑：INSERT 成功才真发；Duplicate entry 说明发过了，跳过
```

`(user_id, biz_date)` 就是幂等键——同一个人同一天，这条唯一约束保证发送动作做两遍只生效一遍。这套机制[PostgreSQL 系列第 06 篇](../2026-08_从真实项目学PostgreSQL/06-幂等与outbox.md)整篇在讲，包括为什么"先查再插"有竞态、必须让唯一约束当裁判。

有人会想用"断点续跑"代替幂等：记录跑到哪个 user_id 了，重跑从断点继续。可以做，但它是优化不是闸门——挂机的瞬间，最后一批可能"发了但断点没记上"（或反过来），断点永远有一小段模糊地带。**断点管效率，幂等管正确性，后者不能省。**

这里的深层逻辑和[第 09 篇 IM 可靠投递](./09-IM消息可靠投递.md)一字不差：**重试保证不丢，幂等保证不重，两个必须成对出现。** 只有重试没有幂等的系统，是一台自动化的事故制造机——它会孜孜不倦地把每次故障放大成一次重复操作。

### 5.3 脑裂双触发：最后一道闸门是唯一键

最阴的一种故障。调度中心 A、B 靠数据库锁选主（3.2 节）。某天：A 抢到锁开始触发，触发到一半网络抖动，锁因超时被释放（或数据库主从切换把锁状态弄丢了），B 一看锁空着，认为自己是主，把同一轮又触发了一遍。**同一个任务、同一个计划时间点，被触发了两次。**

这叫脑裂：集群里同时存在两个"自认为的主"。锁、心跳、租约都只能降低它的概率，不能降到零——网络分区面前，任何选主机制都做不到零脑裂（这是分布式共识的地界，[第 23 篇 Raft](./23-Raft共识.md) 讲为什么）。

概率压不到零，就在结果上兜底。闸门还是唯一键，这次锁的是"触发"这个动作本身：

```sql
CREATE TABLE trigger_record (
    job_id        BIGINT   NOT NULL,
    planned_time  DATETIME NOT NULL,   -- 注意：计划触发时间，不是实际时间
    fired_by      VARCHAR(64),
    fired_at      DATETIME,
    UNIQUE KEY uk_job_planned (job_id, planned_time)
);
```

```
   调度中心 A（自认为主）              调度中心 B（也自认为主）
        │                                  │
        │ INSERT trigger_record            │ INSERT trigger_record
        │ (job_id=42,                      │ (job_id=42,
        │  planned_time='08:00:00')        │  planned_time='08:00:00')
        ▼                                  ▼
   ┌──────────────────────────────────────────────┐
   │       UNIQUE KEY (job_id, planned_time)      │
   │   先到的 INSERT 成功 ✅ → 有资格触发           │
   │   后到的 Duplicate key ❌ → 立刻收手           │
   └──────────────────────────────────────────────┘
```

触发前先 INSERT 占坑，占到的才有资格发令。无论几个节点同时自认为是主，数据库只放一个进来。

这里有个坑：**唯一键里必须用计划时间，不能用实际时间。** A 是 08:00:01 触发的，B 是 08:00:47 触发的——实际时间不同，拦不住；但它们的计划时间都是 08:00:00，一拦一个准。

现在回头看[第 16 篇《分布式锁》](./16-分布式锁.md)：它的方案阶梯从数据库锁/唯一约束起步，一路升级到 Redis、etcd；本篇从 quartz 的数据库行锁起步，一路升级到中心化调度、分片广播。两条路爬到顶，兜底的最后一道闸门都落回了同一个地方——**数据库唯一约束**。首尾闭环。高级方案负责"通常不出事"，土办法负责"真出了事也不重"。

## 6. 选型小表：这活到底归谁干

03 篇和本篇各管一摊，边界经常被搞混。判据一句话：**数一数你有几个"闹钟"。**

- 闹钟个数 = 业务对象数（每笔订单一个，千万个，时刻各不相同）→ 时间轮/延迟消息的地盘；
- 闹钟个数 = 任务数（几十几百个 job，每个 job 到点处理海量数据）→ 调度平台的地盘。

| 你的需求 | 例子 | 该用什么 | 谁的地盘 |
|---|---|---|---|
| 海量对象，各有各的到期时刻 | 每笔订单下单后 15 分钟自动关单 | 时间轮 / 延迟消息 | [03 篇](./03-延迟任务与时间轮.md)、[流量系列 06 篇](../2026-08_流量扛不住了怎么办_六种真实做法/06-1000万订单超时未付自动关单-时间轮与延迟消息.md) |
| 少量任务，周期跑，单次数据量可控 | 每天凌晨 2 点日终对账 | 调度平台（quartz 集群或 XXL-Job 都够用） | 本篇 + [10 篇](./10-支付与对账.md) |
| 少量任务，周期跑，单次数据量海量 | 一亿条还款提醒 | 调度平台分片广播 + MQ 削峰下游 | 本篇 + [14 篇](./14-分库分表.md) |
| 触发精度要求毫秒级 | 撮合引擎里的定时撤单 | 进程内 timer / 时间轮，别指望调度平台 | [03 篇](./03-延迟任务与时间轮.md)、[07 篇](./07-股票撮合引擎.md) |

两个常见的错配：

- 拿调度平台管订单关单——一千万笔订单建一千万个 job，调度平台的任务表当场爆掉。它的任务是"名词"（几百个），不是"实例"（几千万个）；
- 拿时间轮发一亿条提醒——时间轮只负责 8 点整喊一嗓子，喊完之后"一亿条归谁跑"它管不着。喊话之后的事，就是本篇从第 2 节起讲的全部。

两个工具经常合作：时间轮当扳机，调度平台当兵力部署。别让任何一个越界。

## 7. 反直觉结论

### ⚠️ 1. 调度系统的核心指标不是"准时"，是"不重不漏"

还款提醒晚 30 秒，零投诉；晚 5 分钟，大概率还是零投诉。重复发两条，客服电话就来了；要是重复的不是提醒而是扣款任务，就是资损事故、当天写复盘的级别。

所以本篇的所有机器都在为"不重不漏"服务：行锁防重、选主防重、唯一键防重、幂等防重跑、misfire 策略防漏、分片重分防漏——没有一件是为"精确到秒"服务的。

这和[第 09 篇 IM](./09-IM消息可靠投递.md)的"不丢不重"、[第 10 篇](./10-支付与对账.md)的对账是同一条价值观：**分布式系统的终极考题从来不是快，是账对得上。** 消息的账、钱的账、任务执行的账——全系列绕了二十几篇，反复回到这一条。

### ⚠️ 2. quartz 集群加机器不加产能

同一个任务同一时刻只有一个节点跑，其余节点是陪跑的锁竞争者。想加产能，出路不是加节点，是换建模——分片广播。（和流量 00 篇"队列不会创造产能"同源：排队的人变多，不等于干活的手变多。）

### ⚠️ 3. 同一个取模，缓存分片是事故，计算分片是日常

差别只有一个：有没有存量状态。数据躺在机器上，切法一变就要搬家；计算是现场算的，切法随便变。判断一个系统"分片扩容疼不疼"，看状态在哪，不看算法是什么。

### ⚠️ 4. 爬到架构顶端，兜底的还是最土的数据库唯一约束

锁会超时，租约会过期，选主会脑裂——概率能压低，压不到零。真正把"不重"从概率保证变成确定性保证的，是 `UNIQUE KEY (job_id, planned_time)` 这行 DDL。分布式系统里最可靠的仲裁者，经常是那个最没有分布式味道的组件。

## 8. 一句话总结 + 小白词典 + 对照

### 一句话总结

> **单机 crontab 死于单点、容量、重复；quartz 集群用一把数据库行锁治了重复，中心化调度把发令和干活分了家，分片广播才真正把一亿条切给 N 台机器并行——而绕完这一整圈，守住"不重不漏"底线的，仍然是唯一约束和幂等键这两件最土的兵器。**

### 小白词典

| 词 | 人话 |
|---|---|
| 调度中心 / 执行器 | 一个管"到点了，你去跑"，一个管"收到，我跑"。发令的和干活的分开，才能各自扩容 |
| 路由策略 | 调度中心挑执行器的规则：轮询、随机、一致性哈希、故障转移、忙碌转移、分片广播 |
| 分片广播 | 到点时给所有执行器同时发令，每台领个编号，只干总量的 1/N |
| shardIndex / shardTotal | "你是第几片"和"一共几片"。任务代码拿它俩取模，算出哪些数据归自己 |
| misfire | 到点了却没触发成（调度器正好在宕机/重启）。事后补救分三派：立即补跑、跳过、合并 |
| 选主 | 多个调度节点里推一个出来干活，其余待命。朴素做法就是抢一把数据库锁 |
| 脑裂 | 选主失灵，两个节点同时自认为是主，同一件事各干一遍 |
| 幂等键 | 一个唯一标识（比如 user_id + 日期），靠数据库唯一约束保证同一件事做两遍只生效一遍 |
| 触发记录表 | 以（任务 ID + 计划触发时间）为唯一键的表，触发前先 INSERT 占坑——防脑裂双触发的最后闸门 |
