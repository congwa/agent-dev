## 0. 先看一张运营后台的配置表

周四下午，运营在活动后台新建了一个转盘抽奖，配置表长这样：

```
  ┌──────────────────────────────────────────────────────┐
  │  「周年庆大转盘」  活动时长：48 小时                 │
  ├────────────────┬─────────┬───────────────────────────┤
  │  奖品           │  数量   │  中奖概率                │
  ├────────────────┼─────────┼───────────────────────────┤
  │  iPhone         │  1 台   │  0.01%                   │
  │  5 元现金红包   │  10000 个│  5%                      │
  │  满100减10优惠券│  100 万张│  30%                     │
  │  谢谢参与       │  不限   │  兜底（剩下的都归它）    │
  ├────────────────┴─────────┴───────────────────────────┤
  │  活动预算：100,000 元（市场部批的，一分不能多）      │
  └──────────────────────────────────────────────────────┘
```

运营点了保存，转头跟你说："明天上午十点上线，预估 300 万次抽奖，你看着办。"

看起来是个小需求对吧。转盘转一下，随机出个结果，初级工程师半天就能写完。

真上线你就知道了。这张四行的配置表，藏着三条死线，每一条踩了都是要写事故报告的。

## 1. 三条死线，缺一条都是事故

**死线一：概率要准。**

活动规则页上白纸黑字写着"iPhone 中奖概率 0.01%"。这不是装饰，是承诺。羊毛党会真的写脚本抽一万次，把每种奖品的实际出现次数记下来和公示概率对——对不上，轻则客诉发酵，重则合规问题找上门（有奖销售的概率公示在监管上有明确要求，细节不在本篇展开）。

注意，"准"不是"每天报表正好 5%"，是"统计上对得上"。这两者的区别，2.6 节用三次真实运行给你看。

**死线二：库存绝不超发。**

iPhone 只有 1 台。发出去两台，第二台的钱没有预算科目可以走，这是真金白银的事故。红包 10000 个发成 10001 个，看着只多了 5 块钱，但它说明你的扣减路径有洞——有洞就能被脚本放大成 5 万块。

**死线三：预算绝不超支。**

市场部批了 10 万。现金红包 10000 × 5 元 = 5 万是大头，iPhone 采购价算大几千，剩下的留给优惠券核销（券是"用户核销才花钱"的负债，预算口径和现金不同，这里点一句不展开）。活动跑到一半预算烧完了，系统必须自动收口，而不是等财务月底对账时发现多花了三万。

说白了，这三条死线分别是三个老朋友：

```
  概率要准     →  一个数学正确性问题（本篇第 2 节）
  库存不超发   →  秒杀问题换了件马甲（本篇第 3 节）
  预算不超支   →  红包问题换了件马甲（本篇第 4 节）
```

一条一条来。

## 2. 概率怎么落地：先看两个必死的写法

### 2.1 错误写法一：每个奖品各掷一次骰子

最直觉的写法：每个奖品独立判定一次。

```python
# 错误示范一：独立判定
won = []
if random.random() < 0.0001: won.append("iPhone")
if random.random() < 0.05:   won.append("红包5元")
if random.random() < 0.30:   won.append("优惠券")
# won 为空就算谢谢参与
```

看起来每个概率都"对"，对吧？iPhone 确实是万分之一，红包确实是 5%。

坑在于这三次判定**互相独立**。独立意味着可以同时成立：

```
  P(同时中红包和优惠券) = 5% × 30% = 1.5%

  按运营预估 300 万次抽奖：
  300 万 × 1.5% = 4.5 万人 一次抽奖领走两样奖品

  P(三样全中) = 0.0001 × 0.05 × 0.30 ≈ 百万分之 1.5
  300 万次里期望出现 4~5 次 → 有人截图发微博：
  "我转一次转盘中了 iPhone + 红包 + 券"
```

一次抽奖必须恰好出一个结果——这是转盘的产品语义。独立判定从根上违反它。

### 2.2 错误写法二：挨个判断，中了就 return

那加个 return，中了就走，不就互斥了吗？

```python
# 错误示范二：顺序判定，短路返回
if random.random() < 0.0001: return "iPhone"
if random.random() < 0.05:   return "红包5元"
if random.random() < 0.30:   return "优惠券"
return "谢谢参与"
```

这个版本更阴险，因为它**看起来**能用，测试也大概率发现不了。

问题：写在代码里的 `0.30`，实际含义是"**前面都没中的条件下** 30%"。优惠券的真实概率是：

```
  P(优惠券) = (1 - 0.0001) × (1 - 0.05) × 0.30
            = 0.9999 × 0.95 × 0.30
            ≈ 28.50%          ← 配的是 30%，实际 28.5%
```

差 1.5 个百分点。300 万次抽奖，少发约 4.5 万张券。运营看核销报表："券的曝光量怎么比配置低一截？"你查三天代码都想不到是概率写法的问题——因为单看每一行，数字都是"对"的。

有人会说：那我把 `0.30` 改成约 `0.3158`（= 0.30 ÷ 0.9999 ÷ 0.95）补偿回来不就行了？

行是行。但从此运营在后台改任何一个奖品的概率，你都要连锁重算它后面所有奖品的条件概率。配置表上写 30%，代码里存 0.3158——两边永远对不上，交接的人必踩。这不叫方案，叫埋雷。

### 2.3 正解：区间切分法——只掷一次骰子

换个思路。别给每个奖品发骰子，**全场只掷一次**。

把 [0, 10000) 这根整数轴按概率切成段，每个奖品占的格子数 = 它的万分位概率：

```
  [0, 10000) 整数轴，randrange(10000) 掷一次：

  0    1                501                    3501                        10000
  ├────┼─────────────────┼───────────────────────┼───────────────────────────┤
  │iPh │   5 元红包      │       优惠券          │        谢谢参与           │
  │one │                 │                       │                           │
  └────┴─────────────────┴───────────────────────┴───────────────────────────┘
   1 格      500 格             3000 格                  6499 格
  (0.01%)    (5%)              (30%)                   (64.99%)

  掷出 0        → iPhone
  掷出 1~500    → 红包        随机数落在哪一段，
  掷出 501~3500 → 优惠券      就中哪个奖，没有第二种可能
  掷出 3501+    → 谢谢参与
```

三个性质，正好把 2.1 和 2.2 的坑全填上：

1. **互斥**：一个数只能落在一段里，绝不可能一次中两个奖。
2. **完备**：四段拼满整根轴，任何随机数都有归宿，不存在"掷了个寂寞"。
3. **所见即所得**：每个奖品的概率就是它的格子数，配置表上的 5% 就是代码里的 500，改哪个都不影响别人。上线前一行 `assert 总格子数 == 10000` 就能把配置错误拦在门外。

💡 顺带说一句：把 [0, 10000) 切段、按落点分派，这把刀不只切奖品。[第 25 篇灰度发布与 AB 分流](./25-灰度发布与AB分流.md)切的是流量（5% 用户进新版本），用的是同一招——那边用用户 ID 哈希进桶保证"同一个人稳定进同一段"，这边用随机数保证"每一抽独立"。刀一样，握法不同。

### 2.4 十行可运行的 Python

```python
import random
from collections import Counter

PRIZES = [("iPhone", 1), ("红包5元", 500), ("优惠券", 3000), ("谢谢参与", 6499)]
assert sum(w for _, w in PRIZES) == 10000      # 上线前先把轴拼满，差一格都不许跑

def draw():
    r, edge = random.randrange(10000), 0       # 只掷一次 [0,10000) 的骰子
    for name, weight in PRIZES:
        edge += weight
        if r < edge:                           # 落在哪一段，就中哪个奖
            return name

print(Counter(draw() for _ in range(1_000_000)))
```

本篇写作时真实跑出来的一次结果（一百万次抽样）：

```
Counter({'谢谢参与': 649695, '优惠券': 299838, '红包5元': 50367, 'iPhone': 100})
```

期望值分别是 649900 / 300000 / 50000 / 100。都在正常波动范围内。

两句实现层面的话：

- 奖品几十个以内，像上面这样线性扫过去就够了。奖品几百上千个再考虑前缀和 + 二分（`bisect`）。别一上来就搬 Alias Method，奖品表就四行，杀鸡不用牛刀。
- `random.randrange` 是伪随机，对抽奖足够；但**别用时间戳做种子再自己写线性同余**——可预测的随机数会被黑产反推，这不是玄学，是真实攻击面。

### 2.5 纪律：概率用整数万分位，不用浮点

上面代码里有个细节值得单独立成纪律：**概率从头到尾是整数（1、500、3000、6499），不是浮点（0.0001、0.05）。**

为什么？[第 02 篇红包第 5 节](./02-微信红包.md#5-第三次改进把浮点数扔进垃圾桶)用一整节讲过 `0.1 + 0.2 != 0.3` 会怎么把账搞爆，结论是"钱用分，不用元"。概率是同一条纪律的换皮：

```
  钱：    100.00 元  → 存 10000 分     （整数，加减乘除永远精确）
  概率：  0.01%      → 存 1 万分位     （整数，assert 总和 == 10000 可行）

  同一条纪律：凡是要"加起来正好等于一个整体"的量，
  一律换成整数最小单位再进系统。
```

浮点概率的具体死法：区间边界要靠概率累加得出，浮点连加会在第十几位小数上漂移，`r < edge` 的比较偶尔在边界上判错一格。一格是万分之一，平时看不见，对账时就是一笔说不清的差异。整数没有这个问题，还附送两个好处：能直接存数据库当配置、能被审计脚本精确核对。

万分位不够精怎么办？升到百万分位（ppm），轴变成 [0, 1000000)，其他一个字不用改。这和计费系列"分不够精就用厘"是一个动作，详见[计费系列](../2026-07_一分钱都不能丢_高并发计费系统解剖/1_从一个丢钱的bug说起_并发问题入门.md)。

### 2.6 "概率要准"到底准到什么程度：三次真实运行

死线一说"用户抽 1 万次的统计要对得上"。这句话容易被理解歪，这里用真实数据掰一下。

写这篇文章时，2.4 节那份代码连跑了三次，每次一百万抽样，iPhone（期望 100 次）的实际出现次数：

```
  第一次：73 次
  第二次：99 次
  第三次：100 次
```

第一次的 73，偏离期望 27%。代码有 bug 吗？没有。一百万次抽样下，万分之一事件的标准差约是 10 次，73 落在 2.7 个标准差外——少见，但正常，而且就真实发生在写这篇文章的时候。

这给你两个实际的用处：

1. **给运营解释报表**：单日中奖数抖动 ±20% 不代表概率配错了，小概率事件的日级统计天然毛糙。要判断概率有没有 bug，看的是长周期累计值是否落在置信区间内，不是某一天的数字好不好看。
2. **反过来也成立**：如果累计几百万次后，某奖品实际频率持续偏离配置值好几个标准差，那就不是运气，是 2.2 节那种写法的味道，去查代码。

⚠️ 所以"概率要准"的准确含义是：**机制上精确（格子数写死、一次掷骰、互斥完备），统计上收敛（长期频率落在理论区间内）。** 前者靠代码保证，后者靠前者自动成立。反着做——机制随手写，统计靠调参往回凑——是永远凑不平的。

## 3. 中奖了，但库存刚好没了

概率解决了，第二条死线登场。先别急着写代码，拿配置表算笔账。

### 3.1 先算一笔账：库存耗尽是主状态，不是意外

运营预估 300 万次抽奖。把每个奖品"概率上会被命中多少次"和"库存有多少"摆在一起：

```
  ┌───────────┬──────────────────┬──────────┬─────────────────────────┐
  │  奖品      │ 期望命中次数     │  库存    │  结论                   │
  ├───────────┼──────────────────┼──────────┼─────────────────────────┤
  │  iPhone    │ 300万 × 0.01%    │   1 台   │  提名 300 次，只有 1 个 │
  │            │ = 300 次         │          │  名额 → 拦 299 次       │
  ├───────────┼──────────────────┼──────────┼─────────────────────────┤
  │  红包      │ 300万 × 5%       │  1 万个  │  前 20 万次抽奖就发完， │
  │            │ = 15 万次        │          │  之后 14 万次命中全拦   │
  ├───────────┼──────────────────┼──────────┼─────────────────────────┤
  │  优惠券    │ 300万 × 30%      │ 100 万张 │  够发，唯一不缺货的     │
  │            │ = 90 万次        │          │                         │
  └───────────┴──────────────────┴──────────┴─────────────────────────┘
```

看红包那行：10000 个库存 ÷ 5% 命中率 = 20 万次抽奖就耗尽。20 万占 300 万的 7%——**活动前 7% 的流量就把红包抽完了，剩下 93% 的时间里，红包段是个空段。**

iPhone 更夸张：概率上会被命中约 300 次，但只有 1 台。第 2 到第 300 个"抽中 iPhone"的人，全都要被库存闸拦下来。

💡 这就是很多新手想不到的地方：**"概率判定命中，但库存没了"不是罕见的边界情况，而是这类配置表下系统的常态。** 库存闸不是保险丝，是每天上岗拦几十万人的主力闸机。运营配概率时通常是拍"体感中奖率"，跟库存对不对得上，人家不管——对不上的部分，就是你的系统要兜住的部分。

（这个"概率和库存天生对不上"的尴尬，第 5 节的预排布会从根上消灭掉。先按实时摇号的路子把闸修好。）

### 3.2 竞态现场：先查再扣的老病

最直觉的库存写法：

```python
# 错误示范：先查再扣
if get_stock("红包") > 0:      # ① 查：还有 1 个
    decr_stock("红包")          # ② 扣
    return win("红包5元")
```

两个用户同一毫秒抽中红包，库存只剩 1 个：

```
  用户 A                          用户 B
  ────────                        ────────
  查库存 → 1，有货 ✓
                                  查库存 → 1，有货 ✓    ← A 还没来得及扣
  扣库存 → 0
  中奖 ✓                          扣库存 → -1
                                  中奖 ✓                ← 超发，事故
```

①和②之间隔着一段真空，另一个请求钻进来，两人都看到"有货"。这个错误形状叫 check-then-act，[计费系列第 1 篇](../2026-07_一分钱都不能丢_高并发计费系统解剖/1_从一个丢钱的bug说起_并发问题入门.md)用一个真实丢钱 bug 把它讲透了——抽奖只是它的第一百零一个案发现场。

### 3.3 正确顺序：概率只是提名，扣掉库存才算当选

修法不新鲜，直接复用秒杀那套：**别问有没有货，直接扣，用扣减结果说话。**

```
  概率判定落在红包段（提名）
        │
        ▼
  DECR stock:redpacket          ← Redis 单命令，原子，没有真空期
        │
   ┌────┴─────┐
   ▼          ▼
 结果 ≥ 0    结果 < 0
   │          │
   │          ├── INCR 回去（把多扣的还回来）
   │          └── 改判"谢谢参与"（降级，用户无感知）
   ▼
 中奖成立 → 落中奖记录 → 进发放队列
```

要点三条：

1. **DECR 本身就是判定。** 扣完 ≥ 0 说明抢到了，< 0 说明来晚了。判定和扣减是同一个原子动作，check-then-act 的真空期不存在了。
2. **扣穿了要 INCR 还回去。** 不还，库存会一路负下去，监控看着吓人；更重要的是 3.4 节的"重算奖池"要靠库存值判断奖品还在不在。
3. **概率命中只是提名，库存扣减成功才算当选。** 中奖记录必须在 DECR 成功之后落，顺序反了就是超发。

这套"活动前把库存 SET 进 Redis 预热 → 抽中时 DECR → 扣穿回滚 → 异步落库对账"的三板斧，秒杀系列已经完整拆过，包括 Redis 和 MySQL 谁说了算的终审问题，直接看[秒杀系列第 7 篇](../2026-07_秒杀系统源码拆解/7_秒杀库存扣减_Redis和MySQL谁说了算.md)，本篇不重复。[第 01 篇 12306](./01-12306抢票.md) 守余票守的也是同一个数。

抽奖和秒杀有一个舒服的差别，也有一个由此而来的坑：

- **舒服**：秒杀扣穿了只能给用户看"售罄"，用户不爽是明摆的；抽奖扣穿了降级成"谢谢参与"，用户只当自己手气差。抽奖永远有台阶下，而且台阶免费。
- ⚠️ **坑**：正因为降级太顺滑，库存层的 bug 会被"谢谢参与"整个盖住。红包库存被误配成 0？线上零报错，只是没人中奖，用户还以为是自己脸黑。所以抽奖系统必须监控"各奖品实际发放速率 vs 期望速率（概率 × 抽奖量）"，偏离就告警——错误被产品语义吞掉的系统，监控要替产品把嘴撬开。

### 3.4 库存耗尽之后：两种策略是两种产品

红包在第 20 万次抽奖时发完了，后面 280 万次怎么办？两种策略，技术上都不难，**差别在产品语义**：

**策略一：原地降级。** 概率轴不动，落在红包段的请求 DECR 失败后统一改判谢谢参与。

**策略二：重算奖池。** 红包售罄的瞬间，把它的 500 格从轴上拿走，重新切一版概率表（500 格并给兜底，或按比例分给还有货的奖品），后续请求按新轴抽。

```
  策略一（轴不动，命中后降级）：

  0    1      501         3501                10000
  ├────┼───────┼────────────┼───────────────────┤
  │iPh │ 红包✗ │   优惠券   │     谢谢参与      │
  └────┴───┬───┴────────────┴───────────────────┘
           └──▶ 落进来的全部改判"谢谢参与"
               表面概率没变，实际中奖率从 35% 掉到 30%

  策略二（红包的 500 格划给兜底，轴重切）：

  0    1      3001                            10000
  ├────┼────────┼────────────────────────────────┤
  │iPh │ 优惠券 │         谢谢参与               │
  └────┴────────┴────────────────────────────────┘
      优惠券概率仍 30%，兜底从 64.99% 变 69.99%
      （也可以选择把 500 格按比例分给券，把中奖率顶回去）
```

| | 策略一：原地降级 | 策略二：重算奖池 |
|---|---|---|
| 实现成本 | 一个 if | 概率表要带版本号下发 |
| 用户体感 | 后半场中奖率悄悄变低 | 中奖率可以维持住 |
| 预算消耗 | 变慢，可能花不完 | 维持节奏，甚至加速 |
| 适合 | 短平快活动、防守型预算 | 长活动、要冲参与量 KPI 的 |

⚠️ 策略二有个工程小坑：概率表改了，抽奖服务有 N 个实例，内存里缓存的还是旧表。处理办法是概率表带版本号 + 短 TTL 缓存，容忍几秒内新旧表并存——反正 DECR 闸在后面兜着，旧表实例抽中红包也会被拦下降级，错的只是几秒钟的概率，不会错账。**账不能错，概率可以短暂错**——分清这两件事的优先级，很多"要不要强一致"的纠结就没了。

还有一句要说在前面：选哪种策略是运营的决定，不是你的。上线前问清楚，别自己拍。技术方案一样的东西，产品语义天差地别。

## 4. 预算控制：钱比库存更难守

### 4.1 金额随机：一句话复习二倍均值法

前面红包是固定面额 5 元，预算好算：10000 个 × 5 元 = 5 万，守住"个数"就等于守住了钱。

但运营很快会提需求："改成 0.3 ~ 9.9 元随机金额，有惊喜感。"金额一随机，"总和必须恰好等于预算"这个约束就活了——这正是[第 02 篇微信红包](./02-微信红包.md#4-第二次改进方案-b--边抢边算二倍均值法)的主场。一句话复习：**每次发放金额 = 在 [1 分, 剩余预算 ÷ 剩余份数 × 2) 里随机取整数分，最后一份把剩余全拿走**——期望恰好等于均值，守恒由"最后一份全给"这个结构保证，不靠运气。推导和分布图 02 篇有完整版，不重复。

这里只补一个抽奖场景特有的视角：固定面额是随机金额的特例（上限=下限=5 元），所以**系统一开始就该按"金额可随机"来建模**——预算池记的是分，发放记录记的是分，固定面额只是配置表里两个数字恰好相等而已。这样运营改需求时你只改配置。

### 4.2 预算池预扣：第二道闸

现金类奖品要过两道闸：库存闸（个数）+ 预算闸（金额）。预算闸的写法和库存闸完全同构：

```
  预算池：budget:activity = 10,000,000    ← 10 万元，以分计，整数

  概率提名（落在红包段）
        │
        ▼
  ① 库存闸  DECR stock:redpacket
        │ ≥ 0
        ▼
  ② 算金额  amount = 二倍均值法（或固定 500 分）
        │
        ▼
  ③ 预算闸  DECRBY budget:activity {amount}
        │
   ┌────┴──────┐
   ▼           ▼
  ≥ 0         < 0
   │           │
   │           ├── INCRBY 把预算加回去
   │           ├── ⚠️ 还要把 ① 扣掉的库存 INCR 回去！
   │           └── 改判"谢谢参与"
   ▼
  中奖成立 → 落记录 → 发放队列
```

三个坑，按疼的程度排序：

1. **第二道闸失败，要把第一道闸回滚。** 只回滚预算不回滚库存，红包个数会白白蒸发——预算还在，货没了。这种"多步扣减 + 失败补偿"的编排，闻着已经有 [第 20 篇分布式事务](./20-分布式事务的真相.md)里 Saga 的味道了。好在这里两个计数器住在同一个 Redis 实例里，一段 Lua 脚本就能把 ①②③ 打包成原子操作，根本不用请分布式事务出山。**先用部署结构消灭问题，再考虑用技术解决问题**——把需要一起扣的计数器放在一起，是比任何补偿逻辑都便宜的方案。
2. **预算尾巴会卡死。** 预算剩 37 分，红包最小面额 1 分没问题，但如果运营配了"最低 0.3 元"，37 分永远扣不动——之后每个命中红包段的请求都要走一遍"扣、失败、回滚、降级"。处理：预算余额低于最小面额时，直接把现金类奖品从概率轴上摘掉（3.4 节策略二的机制原样复用）。
3. **回滚也要防重。** 发放链路失败重试时，同一笔回滚跑两次，预算凭空多出一份。用中奖记录 ID 当幂等键，回滚前先查这笔是否已回滚过——幂等键哪里来？[第 13 篇雪花算法](./13-雪花算法真实项目调研.md)的活。

### 4.3 预算和库存是同一个抽象

把 3、4 两节摆在一起看，会发现根本是一个东西：

```
  ┌────────────┬────────────┬─────────────┬──────────────┐
  │  资源       │ 计数单位   │  扣减动作   │  扣穿了怎么办 │
  ├────────────┼────────────┼─────────────┼──────────────┤
  │ iPhone 库存 │  台（=1）  │  DECR       │ 回滚 + 降级  │
  │ 红包库存    │  个        │  DECR       │ 回滚 + 降级  │
  │ 券库存      │  张        │  DECR       │ 回滚 + 降级  │
  │ 活动预算    │  分        │  DECRBY     │ 回滚 + 降级  │
  └────────────┴────────────┴─────────────┴──────────────┘

  全都是同一个抽象：有限资源的并发扣减。
  区别只有单位和步长。
```

💡 点题：**这篇文章的骨架，就是 [01 秒杀](./01-12306抢票.md)（守住一个数）加 [02 红包](./02-微信红包.md)（守住一笔账）的合体变形，外面套了一层概率的壳。** 02 篇 0.3 节说过"红包 = 秒杀 + 金额守恒约束"；抽奖再往上套一层："抽奖 = 概率分发 + N 个并行的秒杀 + 1 个红包"。你在前两篇练的每一招，这里全部原样能用——这不是巧合，第 7 节收束时再说透。

## 5. 反直觉主菜：实时摇号是少数派，主流是预排布

到这里，"实时摇号"方案已经完整了：掷骰子 → 库存闸 → 预算闸 → 落记录。它能上线，也真有系统这么跑。

但如果你去翻大厂营销平台的工程分享，会发现一件反直觉的事：**规模化的抽奖活动，多数不是运行时掷骰子，而是活动开始前就把中奖名额排好了。**（此为多家公司公开工程分享中反复出现的设计模式，属行业惯例描述，未逐一经官方文档核实。）

### 5.1 把中奖名额提前撒在时间轴上

预排布（也叫预算撒点、名额投放）的做法：活动配置保存、审核通过的那一刻，跑一个离线任务：

```
  第一步：把 48 小时切成时间片（按小时，或更细到 5 分钟）

  第二步：把每种奖品的名额按流量模型分到各片
          （均匀打底，预估高峰的片多分一点）

  第三步：片内给每个名额随机一个精确的"生效时刻"

  排布完成后的时间轴：

  10:00        11:00        12:00        13:00    ……    次日 10:00
  ├────────────┼────────────┼────────────┼──────────────────┤
  │ 红包 ×180  │ 红包 ×220  │ 红包 ×450  │  ……              │
  │ 券 ×1.8万  │ 券 ×2.2万  │ 券 ×4.5万  │  ……              │
  │            │            │ iPhone ×1  │ ← 孤品被随机撒进  │
  │            │            │  (12:37:41)│   某一片的某一秒  │
  └────────────┴────────────┴────────────┴──────────────────┘

  每个名额 = 一条记录：{奖品, 生效时刻, 状态:未认领}
```

10000 个红包、100 万张券、1 台 iPhone，全变成了一张"名额表"，撒完了，活动还没开始，**这场活动能发出去的每一分钱已经确定了**。

### 5.2 用户的"一抽"变成了什么

对比一下两种架构里，用户点下转盘那一刻系统在干什么：

```
  实时摇号：
  请求 → 掷骰子(随机数) → 库存闸 DECR → 预算闸 DECRBY → 结果
         └── 随机性发生在运行期，三道闸全在热路径上

  预排布：
  请求 → 查名额表："当前时刻之前已生效、且还没被认领的名额，有吗？"
              │
         ┌────┴────┐
         有         没有
         │           │
     原子认领     谢谢参与
    (LPOP 或一条
     UPDATE 抢行)
         │
        中奖
         └── 随机性发生在活动开始前，热路径只剩一次查询 + 一次原子认领
```

注意那个 LPOP。[第 02 篇 3.3 节](./02-微信红包.md#3-第一次改进方案-a--提前拆好存成一排格子)方案 A 的抢红包，就是把预先拆好的金额塞进 Redis List，抢的动作是一次 LPOP。预排布抽奖的认领动作，和它**一模一样**——把"生效时刻已到、未认领"的名额挂进队列，抽奖就是 LPOP 一下，空了就是谢谢参与。

⚠️ 别误会一件事：预排布消灭的是运行期的**概率计算和预算判断**，没有消灭并发本身。同一个名额被两个请求同时认领，还是要靠 LPOP 的原子性或 `UPDATE ... WHERE status='未认领'` 的行锁来裁决。3.2 节的竞态课在这里一分都不能少。

### 5.3 三个好处，每个都值钱

**好处一：预算天然精确——撒出去多少就是多少。**

实时摇号的预算闸是"运行时防守"：每笔发放去撞一下计数器，靠原子性挡住超支。预排布是"根本没有进攻路径"：预算在生成名额那一刻就已经花完了（逻辑上），运行期发生的只是"把已经花掉的钱交到具体的人手里"。名额总面额 = 5 万，就绝不可能发出 5 万零 1 分——不是拦住了超发，是**超发这条路在结构上不存在**。

**好处二：流量峰值时，中奖率自动收紧。**

名额是固定的，流量是波动的。12 点高峰流量翻十倍？那一片的名额还是 450 个红包，单次抽中概率自动变成十分之一。系统不需要感知流量、不需要动态调概率、不需要任何应急预案——**用固定的结构吸收波动的流量**。反观实时摇号：概率是刚性的 5%，流量翻十倍，预算燃烧速度也翻十倍，得靠人盯着预算池拉警报。

**好处三：黑产集中抽，薅不走全部预算。**

脚本一秒打十万次请求，能抢的只有"此刻已生效、未认领"的那几个名额。下一个时间片的名额还没生效，抽奖接口被打穿了也吐不出来——**时间维度成了天然的限流器**。实时摇号没有这层保护：概率对每次请求平等兑现，黑产的十万次请求就是十万次真实的掷骰机会，预算按概率成比例流失。

### 5.4 这和红包"先拆好再抢"是同一招

💡 把三个好处倒回去看根源，就一句话：**把随机性提前算好，运行期只做查询和扣减。**

这正是[第 02 篇](./02-微信红包.md#3-第一次改进方案-a--提前拆好存成一排格子)方案 A（预先拆分）的招式，一寸没变：

```
  02 篇方案 A：  发红包时把 100 元拆成 10 个格子 → 塞进 List → 抢 = LPOP
  本篇预排布：  建活动时把 10 万预算拆成 101 万个名额 → 撒上时间轴 → 抽 = 查表+认领

  同一招。只是"拆完放进一个 List"升级成了"拆完撒上一根时间轴"。
```

更有意思的是，02 篇 3.5 节当时给方案 A 下的结论是：适合"份数小、大概率会被抢完、要提前对账"的场景，比如**活动红包、平台发的营销红包**——而方案 B（二倍均值实时算）适合的是微信群红包那种日均几十亿、大量抢不完的场景。本篇整个第 5 节，其实就是那句话的展开：营销抽奖恰好全中方案 A 的适用条件（名额有限、预算必须提前锁死、活动结束要对账），所以行业主流选了预排布，一点都不奇怪。

反直觉的只是第一印象："抽奖"这个词让人默认随机发生在按下按钮那一刻。实际上随机早就发生完了，你按下按钮时，只是在查询一个几小时前就写好的答案。

### 5.5 预排布的代价与补丁

天下没有白吃的架构，预排布的账单：

1. **公示概率变成了期望值。** 单次抽奖的真实概率随流量波动（名额固定、分母变化），活动规则页得写"数量有限，以实际投放为准"之类的兜底话术——这是产品和法务要一起搞定的事，工程师至少要知道有这一层。
2. **低谷片的名额会发不完。** 凌晨 4 点那片撒了 80 个红包，只来了 30 个用户，剩 50 个名额怎么办？要做**顺延**：未认领名额滚入下一片。顺延本身是个定时扫尾任务，[第 03 篇延迟任务与时间轮](./03-延迟任务与时间轮.md)的活。不做顺延的下场：活动结束预算花不完，运营拿着"预算执行率 70%"的报表来找你聊天。
3. **孤品的排布要人工干预。** iPhone 随机撒点，撒进凌晨 4:17 怎么办？大概率被夜猫子脚本捡走，白天的真实用户全程陪跑。常见做法是给高价值奖品限定投放时段（只撒在黄金时间）——这是公开分享里常见的运营约束（第三方来源，未核实具体某家的实现细节）。
4. **灵活性变差。** 活动中途运营想把红包概率从 5% 调到 8%？实时摇号改个配置就行；预排布得重新生成未来时间片的名额。做得好的系统会把"重排未来、不动过去"做成后台一键操作，但这是额外的工程量。

什么时候仍然选实时摇号？名额巨大且几乎不可能发完（比如纯优惠券活动）、活动极短（几分钟的直播间口令抽奖）、或者就是个低流量小活动犯不上上排布系统。**量小从简，量大从预排**——和 02 篇方案 A/B 的选型结论首尾呼应。

## 6. 防刷与异步发奖：上线前最后两块板

主链路齐了，还差两块板：不让坏人白嫖，以及把奖真的发到用户手里。

### 6.1 频次限制与入口限流

两层，目的不同：

- **单用户频次**：每人每天 3 次抽奖机会（分享 +1 次之类是产品规则，走规则引擎，不展开）。实现就是 `INCR draw:{uid}:{date}` + EXPIRE，超了直接拒。要更平滑的滑动窗口，[第 04 篇分布式限流器](./04-分布式限流器.md)有全套家伙。
- **入口总限流**：抽奖接口整体一个令牌桶，保护的是后面的 Redis 和 DB，不是防某个用户。活动开抢瞬间的脉冲流量，和秒杀开闸是同一个形状——04 篇同样是主场。

注意这两层和 5.3 节好处三的关系：限流是**把请求拦在门外**，预排布是**放进来也没东西可抢**。两层叠加，黑产的收益被压到地板上。防御从来不是单点，是纵深。

### 6.2 奖品分层与设备指纹

频次挡不住"一人千号"。补两招：

- **奖品分层**：高价值奖品加领取门槛——现金红包要求实名/绑卡账户，iPhone 限新客或风控分达标的账户。原则一句话：**不追求拦掉 100% 的作弊，只追求让薅的成本高于收益。** 一张满 100 减 10 的券随便薅，薅一千张也用不掉；现金和实物才是黑产的目标，把门槛精确加在这两类上。
- **设备指纹**：采集设备软硬件特征算出一个跨账号稳定的设备 ID，识别"一台设备登录了两百个账号"。这是风控团队的专业领域，抽奖系统只管接入打分接口，一笔带过。

### 6.3 异步发奖：中奖不等于到账

新手容易把"中奖"和"发奖"焊在一个事务里：抽中红包，同步调支付通道打款，成功了才返回中奖页面。听起来严谨，实际是把最不可靠的环节（外部支付通道）放进了最要求快的路径（用户正转着转盘等结果）。

正确的拆法：**中奖记录同步落，发放动作异步走。**

```
  抽中 → 扣库存/预算 → 落中奖记录(status=INIT) → 立刻返回中奖页面
                              │
                              ▼ 投进发放队列，慢慢消化
        ┌──────────────────────────────────────────┐
        │  INIT ──入队──▶ SENDING ──成功──▶ SUCCESS │
        │                    │                      │
        │               失败/超时                   │
        │                    ▼                      │
        │                RETRYING ──超过N次──▶ MANUAL(人工) │
        └──────────────────────────────────────────┘

  券：    调券系统发放，基本不失败
  现金：  走支付通道——会失败！（账户异常、风控拦截、通道抖动）
          重试必须幂等：中奖记录 ID 当幂等键，通道侧防重
  实物：  转成一张 0 元订单，走正常电商发货流程
```

用户看到"恭喜中奖"时，钱其实还没动。几秒到几分钟后红包到账——用户对这个延迟毫无感知，但系统换来了巨大的从容：支付通道抖一下，重试就好，不影响抽奖主链路。

⚠️ 一个必须提前想清楚的问题：**发放失败到底回不回滚库存和预算？** 一般不回滚。中奖记录已经生成，用户已经看到"恭喜"，回滚等于赖账，客诉比事故还难看。失败单走重试，重试打穿走人工补发。回滚只发生在 3.3、4.2 节说的"中奖成立**之前**"——**中奖记录落库那一行代码，就是回滚与不回滚的国境线。** 线前随便滚，线后认到底。

### 6.4 对账收尾

异步就有失联：进程崩在"扣了库存、还没落记录"的缝里，Redis 计数和 DB 记录就对不上了。收尾靠对账，每天跑一遍四方核对：

```
  概率上应发数（配置概率 × 抽奖流水量）      ← 监控口径，看 3.3 节那个"被吞的bug"
  库存扣减数（Redis 初始值 - 当前值）
  中奖记录数（DB）                            三者环环相扣：
  发放成功流水（支付/券/订单系统）            扣减数 ≥ 记录数 ≥ 成功数
                                              每层的差额都要能说出名字
```

扣减数比记录数多 3？那是崩溃留下的残渣，把库存补回去。记录数比成功数多 40？那是还在重试或已转人工的单子，逐条追踪到终态。对账的方法论——增量核对、差异分类、终态闭环——[第 10 篇支付与对账](./10-支付与对账.md)是完整版，抽奖的对账是它的简化场景：资金单向流出、没有退款分支，比支付好对得多。

到这一步，三条死线各自有了双保险：概率靠机制精确 + 统计监控，库存靠原子扣减 + 对账，预算靠预扣（或预排布）+ 对账。上线。

**没有新技术，只有新组合。** 这是本系列反复念叨的"心法复用"最硬的一个例证：当你把秒杀的库存、红包的守恒、限流的闸门、支付的对账都吃透之后，"抽奖系统"这个看起来全新的需求，摊开就是一张采购清单——你要做的不是发明零件，是画装配图，然后想清楚两个真正的决策点：库存耗尽后走哪种策略（产品决策），以及要不要上预排布（规模决策）。

## 8. 一句话总结 + 小白词典

> **抽奖系统是一道组装题：概率是切区间，库存是秒杀，预算是红包，发奖是支付对账；三条死线守得住，靠的不是更快的代码，而是让超发和超支在结构上无路可走——所以行业主流干脆把随机性提前算完，名额撒上时间轴，运行期只剩查询和扣减。**

### 小白词典

| 词 | 一句人话 |
|---|---|
| 万分位 | 把概率写成"一万份里占几份"的整数，0.01% 就是 1，加起来必须凑满 10000 |
| 区间切分法 | 把 [0,10000) 的整数轴按概率切段，掷一次随机数，落在哪段中哪个奖 |
| 兜底奖 | "谢谢参与"——概率轴上剩下的格子全归它，保证每次抽奖都有个结果 |
| 提名 vs 当选 | 概率命中只是提名，原子扣库存成功才算当选，顺序不能反 |
| 预扣 / 回滚 | 先扣了再说，后面步骤失败就把扣的还回去；还的动作要幂等 |
| 降级 | 大奖给不了时改判成"谢谢参与"，用户只当手气差——抽奖系统免费的台阶 |
| 预排布 | 活动开始前把中奖名额（含生效时刻）全部生成好，抽奖=查表+认领 |
| 二倍均值法 | 随机金额算法：每次在 [最小值, 剩余均值×2) 里随机，最后一份全给，总和守恒 |
| 幂等 | 同一件事执行多次，效果等于一次——重试和回滚的安全带 |
| 对账 | 事后把配置、扣减、记录、发放四本账摆在一起核对，每笔差额都要有名字 |

## 附：和前几篇的对照

2. **和 [02 篇微信红包](./02-微信红包.md)**：接轨了三处——概率整数万分位对应它的"钱用分不用元"（第 5 节）；随机金额直接复用二倍均值法（第 4 节）；预排布就是它方案 A"先拆好再抢"的时间轴放大版，02 篇 3.5 节"方案 A 适合营销红包"那句话，本篇整个第 5 节都在替它交作业。

4. **和 [10 篇支付与对账](./10-支付与对账.md)**：发奖状态机和对账收尾是同款方法论的简化场景——抽奖资金单向流出、没有退款分支，四方核对比支付的双向对账好做得多；先在抽奖系统练对账，再去啃支付，是个不错的爬坡顺序。
5. **和 [25 篇灰度发布与 AB 分流](./25-灰度发布与AB分流.md)**：区间切分是同一把刀——那边把流量按比例切给不同版本，这边把随机数按概率切给不同奖品；差别在"落点怎么定"：灰度用用户 ID 哈希（同一人稳定进同一段），抽奖用随机数（每一抽独立）。刀法学一次，两处都能使。
