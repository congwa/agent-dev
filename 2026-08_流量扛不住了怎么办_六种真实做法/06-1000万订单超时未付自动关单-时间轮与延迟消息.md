# 06 · 1000 万订单超时未付自动关单：时间轮 + 延迟消息

> 适用场景：**海量任务，各有各的到期时间，到点要触发一次。** 订单 15 分钟不付款关单、优惠券到期作废、N 天后发提醒——都是这一类。
>
> 这一篇和前五篇的关系：前五篇讲"流量太多了怎么少干活"，这一篇讲"活儿本身不多，但每一件都约了个不同的闹钟"。它是 01 篇（秒杀）的下游——秒杀抢到之后不付款，就轮到这一篇出场。

**先玩再读**：用浏览器打开 [`demos/timingwheel.html`](demos/timingwheel.html)，这是一个能亲手拨动的分层时间轮动画。重点看那个**延迟 140 秒**的任务：它先落在第三层，144 秒过后不是被执行，而是掉到第二层，再掉到第一层，最后才被触发。手动点几次「走一格」，看着它一层层往下掉，降级这个机制就长在脑子里了。

## 一、先搞清楚：难在哪

需求是"每笔订单在下单后 15 分钟检查一次，没付款就关掉"。

**笨办法 A：轮询扫表**

```sql
SELECT * FROM orders
WHERE status = 0 AND create_time < NOW() - INTERVAL 15 MINUTE;
```

每秒跑一次。问题不在这条 SQL 写得对不对，而在于：1000 万笔订单里，某一秒真正到期的可能只有 100 笔。你为了找出这 100 笔，让数据库翻了 1000 万行——**99.999% 的工作是白干的**，而且这活儿每秒都要重来一遍。

**笨办法 B：一个订单一个定时器**

```java
new Thread(() -> { Thread.sleep(15 * 60 * 1000); closeOrder(id); }).start();
```

1000 万个线程。一个线程栈默认 1MB，直接 10TB 内存。就算换成协程，调度器也扛不住。

**及格办法 C：优先队列（JDK 的 DelayQueue / Timer / ScheduledThreadPoolExecutor）**

底层是个小顶堆，堆顶永远是最早到期的那个。取任务 O(1)，但插入和删除是 O(log n)。1000 万个元素，log₂(10⁷) ≈ 24，每次插入 24 次比较加数组挪动，还要加锁。下单是高频操作，每次下单都插一次——这就是瓶颈。而且现实里订单会被提前支付、取消，要从队列中间删元素，更麻烦。

---

## 二、关键的思维转弯

上面所有办法都在做同一件事：**"我主动去找哪些任务到期了"**。

时间轮做的是反过来的事：**"到期的任务自己会走到我面前"**。

打个比方。快递驿站有一面墙，60 个格子，编号 0~59。今天 3 号，"3 号要取走的包裹"就放进 3 号格子。到了这天，店员只看 3 号格子，里面的东西全部处理掉，其他 59 个格子看都不看。第二天看 4 号格子。

**店员的工作量和驿站总共有多少包裹完全无关。** 这就是 O(1)。时间轮就是这面墙，只不过它是圆的，格子代表的是"秒"而不是"天"。

（如果你读过第 00 篇，会发现这又是那个熟悉的套路：不去优化"搜索"，而是改造数据结构让搜索消失。）

## 三、单层时间轮：三个变量就够了

```
tickMs    = 1000   // 每格代表 1 秒
wheelSize = 60     // 60 个格子
一圈      = 60 秒
```

数据结构极其简单：

```java
// 一个数组，每个元素是一个链表（这一格里的所有任务）
List<Task>[] buckets = new List[60];
long currentTime = 0;   // 指针当前在第几格
```

**放任务**，一次加法一次取模：

```java
void add(Task t, int delaySec) {
    int idx = (int) ((currentTime + delaySec) % 60);
    buckets[idx].add(t);
}
```

延迟 3 秒、指针在 10 → 放进 13 格。延迟 55 秒、指针在 10 → (10+55)%60 = 5 → 放进 5 格（转了一圈多一点，绕回来了）。

**触发**，一个线程每秒醒一次：

```java
void tick() {
    currentTime = (currentTime + 1) % 60;
    List<Task> list = buckets[(int) currentTime];
    buckets[(int) currentTime] = new LinkedList<>();  // 清空
    list.forEach(Task::run);                          // 全执行
}
```

插入 O(1)、触发 O(1)、删除 O(1)（链表里摘个节点）。跟总任务数是 1000 万还是 1 亿，一点关系都没有。

## 四、第一个坑：超过一圈怎么办

一圈才 60 秒，但订单要 15 分钟 = 900 秒。900 % 60 = 0，会和"0 秒后到期"的任务撞在同一格。两种解法，这是理解时间轮的分水岭。

**解法 1：记圈数（Netty 的 HashedWheelTimer 走这条路）**

任务上多存一个字段 `round`（还要转几圈）：

```
900 秒 → 需要走 900 格 → round = 900/60 = 15，idx = 900%60 = 0
```

指针走到第 0 格时，遍历这一格的链表：`round > 0` 的减 1 放回去，`round == 0` 的才执行。

- 优点：实现简单，一个数组就完事。
- 缺点：每次到一格都要遍历整条链表。这格里堆了 1 万个任务但只有 3 个真到期，你还是白遍历了 9997 次——触发从 O(1) 退化成 O(链表长度)。

Netty 选它，是因为它的场景（连接超时检测）任务量相对可控。

**解法 2：分层时间轮（Kafka 走这条路）**

用钟表来理解：秒针走一圈 60 格 = 1 分钟，进位给分针走一格；分针走一圈 = 1 小时，进位给时针。

```
第一层（秒轮）：每格 1 秒   × 60 格 = 覆盖 60 秒
第二层（分轮）：每格 60 秒  × 60 格 = 覆盖 60 分
第三层（时轮）：每格 60 分  × 24 格 = 覆盖 24 小时
```

三个数组一共 144 个格子，就能表达 24 小时内任意一秒的精度。放任务的规则：**从最低层往上找，谁装得下就放谁那儿**。

```
延迟 30 秒            → 秒轮装得下           → 秒轮第 30 格
延迟 900 秒（15 分钟） → 秒轮装不下，分轮装得下 → 分轮第 15 格
延迟 5 小时           → 只有时轮装得下        → 时轮第 5 格
```

## 五、精髓：降级（demotion / reinsert）

这是整个方案最漂亮的一步，也是新手最容易卡住的地方。

**上层格子到期时，它不执行任务，而是把任务重新插一遍。**

跟着这个例子走（用动画里的小尺寸：秒轮 8 格 × 1s，分轮 8 格 × 8s）：

```
t=0   下单，20 秒后关单，到期时间 = 20
      秒轮只覆盖 0~7，装不下
      分轮每格 8s：20 / 8 = 2 → 放进分轮第 2 格
      （分轮第 2 格代表的时间区间是 [16, 24)）

t=16  分轮指针走到第 2 格！
      但现在还不到 20 秒，不能执行。
      把任务掏出来，重新插一次——
      此时到期时间 20，当前 16，还剩 4 秒 → 秒轮装得下了！
      放进秒轮第 20%8 = 4 格

t=20  秒轮指针走到第 4 格 → 执行关单 ✅
```

为什么"重新插一次"**一定**能往下降？因为分轮第 2 格代表的区间是 [16, 24)，指针走到它时当前时间正好是 16，格子里所有任务的剩余时间必然 < 8 秒——正好是秒轮一圈的长度。数学上保证了它一定装得进秒轮。

**分层的自洽之处就在这里：上层的一格 = 下层的一圈。**

代价是什么？一个任务在生命周期里可能被搬动几次。但搬动次数 = 层数 = O(log 时间跨度)，通常就 3~4 次。跟每秒扫 1000 万行比，这点开销可以忽略。

## 六、第二个坑：空转（很多人不知道这一层）

指针线程每秒醒一次，如果这一格是空的呢？那就白醒了。凌晨 3 点没有订单，你的线程还在那儿每秒空转（三层轮各自都要走）。CPU 白白烧掉——这和第 00 篇批评的"轮询"是同一个病，只是病灶从数据库挪到了 CPU。

Kafka 的解法很妙：**把每个格子（bucket）整体当成一个元素，塞进一个 DelayQueue**。

```java
DelayQueue<TimerTaskList> queue;   // 队列里装的是"格子"，不是"任务"
```

队列里最多只有 `层数 × 格子数` 个元素（144 个），不是 1000 万个。所以 DelayQueue 的 O(log n) 完全无所谓，log(144) ≈ 7。工作线程调 `queue.poll()`，会一直阻塞到最近的那个**非空**格子到期为止，然后一步跳过去，中间的空格子零 CPU 消耗。

巧妙之处在于：**用一个小的优先队列去驱动一个大的时间轮**。优先队列只负责"什么时候醒"，时间轮负责"醒了之后 O(1) 拿任务"，两者的缺点互相抵消了。

## 七、回到订单超时：真实系统怎么落地

上面是内存里的时间轮。直接拿它做 1000 万订单的关单，还有几个现实问题。

**1. 进程重启，任务全丢了。** 纯内存结构没有持久化，生产上的做法是：

- **主力：现成的延迟消息中间件**——RocketMQ 的定时/延迟消息、Pulsar 的 delayed delivery。下单时发一条"15 分钟后投递"的消息，到点消费者收到就去关单。RocketMQ 5.x 的定时消息内部实现就是时间轮 + 文件持久化——你没有绕开时间轮，只是让中间件替你扛了持久化。
- **轻量方案：Redis ZSET**，score = 到期时间戳，用 `ZRANGEBYSCORE 0 now` 捞到期的。本质是跳表，不如时间轮快但够用，而且天然持久化 + 多机共享。

**2. 必须有兜底扫表。** 消息可能丢、可能消费失败，所以再挂一个低频补偿任务：

```sql
-- 每 5 分钟跑一次，只捞"早就该关但还没关"的
SELECT id FROM orders
WHERE status = 0 AND create_time < NOW() - INTERVAL 20 MINUTE
LIMIT 1000;
```

注意关键：有了延迟消息兜住 99.9% 的正常流量后，这条 SQL 捞到的行数几乎永远是 0。它从"主力"降级成了"保险丝"，频率从 1 秒一次降到 5 分钟一次。这就是分层设计的价值——和秒杀系列里"Redis 是漏斗、MySQL 是兜底"是同一个思想。

**3. 关单必须幂等。** 任务可能重复触发（消息重投、补偿任务和延迟消息撞车）：

```sql
UPDATE orders SET status = 2 WHERE id = ? AND status = 0;
```

靠 `AND status = 0` 保证只有第一次生效，重复执行不会把已支付的订单错误关掉。

**4. 用户提前支付了怎么办。** 时间轮里那个任务还在。两种处理：一是从链表里摘掉（需要维护 taskId → 节点的映射）；二是干脆不管，让它到点触发，靠上面那条幂等 SQL 自然失效。工程上大多选后者——省掉一整套删除逻辑，代价只是多一次没意义的 UPDATE。

## 八、现实中真的要自己写这玩意吗

绝大多数情况下**不写**。手写时间轮上生产的，基本只有一种人：在做中间件本身的。但"不写"和"不懂"是两回事，先说现实里怎么选。

**场景一：单机内存里的超时控制**（连接超时、RPC 超时、心跳检测、重试退避）——直接用现成的，一行代码：

```java
// Netty 自带，本身就是时间轮
HashedWheelTimer timer = new HashedWheelTimer(100, TimeUnit.MILLISECONDS, 512);
timer.newTimeout(t -> closeConnection(ch), 30, TimeUnit.SECONDS);
```

任务量不大时 ScheduledThreadPoolExecutor（底层是堆不是轮）也够用。这类场景任务丢了无所谓——进程都重启了，那些连接也没了。

**场景二：业务延迟任务**（订单关单、优惠券到期、N 天后提醒）——这才是本篇的场景，答案是延迟消息中间件：

| 方案 | 适用 | 注意 |
|---|---|---|
| RocketMQ 定时消息 | 首选，尤其国内 | 5.x 支持任意精度定时；4.x 只有 18 个固定延迟级别 |
| Redis ZSET | 量不大、想轻量 | 自己写消费循环，要处理多机竞争 |
| Pulsar delayed delivery | 已经在用 Pulsar | 原生支持任意延迟 |
| RabbitMQ TTL + 死信 | **不推荐** | 有队头阻塞，见下面坑一 |

**场景三：定时调度**（每天凌晨对账、每小时同步）——XXL-JOB、PowerJob、Elastic-Job。注意这跟延迟任务是两码事：调度框架是"到点跑一个 job"，延迟任务是"1000 万个独立的、各有各到期时间的小任务"。用 XXL-JOB 做订单关单，你写出来的还是那条扫表 SQL，什么都没解决。这个区分面试也爱问。

**什么时候真会自己写**：造中间件（MQ / RPC 框架 / 网关，Kafka、Netty、Dubbo 里的时间轮就是这么来的）；不能引外部依赖（嵌入式、SDK）；通用实现真成了瓶颈（要有压测数据支撑，不是拍脑袋）。

### 为什么不写也要懂：两个真实会踩的坑

**坑一：RabbitMQ 的 TTL + 死信队列会队头阻塞。** 很多教程教你用它做延迟队列，但 RabbitMQ 的队列是 FIFO，只检查**队头**消息的 TTL。队头是一条 30 分钟的消息、后面排着一条 5 秒的，那条 5 秒的要等 30 分钟才会被投递。理解了时间轮是"按到期时间分格"，就立刻明白 FIFO 队列压根不具备这个能力（要么用 rabbitmq-delayed-message-exchange 插件，要么换方案）。不懂原理的人，通常是在生产上发现"订单有时候半小时才关"才反应过来。

**坑二：Netty 的 HashedWheelTimer 里不能做阻塞操作。** 任务在时间轮自己那一个 worker 线程里执行：

```java
timer.newTimeout(t -> orderDao.closeOrder(id), 15, TimeUnit.MINUTES); // 危险
```

一次数据库慢查询，整个时间轮的指针就卡住，后面所有任务全部延迟。正确写法是把任务扔进业务线程池：

```java
timer.newTimeout(t -> bizPool.submit(() -> orderDao.closeOrder(id)), 15, TimeUnit.MINUTES);
```

同理，`tickDuration` 设太小（比如 1ms）会让 worker 线程疯狂空转烧 CPU——Kafka 用 DelayQueue 装 bucket 就是为了解决这个，而 Netty 没有类似机制，它就是老实空转，所以别设太小。

## 九、一张对比表

| 方案 | 插入 | 触发 | 空间 | 致命伤 |
|---|---|---|---|---|
| 轮询扫表 | O(1) | O(n) 每秒 | 小 | 1000 万行全表扫，数据库崩 |
| 一任务一线程 | O(1) | O(1) | O(n) 线程 | 内存爆炸 |
| 小顶堆 / DelayQueue | O(log n) | O(log n) | O(n) | 高频插入时锁竞争 |
| 单层时间轮 + round | O(1) | O(格内任务数) | O(n) | 热点格链表长 |
| 分层时间轮 | O(1) | O(1) | O(n) | 需要降级搬运（可忽略） |

## 十、面试被问到，答题骨架

1. **点出问题本质**：轮询是"主动搜索"，复杂度和总量绑定；时间轮是"被动等待"，复杂度和总量解耦。
2. **讲清基本结构**：环形数组 + 每格一个链表 + `(current + delay) % size` 定位。
3. **主动展开超圈问题**：round 计数（Netty）和分层（Kafka）两条路，并说明分层为什么更优——上层一格 = 下层一圈，降级必然成功。
4. **加分项**：Kafka 用 DelayQueue 装 bucket 解决空转。这一点能筛掉 90% 只背过八股的人。
5. **回到工程**：内存时间轮不持久化，生产用 RocketMQ 延迟消息（内部也是时间轮）+ 低频扫表兜底 + 幂等关单。

一句话总结：**写代码时你调 API，但选型、排障、面试时你需要那张图。** 这类知识的价值不在于让你造轮子，而在于让你知道手里的轮子是圆的还是方的。
